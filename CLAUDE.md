# Infinite Canvas

Native macOS infinite canvas (an AppKit document app, SwiftUI windows around an AppKit canvas), built from compiled-in plugins.

## How these instructions load

This file holds only what every task needs. The rest is in topic files in `.claude/rules/`, one per subsystem, listed in the [map](#map) below and linked to one another. Each topic file's `paths:` frontmatter names its subsystem's sources and tests: Claude Code puts the file in context when Claude uses Read, Edit or Write on a matching file, and not otherwise (not for Bash or Grep, for instance). So before planning or changing anything in an area, read its topic file, and follow its links as far as the task needs. `docs/plugin-system.md` is the long-form guide with the examples; each topic file links its sections.

Keep it that way: a change to a subsystem updates its topic file in the same commit; a new subsystem gets a topic file with `paths:` (a rules file without them loads in every session) and a line in the map; only what every task needs goes in this file.

## Build and test

- `mise tasks` lists the repository's commands and `mise run TASK` runs one (`mise.toml`): each task runs the script these docs name, which stays the way to do it, so the commands below work without mise. A new script, or a new mode of `build.sh`, gets its task in the same commit ([build](.claude/rules/build.md)).
- `./build.sh && open build/InfiniteCanvas.app` builds the app with `swiftc` directly (SwiftPM is broken with this machine's Command Line Tools) and opens it. In a linked git worktree the build is a copy of the app, an app of its own to macOS ("Infinite Canvas (<worktree>)", its own preferences): a board file opens in the main checkout's build unless it's opened with `open -a build/InfiniteCanvas.app <file>` ([build](.claude/rules/build.md)). Every mode but `agents` audits the module graph first (`./build.sh audit` does only that); `./build.sh agents DIR` puts together the skills the app carries for agents, and `canvas install` puts them where agents read them, and `./build.sh graph`, `dot` and `api <Module>` read the graph: how it builds, and what the audit refuses, in [build](.claude/rules/build.md). `./build.sh bench` runs the benchmarks against their budgets: [benchmarks](.claude/rules/benchmarks.md).
- `./test.sh` builds every module but the app (debug, `-D DEBUG`) and runs the test executables, as many at once as there are cores (`TEST_JOBS=N`), the longest first, one that took long as several processes each running a share of its suites (TestKit's `TEST_SHARD`), printing each one's output whole, in order. One that passed isn't run again while it and what it reads are as they were then (they're named at the end; `TEST_ALL=1` runs them). `./test.sh TypesTests MentionsTests` builds and runs only those: iterate with the targets a change reaches, and run the whole suite before landing. `TEST_FILTER=substring ./test.sh` runs the matching tests, and fails if none match. `TEST_UI_MENUS=1` adds the tests that open real (on-screen) menus, and runs the executables one at a time. Run by hand, a test executable takes `TEST_TIMES=1` (each test's seconds, on standard error). A time budget in a test measures the test thread's CPU time (TestKit's `threadCPUTime`), never the wall clock, which counts whatever else the machine runs; that time is about half again as long with every core busy, so test.sh runs the tests that measure it after the rest, as many at once as half the machine's performance cores. Every `Suite` a test target declares must be passed to `runTests` in its `main.swift`; test.sh fails otherwise.
- If the build fails with "this SDK is not supported by the compiler", a stale newer SDK is being picked. Prefix the command with `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`.
- Sources compile in Swift 6 language mode. Keep them free of warnings (build.sh passes `-warnings-as-errors`).

## Rules for every change

Read `docs/plugin-system.md` first; it's the guide to the plugin system, with the examples.

- `Canvas` (the core) knows no particular shape or concern (its one tool is Hand), and must stay that way. A concern like validity is declared by a plugin (an `ExtensionPoint` in its own module) and other plugins opt in; if the core seems to need to know about one, add a generic extension point instead.
- `Package.swift` is the module graph, a target a line, each tagged `// layer:`, and the list of what ships (the plugins the product is made of, in order, each made by its name), and the audit refuses a cycle, an edge the layers don't allow, imports that aren't exactly a module's declared dependencies, and a module writing another module's kind, tool, plugin, property, channel or edge type id as a literal without depending on it. Modules sit on three rungs, each importing only from its own rung and those below it: core (the canvas and plain libraries: Geometry, Canvas, DrawScript, QueryLanguage, TextEditing, FuzzyMatching, Palette, Chrome and the wire, CanvasRPC; and its private modules, which no plugin may import: the window, the app and the command line, `// layer: core private`), platform (what every shape gets, whatever its kind: the horizontals, the interfaces verticals plug into, something a shape shows up on or has, as Titles and Locking are; things you do, as Jump To and Moving are; the engines any plugin may run, Queries and Draw among them; and what agents speak, `canvas draw` and `canvas query`) and product (the verticals, shapes that hold something of their own: arrows, notes, subboards and frames; nothing imports one, so none knows another). Which way an edge between two platform modules goes is the meaning's, and the graph having no cycle holds it. An engine knows no meaning a horizontal owns: a word in a language is given by the module that owns its meaning, as a plugin value of its own, through the engine's points; when the owner sits below the engine, the engine's module gives it. No module joins two others, and none imports the plugins to list them: shipping a plugin is its line in `Package.swift`'s table. A large module is in parts, folders of its directory with a table of their own in `Package.swift` (Types: nine), and a part names only what is in the parts its line says it uses: the build type-checks each with those sources alone. Plugins can't import CanvasUI, and the app imports no plugin: what a host takes of a plugin's goes through [host slots](.claude/rules/host-slots.md). Read [build](.claude/rules/build.md) before adding a module or an import.
- A plugin's face on kinds it doesn't define (an adornment, a mark, a section, a rule, a shape's menu item or slash command) says which kinds by their opt-in, as data: `registrar.forShapes(holding: P.self)` (the property its feature adds), `forShapes(adopting:)` (a capability), or `forEveryShape` for what every shape has by its nature, never a feature kinds opt into; the registry resolves the scope, names it in its report and refuses a face with none ([plugins and kinds](.claude/rules/plugins-and-kinds.md)).
- Change documents only with `editor.transact`, and name the step a user would call it (`transact("Name")`, `undoHistory.group("Name")` around several). A body that throws commits nothing and opens no step, and the error comes out untyped. Tools see `Pointer` values, never `NSEvent`; timers go through `editor.scheduler`. Model positions are world units; overlay sizes (handles, outlines, hit margins) are view points, divided by `zoom` in world space.
- Conform to `ShapeDefinition` (and capabilities), `Tool`, `Session`, `EditorService`, `MentionScope`, `TransformChannel` and any extension point that implements `check` or `summary` in an extension: only there does the compiler flag a near miss on a defaulted requirement ([plugins and kinds](.claude/rules/plugins-and-kinds.md)).
- A frame costs what's in view and what changed, never the whole board: per-frame code goes through `editor.paintOrder(in:)`, and a service keeps per-shape state and redoes only the shapes a commit's `ChangeSet` names ([drawing](.claude/rules/drawing.md)); `./build.sh bench` holds the budgets.
- Changing how a kind's props encode, even adding a member with a default, needs a migration and a new fixture in `Tests/CompositionTests/Fixtures/kinds` (an added property's value has migrations of its own, and fixtures in `Fixtures/added`); never edit a fixture ([boards on disk](.claude/rules/boards-on-disk.md)).
- A change to `canvas draw` or `canvas query`, their messages, the shipped kinds, the query words or edge types, or the `--ask` prompt changes the canvas skill (`.claude/skills/canvas`) too: SkillTests and QueryPromptTests hold them together ([command line](.claude/rules/command-line.md), [queries](.claude/rules/queries.md)).
- Arrows mirror tldraw's arc arrows: check tldraw before changing arrow behavior and call out any intentional deviation, and never regenerate the proof-of-concept fixtures from the app to make a change pass ([arrows](.claude/rules/arrows.md)).
- UI constants live in each module's `@MainActor` style enum (`Style`, `ArrowStyle`, `NoteStyle`, `TypesStyle`, ...), a kind's skeleton's beside its full look's (`NoteStyle.skeletonFill`, `SubboardStyle.skeletonBorderWidth`, `ReferenceStyle.skeletonFill`, `ArrowStyle.skeletonLineWidth`). The core's are internal (`Style.skeletonZoom`, `Style.skeleton`, `Style.skeletonText`, `Style.drawingPad`): a plugin goes by `editor.drawsSkeletons`, never the number, and one that simplifies further farther out reads `context.zoom`. Pure geometry (Geometry, `ArrowGeometry`) is nonisolated, so its constants live on those types.
- Never print, log or write the Anthropic or TypeSafe API key ([language models](.claude/rules/language-models.md), [decision models](.claude/rules/decision-models.md)).
- Anything a click acts on is reached and done with keys alone, walked in reading order with an exact way back, named for VoiceOver, and tested by a key walk: read the twelve principles in [keyboard navigation](.claude/rules/keyboard-navigation.md) before adding a face, an adornment, a button, a control, a list or a key.
- A commit that lands on main carries its session's record: `python3 .claude/skills/history/condense.py --self` writes this session's record to `history/sessions/<record>/` (its transcript, condensed, and its plan files); the commit adds that directory and names it in a `Session: history/sessions/<record>/` trailer, above `Co-Authored-By`. The message still says why on its own; the record is the evidence behind it ([history](.claude/skills/history/SKILL.md)).

## Tests

Read [testing](.claude/rules/testing.md) before writing a test, and the Testing section of the subsystem's topic file. In every test:

- Never touch the user's pasteboard: give the plugin a private one ([clipboard](.claude/rules/clipboard.md)).
- Never use the app's socket: a test listens on its own (`temporarySocketPath()`, TestKit) ([command line](.claude/rules/command-line.md)).
- Never reach the network or run the person's Claude Code: only the two live tests do, when asked, and every other test that builds the shipped list passes `model: ScriptedLanguageModel()` and gets a `ScriptedDecisionModel` unless it passes one (ShippedTesting's `ShippedPlugins`; the list itself won't load for a test without two models and a pasteboard of its own: [language models](.claude/rules/language-models.md), [decision models](.claude/rules/decision-models.md), [build](.claude/rules/build.md)).
- Close the `BoardDocument`s the test edits ([testing](.claude/rules/testing.md)).

Screen capture isn't permitted here: tests draw into bitmaps, and what a drawing change costs on screen is seen only in the app on screen ([testing](.claude/rules/testing.md)).

- [command line](.claude/rules/command-line.md): `canvas`, the wire, `CommandServer`, Automation's commands (`rehearse` draws several scripts on a copy of the file, `measure` reads a board's types, `capture` takes a picture of one; `apply` is [drawings](.claude/rules/drawings.md)'), `canvas decide` (one yes-or-no question of many shapes), Draw (the engine of `canvas draw`: `is:`, a note's values joined, what each shape's values still need, the members a report adds to a row, an id for a shape with no title), the canvas skill.
- [queries](.claude/rules/queries.md): the query language, what a query sees and where it runs, the words their owners give (Validation's `:invalid`, `:warned` and `:incomplete`; Types' `:is-a`, `:misfit` and paths into a note's values), `canvas query` and `--ask` (what it is told of types, fields and relationship types).
- [drawings](.claude/rules/drawings.md): what a program drew, kept by name in the file (Drawings, `DrawingsProperty`, through Draw's `DrawRecords`), and the doors a program draws through: `canvas apply` (a document by key, every board in one step, drawn on a rehearsal and taken in with `editor.adopt`), `canvas measure` of a document, `canvas draw --drawing`, and the words that read a drawing; the contracts between the layers.
- [digest](.claude/rules/digest.md): the canvas-digest skill, the render layer: a graph document (nodes by key, edges between keys) laid out as boards by a tool outside the app (`digest`, jsc), measured with `canvas measure`, drawn with `canvas apply`; the graph document, the app's kinds it reads, the plan, what it makes public, drawing again in place from where the shapes are; the codebase ingestion built on it is [ingest](.claude/rules/ingest.md)'s.
- [ingest](.claude/rules/ingest.md): the canvas-ingest skill: any git repository drawn as boards by `ingest` (`.claude/skills/canvas-ingest`): the repository's settings (`.canvas/ingest.json`), a scanner's scan, the repository's lens (`.canvas/lens.py`, run twice in isolation) and lenskit, its library, with the default lens that makes the digest, the cache outside the repository that its worktrees share (scan, Swift's index, runs, a drawing record for each file), the lock, and the Swift index; canvas-digest draws it. And what an agent follows to set a repository up with its team over rounds (SKILL.md: the survey, a picture recommended from the code with its files usually typed File, the settings, a lens with types and named rules, art direction), `reference/lens.md`, and the worked examples (`examples/bookshelf`, the usual setup, and `examples/orders`, drawn and queried by their tests).
