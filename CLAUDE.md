# Infinite Canvas

Native macOS infinite canvas (an AppKit document app, SwiftUI windows around an AppKit canvas), built from compiled-in plugins.

## Build and test

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`.
- `./build.sh bench` builds BenchmarkTests in release and runs it: saving, opening, and a hover and a drag frame, on generated boards of 1,000 and 10,000 shapes, against the persistence plan's budgets (open 10,000 shapes in under 1 s, a frame in 16 ms). `./test.sh` runs it small, in debug, without the budgets.
- `./test.sh` builds every module but the app (debug, `-D DEBUG`) and runs each test executable. `TEST_FILTER=substring ./test.sh` runs the matching tests, and fails if none match. `TEST_UI_MENUS=1` adds the tests that open real (on-screen) menus. Every `Suite` a test target declares must be passed to `runTests` in its `main.swift`; test.sh fails otherwise.
- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (foundation, ui, horizontal, vertical, bridge, composition, app, testsupport, test). Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` (it would shadow Swift's in every importer); and on a module writing another module's `ShapeKind`, `PluginID` or `ToolID` string without depending on it. The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool or plugin id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph.
- If the build fails with "this SDK is not supported by the compiler", a stale newer SDK is being picked. Prefix the command with `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`.
- Sources compile in Swift 6 language mode. Keep them free of warnings (build.sh passes `-warnings-as-errors`).

## Architecture

Read `docs/plugin-system.md` first; it's the guide to the plugin system, with the examples.

- `Canvas` (the core) knows no particular shape or concern (its one tool is Hand), and must stay that way. A concern like validity is declared by a plugin (an `ExtensionPoint` in its own module) and other plugins opt in; if the core seems to need to know about one, add a generic extension point instead.
- A plugin is a value (`CanvasPlugin`) that registers into a frozen `Registry`, which refuses a plugin list with a duplicate plugin, a contribution whose owner isn't installed or whose kind nobody registers, or two claims to one key. A rule spanning a point's contributions that keys can't express goes in that point's `static func check(_ registry:)`, which throws `RegistryError.invalid` or any error (reported as `invalid` for the point; the core runs it without knowing what it checks). A kind is its props type (`static let kind`); its behavior is a stateless `ShapeDefinition` (only `render` is required for box kinds, and `geometry` drives hit testing and outlines); more comes from capability protocols (`Editable`, `CustomTranslation`, which moves a kind by its own rules through `beginTranslation` when a `TranslatingSession` moves it, and `PaintOrderAnchored`). Selection declares two more: `HandleProviding` (handles on the only selected shape), and `BrushHitTesting`, which the marquee asks only when it overlaps a shape without strictly containing it (default: `ShapeGeometry.isHit(byBrush:)`, from `geometry`). Behavior intrinsic to a kind is a capability; behavior any plugin can add is an extension point. Conform to `ShapeDefinition` (and capabilities), `Tool`, `Session`, `EditorService` and any extension point that implements `check` in an extension: only there does the compiler flag a near miss on a defaulted requirement.
- Layers: horizontals (Selection, Validation, Titles, DetailPanel, ContextMenus, TableOfContents, Checklists) declare extension points and import no vertical, though one may build on another (Checklists on DetailPanel and ContextMenus; DetailPanel, ContextMenus, TableOfContents and Titles on Selection); verticals (Arrows, StickyNotes, Ellipses, TaskCards, Rectangles, Polylines, Eraser, Reordering) import no other vertical; bridges (EllipseTitles, ValidationDetails) connect them, even two horizontals (ValidationDetails joins Validation and DetailPanel). The shipped list is `ShippedPlugins.all` in Composition.
- The detail panel (DetailPanel, a horizontal) lays out a header, tabs, sections and a footer; plugins fill them with `x.details { DetailSection("…", in: SomeTab.self) { $x in … } }` and `detailStatusForEveryShape`. A tab is a type (`DetailTab`) any plugin may declare, in order bands: 0 a kind's own, 50 a horizontal's feature tab, 100 `StyleTab`, 200 `ArrangeTab`. A horizontal's feature is opt-in sugar on `ShapeRegistrar` that contributes to its own point and calls `details`, so opting in brings its tab (`note.checklist(\.checklist)`). Sections write only through `$x.field` or `$x.update` (one transaction each, on the live shape), bind the narrowest key path, and use `LabeledContent` and DetailPanel's primitives, never their own layout or fonts. Keep the sugar's closure types unannotated, and never name `Transaction` in a file that imports SwiftUI. The app places `ShippedPlugins.detailPanel(editor:onExit:)` in an `.inspector`, with `onExit` set to `CanvasFocus.take` (CanvasUI), which gives the keyboard back to the canvas.
- The table of contents (TableOfContents, a horizontal) is a native `List` in the right-hand panel, with data-canvas's TOC contract: `x.contentsRow(when:nestedUnder:) { ContentsLabel(title, placeholder:, systemImage:, color:, badge:) }`, and `registrar.contentsRow(P.self)` for bridges. The list owns the row's chrome; a row reads only its own shape, and uses `ContentsLabel` so rows from different plugins look alike. A kind without a row gets its placing tool's label and symbol, and `x.contentsRow(when:nestedUnder:)` with no builder keeps that row. Rows are in document order; `nestedUnder` nests a row only while its parent is listed. Arrows nest under the shape they start from. Selecting on the canvas lists just the selection; selecting rows selects and zooms to their shapes (`editor.animateCamera`, `Camera(fitting:)`, `editor.viewportSize`) without changing what's listed (`editor.selectionRevision` tells the two apart). Hover is shared: the pointer on a row sets Selection's `editor.hovered`, which the canvas outlines faintly, and a shape hovered on the canvas tints its row (`isHovered`), in the selection highlight's place; a selected shape shows neither. It's the detail panel's overview: `DetailPanelView(editor:onExit:overview:)` shows the overview with nothing selected, and under the header of several; Composition's `detailPanel(editor:onExit:)` passes `TableOfContentsView`, so neither horizontal knows the other.
- Context menus (ContextMenus, a horizontal) follow the same pattern: `x.contextMenu { MenuItem("…", in: SomeGroup.self, when: { … }) { $0.field = … } }`, `registrar.contextMenu(P.self)` for bridges, `contextMenuForEveryShape(where:)` (`where` picks kinds by their definition, so by capability; Reordering's Arrange submenu leaves out `PaintOrderAnchored` kinds). A group is a type (`MenuGroup`) in the tabs' order bands, with separators between groups; a horizontal's opt-in sugar calls `contextMenu` too, so opting in brings its items (Checklists' bulk actions). `when` leaves an item out (prefer it to `isEnabled`, which dims); nothing left, and the right-click does nothing. The menu is for the selection: a right-click on an unselected shape selects it (only if it has a menu), and with several shapes an item shows when every one shows it (same group and id). The core only lends `registrar.menuForSecondaryClick`, which ContextMenus claims; `CanvasView.menu(for:)` asks it. A Control-click with no menu reaches the tool as a press with `pointer.isControlClick`: the select tool ignores it, and tools that read ⌃ as a modifier (the arrow tool) take it, so ContextMenus answers Control-clicks only in the select tool.
- `CanvasEditor` is the headless brain (document, camera, tools, sessions, input, drawing). What it lends plugins generically: a default tool (`registrar.defaultTool`, else Hand) that Escape and placing return to; `registrar.outlines`, stroked with the hint in one pass, over the faint ones (`Outlines.faintShapes`); commands (`registrar.command`, `editor.perform`: Delete, Return, ⌘A from `CanvasView`); the secondary click's menu (`registrar.menuForSecondaryClick`); `Tool.cancel`; `EditorService.documentDidChange` (with each commit's `ChangeSet`) and `didPlace`; `Session.hidesOutlines` and `draw(in:)`. `CanvasView` (CanvasUI) only turns NSEvents into editor calls and hosts the editing view. Plugins can't import CanvasUI.
- Selection (a horizontal, first in `ShippedPlugins.all`) is built on those hooks alone: the selection state (a service, read as `editor.selectedShapeIDs` and `editor.selection`, the only selected shape, as tldraw's onlySelectedShape), the Select tool (the default) and marquee, handles, Delete/Return/⌘A, and the double-click claim. Every kind is selectable unless it opts out (`x.unselectable()`, or `x.selectable { ... }` per shape); the select tool sees through such shapes, nothing else does. Unlike tldraw (and the POC), the selection stays outlined while it moves. `editor.hovered` is the shape the pointer is over, set by the select tool on the canvas or by any plugin where it shows shapes (the table of contents' rows), in any tool; changing tools clears it. Its outline is faint: wider and lighter than the selection's (2.5 points, the accent at 60%), unlike tldraw's, which strokes a hover like the selection. Code that reads the selection imports Selection; without its plugin, the selection is empty.
- Boards are files, one per board (`docs/plugin-system.md`, "Boards on disk"): `BoardDocument` (CanvasUI, an `NSDocument`, autosaved in place) saves `editor.document` with `BoardCodec` (Canvas). The app is AppKit-run: `InfiniteCanvasApp` sets `BoardDocument.configuration` (the shipped registry, the window's SwiftUI content) and installs `BoardMenus`; the Info.plist that `build.sh` writes exports the `.canvasboard` type (not `.board`: Freeform owns it). Order in the stack is each record's `stackingKey`. A kind's props are versioned by its append-only `static let migrations`: changing how they encode needs a migration and a new fixture in `Tests/CompositionTests/Fixtures/kinds` (never edit a fixture). Shapes the app can't use are kept aside (`AnyShapeRecord.isOpaque`) and saved back as they were; a horizontal that goes through every shape skips them. The camera and whether the details show are remembered per file (`BoardViewMemory`), never in the board.
- Change documents only with `editor.transact`. Tools see `Pointer` values, never `NSEvent`; timers go through `editor.scheduler`. Model positions are world units; overlay sizes (handles, outlines, hit margins) are view points, divided by `zoom` in world space.
- A frame costs what's in view and what changed, never the whole board (`./build.sh bench` holds 10,000 shapes to 16 ms). The editor keeps each shape's geometry and extent, and the paint order (`ShapeIndex`), and redoes them for what each commit's `ChangeSet` names. So a definition looks at other shapes only through its `ShapeContext` (`shape(_:)`, `geometry(of:)`, `hitTest(_:shape:)`: they're tracked, all of `document` or `camera` isn't); a `hitTest` that reaches past the outline declares `hitMargin`; a paint anchor follows from its shape's props and the document's order; per-frame code (overlays) goes through `editor.paintOrder(in:)` with `context.visibleRect`; and a service keeps per-shape state and redoes the shapes a change set names, as `ValidationEngine` does.
- Arrows see other shapes only as `ConnectableShape` (a closed shape's core geometry). Keep specific shape kinds out of arrow code.
- UI constants live in each module's `@MainActor` style enum (`Style`, `ArrowStyle`, `NoteStyle`, ...). Pure geometry (Geometry, `ArrowGeometry`) is nonisolated, so its constants live on those types.

## Arrows follow tldraw

- Arrow behavior and geometry deliberately mirror tldraw's arc arrows: binding precision and timers, clipping, arrowhead gaps, handles and hint overlays. The constants come from tldraw's source.
- Check tldraw (`packages/tldraw/src/lib/shapes/arrow/`, `bindings/arrow/`, `overlays/`) before changing arrow behavior, and call out any intentional deviation.
- Moving arrows is `ArrowDefinition: CustomTranslation`. Alone (or with unrelated shapes) it is the POC's translation exactly; moved with a shape it's bound to, it keeps every binding, as tldraw. Its ends probe at the full delta (tldraw: half), a known deviation the transcript pins.
- CompositionTests holds the app to the proof of concept (commit 804db97): an arrow transcript compared byte for byte, and renders (outlines, binding hints, handles) compared pixel for pixel. `Tests/CompositionTests/Replay.swift` drives both the POC recording and the test. The fixtures come only from the POC, via `scripts/record-poc-fixtures.sh` (re-running it must change nothing). Never regenerate them from the app to make a change pass; an intended change to arrow behavior needs an explicit note. A scenario that ends differently on purpose gets an entry in `intendedDeviations` (TranscriptTests): the golden line, the app's, and why. The one so far: a press doesn't bring a shape to the front (the POC's did; tldraw's doesn't). Scenarios are only ever appended, recorded from the POC. The "pan" scenario presses H and holds still 100 ms before `.up` (both no-ops in the POC), and the welcome renders use the POC's note text, `pocWelcomeTexts`.

## Verifying UI changes

- Screen capture isn't permitted here.
- Drive a headless editor with `EditorHarness` (CanvasTesting), with `SelectionPlugin()` first in its plugins when the test presses, drags or selects as a user does (without it the default tool is Hand): one clock drives event timestamps and the `ManualScheduler`, so pointer speed, the arrow timers and the hand tool's slide (inertia) behave. Check drawing with `renderBitmap`, `pixel` and `changedPixels`.
- For focus, key routing and the editing view, put a `CanvasView` in an unshown `NSWindow` and send it synthesized `NSEvent`s (see CompositionTests).
- For context menus, `h.secondaryClick(at:)` returns the `NSMenu` (or nil); read it with `menu.outline` and run an item with `menu.choose("Status", "Done")`. Nothing goes on screen.
- For the detail panel, check layouts and writes headlessly (`editor.detailPanel?.layout(for:)`, `statuses(for:)`, `editor.shapeBinding`). For its views, host `DetailPanelView` in an `NSHostingView` in an unshown `NSWindow`, beside the canvas when focus matters (DetailPanelTests; `Tests/CompositionTests/InspectorTests.swift` uses the app's own wiring), with the real `TaskScheduler`. CanvasTesting drives the window: `window.spin { condition }` runs the main run loop until the state a test expects arrives (and fails the test after 2 s), `window.settle()` runs it a few turns where there's nothing to wait for, and `focus`, `type`, `press` and `mouse` send input. Call `canvas.mouseDown` directly (`sendEvent` mouse-downs don't reach views in an unshown window).
- For the table of contents, read `editor.tableOfContents?.entries` headlessly (each row's text, symbol and badge through `entry.label`), and drive `select(_:)`, `showAll()`, `hover(_:)` and `endHover(_:)`. SwiftUI's hover doesn't answer synthesized events, so check a row's tint by rendering the list with `snapshot(view)` (CanvasTesting; highlights draw, a source list's vibrant text may not). In a window, its list is an `NSOutlineView` whose first row is the header, a group row (TableOfContentsTests). A shape's panel can hold lists too (a checklist), so CompositionTests tell them apart with `isTableOfContents` (`Tests/CompositionTests/ContentsPanelTests.swift`), and InspectorTests' `tables` leave it out.
