# Infinite Canvas

Native macOS infinite canvas (an AppKit document app, SwiftUI windows around an AppKit canvas), built from compiled-in plugins.

## Build and test

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`.
- `./build.sh bench` builds BenchmarkTests in release and runs it: saving, opening, a hover and a drag frame, reading the table of contents' rows after a commit, and the minimap's first picture (a frame at a time) and a drag frame with it, on generated boards of 1,000 and 10,000 shapes, against their budgets (the persistence plan's: open 10,000 shapes in under 1 s, a frame in 16 ms; and the rows in 1 ms). `./test.sh` runs it small, in debug, without the budgets.
- `./test.sh` builds every module but the app (debug, `-D DEBUG`) and runs each test executable. `TEST_FILTER=substring ./test.sh` runs the matching tests, and fails if none match. `TEST_UI_MENUS=1` adds the tests that open real (on-screen) menus. Every `Suite` a test target declares must be passed to `runTests` in its `main.swift`; test.sh fails otherwise.
- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (foundation, ui, horizontal, vertical, bridge, composition, app, testsupport, test). Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` (it would shadow Swift's in every importer); and on a module writing another module's `ShapeKind`, `PluginID` or `ToolID` string without depending on it. The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool or plugin id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph.
- If the build fails with "this SDK is not supported by the compiler", a stale newer SDK is being picked. Prefix the command with `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`.
- Sources compile in Swift 6 language mode. Keep them free of warnings (build.sh passes `-warnings-as-errors`).

## Architecture

Read `docs/plugin-system.md` first; it's the guide to the plugin system, with the examples.

- `Canvas` (the core) knows no particular shape or concern (its one tool is Hand), and must stay that way. A concern like validity is declared by a plugin (an `ExtensionPoint` in its own module) and other plugins opt in; if the core seems to need to know about one, add a generic extension point instead.
- A plugin is a value (`CanvasPlugin`) that registers into a frozen `Registry`, which refuses a plugin list with a duplicate plugin, a contribution whose owner isn't installed or whose kind nobody registers, or two claims to one key. A rule spanning a point's contributions that keys can't express goes in that point's `static func check(_ registry:)`, which throws `RegistryError.invalid` or any error (reported as `invalid` for the point; the core runs it without knowing what it checks). A kind is its props type (`static let kind`); its behavior is a stateless `ShapeDefinition` (only `render` is required for box kinds, and `geometry` drives hit testing and outlines); more comes from capability protocols (`Editable`, `CustomTranslation`, which moves a kind by its own rules through `beginTranslation` when a `TranslatingSession` moves it, and `PaintOrderAnchored`). Selection declares two more: `HandleProviding` (handles on the only selected shape), and `BrushHitTesting`, which the marquee asks only when it overlaps a shape without strictly containing it (default: `ShapeGeometry.isHit(byBrush:)`, from `geometry`). Behavior intrinsic to a kind is a capability; behavior any plugin can add is an extension point. Conform to `ShapeDefinition` (and capabilities), `Tool`, `Session`, `EditorService` and any extension point that implements `check` or `summary` (how the registry's report shows a contribution) in an extension: only there does the compiler flag a near miss on a defaulted requirement.
- Layers: horizontals (Keyboard, Selection, Validation, Titles, DetailPanel, ContextMenus, TableOfContents, Checklists, Clipboard) declare extension points and import no vertical, though one may build on another (Checklists on DetailPanel and ContextMenus; Clipboard on Keyboard, Selection and ContextMenus; Titles on DetailPanel and TableOfContents; DetailPanel, ContextMenus and TableOfContents on Selection; Selection on Keyboard); verticals (Arrows, StickyNotes, Ellipses, TaskCards, Rectangles, Polylines, Eraser, Reordering) import no other vertical; bridges (EllipseTitles, ValidationDetails, ValidationContents) connect them, even two horizontals (ValidationDetails joins Validation and DetailPanel, ValidationContents Validation and TableOfContents). The shipped list is `ShippedPlugins.all` in Composition.
- The detail panel (DetailPanel, a horizontal) lays out a header, tabs, sections and a footer; plugins fill them with `x.details { DetailSection("…", in: SomeTab.self) { $x in … } }` and `detailStatusForEveryShape`: status lines, the shape's state rather than its settings, in the footer, or with `in: SomeTab.self` in a tab that shows only while the shape has lines there (ValidationDetails' Issues tab). A tab is a type (`DetailTab`) any plugin may declare, in order bands: 0 a kind's own, 50 a horizontal's feature tab, 100 `StyleTab`, 200 `ArrangeTab`, 300 a tab of the shape's state that comes and goes (Issues). A horizontal's feature is opt-in sugar on `ShapeRegistrar` that contributes to its own point and calls `details`, so opting in brings its tab (`note.checklist(\.checklist)`). Sections write only through `$x.field` or `$x.update` (one transaction each, on the live shape, which the binding reads back until the panel redraws), bind the narrowest key path, and use `LabeledContent` and DetailPanel's primitives, never their own layout or fonts. The header is a view made from the shape's binding too, `x.details(header: { $x in DetailHeader(x.title) }) { … }`: a `DetailHeader`, or a view of the kind's own built on `DetailHeaderLabel` (with `DetailHeaderField` for a title renamed in place), so every header looks alike; the panel hands it the kind's name and symbol through the environment, and tests read it back with `layout.header` or `layout.header(as:)`. Keep the sugar's closure types unannotated, and never name `Transaction` in a file that imports SwiftUI. The app places `ShippedPlugins.detailPanel(editor:onExit:)` in an `.inspector`, with `onExit` set to `CanvasFocus.take` (CanvasUI), which gives the keyboard back to the canvas.
- The table of contents (TableOfContents, a horizontal) is a native `List` in the right-hand panel, with data-canvas's TOC contract: `x.contentsRow(when:nestedUnder:) { ContentsLabel(title, placeholder:, systemImage:, color:, badge:) }`, and `registrar.contentsRow(P.self)` for bridges. The list owns the row's chrome; a row reads only its own shape, and uses `ContentsLabel` so rows from different plugins look alike. `registrar.contentsMarkForEveryShape { shape, context in ContentsMark(color:help:) }` puts a dot at a row's trailing end from any plugin (ValidationContents: red or orange for a shape with issues, its tooltip the issues). A mark is part of the row, made with it, so one read from more than its shape names, with `affected:`, the shapes each commit may change the marks of (Validation's `dependents(of:)`): their marks are read again, and their rows replaced only if the marks changed. A row's view reads only its `ShapeRow`, never the document: the list makes every row's view on each redraw. A kind without a row gets its placing tool's label and symbol, and `x.contentsRow(when:nestedUnder:)` with no builder keeps that row. `x.contentsTitle { … }` (`ContentsTitles`) names a kind's rows from another plugin without replacing them: a name that isn't blank takes the place of a `ContentsLabel`'s title, keeping its symbol and badge (Titles names rows this way). Rows are in document order; `nestedUnder` nests a row only while its parent is listed. Arrows nest under the shape they start from. `ContentsState` keeps each shape's row and where it's listed (`ContentsListing`, per scope), and redoes only those of the shapes each commit's `ChangeSet` names: a read after a drag costs the dragged shape's row, not the board. Selecting on the canvas lists just the selection; selecting rows selects and zooms to their shapes (`editor.animateCamera`, `Camera(fitting:)`, `editor.viewportSize`) without changing what's listed (`editor.selectionRevision` tells the two apart). A change of what's listed replaces the rows (`.id(scope)`), bringing the new ones in as one run: rows coming in at several places at once make AppKit, whose table sizes a `List`'s rows, log "a reentrant operation in its NSTableView delegate" (a future assert), as it still does when a list first shows 200 rows or more, or a commit brings rows in at several places. Hover is shared: the pointer on a row sets Selection's `editor.hovered`, which the canvas outlines faintly, and a shape hovered on the canvas tints its row (`isHovered`), in the selection highlight's place; a selected shape shows neither. It's the detail panel's overview: `DetailPanelView(editor:onExit:overview:)` shows the overview with nothing selected, and under the header of several; Composition's `detailPanel(editor:onExit:)` passes `TableOfContentsView`, so neither horizontal knows the other.
- Validation (a horizontal) is ESLint's model: rules (`x.validate { shape, context in … }`, `registrar.validate(P.self)`, `validateEveryShape`) find issues on a shape, each `.error` or `.warning`, two channels of one thing; an error makes a shape invalid. The overlay outlines a shape red with an error, orange with warnings alone, and not at all without issues. Rules see other shapes only through `ValidationContext`; `ValidationEngine` re-checks the shapes each commit's `ChangeSet` names and those whose rules looked one up. Bridges show the issues: ValidationDetails in the panel's Issues tab (worst first; the footer stays empty), ValidationContents as the dot on a row in the table of contents.
- Titles (a horizontal) is what a shape is called, a trait a kind opts into: `x.title { $0.props.title }`. Where it comes from is the kind's business: stored (a note's `title: String?`, nil until named) or derived (EllipseTitles' "Ellipse, 200 × 140"); any shape may have none (nil or blank). A titled shape shows a pill just outside its top-left corner (`TitleOverlay`: 9 points up, no wider than the shape, constant on screen down to 25%; `pill: false` for a kind that draws its own, as task cards do), and its title names its row in the table of contents (`contents: false` keeps the kind's row). `TitleHeader($x.title)` renames a stored title in the detail panel; a kind places it in its own header (`note.details(header: { $note in TitleHeader($note.title) }) {}`), since Titles contributes no header.
- Context menus (ContextMenus, a horizontal) follow the same pattern: `x.contextMenu { MenuItem("…", in: SomeGroup.self, when: { … }) { $0.field = … } }`, `registrar.contextMenu(P.self)` for bridges, `contextMenuForEveryShape(where:)` (`where` picks kinds by their definition, so by capability; Reordering's Arrange submenu leaves out `PaintOrderAnchored` kinds). A group is a type (`MenuGroup`) in the tabs' order bands, with separators between groups; a horizontal's opt-in sugar calls `contextMenu` too, so opting in brings its items (Checklists' bulk actions). `when` leaves an item out (prefer it to `isEnabled`, which dims); nothing left, and the right-click does nothing. Items that aren't one shape's (Cut, Copy, Paste) are the canvas's: `registrar.contextMenuForCanvas { MenuItem("…", when: { $0.editor… }) { ids, editor in … } }`, over the menu's `MenuSubject` (its shapes and the editor), asked once per menu, in every menu after the shapes' own, and alone on empty canvas. The menu is for the selection: a right-click on an unselected shape selects it (only if it has a menu), and with several shapes an item shows when every one shows it (same group and id). The core only lends `registrar.menuForSecondaryClick`, which ContextMenus claims; `CanvasView.menu(for:)` asks it. A Control-click with no menu reaches the tool as a press with `pointer.isControlClick`: the select tool ignores it, and tools that read ⌃ as a modifier (the arrow tool) take it, so ContextMenus answers Control-clicks only in the select tool.
- The clipboard (Clipboard, a horizontal): ⌘X, ⌘C and ⌘V (Keyboard), the `.cut`, `.copy` and `.paste` commands, and Cut, Copy and Paste in every context menu (items for the canvas), on the selection. The pasteboard holds a small board (`BoardCodec` JSON, the app's own type); anything else on it is ignored for now. A paste gets new ids, lands in place if any of it would be in view (else centered, with `transaction.translate`), is selected, and each copy's metadata names its original (`record.copiedFrom`, `meta[CopiedFrom.self]`). Every kind is copyable unless it opts out (`x.uncopyable()`, `x.copyable { … }`; the `ShapeCopyability` point). Every kind whose props name shapes adopts the core's `ShapeReferencing` (arrows, CanvasTesting's `Tag`): deleting a shape asks it of every shape that names it, after `willDelete` handlers (arrows let go where they're drawn), and a copy names the copies of the shapes copied with it and lets go of the rest; it returns nil when it can't let go of a shape it can't find, and a copy then leaves it out. Shape metadata (`AnyShapeRecord.meta`, typed by a plugin's `ShapeMetaKey`, saved under the owner's id, then the name) is the core's generic place for what a plugin keeps about a shape beside its props. A per-kind rule table is `registry.contributionByKind(to:)`, and the union of shapes' bounds `shapeContext.bounds(of:)`.
- `CanvasEditor` is the headless brain (document, camera, tools, sessions, input, drawing). What it lends plugins generically: a default tool (`registrar.defaultTool`, else Hand) that Escape and placing return to; `registrar.outlines`, stroked with the hint in one pass, over the faint ones (`Outlines.faintShapes`); commands (`registrar.command`, `editor.perform`: what menu items run, Edit › Delete and Edit › Select All from `CanvasView`, Go › Back and Edit › Cut, Copy and Paste from `BoardWindowController`, wherever the keyboard is but in text; `isEnabled:` and `editor.canPerform` enable a menu item, and a command's keys); the secondary click's menu (`registrar.menuForSecondaryClick`); key strokes (`registrar.keyStrokes`, which Keyboard claims); `Tool.cancel`; `EditorService.documentDidChange` (with each commit's `ChangeSet`) and `didPlace`; `Session.hidesOutlines` and `draw(in:)`. `CanvasView` (CanvasUI) only turns NSEvents into editor calls and hosts the editing view and the minimap. Plugins can't import CanvasUI.
- Keyboard shortcuts (Keyboard, a horizontal, first in `ShippedPlugins.all`): every key the canvas answers is registered with it, one shortcut per chord (`KeyChord`: `"v"`, `KeyChord("a", .command)`, `.escape`), by the plugin that gives it its meaning: `x.tool(label:systemImage:shortcut:placing:)` and `registrar.tool(descriptor, shortcut:)` for a tool's key, `registrar.command(.delete, shortcuts: [...], isEnabled:)` for a command a menu item also runs (its keys pass while it can't run, as its item dims: ⌘[ and Go › Back), `registrar.shortcut(chord, "Title", when:, repeats:) { editor in … }` for anything else, and `registrar.shortcut(chord, forTool:)` for another plugin's tool (Keyboard gives the core's Hand H, and Escape and ⌘. `editor.cancel()`). The core knows no key: `CanvasView.keyDown` hands every key to the editor as a `KeyStroke` (host API `editor.keyDown`), which passes it to the plugin that claims key strokes, and so does `CanvasView.performKeyEquivalent` for a ⌘ key while the canvas has the keyboard, before the menu bar (so ⌘A is Keyboard's there; with a field focused, the menu's). A key no shortcut takes goes on to AppKit's key bindings, and the standard actions they send that have a key of their own (`deleteBackward:`, `deleteForward:`, `insertNewline:`, `cancelOperation:`) come back to the shortcuts as ⌫, ⌦, ↩ and ⎋, so ⌃H does what Delete does. ⇧ counts when a chord asks for it; a key held with ⇧ answers the chord without it too when ⇧ may be only what typed it (⇧ alone, or punctuation, a symbol or a digit: ⌘? is ⇧⌘/), never for a letter with ⌘, ⌥ or ⌃ (⇧⌘Z isn't ⌘Z). The table of contents' list runs the `.delete` command on Delete, as the canvas does. Every plugin with a key imports Keyboard, so any plugin list with Selection or a shipped tool needs `KeyboardPlugin()`. The toolbar's tooltips ("Note (N)") come from `ShippedPlugins.help(for:in:)`, since CanvasUI can't see Keyboard.
- Selection (a horizontal, after Keyboard in `ShippedPlugins.all`) is built on those hooks alone: the selection state (a service, read as `editor.selectedShapeIDs` and `editor.selection`, the only selected shape, as tldraw's onlySelectedShape), the Select tool (the default) and marquee, handles, Delete/Return/⌘A/Back (their keys registered with Keyboard), and the double-click claim. `editor.goBack()` is data-canvas's selection history: each change of the selection stacks the one it leaves, with the camera as it was then (`editor.cameraTarget`, where it was headed if it was gliding; 50 steps; a select-tool press and its drag are one step; `canGoBack` only when going back would change the selection); the detail panel's header has the back button, and Go › Back (⌘[) works whatever has the keyboard. Every kind is selectable unless it opts out (`x.unselectable()`, or `x.selectable { ... }` per shape); the select tool sees through such shapes, nothing else does. Unlike tldraw (and the POC), the selection stays outlined while it moves. `editor.hovered` is the shape the pointer is over, set by the select tool on the canvas or by any plugin where it shows shapes (the table of contents' rows), in any tool; changing tools clears it. Its outline is faint: wider and lighter than the selection's (2.5 points, the accent at 60%), unlike tldraw's, which strokes a hover like the selection. Code that reads the selection imports Selection; without its plugin, the selection is empty.
- Boards are files, one per board (`docs/plugin-system.md`, "Boards on disk"): `BoardDocument` (CanvasUI, an `NSDocument`, autosaved in place) saves `editor.document` with `BoardCodec` (Canvas). The app is AppKit-run: `InfiniteCanvasApp` sets `BoardDocument.configuration` (the shipped registry, the window's SwiftUI content) and installs `BoardMenus`; the Info.plist that `build.sh` writes exports the `.canvasboard` type (not `.board`: Freeform owns it). Order in the stack is each record's `stackingKey`. A kind's props are versioned by its append-only `static let migrations`: changing how they encode needs a migration and a new fixture in `Tests/CompositionTests/Fixtures/kinds` (never edit a fixture). Shapes the app can't use are kept aside (`AnyShapeRecord.isOpaque`) and saved back as they were; a horizontal that goes through every shape skips them. A record's metadata is saved beside its props (`meta`), members no plugin knows included; a board with any is format 2 (else 1), so an older app refuses it rather than drop the metadata. The camera and whether the details and the minimap show are remembered per file (`BoardViewMemory`), never in the board.
- Change documents only with `editor.transact`. Tools see `Pointer` values, never `NSEvent`; timers go through `editor.scheduler`. Model positions are world units; overlay sizes (handles, outlines, hit margins) are view points, divided by `zoom` in world space.
- A frame costs what's in view and what changed, never the whole board (`./build.sh bench` holds 10,000 shapes to 16 ms). The editor keeps each shape's geometry and extent, and the paint order (`ShapeIndex`), and redoes them for what each commit's `ChangeSet` names; it keeps the board's bounds too, and where each commit moved or reshaped shapes (damage: where the shapes it touched, and those whose geometry followed them, were and are), for pictures of the board kept from frame to frame (host API: `shapeBounds`, `damageMark`, `damage(since:)`). So a definition looks at other shapes only through its `ShapeContext` (`shape(_:)`, `geometry(of:)`, `hitTest(_:shape:)`: they're tracked, all of `document` or `camera` isn't); a `hitTest` that reaches past the outline declares `hitMargin`; a paint anchor follows from its shape's props and the document's order; per-frame code (overlays) goes through `editor.paintOrder(in:)` with `context.visibleRect`; and a service keeps per-shape state and redoes the shapes a change set names, as `ValidationEngine` and `ContentsState` do.
- The minimap (CanvasUI's `MinimapView`, which `CanvasView.showsMinimap` hosts in the canvas's bottom-left corner; View › Show Minimap, ⌃⌘M, remembered per board in `BoardViewState` and `BoardViewMemory`) works as tldraw's: the board and the viewport fitted together; a click beside the viewport eases the camera there over 320 ms, a drag moves it within tldraw's clamp, a double-click centers exactly. It draws every shape as a rough silhouette of its geometry in one color, never its render (no text, no colors), into a bitmap of tiles kept from frame to frame (`MinimapPicture`): damage makes tiles stale, and each frame draws again those stale longest, within its budget (4 ms, and a tile at least), so a frame spends at most that on the picture however big the board, and whatever goes stale every frame, every tile has its turn. The selection shows in the accent color, through `editor.outlines` (host API). Keep it that cheap.
- Arrows see other shapes only as `ConnectableShape` (a closed shape's core geometry). Keep specific shape kinds out of arrow code.
- UI constants live in each module's `@MainActor` style enum (`Style`, `ArrowStyle`, `NoteStyle`, ...). Pure geometry (Geometry, `ArrowGeometry`) is nonisolated, so its constants live on those types.

## Arrows follow tldraw

- Arrow behavior and geometry deliberately mirror tldraw's arc arrows: binding precision and timers, clipping, arrowhead gaps, handles and hint overlays. The constants come from tldraw's source.
- Check tldraw (`packages/tldraw/src/lib/shapes/arrow/`, `bindings/arrow/`, `overlays/`) before changing arrow behavior, and call out any intentional deviation.
- Moving arrows is `ArrowDefinition: CustomTranslation`. Alone (or with unrelated shapes) it is the POC's translation exactly; moved with a shape it's bound to, it keeps every binding, as tldraw. Its ends probe at the full delta (tldraw: half), a known deviation the transcript pins.
- CompositionTests holds the app to the proof of concept (commit 804db97): an arrow transcript compared byte for byte, and renders (outlines, binding hints, handles) compared pixel for pixel. `Tests/CompositionTests/Replay.swift` drives both the POC recording and the test. The fixtures come only from the POC, via `scripts/record-poc-fixtures.sh` (re-running it must change nothing). Never regenerate them from the app to make a change pass; an intended change to arrow behavior needs an explicit note. A scenario that ends differently on purpose gets an entry in `intendedDeviations` (TranscriptTests): the golden line, the app's, and why. The one so far: a press doesn't bring a shape to the front (the POC's did; tldraw's doesn't). Scenarios are only ever appended, recorded from the POC. The "pan" scenario presses H and holds still 100 ms before `.up` (both no-ops in the POC), and the welcome renders use the POC's note text, `pocWelcomeTexts`.

## Verifying UI changes

- Screen capture isn't permitted here.
- Drive a headless editor with `EditorHarness` (CanvasTesting), with `KeyboardPlugin()` and `SelectionPlugin()` first in its plugins when the test presses, drags or selects as a user does (without Selection the default tool is Hand, and without Keyboard no key does anything). `h.key("v")` presses a key on the canvas (with what `h.hold` holds); CanvasTesting's fixture tools have no keys, so pick them with `h.editor.setTool`. One clock drives event timestamps and the `ManualScheduler`, so pointer speed, the arrow timers and the hand tool's slide (inertia) behave. Check drawing with `renderBitmap`, `pixel` and `changedPixels`.
- For focus, key routing and the editing view, put a `CanvasView` in an unshown `NSWindow` and send it synthesized `NSEvent`s (see CompositionTests).
- For the minimap, CanvasUITests put a `CanvasView` with `showsMinimap` in an unshown window, send `canvas.minimap` mouse events, and hold its picture, kept through edits, to a fresh `MinimapView`'s, pixel for pixel.
- For context menus, `h.secondaryClick(at:)` returns the `NSMenu` (or nil); read it with `menu.outline` and run an item with `menu.choose("Status", "Done")`. Nothing goes on screen.
- For the clipboard, never touch the user's pasteboard: give the plugin a private one (`ClipboardPlugin(pasteboard: NSPasteboard.withUniqueName())`, `ShippedPlugins.makeEditor(pasteboard:)`, `configureBoards(pasteboard:)` in CompositionTests) and `releaseGlobally()` it after.
- For the detail panel, check layouts and writes headlessly (`editor.detailPanel?.layout(for:)`, a tab's status lines with `layout.statuses(in:)`, the footer's with `statuses(for:)`, `editor.shapeBinding`). For its views, host `DetailPanelView` in an `NSHostingView` in an unshown `NSWindow`, beside the canvas when focus matters (DetailPanelTests; `Tests/CompositionTests/InspectorTests.swift` uses the app's own wiring), with the real `TaskScheduler`. CanvasTesting drives the window: `window.spin { condition }` runs the main run loop until the state a test expects arrives (and fails the test after 2 s), `window.settle()` runs it a few turns where there's nothing to wait for, and `focus`, `type`, `press` and `mouse` send input. Call `canvas.mouseDown` directly (`sendEvent` mouse-downs don't reach views in an unshown window). Once there's a step back, the header has a back button, an `NSButton` in the panel's top 44 points, and a kind renamed in its header has a text field there, so tests that count the panel's buttons, checkboxes or fields leave the header out (`isInPanelHeader`). Render the panel standalone: in the app's `.inspector` it doesn't draw offscreen.
- For the table of contents, read `editor.tableOfContents?.entries` headlessly (each row's text, symbol and badge through `entry.label`, its marks through `entry.marks`), and drive `select(_:)`, `showAll()`, `hover(_:)` and `endHover(_:)`. SwiftUI's hover doesn't answer synthesized events, so check a row's tint by rendering the list with `snapshot(view)` (CanvasTesting; highlights draw, a source list's vibrant text may not). In a window, its list is an `NSOutlineView` whose first row is the header, a group row (TableOfContentsTests). AppKit's warnings go only to standard error: `standardError(during:)` (CanvasTesting) returns what was logged, so a test can check a list's update logged no `tableReentrancyWarning`. A shape's panel can hold lists too (a checklist), so CompositionTests tell them apart with `isTableOfContents` (`Tests/CompositionTests/ContentsPanelTests.swift`), and InspectorTests' `tables` leave it out.
