# Infinite Canvas

Native macOS infinite canvas (an AppKit document app, SwiftUI windows around an AppKit canvas), built from compiled-in plugins.

## Build and test

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`. The app carries its command line, `canvas` (`Contents/Helpers/canvas`; `build/canvas` links to it): with the app open, `build/canvas help`.
- `./build.sh bench` builds BenchmarkTests in release and runs it: saving, opening, validation's first read (every shape, checked against its kind's schema too) and its read after a drag, a hover and a drag frame (titles' pills, checklists' tallies and locks in view), a hover on a note's port dot and a drag from it, a hover onto a title's pill, reading the table of contents' rows after a commit, and the minimap's first picture (a frame at a time) and a drag frame with it, on generated boards of 1,000 and 10,000 shapes, against their budgets (the persistence plan's: open 10,000 shapes in under 1 s, a frame in 16 ms; validation's first read of 10,000 in 100 ms; and the rows, and validation after a commit, in 1 ms). It only reports the first frame and the next zoomed out to fit the board (at 10,000 shapes, as far as the 10% zoom goes). `./test.sh` runs it small, in debug, without the budgets.
- `./test.sh` builds every module but the app (debug, `-D DEBUG`) and runs each test executable. `TEST_FILTER=substring ./test.sh` runs the matching tests, and fails if none match. `TEST_UI_MENUS=1` adds the tests that open real (on-screen) menus. Every `Suite` a test target declares must be passed to `runTests` in its `main.swift`; test.sh fails otherwise.
- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (wire, foundation, ui, horizontal, vertical, bridge, composition, app, cli, testsupport, test). Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` (it would shadow Swift's in every importer); and on a module writing another module's `ShapeKind`, `PluginID`, `ToolID`, `PropertyKey` or `ChannelID` (Ports') string without depending on it (a name in a property list, `Property("…")`, is exempt, and so is a JSON member named by a JSON Schema keyword, a subscript's key, `json["title"]`, or a key before a colon where a member's name starts, but not in a `case`'s patterns or `where` or a ternary, even across lines: the `title` keyword is also Titles' property key; any other member's name, `json["locked"]`, counts). The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool, plugin, property or channel id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph.
- If the build fails with "this SDK is not supported by the compiler", a stale newer SDK is being picked. Prefix the command with `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`.
- Sources compile in Swift 6 language mode. Keep them free of warnings (build.sh passes `-warnings-as-errors`).

## Architecture

Read `docs/plugin-system.md` first; it's the guide to the plugin system, with the examples.

- `Canvas` (the core) knows no particular shape or concern (its one tool is Hand), and must stay that way. A concern like validity is declared by a plugin (an `ExtensionPoint` in its own module) and other plugins opt in; if the core seems to need to know about one, add a generic extension point instead.
- A plugin is a value (`CanvasPlugin`) that registers into a frozen `Registry`, which refuses a plugin list with a duplicate plugin, a contribution whose owner isn't installed or whose kind nobody registers, or two claims to one key. A rule spanning a point's contributions that keys can't express goes in that point's `static func check(_ registry:)`, which throws `RegistryError.invalid` or any error (reported as `invalid` for the point; the core runs it without knowing what it checks). A kind is its props type (`static let kind`, defined by its list of properties); its behavior is a stateless `ShapeDefinition` (only `render` is required for box kinds, and `geometry` drives hit testing and outlines); more comes from capability protocols (`Editable`, `CustomTranslation`, which moves a kind by its own rules through `beginTranslation` when a `TranslatingSession` moves it, `PaintOrderAnchored`, and `DerivedProps`, whose `derive` puts what follows from the rest of the props in step, as the kind's setters would, in a shape made from properties, `registry.shape(_:properties:)`: a schema card's height). Escape on a `TranslatingSession` puts back only what the drag moved (a box's origin; a `CustomTranslation` kind's whole record from before its begin), so a plugin's write to a shape while it moves (a model's answer landing) stays. Selection declares two more: `HandleProviding` (handles on the only selected shape), and `BrushHitTesting`, which the marquee asks only when it overlaps a shape without strictly containing it (default: `ShapeGeometry.isHit(byBrush:)`, from `geometry`). Behavior intrinsic to a kind is a capability; behavior any plugin can add is an extension point. Conform to `ShapeDefinition` (and capabilities), `Tool`, `Session`, `EditorService` and any extension point that implements `check` or `summary` (how the registry's report shows a contribution) in an extension: only there does the compiler flag a near miss on a defaulted requirement.
- A kind's props, and any struct stored in them, are a list of properties (`SchemaDefined`): `static let properties = Properties<StickyNote>(title: "Sticky note") { Property("frame", \.frame).required(); Property("text", \.text).description("…") }`, with `init()` giving the defaults. The list is the type's `Codable` (a member missing from a board reads as its default; a `required()` one has none) and its JSON Schema (2020-12): each property's type from its member's (`SchemaDescribed`: the core's geometry and `ShapeID` as `core.*` definitions, `SchemaCases` for a string enum, a nested struct in place or, with `definition:`, shared and named after its module, `checklists.item`), its default, and what its modifiers add (`PropertyModifiers`: `minimum`, `maxLength`, `pattern`, `examples`, `keywords` for any other). A type that codes itself by hand writes `schema(in:)` by hand (`ArrowTerminal`). The registry describes every kind's and added property's schema as it's built, and refuses a list of any struct those reach that misses a stored member (a board wouldn't save it), names a non-member or has a key path that isn't its member (a computed view), lists one twice, writes one member twice, has an optional that's required or defaults to non-nil, or holds optionals in a collection (nor may an added property's value); the first problem is the one reported, a property value's against its declarer; and two types under one definition name, or a struct that holds itself with no name. `registry.schema(for: kind)` is the kind's whole schema, its added properties included. `registry.schemaViolations(of: shape)` checks a shape against it (its own and added properties as one object, `record.propertiesJSON`, through a fast `JSONValueEncoder`; each kind's schema compiled as the registry is built, `SchemaValidator`, which checks any JSON against any schema, strings code point for code point and patterns as ECMA-262 reads them; and a schema it couldn't check, a `$ref` to nowhere or back to itself before going into the value, a pattern ICU can't read, refuses the plugin list, a kind's or an added property's): typed props always have the schema's shape, so what breaks it are bounds (`maxLength`, `minimum`) and numbers that aren't finite. A bound is a guideline, never a refusal: Validation warns about each violation. Agents get the schemas from the command line (`canvas kinds --schema`).
- Added properties are what a plugin adds to the kinds that opt in: something the shapes know that their kind doesn't declare (a checklist). The type is the key: `enum ChecklistProperty {}` with `extension ChecklistProperty: ShapeProperty { static let key: PropertyKey = "checklist"; static var defaultValue: [ChecklistItem]? { [] } }` (a nil default: only the shapes it's set on have one), and `static var keywords: PropertyKeywords<Value>` for what its schema says beyond its type (Titles' title: `.minLength(1).maxLength(80)`), and `static func isNone(_:)` for a value that's no value at all (Titles' blank title), which no shape holds: a shape set to one, or read from a board with one, holds nil, or the default for a property that has one (which can't be none). A value a board writes as null, added, kept or handed over, is none too. Its owner declares it (`registrar.declare(P.self)`); a kind opts in through the owner's sugar (`ShapeRegistrar.optIn(to:)`, as `note.checklist()` does), a bridge's `registrar.optIn(Kind.self, to:)`, or `optInEveryShape(to:where:)`. The registry refuses an opt-in to a property nobody declares, a key declared twice, a kind opted in twice, and a key that's one of the kind's own property names; its report lists `property checklist` and `property checklist → sticky-note`. Read and write `shape[P.self]` (`record[P.self]`), in a transaction like the props; a write the shape can't hold (its kind doesn't opt in, nil for a property with a default, a value kept aside) is dropped. A placement sets one on what it places with `.setting(P.self, to:)`. Defaults are filled where shapes enter an editor (inserted or placed, `CanvasEditor.init`, `replaceDocument`, a board read; `registry.fillingDefaults`); filling never marks a board edited by itself. In a kind's schema each one is a property marked `x-canvas-owner`. What a shape knows is a property; what a plugin keeps about a shape (the one it was copied from) is `ShapeMeta`, never a property.
- Layers: horizontals (Keyboard, Selection, Validation, Titles, DetailPanel, ContextMenus, TableOfContents, Adornments, Checklists, Clipboard, Locking, Ports, Automation, LanguageModels) declare extension points and import no vertical, though one may build on another (Checklists on Adornments, DetailPanel and ContextMenus; Clipboard on Keyboard, Selection and ContextMenus; Locking on Adornments, ContextMenus and Selection; Ports on Selection; Titles on Adornments, DetailPanel and TableOfContents; Adornments, DetailPanel, ContextMenus and TableOfContents on Selection; Selection on Keyboard); verticals (Arrows, StickyNotes, Ellipses, TaskCards, Schemas, Rectangles, Polylines, Eraser, Reordering) import no other vertical (StickyNotes, TaskCards and Schemas import Ports, each for a channel of its own); bridges (EllipseTitles, ValidationDetails, ValidationContents, ArrowPorts) connect them, even two horizontals (ValidationDetails joins Validation and DetailPanel, ValidationContents Validation and TableOfContents), and ArrowPorts joins Arrows and Ports, the only code that knows both arrows and channels. The shipped list is `ShippedPlugins.plugins(pasteboard:model:)` in Composition (and `registry(pasteboard:model:)`, `makeEditor(document:scheduler:pasteboard:model:)`); the app passes `ShippedPlugins.anthropicModel`.
- The detail panel (DetailPanel, a horizontal) lays out a header, tabs, sections and a footer; plugins fill them with `x.details { DetailSection("…", in: SomeTab.self) { $x in … } }` and `detailStatusForEveryShape`: status lines, the shape's state rather than its settings, in the footer, or with `in: SomeTab.self` in a tab that shows only while the shape has lines there (ValidationDetails' Issues tab). A tab is a type (`DetailTab`) any plugin may declare, in order bands: 0 a kind's own, 50 a horizontal's feature tab, 100 `StyleTab`, 200 `ArrangeTab`, 300 a tab of the shape's state that comes and goes (Issues). A horizontal's feature is opt-in sugar on `ShapeRegistrar` that contributes to its own point and calls `details`, so opting in brings its tab (`note.checklist()`). An added property's sections are over its value: `x.details(of: P.self) { DetailSection(…) { $items in … } }`, or on `PluginRegistrar` for every shape that has it; a kind's own sections and header read added values through `$x.shape`, the whole record (`$task.shape.summary`), and bind one, nil while the shape has none, with `$x[P.self]` (a `Binding<P.Value?>`, as `TitleHeader($x)` does; the bindings one `$x` makes of its added properties read back the last write through any of them; on a kind that doesn't opt in, it reads nil and drops writes, and `$x.holds(P.self)` says which, so `TitleHeader($x)` on a kind that doesn't opt into titles stops a debug build). Sections write only through `$x.field` or `$x.update` (one transaction each, on the live shape, which the binding reads back until the panel redraws), bind the narrowest key path, and use `LabeledContent` and DetailPanel's primitives, never their own layout or fonts: among them `DetailTextArea` (with `placeholder:`, and `onCommit:`, which makes Return commit, ⇧↩ a new line, and the keyboard leaving commit too, a turn later if the view left the window with it, so a commit captures its service weakly), `DetailCodeEditor` (code typed as keyed: monospaced, every substitution, completion, prediction and Writing Tools off; lines never wrap; as tall as its lines, from `DetailStyle.codeEditorHeight` to what the panel shows; ⌘↩ and the keyboard leaving commit; `coloring:` names its runs, `DetailCodeSpan`, and the panel colors them), `.detailUpdating(_:)` (read-only and dimmed while something else writes the box; the words go on a status line where the person is, never over the text), and `DetailStatusLine` (a tone's symbol or, `isBusy`, a spinner, then the text, with `DetailStatusAction` buttons under it). A section reaches a service of its plugin's with `$x.service(S.self)` (the schema card's `SchemaSync`), never the editor. A read-only shape's panel (a locked one) shows everything with its sections' controls and its header disabled (`registry.isReadOnly(record)`, so the panel never reads the document); Back, the tabs and collapsing still work. The header is a view made from the shape's binding too, `x.details(header: { $x in DetailHeader("…") }) { … }`: a `DetailHeader`, or a view of the kind's own built on `DetailHeaderLabel` (with `DetailHeaderField` for a title renamed in place), so every header looks alike; the panel hands it the kind's name and symbol through the environment, and tests read it back with `layout.header` or `layout.header(as:)`. Keep the sugar's closure types unannotated, and never name `Transaction` in a file that imports SwiftUI. The app places `ShippedPlugins.detailPanel(editor:onExit:)` in an `.inspector`, with `onExit` set to `CanvasFocus.take` (CanvasUI), which gives the keyboard back to the canvas.
- The table of contents (TableOfContents, a horizontal) is a native `List` in the right-hand panel, with data-canvas's TOC contract: `x.contentsRow(when:nestedUnder:) { ContentsLabel(title, placeholder:, systemImage:, color:, badge:) }`, and `registrar.contentsRow(P.self)` for bridges. The list owns the row's chrome; a row reads only its own shape (unless it names what else it reads, below), and uses `ContentsLabel` so rows from different plugins look alike. `registrar.contentsMarkForEveryShape { shape, context in ContentsMark(color:help:) }` puts a dot at a row's trailing end from any plugin (ValidationContents: red or orange for a shape with issues, its tooltip the issues). A mark is part of the row, made with it, so one read from more than its shape names, with `affected:`, the shapes each commit may change the marks of (Validation's `dependents(of:)`): their marks are read again, and their rows replaced only if the marks changed. A row's view reads only its `ShapeRow`, never the document: the list makes every row's view on each redraw. A kind without a row gets its placing tool's label and symbol, and `x.contentsRow(when:nestedUnder:)` with no builder keeps that row. `x.contentsTitle { … }` (`ContentsTitles`) names a kind's rows from another plugin without replacing them: a name that isn't blank takes the place of a `ContentsLabel`'s title, keeping its symbol and badge (Titles names rows this way). Rows are in document order; `nestedUnder` nests a row only while its parent is listed. Arrows nest under the shape they start from. `ContentsState` keeps each shape's row and where it's listed (`ContentsListing`, per scope), and redoes only those of the shapes each commit's `ChangeSet` names: a read after a drag costs the dragged shape's row, not the board. Selecting on the canvas lists just the selection; selecting rows selects and zooms to their shapes (Selection's `editor.reveal`) without changing what's listed (`editor.selectionRevision` tells the two apart). A change of what's listed replaces the rows (`.id(scope)`), bringing the new ones in as one run: rows coming in at several places at once make AppKit, whose table sizes a `List`'s rows, log "a reentrant operation in its NSTableView delegate" (a future assert), as it still does when a list first shows 200 rows or more, or a commit brings rows in at several places. Hover is shared: the pointer on a row sets Selection's `editor.hovered`, which the canvas outlines faintly, and a shape hovered on the canvas tints its row (`isHovered`), in the selection highlight's place; a selected shape shows neither. A row's tint observes only its own shape's hover (`editor.isHovered`) and, while that shape is hovered, the selection, so a hover redraws the row it leaves and the row it reaches: rows that read `editor.hovered` would all be redrawn on every hover change. It's the detail panel's overview: `DetailPanelView(editor:onExit:overview:)` shows the overview with nothing selected, and under the header of several; Composition's `detailPanel(editor:onExit:)` passes `TableOfContentsView`, so neither horizontal knows the other.
- A table-of-contents row read from more than its shape (an untitled note's text with the live names of the shapes it mentions): `x.contentsRow(when:nestedUnder:affected:) { shape, context in ContentsLabel(…) }` (`registrar.contentsRow(P.self, affected:)` for bridges), whose builder gets the shape and a `ContentsContext` (services) and returns a `ContentsLabel`, and whose `affected: { changes, context in … }` names the shapes each commit may change the rows of without changing them. `ContentsState` makes those rows again on the next read and replaces a row (so the list redraws it) only if its label changed (title, placeholder, symbol, color and badge), as marks' `affected` does; a read before it hears a commit makes every kept row of such a kind again. `affected` runs on every commit, listed or not, so it must cost O(changed): a service keeps who reads what, per shape (AffectedRowTests' `RefIndex`). `when`, `nestedUnder` and `contentsTitle` work as for any row.
- Validation (a horizontal) is ESLint's model: rules (`x.validate { shape, context in … }`, `registrar.validate(P.self)`, `validateEveryShape`) find issues on a shape, each `.error` or `.warning`, two channels of one thing; an error makes a shape invalid. Validation's own rule, for every kind, checks each shape against its kind's schema (`registry.schemaViolations(of:)`): each violation is a warning about the property it's in ("Title is 95 characters long, and should be at most 80.", `field: "title"`). The overlay outlines a shape red with an error, orange with warnings alone, and not at all without issues. Rules see other shapes only through `ValidationContext`; `ValidationEngine` re-checks the shapes each commit's `ChangeSet` names and those whose rules looked one up, and keeps each shape's schema check until a commit changes the shape other than by moving it (`ChangeSet.moved`, the shapes a commit only moved with `Transaction.moveBox`, which a drag and `translate` use: a drag moves every shape it drags, every event). Bridges show the issues: ValidationDetails in the panel's Issues tab (worst first; the footer stays empty), ValidationContents as the dot on a row in the table of contents.
- Titles (a horizontal) is what a shape is called, a trait a kind opts into. A title someone names is Titles' to keep: `x.title()` opts the kind into `TitleProperty` (key `title`, nil until named), so the kind's schema has it with its bounds, 1 to 80 characters (`TitleProperty.maxLength`), and a longer title is kept and warned about (Validation's schema rule). No kind keeps a title of its own: notes and tasks handed theirs over (a task's blank title became none). A blank title is none (`TitleProperty.isNone`), so no shape holds one: naming a shape "  " leaves it untitled, and a board's empty title reads as none. A title can instead be derived from what the kind keeps (`x.title { ... }`, EllipseTitles' "Ellipse, 200 × 140"), and isn't in its schema; any shape may have none (nil or blank). A titled shape shows a pill just outside its top-left corner (`TitlePill`, an adornment Titles places on every titled shape: the row above the top edge, from its left end, as long as the title and no longer than the row leaves it, less what's at its right end, a lock; `pill: false` for a kind that draws its own, as task cards do), and its title names its row in the table of contents (`contents: false` keeps the kind's row). `TitleHeader($x)` renames the title Titles keeps in the detail panel (`TitleHeader($card.text)` renames a derived one at its source); a kind places it in its own header (`note.details(header: { $note in TitleHeader($note) }) {}`), since Titles contributes no header.
- Adornments (a horizontal, on Selection) lays out and draws the small things shown on a shape, just outside it or on its corner, from what the shape knows: Titles' pill (`TitlePill`), Checklists' tally (`ChecklistChip`) and Locking's lock (`LockChip`) are adornments. An adornment is a type (`Adornment`: its `placement` and its `order`, in the tabs' bands: 0 a kind's own, 50 a horizontal's feature, 300 a state that comes and goes), never a record. Any plugin places one, on kinds it defines or not: `x.adornment(A.self) { shape in … }` for a kind's own (a horizontal's opt-in sugar may call it, so opting in brings the adornment), `registrar.adornment(A.self, on: Kind.self) { … }` for a bridge, and `registrar.adornmentForEveryShape(A.self, where: { kind in … }) { shape, context in … }`, where `where` (an `AdornableKind`, asked once per kind) picks kinds by their definition, by what the registry says of them (Titles: the kinds whose title shows a pill), or by the added properties they hold (`$0.holds(LockedProperty.self)`: Locking's lock goes only on kinds that can be locked). A kind's own takes the place of an every-shape one of the same type, and one adornment twice on a kind is a conflict (`ShapeAdornments` is keyed). A label is an `AdornmentLabel` (one line of text, or an SF Symbol in a disc; `tone: .success` is green; `opacity(_:)`), or nil for none on that shape, and every plugin's looks alike. It reads only its shape, the registry, and services that call `editor.adornmentsDidChange(for:)` when what they keep changes (Locking's open lock, fading). Places (`AdornmentPlacement`): the row 9 points above the top edge, 18 tall, from its left end (`aboveTopLeft`: text gives way to what's at the other end, ending in "…", and needs 30 points) and from its right end (`aboveTopRight`: whole); and the top-right corner (`onTopRightCorner`: 16 tall, centered on the top edge, from 6 points past the right edge). Each place is a run, 4 points apart, so on one shape none overlap, by construction (`AdornmentLayout`, pure); the row's right end and the corner reach no more than 200 points (what would is left out), and its left end stays within the shape's width, which bounds culling and hit testing; sizes are view points, constant down to 25%. `AdornmentState` keeps each shape's labels, made and measured, and drops those each commit's `ChangeSet` names; read before it has heard a commit, it makes them afresh and keeps nothing. `AdornmentOverlay` draws them in one pass over `editor.paintOrder(in:)` (the view grown by `context.worldDrawingReach` too, so a shape shaken into view shows them), above every shape, where the shape is drawn (a shake moves them), never in the minimap. A `ClickableAdornment` (the lock) is a canvas button, and its shape's only for the context menu; any other adornment is its shape for the select tool, hover and a double-click, and every adornment, the lock too, for the context menu (Selection's `DecorationHits`). `editor.adornmentFrames(of:)` is where each of a shape's is, in world units.
- Context menus (ContextMenus, a horizontal) follow the same pattern: `x.contextMenu { MenuItem("…", in: SomeGroup.self, when: { … }) { $0.field = … } }`, `registrar.contextMenu(P.self)` for bridges, `x.contextMenu(of: P.self) { … }` over an added property's value (on `PluginRegistrar`, every shape that has it), `contextMenuForEveryShape(where:)` (`where` picks kinds by their definition, so by capability; Reordering's Arrange submenu leaves out `PaintOrderAnchored` kinds). A group is a type (`MenuGroup`) in the tabs' order bands, with separators between groups; a horizontal's opt-in sugar calls `contextMenu` too, so opting in brings its items (Checklists' bulk actions). `when` leaves an item out (prefer it to `isEnabled`, which dims); nothing left, and the right-click does nothing. Items that aren't one shape's (Cut, Copy, Paste) are the canvas's: `registrar.contextMenuForCanvas { MenuItem("…", when: { $0.editor… }) { ids, editor in … } }`, over the menu's `MenuSubject` (its shapes and the editor), asked once per menu, in every menu after the shapes' own, and alone on empty canvas. The menu is for the selection: a right-click on an unselected shape selects it (only if it has a menu), and with several shapes an item shows when every one shows it (same group and id). The core only lends `registrar.menuForSecondaryClick`, which ContextMenus claims; `CanvasView.menu(for:)` asks it. A Control-click with no menu reaches the tool as a press with `pointer.isControlClick`: the select tool ignores it, and tools that read ⌃ as a modifier (the arrow tool) take it, so ContextMenus answers Control-clicks only in the select tool.
- The clipboard (Clipboard, a horizontal): ⌘X, ⌘C and ⌘V (Keyboard), the `.cut`, `.copy` and `.paste` commands, and Cut, Copy and Paste in every context menu (items for the canvas), on the selection. The pasteboard holds a small board (`BoardCodec` JSON, the app's own type); anything else on it is ignored for now. A paste gets new ids, lands in place if any of it would be in view (else centered, with `transaction.translate`), is selected, and each copy's metadata names its original (`record.copiedFrom`, `meta[CopiedFrom.self]`). Every kind is copyable unless it opts out (`x.uncopyable()`, `x.copyable { … }`; the `ShapeCopyability` point). Every kind whose props are bound to shapes adopts the core's `ShapeReferencing` (arrows, CanvasTesting's `Tag`): deleting a shape asks it of every shape bound to it, after `willDelete` handlers (arrows let go where they're drawn), and a copy is bound to the copies of the shapes copied with it and lets go of the rest; it returns nil when it can't let go of a shape it can't find, and a copy then leaves it out. Shape metadata (`AnyShapeRecord.meta`, typed by a plugin's `ShapeMetaKey`, saved under the owner's id, then the name) is the core's generic place for what a plugin keeps about a shape beside its props; what the shape itself knows is an added property. A per-kind rule table is `registry.contributionByKind(to:)`, and the union of shapes' bounds `shapeContext.bounds(of:)`.
- References between shapes have two forms behind one entry, `record.remappingReferences(_:in:)` (`docs/plugin-system.md`, "Values that name shapes"). Bindings (`ShapeReferencing`, a kind's definition: an arrow's ends) must be on the board: a delete lets them go, a copy renames those copied along and lets the rest go, and `canvas create` refuses one that isn't there (`record.boundShapes(in:)`). Names (`ShapeNaming`, a value: a mention) may outlive their shapes: a copy renames those of shapes copied along and keeps the rest (nil keeps a name), a delete never looks for them (it asks only `referencingKinds`, so deleting a mentioned shape writes nothing), and `create` keeps a name of a shape that isn't there and warns ("lead names shapes that aren't on this board: …; they show as missing."). The core finds names through property lists: a kind's props by their list (a property whose member's type is `ShapeNaming`, found once by a runtime check, so a plain property carries nothing), a struct in them or in an added value adopts `ShapeNaming` in an extension with nothing to write (`extension ChecklistItem: ShapeNaming {}`), and the registry refuses one that holds names without adopting it; optionals, arrays, sets and dictionaries keyed by strings (an object with `additionalProperties` in a schema) of names are names, and a leaf coded by hand implements `forEachNamedShape` and `renamingShapes` (pure). `registry.namingKinds` are the kinds whose props or opted-in added values can hold names, and `record.forEachNamingValue(in:)` walks a shape's, with the property each is in (none kept aside, which a copy doesn't rename either). A kind without names costs a set lookup where names are walked, and nothing on a delete. Core tests use CanvasTesting's `NamingPlugin`: `Citation` (a leaf that counts its visits), `Memo` (names in a struct in a list, an optional, a dictionary, and `CitationsProperty`) and `CitingTag` (binds and names).
- Locking (a horizontal, on Adornments, ContextMenus and Selection): any shape can be locked, from the context menu only (Lock, or Unlock once every shape the menu is for is locked, as tldraw's toggle; items for the canvas in `LockMenuGroup`, order 300; no key), and unlocked there or with a click on its chip (`LockChip`, a clickable adornment). Once a shape is unlocked, however, its chip shows the lock open for 1.5 s, more while the pointer's on it, then fades over 0.3 s; a click on the open lock locks the shape again, so a click by mistake can be taken back. Locked is something the shape knows: `LockedProperty` (`locked: true`, nil when unlocked), an added property every kind opts into (`optInEveryShape`), read as `record.isLocked`, set with `editor.lock(ids)` and `editor.unlock(ids)`; a locked shape's copy is locked. Locking tells the core locked shapes are read-only (`registrar.readOnlyShapes`), so nothing changes, moves, restacks, edits or deletes one (a drag moves the rest of the selection, Delete and Cut take the rest, the panel is disabled, there are no handles), while it's still selected, copied, listed and bound to. Each try shakes it (`LockState` hears `didRefuseChanges` and plays `editor.setDrawingOffset`: 5 points side to side, 3 times over 360 ms, dying away; a try while it plays doesn't start it over; a click doesn't count). A chip (`LockChip`: an 18-point disc with a lock, on the kinds that hold `LockedProperty`, at the right end of the row above the top edge, order 300, so a title's pill stops 4 points short of it; lighter hovered, darker pressed) marks it; its open, fading lock is a label `LockState` keeps (`openLockOpacity(of:)`, with `editor.adornmentsDidChange`). Core and horizontal tests use CanvasTesting's `FreezingPlugin` and `Frozen` for read-only shapes, never Locking.
- Ports (a horizontal, on Selection; data-canvas's) are dots just outside a shape's sides, from which a drag draws a connection (an arrow) that may end only on a shape that takes its channel. A channel is a kind of connection, a type (`Channel`: `static let id: ChannelID`, and `static var color` for its dots, computed, gray by default), declared by the plugin that owns what it means (`registrar.channel(NoteLink.self)`, the `Channels` point; one declaration per id). `ChannelID` is what a connection keeps, so it never changes once shipped, and the id audit holds its literal to the module that declares it. A kind has ports on a channel with `x.ports(C.self, sides:role:)` (`registrar.ports(K.self, on: C.self, sides:role:)` from a bridge; the `ShapePorts` point, one per kind and channel, and a kind may have ports on several): a dot at the middle of each of `sides` (`PortSide`, all four by default), and a `PortRole`, `.both` (the default), `.source` (dots; nothing ends on it) or `.target` (connections end on it; no dots). `ShapePorts.check` refuses ports on a channel no installed plugin declares, or on the connector's own kind. One plugin draws connections, the connector (`registrar.connects(K.self, canConnect:begin:)`, the `Connectors` point, at most one): `K` opts into `ChannelProperty` (key `channel`, nil by default, so only a connection drawn from a port has one; an arrow from the arrow tool has none), `canConnect` says which shapes one may start from and end on, and `begin` gets the `Connection` (`shape`, `side`, the dot's `channels` in plugin order, `origin`, where it was pressed, world units) and returns the session the press hands the drag to (nil: nothing). Without a connector no shape shows ports. `editor.channel(of:endingAt:)` is the first of a connection's channels a shape's kind takes as a target (nil for the shape it starts from, or one kept aside); `registry.accepts(shape, on:as:)` and `registry.declares(_:)` are what rules for connections already drawn go by. The dots are Selection's canvas buttons, dragged (`PortDot`, from `PortState.dot(atViewPoint:)`), shown for one shape, the host: the one whose dot the pointer is on (any shape's, so a dot reached straight from empty canvas shows its shape's, as data-canvas's halo does), else the shape with dots under the pointer, kept while the pointer stays within reach of its dots (its view bounds grown by 24 points) over empty canvas or a shape without ports; none while a handle is under the pointer (it takes the hover), and none once the tool changes or the shape is deleted. A shape has dots when its kind has a side that isn't `.target`, it isn't kept aside, and `canConnect` allows it. They show in the select tool only, at 25% zoom and up (`PortStyle.minZoom`), while the pointer's over the canvas (`editor.pointerOverCanvas`) and, where it is now (`editor.pointerWorldLocation`), within reach of them, and nothing is under way but a dot's press: each 12 view points out from the middle of its side of the shape's bounds, a disc 8 points across in its first channel's color at 60% in a white 1.5-point ring, and hovered or pressed 10 points across at full color in a halo 24 points across at 24% (`PortStyle`'s radii: 4, 5, 12); constant on screen, following the host's drawing offset (a locked shape's shake). A dot shows, and is hit, only while no selectable shape painted above its own covers its center (an arrow leaving the shape there, a neighbor on top; `PortState.liveDots(of:)`), so a shape lying on a bigger one shows its dots over it. The nearest showing dot within 12 view points is pressed (none where the select tool hasn't seen the pointer move, just after a tool change or a first click into the window, since none shows there); past the drag threshold the connector draws, and while it does each shape in view the connection could end on is outlined faintly, as a hover (the one it would end on now gets the hint). `PortsPlugin` comes after `AdornmentsPlugin` in the shipped list, so a dot is found before a lock chip (a clickable adornment) and draws above it. Locked shapes keep their ports: connecting doesn't change them. ArrowPorts makes arrows the connector (`canConnect` is `editor.canBindArrow(to:)`, `begin` is `editor.beginArrow(from:at:canBind:complete:)`, `canBind` a shape that takes one of the port's channels (`editor.channel(of:endingAt:)`), and `complete` sets the arrow's `ChannelProperty`), and its `arrowBindingRule` keeps an arrow with a channel some installed plugin declares to shapes that take it at that end (the start as `.source`, the end as `.target`), re-aimed or moved; one without (the arrow tool's), or with an undeclared channel, binds wherever an arrow can. Shipped: notes have ports on `NoteLink` (`note-link`, a brown amber) on every side but the top, where a titled note's pill is (`NoteLinks.swift`), and tasks on `TaskLink` (`task-link`, purple) on all four, since a task draws no pill (`TaskCardLinks.swift`), each declared by its kind's plugin, so a note links only to a note and a task only to a task.
- The command line (`canvas`, for agents first, people too; `docs/plugin-system.md`, "The command line"): agents never read or write a board's file, only run `canvas`, which asks the running app. The wire is CanvasRPC (layer `wire`: knows no canvas, plugin or AppKit): JSON-RPC 2.0, a message a line, over a Unix-domain socket only this user can reach (`~/Library/Application Support/InfiniteCanvas/canvas.sock`, or `CANVAS_SOCKET`; the app that holds `canvas.sock.lock` listens, so a second app gives up and a crashed one's socket is taken over); `CommandSpec`, a command's description with its params as a JSON Schema, and how params are spelled as arguments (`spec.params(from:)`, `usage()`, `help()`); the blocking `RPCClient` and the `RPCListener`, which answers on the main actor. `canvas` is CanvasCLI (layer `cli`: the wire only, never the app) and knows no command but `help`: each run asks the app (`describe`) and makes the commands, their arguments and their help from what it says, so a plugin's command needs nothing of `canvas`, and it refuses an app of another `RPC.protocolVersion`. Results go to standard output (JSON when it isn't a terminal, text for people, `--format`), errors to standard error with a `reason` and a `hint`, and it exits 0 done, 1 the app couldn't, 2 usage, 3 unreachable. The app's end is CanvasUI's `CommandServer`, started by the app: `status` and `boards` are its own, and it runs the rest on the board a request names (`--board`: its number, `BoardDocument.number`, its file, or its name) or the one in front. Every other command is Automation's (a horizontal, which the app reaches through Composition's `commands(in:)`): `registrar.automationCommand("name", "summary", params: P.self, positionals:, examples:) { params, context in … }`, its params a `SchemaDefined` list (each property an option, `fooBar` as `--foo-bar`; `x-value-name` for help), checked and decoded before it runs, its output anything `Encodable`, its errors `AutomationError(_:reason:hint:)`, a board command's changes through `context.board()`'s `transact`. The registry refuses a name `canvas` can't type or that's kept (`RPC.reservedCommandNames`: `describe`, the server's `status` and `boards`, `canvas`'s `help`), a param named `board` or like `canvas`'s own options, and two commands of one name. A command's options may come before its name (`canvas --board 2 create ellipse`). Automation's own: `create` (what the kind's tool places, `registry.placement(for:)` and `placement.shape(at:)`, with `--props` and `--set` over it, through `registry.shape(_:properties:)`, the inverse of `propertiesJSON` but for what a kind derives (`DerivedProps`); a shape past its schema's bounds is made, with warnings, and one bound to shapes not on its board, `ShapeReferencing`'s, isn't, while one that only names them, `ShapeNaming`'s, is, with a warning) and `kinds` (each kind's properties, and `--schema`).
- Language models (LanguageModels, a horizontal that declares no point) lend every editor one model for any plugin to ask: `editor.languageModel` (nil without `LanguageModelsPlugin(model:)`), a `LanguageModel`, whose one call is `respond(to: ModelRequest) async throws(LanguageModelError) -> ModelResponse` (a system prompt, `ModelMessage`s, `maxTokens`, `temperature`, `stopSequences` in; text, `stopReason`, token counts out). Every `LanguageModelError` has a short `message` for a person ("Add your Anthropic API key in Settings…") and `isTransient`; cancelling the asking task throws `.cancelled`. It knows nothing of what plugins ask. The app's model is `AnthropicModel` (Claude Haiku 4.5, `claude-haiku-4-5`, over URLSession straight to `https://api.anthropic.com/v1/messages`; no SDK, streaming or retries), which waits for an answer a minute and a second more for every 100 tokens it may write (it comes whole, nothing streams: `timeout(for:)`, `.timedOut` past it), and reads the key at every call from `AnthropicKeyStore.standard`: `~/Library/Application Support/InfiniteCanvas/anthropic-api-key`, the key alone, mode 0600, written whole and renamed into place, a missing file no key (not the Keychain: the app isn't signed). Infinite Canvas › Settings… (⌘,, `BoardMenus.showSettings`, answered by the app's delegate) shows one reused window hosting `ShippedPlugins.settings()` (`AnthropicSettingsView`: a secure field, Save, Remove, Test with a five-token call; its logic is `AnthropicKeySettings`, whose Save and Remove post `Notification.Name.languageModelKeyDidChange`, so what failed for want of a key can try again by itself; its metrics are `SettingsStyle`). Never print, log or write the key. No test reaches the network but SchemasTests' live smoke test, which runs only with `SCHEMA_LIVE=1` (test.sh never sets it): every test that builds the shipped list passes `model: ScriptedLanguageModel()` (the parameter has no default), which keeps `requests`, answers from its queue (`queue(_:)`, else `fallback`, else fails), and while `holdsAnswers`, keeps each call waiting until `release()`; its calls land on the main actor, so a test turns the main run loop (TestKit's `spinRunLoop(until:)`, `awaitResult { … }`). LanguageModelsTests stub URLSession with a `URLProtocol`.
- Schema cards (Schemas, a vertical; `docs/plugin-system.md`, "Schema cards"): a `SchemaCard` (kind `schema-card`, the Schema tool, S, `curlybraces`) is a JSON Schema kept as its text (`schema`: order and half-typed text survive; `prompt` beside it), named by its root `"title"` (a derived title, `x.title(pill: false) { … }`, never Titles' `TitleProperty`, so it's said in one place; `setTitle` rewrites only that member), which the card draws inside, so it has no `TitlePill`, as a task card has none (its lock, an adornment, still shows). `JSONReader` reads JSON in order, with ranges, line and column, tokens, and a depth limit; `SchemaDocument` reads the title, the top-level fields and the root's rules, and each `SchemaField` its type and fields a level at a time (`$ref`s within the document, bounded). The card shows a row per top-level field, at most 7 (8 or more: 6 and `+N more`), nested fields inside their parent's row (`{ name · email }`, `[ sku · price ]`, `{…}` deeper), never as rows. Write the schema only with `setSchema` (`schema` is `internal(set)`), which fits the height in the same transaction (`SchemaCard.height(for:)`: 45 + 22 a row, 89 empty; a text that isn't JSON leaves the frame); the width is the person's; a card made from properties (`canvas create`) is fitted too (`DerivedProps`), unless `--size` says otherwise. `SchemaReadings` keeps a reading (and its layouts) per card, read again only when the card's text changes, so a frame of cards that didn't change parses nothing however many different schemas are in view; the sync drops a card's once it's deleted, and past 4,096 those used longest ago go (`SchemasPlugin.schemasRead` counts reads in debug builds). Its panel is its only editor: the header renames the root `"title"` (`setTitle`; off while the model writes the schema); the Schema tab has the description (`prompt`, a `DetailTextArea` with `onCommit:`) over the JSON Schema (a `DetailCodeEditor` colored by `JSONReader.tokens`, the token where it stops being JSON marked, with the line and column under it). `SchemaSync` (`editor.schemaSync`) keeps the two in step through `editor.languageModel` (`SchemaPrompts`): only the person's edits to the two sides sync (not its own write, a board read again, a move or a lock), on a commit (Return, ⌘↩, the keyboard leaving) or 3 s after the last (`editor.scheduler`); a changed prompt rewrites the schema (whole: past `SchemaPrompts.toSchemaMaxLength`, 34 KB, it's never sent, and the status says to edit it by hand), else a schema changed in meaning rewrites the prompt; never for text that isn't a JSON object, a read-only card, an empty new card, or without a model; a card first seen is in step, but for a prompt over a schema with no fields, which was never answered; the side being written is read-only (`.detailUpdating`) and its answer dropped if it changed; edits to the other side sync once it lands; `NO_CHANGE` (the first word, or the last line) writes nothing. Its status (`SchemaSyncStatus`: updating, or a `SchemaSyncFailure` with its remedy: Retry, Open Settings… and Retry, or `editByHand`, no button, for a schema too long to write whole) shows under the side the person edited, so it's in view whichever section is collapsed, and a key saved in Settings retries the cards that failed for want of one. The quick evals are `scripts/schema-prompts` (they read the prompts, their settings, the model and the starter out of the Swift). Validation: not JSON (line, column) or not an object is an error; `required` naming no property a warning. The table of contents' badge is the top-level count. Ports on all four sides, on a channel of its own (`SchemaLink`, `schema-link`), as notes and tasks have: a schema links only to a schema.
- `CanvasEditor` is the headless brain (document, camera, tools, sessions, input, drawing). What it lends plugins generically: a default tool (`registrar.defaultTool`, else Hand) that Escape and placing return to; `registrar.outlines`, stroked with the hint in one pass, over the faint ones (`Outlines.faintShapes`); read-only shapes (`registrar.readOnlyShapes { record in … }`, `editor.isReadOnly`, `registry.isReadOnly`: a transaction doesn't change, restack, `translate` or delete a shape that was in the document before it and is read-only, unless the change leaves it no longer read-only, and what a deletion does to keep the board whole still goes through: its `willDelete` handlers' changes (a read-only dependent goes with its shape) and letting go of a deleted shape (`ShapeReferencing`); a rule reads only the record; `TranslatingSession` leaves them out of what moves, `beginEditing` refuses them, and services hear each refusal once it's done, `EditorService.didRefuseChanges`, a drag's once past the drag threshold); drawing offsets (`editor.setDrawingOffset(_:for:)`, view points: the shape and its outlines draw there, overlays that decorate it (adornments, the validation outline) follow with `context.worldDrawingOffset(of:)` (and may grow the rect they cull by with `context.worldDrawingReach`, the farthest any shape is drawn from where it is, as adornments do), and nothing else moves: hit testing, handles, the minimap); commands (`registrar.command`, `editor.perform`: what menu items run, Edit › Delete and Edit › Select All from `CanvasView`, Go › Back and Edit › Cut, Copy and Paste from `BoardWindowController`, wherever the keyboard is but in text; `isEnabled:` and `editor.canPerform` enable a menu item, and a command's keys); the secondary click's menu (`registrar.menuForSecondaryClick`); key strokes (`registrar.keyStrokes`, which Keyboard claims); `Tool.cancel`; `EditorService.documentDidChange` (with each commit's `ChangeSet`, whose `replacedDocument` tells `replaceDocument`, a board read again from disk, from an edit) and `didPlace`; `Session.hidesOutlines` and `draw(in:)`. `CanvasView` (CanvasUI) only turns NSEvents into editor calls and hosts the editing view and the minimap. Plugins can't import CanvasUI. A tool may let a press pass as though it never came (`Tool.ignoresPress`, asked first of every press: the camera goes on moving, editing goes on, no session starts), for the rest of a click it has already acted on.
- Editing in place (`Editable`): `editor.beginEditing(id, at: point)` says where the press that began it was (world units), which the editing view reads as `EditContext.startPoint` to put its selection there, and the editor keeps as `editingStartPoint` while editing lasts; Selection's double-click and Return, and a placement, pass none, and the view chooses as it always has. `EditContext.service(_:)` lends an editing view the editor's services, as the panel's, the table of contents' and adornments' contexts do.
- Keyboard shortcuts (Keyboard, a horizontal, first in the shipped list): every key the canvas answers is registered with it, one shortcut per chord (`KeyChord`: `"v"`, `KeyChord("a", .command)`, `.escape`), by the plugin that gives it its meaning: `x.tool(label:systemImage:shortcut:placing:)` and `registrar.tool(descriptor, shortcut:)` for a tool's key, `registrar.command(.delete, shortcuts: [...], isEnabled:)` for a command a menu item also runs (its keys pass while it can't run, as its item dims: ⌘[ and Go › Back), `registrar.shortcut(chord, "Title", when:, repeats:) { editor in … }` for anything else, and `registrar.shortcut(chord, forTool:)` for another plugin's tool (Keyboard gives the core's Hand H, and Escape and ⌘. `editor.cancel()`). The core knows no key: `CanvasView.keyDown` hands every key to the editor as a `KeyStroke` (host API `editor.keyDown`), which passes it to the plugin that claims key strokes, and so does `CanvasView.performKeyEquivalent` for a ⌘ key while the canvas has the keyboard, before the menu bar (so ⌘A is Keyboard's there; with a field focused, the menu's). A key no shortcut takes goes on to AppKit's key bindings, and the standard actions they send that have a key of their own (`deleteBackward:`, `deleteForward:`, `insertNewline:`, `cancelOperation:`) come back to the shortcuts as ⌫, ⌦, ↩ and ⎋, so ⌃H does what Delete does. ⇧ counts when a chord asks for it; a key held with ⇧ answers the chord without it too when ⇧ may be only what typed it (⇧ alone, or punctuation, a symbol or a digit: ⌘? is ⇧⌘/), never for a letter with ⌘, ⌥ or ⌃ (⇧⌘Z isn't ⌘Z). The table of contents' list runs the `.delete` command on Delete, as the canvas does. Every plugin with a key imports Keyboard, so any plugin list with Selection or a shipped tool needs `KeyboardPlugin()`. The toolbar's tooltips ("Note (N)") come from `ShippedPlugins.help(for:in:)`, since CanvasUI can't see Keyboard.
- Selection (a horizontal, after Keyboard in the shipped list) is built on those hooks alone: the selection state (a service, read as `editor.selectedShapeIDs` and `editor.selection`, the only selected shape, as tldraw's onlySelectedShape), the Select tool (the default) and marquee, handles, Delete/Return/⌘A/Back (their keys registered with Keyboard), and the double-click claim. `editor.goBack()` is data-canvas's selection history: each change of the selection stacks the one it leaves, with the camera as it was then (`editor.cameraTarget`, where it was headed if it was gliding; 50 steps; a select-tool press and its drag are one step; `canGoBack` only when going back would change the selection); the detail panel's header has the back button, and Go › Back (⌘[) works whatever has the keyboard. Every kind is selectable unless it opts out (`x.unselectable()`, or `x.selectable { ... }` per shape); the select tool sees through such shapes, nothing else does. A read-only shape (a locked one) is selected, hovered and outlined as any other, but shows no handles, so a press there presses the shape. A plugin can put buttons on the canvas (the `CanvasButtons` point: where they are, in view points, and what they do), clicked (`registrar.canvasButtons(at:click:)`, Adornments' clickable adornments: the lock chip) or dragged (`registrar.canvasButtons(at:drag:)`, Ports' dots): in the select tool only, they win over handles and shapes (the later plugin's first, as its overlay draws on top); a press and a release on a clicked one click it (dragged off, nothing), with the pointing hand over one (`CanvasCursor.pointingHand`); a dragged one's press, past the drag threshold, hands the drag to the session `drag` returns (given the button and where it was pressed, world units; nil ends the press), and released without a drag does nothing, with the open hand over one and the closed hand while it's pressed; Escape lets go of either. `editor.hoveredButton` and `editor.pressedButton` say what to draw hovered and pressed (both cleared as a drag hands over), a plugin whose buttons change without a commit calls `editor.canvasButtonsDidChange()`, and `editor.pointerOverCanvas` is where the pointer is over the canvas in the select tool (view points, as it last moved with nothing under way; nil once it's left the canvas or gone over the minimap or the editing view, another tool is current, or Escape let go of a dragged button's press, until it moves again), for buttons that show only while it's near (a port's dots). Something drawn for a shape outside it (`registrar.decorationHits`, the `DecorationHits` point: every adornment) is that shape for the select tool (a press, a drag, the release, a double-click), hover and the context menu: `editor.selectableShape(at:)` asks it first, the last plugin's first, with `isSelectable` as its `include`, so an unselectable shape's is seen through; buttons still come before it, and the core's `shape(at:)`, the marquee, the eraser and the arrow tool never see it. Unlike tldraw (and the POC), the selection stays outlined while it moves. `editor.hovered` is the shape the pointer is over, set by the select tool on the canvas or by any plugin where it shows shapes (the table of contents' rows), in any tool; changing tools clears it. `editor.isHovered(id)` is observed per shape (a key path per shape), so a view of one shape hears only that shape's hover change. Its outline is faint: wider and lighter than the selection's (2.5 points, the accent at 60%), unlike tldraw's, which strokes a hover like the selection. Code that reads the selection imports Selection; without its plugin, the selection is empty.
- Going to shapes is Selection's, one way for every plugin: `editor.reveal(ids)` only moves the camera (centers the shapes' bounds, fitted with 100 points of margin, no closer than 120%, over 200 ms: `SelectionStyle.reveal*`, data-canvas's zoomToBounds), and is what selecting table-of-contents rows does. `editor.goTo(ids)` is following a link (a mention): it ends editing, selects the selectable ones (a Back step only when that changes the selection; to what's selected already, or to unselectable shapes, it only moves the camera), and reveals unless they're all in view, where the camera is headed (`cameraTarget`), at a readable zoom: `SelectionStyle.readableZoom` (70%: a note's 16-point text reads at 11.2 points there, just over `NSFont.smallSystemFontSize`), or as close as fitting them would bring them (a shape too big for 70% that's all in view stays put). Nothing mid-gesture, or when none of the shapes is on the board.
- Faces (Selection's `ShapeFaces` point, `registrar.shapeFaces(at:click:doubleClick:hovering:)`) are parts of a shape's content that answer a click without taking the shape's press: a mention's pill in a note, a link, a checkbox on a card. `at` is asked only for a plain press (no ⇧, ⌘ or ⌥, not a Control-click) on the shape the select tool would press, selected or not, at a world point on that shape itself (a point on what `DecorationHits` draws for a shape is no face's), after canvas buttons and handles, and looks at that one shape; the last plugin's first. The press is the shape's: it selects the shape as any press does and, past the drag threshold, moves the selection from the press; on a lone box it waits for the threshold too (an intended deviation from the lone box's press, pinned in SelectionTests). Released within the threshold, the shape is selected alone and `click` runs; Escape lets go first. A double-click whose press lands on one selects the shape alone and runs `doubleClick` in place of editing it, a read-only shape's too; without `doubleClick`, a double-click there edits an `Editable` shape and is otherwise one more click. The pointer over one hovers the shape `hovering` names (`editor.hovered`, so hover keeps one path), or its own shape when it names none, or one that isn't there or can't be selected; hover asks whatever keys are held, and the cursor stays the arrow. `click` runs once the press is over, so it may `goTo` or go back, and what it selects is a Back step of its own; it isn't given the press, so a face that needs a point carries it in its value (a pill edits its note from there, `editor.beginEditing(id, at:)`), and a click that begins editing leaves the pointer over the editing view, which ends the hover. CompositionTests' canvas view tests hold these pieces together with `pillsPlugin`, a pill-like face in a note: edited from the pill on a click, not hovered under its text, and gone to (`goTo`) from a locked note's double-click. A face that edits its shape checks `editor.isReadOnly` first (as `pillsPlugin` does): a refused edit is a try, which Locking shakes, and a click on a locked shape isn't one. A click on a face that goes somewhere (it changes the selection or moves the camera: a link's `goTo`) makes the rest of its double-click its own: the select tool ignores each press after it with a click count of 2 or more, until one of 1 (`ignoresPress`), so the camera goes on to where the click sent it and nothing is placed, edited or pressed where it has got to; a click that goes nowhere (a pill's) leaves the double-click to `doubleClick`.
- Boards are files, one per board (`docs/plugin-system.md`, "Boards on disk"): `BoardDocument` (CanvasUI, an `NSDocument`, autosaved in place) saves `editor.document` with `BoardCodec` (Canvas). The app is AppKit-run: `InfiniteCanvasApp` sets `BoardDocument.configuration` (the shipped registry, the window's SwiftUI content) and installs `BoardMenus`; the Info.plist that `build.sh` writes exports the `.canvasboard` type (not `.board`: Freeform owns it). Order in the stack is each record's `stackingKey`. A kind's props are versioned by its append-only `static let migrations`: changing how they encode needs a migration and a new fixture in `Tests/CompositionTests/Fixtures/kinds` (never edit a fixture), even a new member with a default (`PropsMigration("name")`, which rewrites nothing). An added property's value is versioned by its own (`PropertyMigration`, over the value's JSON), whatever kinds opt in, with fixtures in `Fixtures/added` (`expectPropertyFixtures`); `PropsMigration.handOver("checklist", to: ChecklistProperty.self)` hands a kind's own member over to one. Shapes the app can't use are kept aside (`AnyShapeRecord.isOpaque`) and saved back as they were; a horizontal that goes through every shape skips them. A record's metadata is saved beside its props (`meta`), members no plugin knows included, and its added values in `added`, by key; those the app can't use (not declared, not opted into, newer, unreadable) in `kept`, with their versions, saved back as they were and listed in `LoadReport.keptValues` (the alert never offers to delete them). A board is written in the oldest format that holds it: 3 with added values (the envelope's `versions` has `kinds` and, when any, `added`), else 2 with metadata, else 1 (both with `schema`), so an older app refuses what it would save without. The camera and whether the details and the minimap show are remembered per file (`BoardViewMemory`), never in the board.
- Change documents only with `editor.transact`. Tools see `Pointer` values, never `NSEvent`; timers go through `editor.scheduler`. Model positions are world units; overlay sizes (handles, outlines, hit margins) are view points, divided by `zoom` in world space.
- A frame costs what's in view and what changed, never the whole board (`./build.sh bench` holds 10,000 shapes to 16 ms). The editor keeps each shape's geometry and extent, and the paint order (`ShapeIndex`), and redoes them for what each commit's `ChangeSet` names; it keeps the board's bounds too, and where each commit moved or reshaped shapes (damage: where the shapes it touched, and those whose geometry followed them, were and are), for pictures of the board kept from frame to frame (host API: `shapeBounds`, `damageMark`, `damage(since:)`). So a definition looks at other shapes only through its `ShapeContext` (`shape(_:)`, `geometry(of:)`, `hitTest(_:shape:)`: they're tracked, all of `document` or `camera` isn't); a `hitTest` that reaches past the outline declares `hitMargin`; a paint anchor follows from its shape's props and the document's order; per-frame code (overlays) goes through `editor.paintOrder(in:)` with `context.visibleRect`; and a service keeps per-shape state and redoes the shapes a change set names, as `ValidationEngine`, `ContentsState` and `AdornmentState` do.
- The minimap (CanvasUI's `MinimapView`, which `CanvasView.showsMinimap` hosts in the canvas's bottom-left corner; View › Show Minimap, ⌃⌘M, remembered per board in `BoardViewState` and `BoardViewMemory`) works as tldraw's: the board and the viewport fitted together; a click beside the viewport eases the camera there over 320 ms, a drag moves it within tldraw's clamp, a double-click centers exactly. It draws every shape as a rough silhouette of its geometry in one color, never its render (no text, no colors), into a bitmap of tiles kept from frame to frame (`MinimapPicture`): damage makes tiles stale, and each frame draws again those stale longest, within its budget (4 ms, and a tile at least), so a frame spends at most that on the picture however big the board, and whatever goes stale every frame, every tile has its turn. The selection shows in the accent color, through `editor.outlines` (host API). Keep it that cheap.
- The views `CanvasView` hosts, the minimap and the editing view, have the pointer where they are: over one the pointer isn't over the canvas, though AppKit tells the canvas it moved (its tracking area covers them), so the tool hears it leave (`pointerExited`), once, as it moves or is released there (the press that began editing), and nothing more until it's back on the canvas. So the select tool hovers no shape under a note's text (`editor.hovered` is only what another plugin sets there), `editor.pointerOverCanvas` is nil there, and the canvas leaves the view's cursor alone. Once editing ends, where the editing view was is the canvas again.
- Arrows see other shapes only as `ConnectableShape` (a closed shape's core geometry). Keep specific shape kinds out of arrow code.
- UI constants live in each module's `@MainActor` style enum (`Style`, `ArrowStyle`, `NoteStyle`, ...). Pure geometry (Geometry, `ArrowGeometry`) is nonisolated, so its constants live on those types.

## Arrows follow tldraw

- Arrow behavior and geometry deliberately mirror tldraw's arc arrows: binding precision and timers, clipping, arrowhead gaps, handles and hint overlays. The constants come from tldraw's source.
- Check tldraw (`packages/tldraw/src/lib/shapes/arrow/`, `bindings/arrow/`, `overlays/`) before changing arrow behavior, and call out any intentional deviation.
- Moving arrows is `ArrowDefinition: CustomTranslation`. Alone (or with unrelated shapes) it is the POC's translation exactly; moved with a shape it's bound to, it keeps every binding, as tldraw. Its ends probe at the full delta (tldraw: half), a known deviation the transcript pins.
- What an end may bind to is tldraw's canBind, from any plugin: `ArrowBindingRules` (`registrar.arrowBindingRule { query in … }`, over `ArrowBindingQuery`: the arrow as it is, the end, a shape under it, the registry). An end binds only to a shape every rule allows, looking through the rest to the shapes behind, wherever an end binds: `ArrowTargeting.bindTerminal` (the tool's drags, re-aims, the precise timer, a modifier's change) and a lone arrow's translation probe (`beginTranslation`); rules are asked only of the shapes the point hits, and with none nothing is filtered. Arrows knows no channel: ArrowPorts' rule does, and lets an arrow without one bind to anything, so the arrow tool's arrows behave exactly as before (the transcript holds them). `editor.canBindArrow(to:)` is whether an arrow can bind to a shape (there, closed, not an arrow), and `editor.beginArrow(from:at:canBind:complete:)` draws one for another plugin's gesture (a port's drag): it inserts an arrow, its start bound to the shape at its center (imprecise) and its end free at `origin`, and returns an `ArrowHandleDragSession` dragging the end (`connecting`), which binds by tldraw's rules (fast to the center, slow or after a 320 ms dwell precise, ⌥ exact, ⌘ or ⌃ nothing, ⇧ snaps the angle) only to shapes `canBind` and the rules allow, seeing through the rest; released bound, `complete(&record, target)` finishes it in one transaction. `BindingHintsOverlay` draws for the arrow being dragged (the session's `arrowID`), else the selection, so the tool's arrows, re-aims and a port's arrow hint alike. A port's drag deviates from tldraw on purpose, as data-canvas's does: released free (or on Escape) the arrow is deleted, where tldraw keeps a free end; its start is the port's shape's center, with none of the arrow tool's hover and press timers; and the selection and the tool are left alone (no selecting the new arrow, no step of the selection's history).
- CompositionTests holds the app to the proof of concept (commit 804db97): an arrow transcript compared byte for byte, and renders (outlines, binding hints, handles) compared pixel for pixel. `Tests/CompositionTests/Replay.swift` drives both the POC recording and the test. The fixtures come only from the POC, via `scripts/record-poc-fixtures.sh` (re-running it must change nothing). Never regenerate them from the app to make a change pass; an intended change to arrow behavior needs an explicit note. A scenario that ends differently on purpose gets an entry in `intendedDeviations` (TranscriptTests): the golden line, the app's, and why. The one so far: a press doesn't bring a shape to the front (the POC's did; tldraw's doesn't). Scenarios are only ever appended, recorded from the POC. The "pan" scenario presses H and holds still 100 ms before `.up` (both no-ops in the POC), and the welcome renders use the POC's note text, `pocWelcomeTexts`.

## Verifying UI changes

- Screen capture isn't permitted here.
- Drive a headless editor with `EditorHarness` (CanvasTesting), with `KeyboardPlugin()` and `SelectionPlugin()` first in its plugins when the test presses, drags or selects as a user does (without Selection the default tool is Hand, and without Keyboard no key does anything). `h.key("v")` presses a key on the canvas (with what `h.hold` holds); CanvasTesting's fixture tools have no keys, so pick them with `h.editor.setTool`. One clock drives event timestamps and the `ManualScheduler`, so pointer speed, the arrow timers and the hand tool's slide (inertia) behave. Check drawing with `renderBitmap`, `pixel` and `changedPixels`.
- For focus, key routing and the editing view, put a `CanvasView` in an unshown `NSWindow` and send it synthesized `NSEvent`s (see CompositionTests).
- For an editing view's text against its shape's render, `renderBitmap(editor, size:scale:editing:)` (CanvasTesting) draws the view from `editor.makeEditingView()` over the canvas as `CanvasView` lays it out (frame in view points, bounds in world units); `lineTops(_:over:in:scale:)` is where each line starts, against the same drawing without the text, and `largestDifference(_:_:in:scale:)` holds every pixel to anti-aliasing (StickyNotesTests' `noteEditorTests`, at 1× and 2×, zoomed in and out). The note's render (string drawing) and its editor (TextKit 2) share `NoteStyle.textAttributes`, whose paragraph fixes each line at 19 points, string drawing's own pitch, and the editor's text starts a point higher (`NoteStyle.editorInset`), since TextKit 2 sets a line's glyphs a point lower in it; so nothing moves when editing starts.
- For the minimap, CanvasUITests put a `CanvasView` with `showsMinimap` in an unshown window, send `canvas.minimap` mouse events, and hold its picture, kept through edits, to a fresh `MinimapView`'s, pixel for pixel.
- For the pointer over the views the canvas hosts, CanvasUITests' Pointer suite sends a `CanvasView` editing a card (CanvasTesting) moves and releases, and reads what a probe tool heard (`PointerLog`); CanvasUITests can't import Selection, so CompositionTests' canvas view tests check `editor.hovered` over a note being edited.
- For adornments, `AdornmentLayout.frames(of:width:)` is pure (AdornmentsTests' layout tests and their seeded property check), and `editor.adornmentFrames(of:)` gives a shape's headlessly, in world units, where it is (not where a shake draws it). Pixels go through `renderBitmap` and `changedPixels`; a clickable one's identity, as `editor.hoveredButton` holds it, is `AdornmentButton(A.self, on: id)`. AdornmentsTests use fixtures only, with adornments of their own (declare a test's adornment types internal, not private, so a conflict key names one as `Module.Name`). Any plugin list with Titles, Checklists or Locking needs `KeyboardPlugin()`, `SelectionPlugin()` and `AdornmentsPlugin()`; put `AdornmentsPlugin()` where the shipped list has it, after Validation (so adornments draw over its outline) and before the plugins that place them.
- For context menus, `h.secondaryClick(at:)` returns the `NSMenu` (or nil); read it with `menu.outline` and run an item with `menu.choose("Status", "Done")`. Nothing goes on screen.
- For the command line, never use the app's socket: tests listen on their own (`temporarySocketPath()`, TestKit). The app answers on the main actor, so a test that's the client too asks off the main thread (`offMain`) or runs `canvas` as built (`run(builtExecutable("CanvasCLI"), arguments)`), both of which turn the main run loop until the answer comes. CanvasCLITests hold `canvas` to an app of their own (`FakeApp`); CompositionTests' CommandLineTests run it against `CommandServer` on real boards.
- For the clipboard, never touch the user's pasteboard: give the plugin a private one (`ClipboardPlugin(pasteboard: NSPasteboard.withUniqueName())`, `ShippedPlugins.makeEditor(pasteboard:model:)`, `configureBoards(pasteboard:)` in CompositionTests) and `releaseGlobally()` it after.
- For ports, PortsTests use fixtures only, and no arrow: `portsHarness` installs Keyboard, Selection, the fixtures, Ports, `channelsPlugin` (boxes have ports on its `Wire` channel, `sides:` and `role:` as a test asks, discs on `Pipe`) and a recording connector over CanvasTesting's `Tag` (`connectorPlugin(Connections())`: `begun` lists each `Connection`, its session records each drag in `drags`, and `canConnect` and `draws` refuse). A 200 × 100 box at (100, 100) (`boxFrame`) has its dots at `topDot`, `rightDot`, `bottomDot` and `leftDot` at zoom 1. Move onto a dot before pressing, as a user does (`h.hoverDot` comes from the shape's middle): dots draw only while `editor.pointerOverCanvas` is set. ArrowPortsTests draw real arrows between fixtures on a `PortBoard` (boxes A and B where the POC's first two welcome notes are, taking `Wire`, and a disc C below B taking `Pipe`; `board.connect(to:speed:release:)` hovers A and drags from its right dot, `aRightDot`, at `fast` or `slow`), and read `board.arrows`, their bindings and their `ChannelProperty`.
- For the detail panel, check layouts and writes headlessly (`editor.detailPanel?.layout(for:)`, a tab's status lines with `layout.statuses(in:)`, the footer's with `statuses(for:)`, `editor.shapeBinding`, `editor.propertyBinding(id, P.self)`). For its views, host `DetailPanelView` in an `NSHostingView` in an unshown `NSWindow`, beside the canvas when focus matters (DetailPanelTests; `Tests/CompositionTests/InspectorTests.swift` uses the app's own wiring), with the real `TaskScheduler`. CanvasTesting drives the window: `window.spin { condition }` runs the main run loop until the state a test expects arrives (and fails the test after 2 s), `window.settle()` runs it a few turns where there's nothing to wait for, and `focus`, `type`, `press` and `mouse` send input. Call `canvas.mouseDown` directly (`sendEvent` mouse-downs don't reach views in an unshown window). Once there's a step back, the header has a back button, an `NSButton` in the panel's top 44 points, and a kind renamed in its header has a text field there, so tests that count the panel's buttons, checkboxes or fields leave the header out (`isInPanelHeader`). Render the panel standalone: in the app's `.inspector` it doesn't draw offscreen.
- For the table of contents, read `editor.tableOfContents?.entries` headlessly (each row's text, symbol and badge through `entry.label`, its marks through `entry.marks`), and drive `select(_:)`, `showAll()`, `hover(_:)` and `endHover(_:)`. `rowsRedrawn` (debug builds) counts how often the list has asked a row for its view, so a test holds a change to redrawing the rows it changes (HoverTests). SwiftUI's hover doesn't answer synthesized events, so check a row's tint by rendering the list with `snapshot(view)` (CanvasTesting; highlights draw, a source list's vibrant text may not). In a window, its list is an `NSOutlineView` whose first row is the header, a group row (TableOfContentsTests). AppKit's warnings go only to standard error: `standardError(during:)` (CanvasTesting) returns what was logged, so a test can check a list's update logged no `tableReentrancyWarning`. A shape's panel can hold lists too (a checklist), so CompositionTests tell them apart with `isTableOfContents` (`Tests/CompositionTests/ContentsPanelTests.swift`), and InspectorTests' `tables` leave it out.
