# Boards in a file

A file as a tree of boards (`CanvasFile`): ids unique across it, board revisions, the delete cascade, shapes moved onto any board of it and put down there, `transact(on:)`; and showing a board, step by step, with what services hear.

Related: [boards](boards.md), [subboards](subboards.md), [boards on disk](boards-on-disk.md), [undo](undo.md), [containers](containers.md), [editor](editor.md), [drawing](drawing.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Boards in a file](../../docs/plugin-system.md#boards-in-a-file), [Showing a board](../../docs/plugin-system.md#showing-a-board).

## Boards in a file

- Boards in a file (`docs/plugin-system.md`, "Boards in a file"): a file is a tree of boards, `CanvasFile`: the root board, and `children`, a board for each shape of a `BoardOwning` kind, keyed by the owner's `ShapeID` (a board is named by a `BoardID`, `.root` or `BoardID(owner:)`, written "root" or the id), never in the owner's props (its schema is marked `x-canvas-board`). So the tree is a function of where shapes are: a board has one owner, a copy (a new id) has a board of its own, and nothing done in the app makes a loop or an orphan (only a file edited by hand, which reading keeps and reports). Shape ids are unique across the file (`file.board(containing:)`, `file.record(_:)`); a board with no shapes isn't kept, so placing an owner makes only the shape; each board has a revision (`file.revision(of:)`) that changes with its shapes and never comes back, which is what anything kept about a board (an index, rows, issues, locks, a preview) is checked against. One editor holds a whole file (`editor.file`) and shows one board of it (`editor.board`) as `document`: what's local to a board comes from reading `editor.document`; never list shapes from `editor.file`. `editor.contents(of:)` and `editor.owner(of:)` read any board. A transaction is on the board shown and reads the file through the editor, never holding a copy; deleting a shape takes its board and every board under it in the same commit (the cascade, `ChangeSet.boardsRemoved`, in `Transaction.delete`, one undo step that undo puts back whole, every id), unless a read-only shape is on any of them, which keeps the owner from being deleted; `transaction.insert(_:contents:)` brings a shape in with its boards (a paste, `boardsAdded`); `transaction.move(_:to:)` takes shapes of this board onto any other board of the file, up, down or across the tree (`move(_:toBoardOwnedBy:)` onto the board a shape on it owns: false for an owner not on it, or of a kind that owns none, so a plugin that turns it first moves only if `turn` took), under their ids, in their order, on top of what that board holds as the transaction leaves it (`transaction.contents(of:)`, any board: its own `document`, one it staged, none for one it took, else the file's), each with its props, added values and metadata, what a container among them holds at any depth (a shape stays in a container that moves with it, and is in none there otherwise) and the boards they own (a board goes with its owner wherever that is): the board is new to the file (`boardsAdded`) or, if the file held shapes there, changed (`boardsChanged`, the root always, written in place: `writeBoards` sets it, as `insertBoards` wants a new one), the shapes are `removed` from this board and `elsewhere`, and a shape added earlier in the same transaction lands there and was never `removed`. The transaction stages other boards by `BoardID` (`stagedBoards`) and goes by where each owner is as it leaves the file (an owner it moved is on the board it moved it onto): a board the editor couldn't show then (`canShow`'s rule, the file's above the transaction's board, `FileAccess.canShow`) takes nothing, and `move` says false, refusing nothing; its own board, a board going with a shape it deleted, and the board of a shape that moves or one under it (a loop) are preconditions, and so is deleting, in the same transaction, a shape that owns a board it moved shapes onto or settled on, or is above one (that board would go, and the boards the moved shapes own with it; no flow does). Bindings (`ShapeReferencing`) are to shapes on the same board, so those across the edge are let go of both ways before anything leaves, as a deletion's are (an arrow's end stays where it's drawn), read-only shapes' too, while names (mentions) are kept. It's all or nothing for read-only shapes: if the board's owner, or any shape that would move, is read-only or in a read-only container, or the board it would go onto or leave is read-only (a locked subboard's, or one under it: [editor](editor.md)), nothing moves, it returns false, and each is noted in `transaction.refusedShapes` for services to hear (the owner is held as `setContainer` holds a container, on its own board as the transaction leaves it, or as its board is read-only, climbing owners as the transaction leaves them, `isReadOnly(board:)`; one the transaction brought there isn't held, and the root has no owner). Nothing else is asked of a moved shape (no `willDelete` handlers run). `transaction.translate(_:by:on:)` moves shapes on another board as `translate` does on this one (what a container holds goes along), in a transaction over that board as this one leaves it, as `settle(_:on:)` settles (what this one brought there isn't held; a read-only shape that was there stays, refused; on the transaction's own board it's `translate`, and a board the editor couldn't show moves nothing), so what `move(_:to:)` took there, letting go of its bindings across the edge where it was drawn, can go somewhere else there (Moving's commands: [moving](moving.md)). `transaction.move(_:from:to:)` moves shapes off any board onto any other, as `move(_:to:)` moves this board's (on this board it's `move(_:to:)`): in a transaction over the source as this one leaves it that reads every other board, and where each shape is, as this one leaves the file (`transaction(on:readingThrough:)`), whose source board, and the boards it stages, this one takes in; onto this board, on top of `document` (`added`, or `changed` for a shape this transaction had taken off it); false, nothing moving, for a source or a destination the editor couldn't show; the source `boardsChanged`, what left it `elsewhere`, a board it empties gone from the file. `move(_:above:on:)` and `move(_:below:on:)` restack on another board, in a transaction over it (`transaction(on:)`, `take`), as `translate(_:by:on:)` moves there (the table of contents' restack of rows of a board open under its owner's). A commit writes every board it changed, its own among them, together (`writeBoards(of:own:)`, `CanvasFile.set` of several: each lets go of what leaves it before any takes in what comes), so a shape moved either way between two boards, the board shown among them, is on one at a time. `transaction.settle(_:on:)` puts down what moved by the in-or-out rule on the board it moved onto ([containers](containers.md)): `settle(_:)` in a transaction over that board as this one leaves it (same registry, camera, keys and file; what this one brought there taken as added, so it isn't held), whose board is staged if it changed (`boardsChanged`) and whose refusals are this one's (a refusal changes nothing there: the caller throws to drop the move); on the transaction's own board it's `settle(_:)`, and a board the editor couldn't show settles nothing. One step holds the boards it reached whole, so undo and redo put every shape back (`DocumentDelta.boards`, from `ChangeSet.boardsReached`), the step made on the board shown. A commit says what it did beyond its board in `ChangeSet.elsewhere` (every shape of the boards it took or brought, each that differs on a board it changed, moved onto or settled on, and, for a file put in place over the board shown, those its other boards changed), for what reads shapes anywhere in the file. Only `editor.transact(on: board, "Name") { … }` edits a board that isn't shown (what lands late: a sync's answer): its commit changes that board in the file, is an undo step of its own made on that board (undoing it shows the board first; a step open on the board shown stays open, after it), and services hear it as `boardsChanged` (the board's, and any it moved shapes onto that held some) with its shapes `elsewhere`; it can't take the board shown or one above it, nor reach the board shown (moving shapes onto it, or settling there: its `document` would go stale), commits nothing then, shakes nothing, and returns nil for a board `canShow` refuses; on a read-only board (`isReadOnly(board:)`) it changes nothing that was there and puts nothing there, shaking nothing; one that locks the owner of the board shown, or a board above, makes the board shown read-only as it commits (`isBoardReadOnly`). Core and horizontal tests nest boards with CanvasTesting's `PocketsPlugin` (a `pocket` kind that's `BoardOwning`, apart from `FixturesPlugin` so the reports tests pin don't change), never with Subboards; CanvasTests' `TurningTests` hold `move(_:toBoardOwnedBy:)` (and `turn`) with pockets and corrals, the pattern of a frame turned into a subboard, and `MovingAcrossBoardsTests` hold `move(_:to:)`, `translate(_:by:on:)` and `settle(_:on:)` up, down and across the tree, and `MovingOffBoardsTests` `move(_:from:to:)` (onto the root shown, across, up, off the board shown and back, then moved and settled there) and restacking on another board. Moving's `/move-to` and `/move-near` move a shape onto another board with them ([moving](moving.md)).

## Showing a board

- Showing a board: `editor.showBoard(board)` (true once it's shown; false while a session runs, or for a board `canShow` refuses: one whose owners, root down, aren't all in the file, of a `BoardOwning` kind, none kept aside: the file's rule, `file.canShow(_:boardOwningKinds:)`, nonisolated, which the editor's calls) makes it `document`, and `editor.board` and `editor.boardPath` (root first) say where the editor is. It's not an edit. In order: services hear `boardWillChange(from:to:)` while the old board is shown (save what's its: a draft, state in a `BoardStash`), editing ends, the default tool comes back, camera motion stops, the old board keeps its camera (`cameraTarget`) and index, the new board takes back its `ShapeIndex` if its revision (`file.revision(of:)`) hasn't changed since (the last 8 boards; those on the path are kept longest), `revision` bumps once, the camera is the one the board was left with, else the host's `rememberedCameras`, else a first visit's fit (inset 64, no closer than 100%, into what the host leaves clear of the view on that board, `coveredTop`), else `Camera()`; then services hear `boardDidChange(BoardChange)` (`from`, `to`, `leftCamera`, and `changes`, worked out only if read: by default a service hears it as `documentDidChange` of every shape of one board gone and every shape of the other come, right for per-shape state; one that keeps state per board overrides it, and reads no other service there; one that keeps nothing per shape overrides it with nothing, as ContextMenus, Keyboard, Clipboard, DetailPanel, LanguageModels and Arrows do; the table of contents, Validation and Locking keep each board's rows, issues and locked shapes in a `BoardStash`, Selection makes the board left a step back, Boards makes the path again, Ports lets go of the dots it showed, Adornments drops its labels (made again only for what a frame draws), the schema cards' sync keeps every card of the file by id, and Topology's index and Mentions' resolutions and catalog are the file's, so no shipped service works out the change set; CompositionTests' BoardsTests hold the shipped list to that), and the host `editorBoardDidChange`. Arrows stop aiming in `boardWillChange`. `replaceFile(with:showing:)` stays on the board shown if the new file can show it, else goes to the nearest board above it, or the root, as a switch does (and `CanvasEditor(registry:file:showing:)` opens on one). A `BoardStash<State>` is a service's state per board, taken back only while the board's revision is unchanged; `BoardChange.isFileReplaced` says a `replaceFile` came with the switch, so what a service keeps across the file by shape id is taken afresh. Damage marks are per index (`DamageMark`, host API; `editor.isCurrent(mark)`), so a picture kept for a board (the minimap's) is current only while the editor kept that board's index. A render may read `context.shapeCount(inBoardOwnedBy:)` and `context.shape(inFile:)` (a shape on any board the editor can show: a mention's pill; `editor.shape(inFile:)` elsewhere), and draw `context.drawBoardPreview(ofBoardOwnedBy:in:)` (only on `RenderContext`: geometry and hit tests never read another board). The command names `.openSelection` and `.enclosingBoard` are the core's, for plugins to claim (Selection claims `.openSelection`, Boards `.enclosingBoard`). A switch isn't an undo step: it closes the one under way, and undoing or redoing a step made on another board shows that board first. Host SPI: `boardCameras` (every board's camera, for the view memory) and `rememberedCameras`.
