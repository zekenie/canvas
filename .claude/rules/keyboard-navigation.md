# Keyboard navigation

The principles every surface of the app meets: anything a click does, the keys do; Tab walks every stop in reading order and leaves a thing only after its parts; the way back is exact; and VoiceOver can name wherever the keyboard is. Then how the app meets them.

Related: [keyboard](keyboard.md) (shortcuts, chords, the menu bar), [selection](selection.md) (stepping between shapes), [editing](editing.md), [types](types.md) (a note's rows), [detail panel](detail-panel.md), [table of contents](table-of-contents.md), [testing](testing.md) ([every topic](../../CLAUDE.md#map)).

The owner's words (2026-10-21): "you should be able to navigate to any interactive element with the keyboard. this should just work by default everywhere as much as possible, but when needed there should be custom code. there should be tests. this is as much about a11y as it is about pro users."

## The principles

Each is a rule and the check a test makes of it. A change that adds something a click acts on, a key, a control or a surface meets all twelve, and says so in its tests.

1. **Reach.** Everything a click does something on can be reached and done with keys alone: shapes (arrows too), a note's rows, chips, pills, canvas buttons, cards, the panel, the table of contents, lists and menus. *Check:* for each face, clickable adornment, canvas button and control, a test reaches it and acts on it with key events only.
2. **Shared first.** Reach comes from shared machinery (AppKit's key view loop, SwiftUI focus, Keyboard's registry, Selection's stepping), so a new element is reachable with no key code of its own. Custom keys are written only where nothing shared can see the element, which is what the canvas draws, and then once, as one mechanism plugins hand stops to. Standard controls follow macOS's Keyboard navigation setting; what the canvas draws is always reachable. Walk tests run with that setting on and off: with it off a standard control may drop out of the Tab order, but an action that lives only on such a control also has a menu item or a key. *Check:* a test adds a clickable part to a shape, or a row to a list, with no key handling, and it is reachable.
3. **Reading order, parts first.** Tab and ⇧Tab follow reading order (top to bottom, then left to right: Selection's order) and wrap. Inside a thing being edited, Tab visits its parts before the next thing. On the canvas Tab steps between things, and a selected thing's drawn parts (chips, pills, buttons, handles, its arrows) are one level in, reached with ⌥Tab. *Check:* in every surface, Tab from the first stop visits every stop once, in reading order, and comes back to the first.
4. **Exact way back.** ⇧Tab undoes Tab, ↑ undoes ↓, ← undoes →, from any stop. A step that starts somewhere that is no stop (several shapes selected, an arrow) is undone by the opposite key, back to exactly that. *Check:* for every stop, Tab then ⇧Tab lands on it again.
5. **One level at a time.** Return or ⌘↓ goes into a thing's content (edits it, opens it, enters its children), ⌥Tab into its drawn parts; Escape comes out one level and leaves that thing selected or focused. Never two levels at once, never losing what was typed. *Check:* from depth n, n Escapes reach the canvas, each landing on the container of the last.
6. **Same key, same meaning.** Tab and ⇧Tab move between stops; ↑ ↓ move in a list or column; ← → in a line; Return does or opens the focused thing; Space toggles or presses it; Escape backs out; ⌘↩ finishes; typing on a list filters it. The named exceptions below are the only others, each held as data in the test with its reason. *Check:* a table of surfaces by keys, held by tests, has no cell that means something else.
7. **Focus shows.** One place has the keyboard at a time, and it shows: a caret, an accent outline or the selection. It comes into view when it moves, and an empty field gets room rather than hiding its caret. *Check:* after each key in a walk, the focused thing is drawn with its mark and lies in the visible part of the canvas or panel.
8. **No traps, no leaks.** A focused thing keeps the keys it uses and always lets Tab, ⇧Tab and Escape move on. A key it has no use for never reaches a shortcut that changes the board (Backspace deleting the note being edited, a letter switching tools). *Check:* in each focus state, every unhandled key changes no document, and Tab and Escape always move the focus.
9. **Named for VoiceOver.** Whatever can take the keyboard has an accessibility role, label and value, including what the canvas draws, and moving the keyboard announces where it went. *Check:* in each focus state, the focused accessibility element has a role and a label.
10. **Nothing pointer-only.** Every action in a context menu, a chip's menu or a canvas button has a menu bar item or a key, and every drag has a keyboard way (move, connect, reorder, resize). *Check:* each pointer-only action has an item or a key listed in the Keyboard Shortcuts window.
11. **Tested by keys.** Every surface with stops has a test that walks them forward and back with real key events, through one shared harness that makes it a few lines. *Check:* each surface has a walk test in its module's tests.
12. **Pro speed.** The common path takes no more key presses than clicks, held keys repeat, and the last thing done can be done again from where you are. *Check:* the first-minute tasks (a note, its words, a type, its fields, two notes connected, a frame around them) each take no more key presses than clicks, typing aside.

## What each key means

| Key | Meaning everywhere | Named exceptions, with their reason |
| --- | --- | --- |
| Tab, ⇧Tab | the next, the previous stop, in reading order, wrapping | On the canvas, the next and previous shape (landed: shapes are the canvas's stops). In a list that completes typed text (@, /, completions, Jump To) Tab picks the highlighted row, and with none closes the list and moves on; ⇧Tab closes and moves on. In a note picker Tab never picks (a pick draws an arrow). In the command bar Tab with nothing to complete moves nothing: the bar is one line for one command, modal as Jump To's palette, and Escape leaves it. |
| ⌥Tab, ⌥⇧Tab | into a selected thing's drawn parts, and between them | In text (a box of the panel, a row's value) ⌥Tab types a tab, and in the JSON editor indents, since Tab there moves on. |
| ↑ ↓ | the row above, below, in a list or column | On the canvas, nudge the selection; with nothing selected, pan. |
| ← → | the item before, after, in a line | On the canvas, nudge or pan as ↑ ↓. In an outline (the table of contents) → opens a row and ← closes it, as macOS's outlines do. |
| Return | do or open the focused thing | In text, a new line where the text takes several (a note's words); in a one-line value (a row's) it ends editing, as a form's field commits; a box row ends editing too (Space toggles it, as macOS checkboxes do). |
| Space | toggle or press the focused thing | On the canvas with nothing focused, held: the Hand. |
| Escape | back out one level, keeping what was typed | |
| ⌘↩ | finish (end editing, close and commit) | |
| ⌘↓, ⌘↑ | into a thing's content, out to its container | |
| Page Up, Page Down | a page: the canvas pans, a list's table scrolls a screenful | In the issue walk's list (a list grouped by board whose rows are a walk's), the first stop of the previous and next board, wrapping: the list is read by board, and a screenful of it is not a place anyone is going. |
| typing | filters a focused list | |

## How the app meets them

- **The canvas.** Every key the canvas answers is registered with Keyboard, one shortcut per chord, and listed in the Keyboard Shortcuts window, generated ([keyboard](keyboard.md)). Tab and ⇧Tab, ⌥⌘ with an arrow, ⌘↓ and ⌘↑ step the selection between shapes in reading order ([selection](selection.md), Moving between shapes); arrows are not Tab stops (landed 2026-10-18).
- **A note being edited** is walked words, each row, then the next note: Tab in the words goes to the first row, Tab off the last row edits the next note at its words (`RowsHost.tabbedOut`), ⇧Tab from a note's words begins the previous note at its last row (`NoteHops.startsAtLastRow`), and with no other note the walk comes round inside the note. While a typed note is edited its words keep a line however empty they are, so the caret sits above its rows (`RowsExtent.wordsLine`; the core lays the edited shape out afresh as editing begins and ends) ([editing](editing.md), [types](types.md#typing-in-a-row)).
- **A note's rows** (Types, StickyNotes): `RowsView.keyDown` and `RowField.doCommand` read `KeyMeaning`; Return, Space and Backspace act once for a held key (Tab and the arrows repeat), Return follows a focused pill or pops a choice's menu, ⇧Return adds a note beside, and VoiceOver reads each row (`Fields` group, a role by row class, the field's name, its value, `needed` or `wrong` as help) ([types](types.md#typing-in-a-row)).
- **The panel** is AppKit's key view loop and SwiftUI focus; View › Focus Inspector (⌥⌘I, dimmed while it has nothing to show) gives it the keyboard and Escape gives it back ([host slots](host-slots.md)).
- **The sidebar** is the table of contents' list (below); View › Focus Sidebar (⌥⌘S) gives it the keyboard, showing the sidebar if it's hidden, and Escape gives it back ([host slots](host-slots.md)).
- **The panel's band** (P1, P2, P10). A band over the panel (`registrar.detailBand`) is first in the ring, and splits the two keys that leave: Escape is one level out (the takeover closes, the band has the keyboard, then from the band the canvas, the band staying), ⌘. all the way (the takeover's escape, the band's cancel, the canvas); a band with no control the keys reach (a button, with Keyboard navigation off) lets Escape through to the canvas, so the key is never dead, and whatever the band's buttons do also has a menu item or a key (P2, P10) ([detail panel](detail-panel.md)). The issue walk's band is the first (‹ 12 of 63 › and Done, Validation's `IssueWalkPanelPlugin`): ‹, › and Done are the buttons of Previous Issue, Next Issue and End Issue Walk (Go's items, ⇧⌘', ⌘' and none), the count's click or Return toggles the list state, Escape in the content goes to the band when Keyboard navigation is on (its buttons are then stops, walked by Tab and ⇧Tab and named "Previous Issue", "12 of 63", "Next Issue", "Done") and straight to the canvas when it is off, Escape in the band to the canvas with the walk going on, and ⌘. in the band, in the content, and hiding the inspector end it; with Keyboard navigation off the menus and ⌘' hold everything the buttons do, and the walk's light, which shows while the keyboard is in the band, simply never shows ([validation](validation.md)). The walk's list (Go › Issue List, ⌃⌘', Validation's `IssueList`: a takeover over the panel, [validation](validation.md)) is such a list: it takes the keyboard as it opens, on the current stop's row, and ↑ ↓ move the walk (a head moves nothing), Page Up and Page Down go to the first stop of the previous and next board (the named exception above, `KeyMeanings`' `board-pages`), ← → fold a board, Return closes the list on the current stop with the keyboard in the shape's panel and the band staying (P5), Escape closes it and gives the band the keyboard (the canvas with Keyboard navigation off), and ⌃⌘' closes it giving the keyboard back where it was when it opened, the band if that was a field of the panel the list replaced (P3, P4); the list is named "Issue List", a row says its name, board and place, a head its count and fold, and the list is one Tab stop of the panel's loop (as the Connections list is; its rows are ↑ ↓'s), so Tab and ⇧Tab go on past it to the panel's next and previous stop, no exception (a `KeySurface` says so with `isOneStopOfLoop`). Everything the list does has a key and a menu item (Go's Issue List).
