# Boards on disk

`BoardDocument` and `BoardCodec`: the file formats, migrations and fixtures, what's kept aside, the view memory, saving and autosave.

Related: [boards in a file](boards-in-a-file.md), [properties and schemas](properties-and-schemas.md), [undo](undo.md), [subboards](subboards.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Boards on disk](../../docs/plugin-system.md#boards-on-disk).

## Architecture

- Boards are files, one per board, with the boards inside it (`docs/plugin-system.md`, "Boards on disk"): `BoardDocument` (CanvasUI, an `NSDocument`, autosaved in place) saves `editor.file`, every board of it, with `BoardCodec` (Canvas), and opens one with `replaceFile`; only a board's document writes its file, a new one too (`BoardDocument.newFile(at:)`, `canvas new`'s: a new, empty board saved there as Save As saves one, unedited, its type the app's, closed if the save fails); `openWindow()` opens a board in a window of its own, one of the app's documents, as File › Open does (File › New's, an earlier version's copy, `canvas new`'s). The app is AppKit-run: `InfiniteCanvasApp` sets `BoardDocument.configuration` (the shipped registry, the window's SwiftUI content) and installs `BoardMenus`; the Info.plist that `build.sh` writes exports the `.canvasboard` type (not `.board`: Freeform owns it), or in a worktree's build, a copy of the app, imports it ([build](build.md)). Order in the stack is each record's `stackingKey`. A kind's props are versioned by its append-only `static let migrations`: changing how they encode needs a migration and a new fixture in `Tests/CompositionTests/Fixtures/kinds` (never edit a fixture), even a new member with a default (`PropsMigration("name")`, which rewrites nothing). An added property's value is versioned by its own (`PropertyMigration`, over the value's JSON), whatever kinds opt in, with fixtures in `Fixtures/added` (`expectPropertyFixtures`); `PropsMigration.handOver("title", to: TitleProperty.self)` hands a kind's own member over to one. Shapes the app can't use are kept aside (`AnyShapeRecord.isOpaque`) and saved back as they were, each with its own version (`v`), since the envelope lists only the kinds the app writes; a horizontal that goes through every shape skips them. A kind the app no longer has (the schema card, retired for type notes) is such a shape: `Fixtures/files/frames.v5.json` holds one, read kept aside and written back as read but for that version moving onto the card (FramesShippedTests). A record's metadata is saved beside its props (`meta`), members no plugin knows included, and its added values in `added`, by key; those the app can't use (not declared, not opted into, newer, unreadable) in `kept`, with their versions, saved back as they were and listed in `LoadReport.keptValues` (the alert never offers to delete them). A board is written in the oldest format that holds it: 6 when the file holds a value of its own (File values, below), else 5 when a shape on any board is in a container (its `container`, beside its props, read only from 5; reading drops one not on the shape's own board or in a loop, `LoadReport.Repair.droppedContainer`, and keeps one that can't hold, kept aside or of a kind that holds nothing here, as written), else 4 with any board besides the root (`BoardCodec.encode(CanvasFile)`: `boards`, one flat map by owner id, never nested (Foundation's JSON reader stops at 512 levels), each `{ "shapes" : [...] }`, under the root's `versions`; read only from format 4), else 3 with added values (the envelope's `versions` has `kinds` and, when any, `added`), else 2 with metadata, else 1 (both with `schema`), so an older app refuses what it would save without. `LoadedBoard.file` is every board (`document` its root); reading walks the boards in tree order with one set of ids, so a repeated id is the first holder's, with the board it owns, and keeps the boards it can't show (`LoadReport.keptBoards`, `KeptBoard`: an owner kept aside, of a kind that owns none, inside such a board, unreachable, or an entry that isn't a board, kept verbatim in `CanvasFile.unreadableBoards`), writing them back; `KeptShape` and `KeptValue` name their `board`. The camera on each board, the board left open, whether the sidebar, the details and the minimap show, and how wide the sidebar and the inspector were left are remembered per file (`BoardViewMemory`: `View`'s `board`, `boards`, `showsSidebar`, `sidebarWidth` and `inspectorWidth`, read with `decodeIfPresent`, so an older entry is the root's, shows the sidebar and has each pane as wide as it starts; saved for the boards the file can still show, `editor.boardCameras`: the one shown and those above it, then those shown most lately, up to `BoardViewMemory.boardLimit`, 50, by `editor.boardsLeft` and the last session's `recent`), never in the file; a file opens on the board left open if it can still show it, through `replaceFile(with:showing:)`, so it's no step back nor an edit, each board with its camera (`rememberedCameras`); the board shown's camera comes back before the window makes its canvas, so the zoom it opens at isn't shown as a change ([drawing](drawing.md)). A board document has no undo manager (`hasUndoManager = false`): it counts its changes by its history's events (`undoHistory.didChange`, host API: a step began, came to nothing, was undone or redone), at once, so undoing to what was saved reads unedited. Every save closes the open step (`breakStep`), so undo returns to exactly what was saved; a periodic autosave during a press, or while a key is held whose repeats are one step (`undoHistory.isKeyHolding`: an arrow key's nudges), gives way (`userCancelled`) and runs once it's let go. **A save is written off the main thread** (`canAsynchronouslyWrite`, true for every operation): `changeCountToken(for:)`, which NSDocument calls on the main thread some turns of the run loop after the save was asked for and which takes the count the save will mark saved, also closes the step and takes the file (`editor.file`, a value: O(1)) or, for an autosave that can wait, that it gives way (`begin(implicitlyCancellable:)`: `Saving.file` or `.gaveWay`, in a lock, `saving`; taking them in the one call is what keeps the count and the file the same moment, which taking the file when the save was asked for would not); NSDocument then calls `data(ofType:)` on another thread (`nonisolated`) with the main thread held until the writing thread has what it needs, and it takes the file out, lets the main thread go at once (`unblockUserInteraction()`) and only then encodes it (`BoardCodec.encode`, which reads nothing of the main actor) and hands the bytes back to be written, throwing `userCancelled` for the one that gave way. So a board of 100,000 shapes holds the main thread for a snapshot and NSDocument's turns (some ms) and not for the encoding (1.3 s for the generated board of 100,000 shapes, 2.6 for fuller records); what is changed meanwhile is not in the file and leaves the board edited, and the first commit after the snapshot copies the tables it changes (the snapshot holds the old ones, as a query holds the file it took up). `data(ofType:)` asked on the main thread (a test, a caller that wants the board as it is, `snapshot(implicitlyCancellable:)`) encodes there, from the board as it is; on another thread with no save under way it takes the board from the main thread once that has been let go (a save always took its count first, so this is for a caller of its own). Debug builds say where the last file was encoded (`BoardDocument.lastEncodedOnMainThread`) and can hold the writing thread before it encodes (`beforeEncoding`, for a test that edits the board meanwhile). Its window is a `BoardWindow`, which answers Edit › Undo and Redo: the text's own while text has the keyboard (its `textUndo`, the only undo manager text views see, or a field's; forgotten when the text loses the keyboard; after each, the text says it changed, so a note or a field's binding writes it), else the board's `.undo`/`.redo`, named ("Undo Move"); it seals a run of panel writes on a click, a key on a control, or the keyboard moving, and every board's window seals on a click in a window that isn't a board's (the color panel), but not in a board's child window (the `@` picker beside a panel's text, whose pick is part of the typing).
- File values ([properties and schemas](properties-and-schemas.md), File values) are saved in the envelope's `values`, by key, each `{ "v" : its version, "value" : … }`, which makes the file format 6, the newest (`BoardCodec.format`): a board is written in the oldest format that holds it, so 6 only when the file holds a value (one that differs from its default), else 5, 4, 3, 2 or 1 as before, byte for byte; read only from 6 (an older format's `values` isn't read). A value of an older version goes through its property's migrations (`FileProperty.migrations`, `PropertyMigration`s over the value's JSON, as an added property's) and is saved at today's; one that reads as its default, or is written null, is none. What the app can't use (no installed plugin declares the key, a newer version, a value that doesn't read or migrate, an entry that isn't a value with its version) is kept as its whole entry was (`CanvasFile.keptFileValues`), reads as the default, takes no write, is written back as read, and is listed in `LoadReport.keptFileValues` (`KeptFileValue`: `notDeclared`, `newerVersion`, `unreadable`), which the window's alert says in a line of its own and never offers to delete; `values` that isn't an object, or an entry JSON can't hold, refuses the file, as `boards` does. `BoardDocument` carries them with no code of its own: it saves `editor.file` and opens and reverts with `replaceFile`. A shipped file property's value is held to fixtures in `Tests/CompositionTests/Fixtures/file` (`<key>.v<N>.json`, the file's value at version N, never edited; `expectFilePropertyFixtures`, CanvasTesting, through `BoardCodec.version(ofFileProperty:)` and `migrateFileValue`), as `expectPropertyFixtures` holds an added property's, since its key and what its versions wrote never change: a new shipped file property needs a fixture at v0, and a change to how its value encodes needs a migration and a fixture for the new version (Colors' `colors`, the file's own named colors, is the first; the core's `kits`, the kits a file has on, has `Fixtures/file/kits.v0.json`: [kits](kits.md)). CanvasTests' `fileValueCodecTests` hold the written form, the round trip, a file with none, what's kept and the migrations; CompositionTests' BoardDocumentTests a real document's save, open and revert, with CanvasTesting's `LetterheadPlugin` after the shipped list, and SavingTests (`savingTests`) the save off the main thread: the file written is what the codec writes, encoded off the main thread; the main run loop turning, and the board edited, while the writing thread is held before it encodes (the file is the board as the save took it, the board still edited, and saved again it is whole); an autosave that can wait giving way to a press through NSDocument's own flow (`autosave(withImplicitCancellability:)`: nothing written, scheduled again once the press ends) and writing in place when nothing waits; and the bytes asked for on another thread with no save under way. BenchmarkTests' `Budget.saveMain` holds the main thread's time of a save (a snapshot, not an encoding: 1.4 ms against 1.3 s at 100,000 shapes of the generated board) beside what encoding it on the main thread costs.
- A shape's stored box is the shape with no layout input: a kind laid out larger or smaller than it stores (`LaidOutBox`, [editor](editor.md); a note with rows) never writes the laid-out size, so the codec, the migrations and the fixtures see the box as it was, a preview draws it as stored, and a shape whose rows go is the size it was. Nothing is stored for rows. A note's kind is at version 4 since notes resize: `givenHeight`, the height it was given (a resize, draw's `size:`), the least it is, a member that's new (`PropsMigration("givenHeight")`: a note saved before reads none, so it's never shorter than a new one, as it was), and `Fixtures/kinds/sticky-note.v4.json` sets it ([editing](editing.md)).
- A field once named a note (a pointer: a mention token in a string of `fieldValues`, its type's schema a string of media type `text/x-canvas-link`): no field does now, and nothing was migrated. The token stays in the file as the text it is (a text row shows it, no check calls it wrong, no edge comes of it), and a schema that held the media type reads as a text field; no encoding changed, so no fixture was made or edited (TypesShippedTests opens such a board).
- Two added properties came with relationships, each a new key no board holds yet, so neither needed a migration, and each has its fixture in `Fixtures/added`, the codec's own bytes: `relationship` (a bare `true`, a type's mark) and `endRule` (an object, `needed` and `onlyOne`, an arrow's rule for the end it is). No kind's props changed, so `Fixtures/kinds` has nothing new. [Types](types.md) says what each means. Subboards and frames opting into `is` and `fieldValues` (and a subboard into `autofill`) changed no encoding either: an added property's value reads and writes as it did, so those opt-ins needed no migration and no fixture.
- One more came with filling a note's fields from its words: `autofill` (Types', a Bool, `false` a value: whether a shape of a type fills, and on a type whether its shapes do), a new key no board holds, so no migration; its fixture is `Fixtures/added/autofill.v0.json`, a bare `false`. The sticky note's schema says it (`SchemaTests`). [Types](types.md) says what it means.
