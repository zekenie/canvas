# Kits

A kit is a named set of the plugins the app ships, which a file turns on or off as one (File ▸ Kits ▸ Stickers): joining a kit, the points a kit switches and how they're read, the file value that says which kits are on, File ▸ Kits and an off kit's items in the menu bar, the toolbar's segment and Insert's submenu for a kit, and the example kit, Stickers.

Related: [plugins and kinds](plugins-and-kinds.md), [properties and schemas](properties-and-schemas.md), [editor](editor.md), [host slots](host-slots.md), [keyboard](keyboard.md), [slash commands](slash-commands.md), [context menus](context-menus.md), [selection](selection.md), [clipboard](clipboard.md), [boards on disk](boards-on-disk.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Kits](../../docs/plugin-system.md#kits). The design and what the owner decided are the doc "Kits" (https://claude.ai/artifact/8g1EBrRC3bMKUdGkAfL1pc).

## Architecture

- **What a kit is.** The core's, generic (`Sources/Canvas/Plugins/Kits.swift`, `Sources/Canvas/Editor/CanvasEditor+Kits.swift`): the core knows what a kit is and never which kits exist, as it knows what a command is and never which commands exist. A kit is a type, the key, as a file property's is (`enum StickersKit {}`, `extension StickersKit: Kit { static let id: KitID = "stickers"; static var title: String { "Stickers" } }`: `id` what a file keeps, never changed once shipped; `title` its item in File ▸ Kits, its submenu in Insert, its toolbar segment's name and the steps "Turn On Stickers" and "Turn Off Stickers"). A plugin joins one in its `register(into:)` (`registrar.join(StickersKit.self)`, the `KitMemberships` point, the core's), and the kit is the plugins that join it: no list of a kit's plugins is written anywhere. A face is the kit's through its plugin: everything a plugin in a kit gives a point a kit switches is the kit's, and nothing else it gives is, so a module whose ways in are partly always on puts those in a plugin value of their own that joins nothing (as a face a list should be able to leave out already is one). The registry refuses a plugin that joins two kits or one twice, two kit types of one id, and two kits of one title (`KitMemberships.check`, `invalid`); the report says `kit stickers` first on each member's line. `registry.kits` (each once, in the order first joined: `KitDescriptor`, `id` and `title`), `kit(_:)`, `kit(of: plugin)`, `kit(ofTool:)`, `kit(ofCommand:)` and `plugins(in:)` read them (`KitTable`, made as the registry is built).
- **What the core gives once a plugin joins a kit** (`Registry.kitContributions`, run as the registry is built, before its checks; for a list where no plugin joins one, nothing, so its report is as it was): the file value `kits` (`KitsOn`, below), declared by the core; for each kit a command, `CanvasCommand.kit(id)` (`kit:stickers`), titled as the kit, in File ▸ Kits (`FileMenu.KitList`, a submenu of `FileMenu.Kits`, the core's section after the window's own File sections), checked while the kit is on (`isChecked:`) and running `editor.turn(kit:on:)` the other way, contributed as the core's so no kit switches it; and each Insert item of a kit's tool (`CommandRegistration.inserts`, which `ShapeRegistrar.tool(placing:)` sets) placed in the kit's submenu of Insert (`KitShapes<K>`, a generic section, `.submenu(K.title, in: InsertMenu.Shapes.self)`, the report's `in KitShapes<StickersKit>`) rather than in Insert's own section.
- **What a kit switches** (`KitSwitched`, a marker protocol, not refining `ExtensionPoint`, so a point's owner adds it in an extension of its own without touching how its other conformance infers isolation; `editor.contributions(to:)` takes `P: ExtensionPoint & KitSwitched`): the ways in a person makes or does something with, and nothing else. The core's `CorePoints.Tools` and `Commands` and `KeyHints`; Keyboard's `KeyboardShortcuts`; SlashCommands' `ShapeSlashCommands` and `SelectionSlashCommands`; ContextMenus' `ShapeContextMenus` and `CanvasContextMenu`; Selection's `DoubleClickPlacement`; Clipboard's `PasteReaders` ([clipboard](clipboard.md)). A kit's kinds, properties, file values, services, overlays, adornments, panel tabs, rows, rules, looks and its words for `canvas draw` and `canvas query` are never switched: the registry is built once with every plugin, so a shape drawn with a kit stays drawn, editable and checked with it off, and agents' words work in every file (the owner's call: a kit hides what a person sees, and agents' words show nothing). A point that adds a new kind of way in conforms to `KitSwitched` and is read through the editor.
- **Which kits are on** (`editor.kits`, `Set<KitID>`): what the file keeps (`KitsOn`) that the registry has, worked out as the editor is made, as a commit, an undo or a redo changes the value (`ChangeSet.fileValues` names `kits`; `noteKits()` before services hear, beside `noteBoardReadOnly()`) and as a file is put in place (`show`, `replaceFile`), and set only when it changes: observed apart from `document`, so the toolbar redraws as a kit turns on or off and never on every commit. `isOn(_ kit:)`, `isOn(K.self)`, `isOn(plugin:)` (true for a plugin in no kit) read it. `editor.turn(kit:on:)` (and `turn(K.self, on:)`) writes it in one step named "Turn On Stickers" or "Turn Off Stickers", the ids the file holds sorted and kept, those of a kit this app doesn't have too; nothing for a kit no plugin joins or one already so.
- **Reading a switched point**: `editor.contributions(to:)`, `(to:for:)` and `(to:reaching:)` are the registry's reads less what a plugin of a kit that's off in the file gave, kept once a point, kind and set of kits on (`registry.memo`, keyed by `SwitchedRead`), and the registry's own when every kit is on (a list with none: always), so a per-shape ask costs what it did. The registry's `contributions(to:)` still holds every contribution, a kit's too: a point's own `check`, a report and anything about every plugin read it there. The readers of switched points: Keyboard's chord table (`KeyboardState`, gathered again when `editor.kits` differs from the set it was gathered for), SlashCommandState's lists (a kind's candidates, kept by the kits they were gathered for, and the commands about the bar's target), ContextMenuState's (a kind's items, kept the same way, and the canvas's items), the select tool's double-click and Clipboard's readers (read again when the pasteboard or the kits change).
- **The core's own**: a tool whose plugin's kit is off isn't enabled (`isToolEnabled`, so `setTool` refuses it and its key passes), and a tool in use whose kit goes off gives way to the default tool (`leaveDisabledTool`, as on a board turned read-only). A command whose plugin's kit is off isn't claimed in the file (`editor.claims(_:)`; `perform`, `canPerform`, `attempt`, `menuTitle(of:)` and `isChecked(_:)` go through `registration(of:)`), so its keys pass, a context menu leaves out an item that runs it (`dims: true` too: `MenuItem.isClaimed` and the resolution ask `editor.claims`), a slash command typed for it isn't offered (`tries:` asks `editor.claims`), and its menu bar item is hidden (below). Commands gained a check for any toggle: `registrar.command(…, isChecked:)`, read as the item is validated (`editor.isChecked`, which `BoardWindowController.validateMenuItem` sets as the item's `state`).
- **The window** (CanvasUI): File ▸ Kits is the core's commands, placed as any command's item is. The menu bar is the app's and follows the key window's file: `BoardMenus.showCommands(of:in:registry:)` hides the item of every command the editor doesn't claim (not dimmed), an other key's hidden item (`otherKeyTag`) answering no key, a submenu left with nothing that shows and a line with nothing on one side, and shows them again for a file with the kit on; with no board's window every kit is off; nothing for a list with no kit. `install` runs it with no window, a `BoardWindow` as it becomes key and as it closes leaving no board's window with the keyboard (every kit off then), and `BoardWindowController.followKits()` as its file's kits change while it's key. The Keyboard Shortcuts window lists the keys of the kits the key window's file has on (`KeyboardShortcutsWindow(kits:)`, `registry.keyboardHelp(kitsOn:)`, Keyboard's `keyboardHelpRows(kitsOn:)`; the `KeyboardHelp` slot is asked with the kits on). The toolbar (`ToolPicker`): a segment a tool in no kit, then one segment for each kit on in the file (`ToolGroup.groups(in:kitsOn:)`), showing the last of its tools used (its first, until one is; the coordinator's `lastUsed`, per window, never saved), a click taking that tool, its menu (`setMenu(_:forSegment:)` with the indicator: its arrow, or a long press) every tool of the kit, the current one checked; its symbol's description "Stickers, Thumbs Up" for VoiceOver; none for a kit that's off. Insert lists a kit's tools in its submenu (above), so every kit tool has a menu item and a way by keys.
- **The file value**: `KitsOn`, key `kits`, a sorted list of kit ids, `[]` by default (every kit off, which no file holds, so a file with none on is written as it always was, byte for byte, and format 6 only while a kit is on), version 0 with no migration; an id no installed plugin joins stays and is written back. Its fixture is `Tests/CompositionTests/Fixtures/file/kits.v0.json` ([boards on disk](boards-on-disk.md)).
- **Pasting what only an off kit reads**: off means off (the owner's call): an off kit's reader is never asked, so text only it reads pastes nothing, and the kit is turned on in File ▸ Kits. Pasting this app's own shapes, a kit's included, is never switched.
- **The example kit, Stickers** (`Examples/Stickers`, product, shipped last, after Reordering: one line to delete when the first real kit lands, with its tests and the canvas skill's kinds page made again): `StickersKit` (`stickers`), joined by `StickersPlugin` (`stickers`), which gives the `emoji-sticker` kind (`Sticker`: `frame` and `emoji`, `minLength` 1, so an empty one warns; drawn as its emoji as big as the square holds; the core's gray skeleton; `NeverPublic`, as nothing names one; resized by its handles, Selection's; VoiceOver its emoji as its value; called Sticker, `face.smiling`), four tools (Thumbs Up 👍, the kind's own id; Heart ❤️, Star ⭐ and Party 🎉, `emoji-sticker-heart`, `-star`, `-party`; 96 × 96, no keys) with their Insert items in Insert ▸ Stickers, `/sticker` (a choice, `.together`, on the stickers selected in the command bar: the four, or any emoji typed, one Change Sticker step), Change Sticker ▸ in a sticker's menu (the four, its own checked) and a paste reader (`emoji`: text that is nothing but emoji, spaces and line breaks between, at most twelve, a sticker each, 96 wide and 16 apart in a row). `canvas kinds` and the canvas skill's `reference/kinds.md` list `emoji-sticker` while it ships.

## Testing

- CanvasTesting's `Kits.swift`: the tests' kits, `Workshop` (`workshop`) and `Studio` (`studio`), and `WorkshopPlugin(id:kit:log:)` (planks, `Plank`, with the Plank tool and its Insert item, and Edit ▸ Carve, `.carve` in `WorkshopSection`, counted in `WorkshopLog`), in a kit or none: each module's tests join a kit with fixture plugins of their own, so no test depends on Stickers.
- CanvasTests' `kitTests` (`KitTests.swift`): the registry's kits, tools and commands, the report's lines, a list with no kit unchanged, the refusals, every kit off in a new file (the tool, the command, the Insert item, the kind still there), Turn On and Turn Off each one step with undo and redo, a tool in use given up as its kit goes, a shape drawn with a kit moved, deleted and undone with it off, the switched reads over a point of the test's own against one a kit doesn't switch, the file value (sorted, an unknown id kept, absent with every kit off, written at format 6 and read back), a file put in place and an editor opened with a kit on, and the hints of the Keyboard Shortcuts window.
- KeyboardTests' `kitKeyTests`, SlashCommandsTests' `slashKitTests`, ContextMenusTests' `menuKitTests`, SelectionTests' `selectionKitTests` and ClipboardTests' `pasteReaderTests` hold each switched point gone while its kit is off and back on; CanvasUITests' `kitWindowTests` File ▸ Kits, `showCommands` (Insert going whole, Carve's item and its line, back for a file with the kit on, every kit off with no window) and the toolbar's segment (none off, one on, its menu, the tool it shows, the last used kept, gone off with its tool).
- StickersTests (`stickersTests`) hold the example over the plugins it fills; CompositionTests' `kitsShippedTests` hold it on the shipped list (off in a new file and every way in gone, Insert ▸ Stickers hidden, on in one step and back, a sticker pasted, off again with the stickers still there, locked as any shape and checked against its schema, a real board saved, opened and reverted with it on and saved as before with it off again, the window's File ▸ Kits ▸ Stickers checked while on), and the shipped pins say it (the report's core and stickers lines, the File and Insert menus, the toolbar's tools in no kit, the census board's sticker with the kit on, the kind's fixture `Fixtures/kinds/emoji-sticker.v0.json`).
