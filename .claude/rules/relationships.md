# Relationships

Relationships: what an arrow between two notes of a relationship type means, in Types and with Types naming no kind: the mark of a relationship type, an arrow's rule for the end it is, the ends of a relationship type compiled from the arrows between it and other types, the one function that fits a note to a side, the rows a type's notes get (shown by [types](types.md#relation-rows)), `RelationshipIndex` (what it keeps and says moved), how an end is read through a pill, and the check on an arrow (a misfit, an end that cannot be read, a free end). What a person does with it from a row is [below](#relating-from-a-row); the rows are [types](types.md#relation-rows)'.

Related: [types](types.md), [topology](topology.md), [connections](connections.md), [arrows](arrows.md), [properties and schemas](properties-and-schemas.md), [boards on disk](boards-on-disk.md), [command line](command-line.md), [benchmarks](benchmarks.md), [testing](testing.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Types](../../docs/plugin-system.md#types-shapes-that-hold-a-schema).

## The words

- A relationship is an arrow between two notes that is of a relationship type and holds that type's values (its `is` names the type; its `fieldValues` are the values). A relationship type is a type (a shape that holds `schema`) that also holds the mark `relationship`. Its from and to are the types allowed at each end, a type that builds on one counting. A reference is the pill that stands for a public shape, and only that. A related type is two arrows, never a two-headed one.
- Nothing a user or an agent reads says "edge type" or "link" for any of this. Topology's own words (an edge, an edge type) stay Topology's.

## What is stored

- Two added properties, both declared by `TypesPlugin`, each with a fixture in `Fixtures/added` (the codec's own bytes, never edited) and no kind migration (no kind's props changed): `relationship` (`RelationshipProperty`, `Type/RelationshipMark.swift`: a bare `true`, nil while not, `false` is none), opted into by `canBeRelationshipType()` (the note calls it beside `canBeType()`); and `endRule` (`RelationshipEndProperty`, `Fields/Relating.swift`: `EndRule { needed, onlyOne }`, an object, nil while both are false), opted into by `relating()` (the arrow calls it beside `typeable()`). A kind that holds `endRule` is a relating kind (`registry.relates(kind)`); Types finds the kinds by the property and names none.
- `TypeWords.check` holds both: the mark needs `schema` on its kind, and a relating kind holds `is` and `fieldValues` (the keys the Type part names that a higher part declares are `RelationshipKeys`).
- A shape is a relationship type exactly while it holds `schema` and the mark; the mark alone is inert; Remove Type clears both in its one update. `endRule` on an arrow that is no end is inert. On an end it is read into the compiled end (`RelationshipEnd.rule`) and the row (`RelationshipRow.rule`, the union of the ends merged into it). `canvas draw` writes both: `relationship: true` on a note, `edge … endRule: {needed: true}` joined member by member (`EndRuleMerge`, in `FieldValuesPlugin`). The skill's attribute tables and `canvas kinds` say so (SkillTests).
- Nothing is stored for an end: a relationship type's ends are the arrows between it and other types, read from records. An arrow from a type into a relationship type is a from end, an arrow out of it to a type a to end; the arrow's first line of words names the row.

## The values and the fit (`Type/RelationshipGraph.swift`, `Type/ArrowRole.swift`)

- Pure and `Sendable`, every type of `Type/RelationshipGraph.swift`. `RelationshipEnds.rows(of:sides:)` is the one place the merge rule lives: ends of one typed name on one type are one row on every side that has one; unnamed ends on both sides with the same types are one row, else a row a side; a row's rule is the union of its ends'; it never reads a title.
- `RelationshipGraph.side(_:at:of:)` is THE rule: an end that is not a note is unjudged; a side with no end drawn is open; an end that is itself a type is a misfit (a type's own note is never an instance); else the end fits when what its types lead to (`TypeGraph.ancestors`) meets the side's types. `fit`, `fitting` (taken: both sides hold and one fits by a drawn end; open: no end on either side, offered after and never taken; neither when an end is a type's own note or not a note), `rows(for:isType:)` (a shape's types' and their ancestors' rows, the general type's block first; nothing for a relationship type's own note or from a relationship type in the list), `fits(_:otherEndOf:)` and `relationshipTypes(joining:and:)` all call it.
- `ArrowRole.of(from:to:registry:)` is what an arrow is by its two end records alone: an end joins a marked type and an unmarked one; a free end says nothing. It reads `schema`, the mark and `canBeType` and no graph, so a run that has written types the file does not hold yet can ask it. A pill is no type to it; reading through one is the index's.

## The service (`Fields/RelationshipIndex.swift`)

- `RelationshipIndex` (`editor.relationships`, an `EditorService`) is registered right after `TypeIndex`. Each member is said on it: `graph`, `revision`, `stamp(of:)`, `end(_:)` and `rows(for:isType:)` (memoised by the list while the revision stands) are kept; `ruledRows(for:)`, `relations(of:)`, `relations(of:in:)`, `candidates(for:of:)`, `fits(of:)` and `subjects(of:)` are read when asked and kept nowhere. `isActive` is whether a marked type exists now: every path's first test. It never transacts, never calls `topology.provide` and never calls Validation.
- An end is found by the connection (`Edge.isConnection`: the empty slot) of a relating kind, read in the literal view: each end is the shape if it is a type, or what a direct pill's record names if that is one shape and still a type, whether or not the pill reads through; a pill that finds shapes, stands for nothing, or for a shape that is no type, is no end. A connection with a relationship type at one end and an unmarked type at the other is an end of that type, on the side its direction says. A relationship type is rebuilt from its end arrows' records, never by scanning the edges at it; it is read from its edges when it is marked, unmarked, comes or goes as a type, or is touched with no carrier to explain it. The connections at a shape are its recorded edges in the empty slot and those at a pill whose record names it (`topology.standIns(naming:)`: the recorded view keeps a not admitted pill's edge at the pill), so the same arrow is an end when it is drawn, when the file is opened, when its type is marked later and when its type is deleted and the delete undone.
- A commit is heard in this order, by construction: Topology's follower only collects the ends touched by edges other than the `is-a` and mention edges; Validation and the rest hear; `TypeIndex` tells `onChange`, which the index only collects; then the index's own `documentDidChange` (guarded by its heard revision, a cheap return when no marked type exists before or after or nothing but a move happened), which drains the change set (the kind first), the follower's collection and the `TypeChange`, recompiles each dirty relationship type, moves the stamps and the revision, and delivers one `RelationshipChange { arrows, notes, layout, rows, everything }`. `catchUp(_:)` is the same for a reader that runs before the index's turn. A board switch changes nothing and works out no change set; a file put in place compiles everything again.
- What each change names: an end drawn, deleted or re-aimed names its instances (`arrows`) and the end types whose notes gain or lose a row (`layout`); an end's words or rule names the end and redraws (`rows`), never the instances; a mark flip, in both directions, names the type's instances and the relating shapes bound to it (a loose end is a function of the mark; one pass over each board for all the marks of a commit), and the relationship types with an end at it; a note that becomes or stops being a type rereads the connections at it, and its instances (a type deleted that notes still name) are in `notes` and `layout`, with the shown rows of a list moved by it; a lineage change, or a list changed on a shape that is no type but has instances (a type taken away that they still name), names the instances in `notes` and the shape and the types whose notes read rows from another place in `layout`; a row renamed to a row the type's builders or the type builds on already have lays out the types whose merged row count changed; a ruled row's verdict depends on its partition (the carriers in it, its sides and its rule: `RuledPart`, never its label), so when the ruled rows of an end type differ in that before and after a recompile (a row came, went, merged with another by name, split from one, changed rule or sides) `notes` gains the end type's notes, near and far (`TypeIndex.affected(by:)`, less the types), a row of the same key at another end type (a type that builds on this one, a note's second type) is the one the note reads where the later block's stands, so a row that came, went or changed at an end type while another end type has a row of its key, either ruled, names the end type's notes too (`changesMerge`, over every end type's rows made first), and a rename that leaves every ruled row's partition equal announces `rows: true` alone (RelationRuledRowsTests), and `FieldChecks` then has Validation check again the notes whose Only one issue says the old name, and only mark stale (`ValidationEngine.recheckWords`) the words of those whose Needed issue says it, checking none (a benchmark holds a keystroke in a Needed end's label with 1,000 empty notes to making no note's check again, on a board that was read); `rows: true` is told whenever the rows differ, a change of count included; a shape's `is` list moves its stamp and its connections'; a pill a commit changed is read again where it is an end, though no edge changed. Missing a name is a correctness bug, not a cost: Validation keeps each shape's issues until told.
- A pill a commit changed names the relating arrows drawn at it (`arrows`, and the notes at their ends), and so does a commit that touched one whose shape went private, public or away: what an arrow runs to changes with its pill, though no end and no type moved. A mark flip names the notes at the ends of the arrows of the type too, since a relationship is an arrow of a marked type and their relations come and go with it.
- A drag session's arrow is not counted until the drag ends: `Session.touching` names the arrow a port's drag draws or a re-aim moves, from the press to the release, and the index leaves a connection the session names as it was before the drag (`held`, `isHeld`): a commit whose only changed shapes are such connections (every hover) reads nothing and names nothing (`holdsOnly`: no followers' touched ends, no stamp, no `RelationshipChange`), a connection named among other changes is left out of the drain, a relationship type's recompile keeps a held end as it was, and a held connection no session names any more is counted by the next commit. `release(_:)` (`editor.connectionReleased(_:)`, once on every way a drag ends; `connectionDrawn` calls it) counts the connection as a commit that named it would have, with it exempt from the `touching` test since `editor.session` is cleared only when the press ends: its end is read, the relationship type recompiled, the instances laid out, the arrow and the notes at its ends announced, all in the press and so the press's step. The release names the notes the arrow left as well as the ones it reached (`noteEndsOf`: the shapes at its ends when it was last counted, types included since one may stop being a type while the arrow is held), so a note a re-aim leaves is checked again. A pass over a relationship type therefore names no instance until the release, and Escape (the arrow deleted) leaves nothing held (`heldConnections`, debug builds). RelationshipHoldTests.
- `graph(in: reading)` is the committed graph for the editor's own reading, and, for a transaction's, the committed graph with what the run has written put back (`Fields/RelationshipRun.swift`, `RunGraph`): the types it made or took the schema or the mark from, the lists it wrote, the arrows it drew as ends (read from `registry.edges(of:)` and `standIns.forwarding(of:)`, as the index reads a committed one), and the rows they give. It is kept up from the reading's log (`LayoutReading.changes`, [editor](editor.md)), as `RelationshipRun.swift`'s head comment says. A reading older than what the graph has read (or another run, or another commit) makes it again. The arrows at a shape are found literally (an arrow drawn at a pill is found at the pill, whatever the committed pill forwards it to, so a pill the run re-pointed re-reads its arrows), a side's ends are put in the file's order (the arrows the file has by `fileOrderKey`, those the run drew after them in the order it drew them), and the rows an end type gets from each relationship type the run compiled again are kept for the run and ranked by the file order of each type's first end, as a compile of the file gives them. `subjects(of:in:)` and `reading(ofEnd:in:)` read an arrow's ends over the reading (a pill that stands for a shape the run has, admitted or not; a gone one asks Topology whether the board is unavailable), and `relations(of:in:)` is a note's relations over it (the committed ones less those the run changed, and the run's own; a note is an end of an arrow into a pill as the recorded edges have it, so a pill that stands for two admitted notes gives each the relation), kept by the reading's `writeCount`.

## Reading an end (`Fields/RelationshipFar.swift`)

- `reading(ofEnd:)` is one classification from records and the file, an `EndReading` (each case said on it). The name a gone, unavailable or query pill keeps is `registry.standIns.calls(pill)`, which outlives the shape.

## The check on an arrow (`Checks/RelationChecks.swift`, `Checks/RelationWords.swift`, `FieldChecks`)

- `RelationChecks.arrow(types:ends:graph:naming:)` is pure (handed the graph, the arrow's two ends as the index read them, and the names the sentences use) and says, for each marked type in the arrow's `is` list, in list order, each side from first: a misfit is one error at `.end(side)`, `Employment runs to a Company. “foundation” is a Layer.` (the arrow's type, the side's types, then the end's name and what it is: its types, `a type`, `no type`, or the kind it is); an end that cannot be read (`EndReading` a pill that is gone, not admitted, finds shapes or stands for nothing) is one warning there (`Employment runs to “Acme”, which isn’t public.`: the word is the stand-in kind's own); one the app cannot show says nothing; an arrow of a relationship type that is not bound at both ends is one warning at `.end(nil)` (`Employment isn’t attached at both ends.`), once for all its types. Equal problems are said once. Nothing is refused. `ArrowVerdict` also names the notes whose labels the sentences quote. Every sentence is `RelationWords`; "edge type" and "link" are never in them.
- `FieldProblem` has a `locus` (`FieldLocus`: `.field(path)`, `.end(side?)`, `.row(key)`; the default is the field's, so every call of the validator's is unchanged) and one mapping, `placeName` and `pointer`, that Validation's rule, draw's rows and the queries' `problems` all use: `field: "email"`, `"from"`, `"to"`, or a row's name. A reader of a field's path (`mark(at:)`, `problems(at:)`, `leaving(out:)`) sees `.field` problems only, so a row named like a field never marks it; `endMark(_:)`, `worstEnd`, `isMisfit` and `removingRelations()` read the ends.
- `FieldChecks` keeps the part with each answer, apart from the validator's (`Answer.base`), made with the index's `stamp(of: arrow)` and `revision` and the rename count when its words name a title. It is current while those hold; the validator's part is not asked again when only it is stale. While no relationship type exists a kept part is current only if it is empty (`relationCurrent`), so unmarking or deleting the file's last one, and the undo of its first, clear and bring back what it said. The part is made only for a relating kind with a marked type in its list. It is told by `RelationshipIndex.onChange` after every service has heard (`validation.recheck(arrows ∪ notes)`, never inside a follower).
- Nothing tells an arrow that the note it quotes was renamed, so `FieldChecks.quotes` keeps the label each sentence quoted by the note and the arrows that quote it; a commit that names such a note compares its label now (one dictionary miss for any other; with no misfit in the file the table is empty). A keystroke below a note's first line leaves its label, and every part, alone; a rename makes the kept label the new one, however many arrows quote the note. A commit that changes the chain also checks again every arrow whose sentence names a type or a note (a type of an end that went or lost its schema, or was renamed with it), and a type that leaves the file while notes still list it is a lineage change for them (the arrows of their relationship types are checked again). A commit heard out of turn checks again the loose ends too (`FieldChecks.looseEnds`: they keep no answer). A pick from Is a ▸ or `/is-a` reaches only the shapes whose role offers the type: relationship types the arrows, plain types the rest.
- A relating arrow with no `is` that is bound to a marked type and has no connection carries one warning at `.end(nil)`: a function of the arrow's record and the marks, so it is right after a reopen and an undo; with no relationship type in the file it is not reached. (An arrow left bound to a type's note with a label or a rule on it is a loose end too, below.)
- A run says what an arrow's ends say, over the run's own graph: `FieldChecks.check(of:reading:)` (and `drawn`) makes the relation part of an arrow of a relating kind whose list has a marked type in `graph(in: reading)`, from `subjects(of:in:)`, `RelationChecks.arrow` and names read from the reading, and puts it in place of the committed answer's (which it strips): a misfit, an unread end and a free end for an arrow the script draws, a type or note the script draws or changes, an end it deletes. Nothing is kept for it. The commit's rings say the same, which the run's tests hold (`relationshipRunTests`).
- Validation re-runs the rule for the shapes `recheck` names; the agreement test (`relationshipAgreementTests`, typed runs) holds that Validation's kept issues for every arrow on the board shown are the pure verdict of a fresh read of the file after every step of a seeded run: drags of an arrow's end with their hovers and release, mark flips and their undo, lineage edits, a relationship type moved alone, moves across boards, re-aims, retypes, pills made private. A change that can move a verdict and names nobody is a bug there. The typed runs also hold what a run would say: each step is made again as writes not yet committed over the file as it was before the step (a second editor, the step's changed records written in one transaction that is thrown away), and the shapes those writes bring an issue to, among the shapes they do not write (asked as `canvas draw` asks: `validationTouched`, each one's issues before and after), are exactly the shapes not written whose kept issues gained one in the commit.

## The check on a note's rows (`Checks/RelationChecks.swift`, `FieldChecks`)

- `RelationChecks.note(rows:count:graph:)` is pure, handed a note's ruled rows (`RelationshipIndex.ruledRows(for:)`), how many relationships it has in each (`relations(of:in:)`, each arrow once; a misfit, an end that cannot be read and a relationship through a pill all count, a free-ended arrow is in no row) and the graph, and says for each ruled row, in the rows' order: a Needed row with none is one `needed` problem (`layer is needed`, keyword `required`, at `.row(key)`: amber on the row and `:incomplete`, an issue of Validation's third level: valid, no ring, no Issues line, not `:invalid`, as a needed field is), and more than one where Only one is set is one `wrong` (`layer has 2 notes, and should have at most 1`, keyword `onlyOne`: red on the row, an error on the note and none on the arrows, `RelationWords.onlyOne`). A row is called by `RelationshipRow.name(in:)` (the table's `company · Employment` for the later of two relationship types' rows of one name is the table's alone). A relationship's own wrong or needed value marks its arrow only. `FieldCheck.mark(at: RelationshipRowKey)` is the row's mark; a reader of a field's path never sees a row.
- `FieldChecks` makes the part for a note of a kind that says where its rows go (`rowKinds`, handed in by `TypesPlugin`: `TypeRows` is in Rows, which this part sits below) in the arrow part's seat, with `(stamp, revision)`: every end, mark or lineage change moves the revision, so a part is made again by the next ask (cheap: no ruled row, no work). What names the notes whose verdict moved is the index: `notes` for a relationship drawn or deleted at the note, an end's rule or partition, a lineage or a membership change. A part names a title only for a row with no name typed (`RelationChecks.namesATitle`), so a rename of a type makes again only the notes whose words say one; a rename of a ruled row that keeps the partition names no note, and `rows: true` makes again the notes whose kept Only one issue says a row name the row is not called now (`rowErrors`: by row, each note with the name its issue says) and marks stale the words of those whose Needed issue says it (`rowNeeded`, `recheckWords`), for the words of Validation's issue (a Needed row's issue is kept like any, and its words went stale until the agreement test found it); a keystroke in an end of another relationship type makes none. A run says the same over its own graph (`noteProblems`, `relations(of:in: reading)`): a note the script draws or restates carries `problems` for a row it breaks (`field` is the row's name, `class` `needed` or `wrong`), and the error is among the run's warnings like any.

## What a run's writes reach

- **A run says what it breaks on a shape it did not write** ([command line](command-line.md#what-a-run-brings-to-shapes-it-did-not-write), [validation](validation.md)): `canvas draw` asks Validation which shapes its writes touch, checks each before and after, and warns of what is new. Types' answer is `FieldChecks.touched(by:reading:)` (`Checks/RunTouches.swift`, the `touches` of the rule over values and relationships): the reach of "What each change names" above and of `TypeIndex.onChange`, before a commit, read from the committed index, the reading's records and the run's own graph. It may over-name (the run compares the check before and after) and must not miss, and names nothing that is cheaper to leave out:
  - **A relationship** (a relating shape whose list has a marked type, in the committed graph for the record as it was, in the run's graph for the record as it is) drawn, deleted, re-aimed or retyped: the shapes at its ends, as they were and as they are (`shapesAtEnds(of:named:)`: each end as the record names it and, at a pill, every shape the pill names, admitted or not, so a note on another board is reached through the pill the run draws beside its start; what an end names is read once a question, so 2,500 relationships between a hundred notes read a hundred ends). An arrow that is no relationship before or after names nothing, and in a file with no relationship type committed or written a relating shape costs its record alone.
  - **An end** drawn, deleted, renamed or given a rule, **a mark** that comes or goes, and **a type at an end** that comes or goes: the run's graph has compiled its relationship type again (`RunGraph.recompiled`, `relationshipTypesCompiled(in:)`; walked only when the writes asked of include a type or an arrow bound to one, so a statement beside an end given a rule, asked alone for its line, names nothing of it); for each such type, the notes near and far of every end type whose rows differ between the committed graph and the run's (`TypeIndex.affected(by:)`, less the types: a rename is a difference, since an Only one issue says the row's name), its arrows where the types at its ends or its mark differ, and for a mark the shapes at those arrows' ends and the arrows drawn at the type (its loose ends).
  - **A type** whose text, title, own list, mark or being a type moved: what `typesChanged` reaches after a commit (`FieldChecks.reached(byTypes:)`: its instances and the types whose JSON refers to it, over and over) and the shapes whose answer says a type's name. A lineage or a membership change (and a list changed on a shape that is no type and that notes still name) reaches its instances near and far (`affected(by:)`) and, with a relationship type in the file, the arrows at each (they fit by another lineage).
  - **Any other shape** that came, went, changed its own types, became or stopped being a type, is a pill, or that a stand-in kind admits now and did not (or the other way): the arrows drawn at it and at the pills that name it, with those left bound to it at one end alone (`RelationshipIndex.arrows(at:in:)`: the committed connections and halves, and those the run drew); a pill, also the shapes it named and names and the shapes at the ends of the arrows drawn at it. And the arrows whose sentence quotes the shape by its label (`arrowsQuoting`).
- **The check of a shape the run reaches is the run's.** `FieldChecks.check(of:reading:)` makes a note's relationship part and an arrow's over the run's graph whether or not the shape itself changed in the reading (`relationProblems`, `noteProblems`), so a note the run touches is judged as one it draws; and it now says a loose end over a reading too (`looseEnd(of:reading:)`: the marks from the run's graph, which notes are types and what a pill names from the reading's records, whether the arrow is bound at both ends from its own record), which the run's check never said before (an arrow with no type answered clean, committed or not). A type's own warnings are said over a reading as well (`typeWarnings(of:reading:)`, [types](types.md#checks)).
- A subboard deleted puts every shape of its board in the writes (`Transaction.pending`'s `elsewhere`), so a relationship that ran through a pill to a note on that board is reached as the delete of the note itself is. CompositionTests' `drawBroughtFarShippedTests` hold it through `canvas`.
- TypesTests' `runTouchesTests` hold it: the owner's example through draw (one warning naming Ann on the edge's line, dry and real, nothing on the run again), the note's part over the run's graph for a note whose record is as committed, and, each made in a transaction thrown away (asked as draw asks: `validationTouched`, each shape's issues before and after over its own board) and then made for real and held against what Validation keeps: a relationship drawn, deleted, retyped and re-aimed; an end given a rule, renamed, made needed, deleted and drawn again; the mark taken off and put back; a type that comes to build on an end's type; a type restated (a value its fields now refuse, a field made needed: each instance warned of at the third level) near and far, an end made Needed (the notes at it with none warned of, `incomplete`), by hand and by a run; a relationship into a pill for a note on another board, a pill re-pointed, and the note behind two pills made private (each arrow into one warned of, as the board then says); a type deleted that another refers to; a loose end said in a run and reached by a mark; a rule set at a type with 1,000 instances (twenty said, 980 counted: the whole run 120 ms of the test thread's CPU in a debug build, held to 600); and 2,500 arrows that are no relationship naming nothing, with a relationship type in the file and with none (the question alone 4.1 ms and 2.7 ms, held to 60 and 40). ## Deleting a relationship type, and what is left behind

- **The delete takes the end arrows** (`IsA/RelationshipDeletes.swift`, Types' `willDelete`, registered by `registerRelationshipDeletes`): for each deleted id that holds the mark (`transaction.document[id]?[RelationshipProperty.self]`, one added-value lookup an id, and nothing else for a delete of shapes that are none: `endDeleteIdle`) it takes the type's end arrows (`RelationshipIndex.endArrows(of:reading:)`; the handler reaches the index through the transaction's `shapes.service(_:)`): the arrows the index knows (`endArrows(of:)`, O(its ends)) and every relating shape on the type's own board bound to it, each read again from the transaction's own record (`boundShapes(in:)`) so an end the same transaction drew counts, one it re-aimed at a note that is no type does not, and one whose other end was freed earlier goes (one pass over the type's board for the delete of a relationship type, which the core's own letting go makes for every delete); and deletes them with `transaction.delete(inFile:)`, whichever board each is on, in the delete's own step: one Undo brings the type and its end arrows back on every board, as whole files and as `BoardCodec` bytes. An end arrow is bound to the type (or a pill that names it) and, at its other end, to a type's note, a pill that names a type, or nothing; an arrow between the type and a note that is no type is a plain arrow and stays, let go of the type where it was drawn, and so is one between two relationship types. A delete from a board not shown by the core's `delete(_:on:)` or `delete(inFile:)` in a step on the board shown runs the same handler on the type's board. A step on a board that is not shown (`transact(on:)`, which `canvas draw` commits in when its board is not the one on show) cannot reach the board shown, and a commit that did would be dropped whole (`Transaction.mayReachBoardShown` is false there), so the handler leaves the end arrows on the board shown where they are, let go of the type, and the type is deleted; those ends say nothing, bound to a pill for a gone shape. Its ends on any other board go. **A locked arrow stays**: a handler runs where the core's refusal checks are off, so it asks `RelationshipIndex.isLocked(_:)` (`editor.isReadOnly(inFile:)`: a lock on the arrow, a frame that holds it, or its board) itself and leaves such an arrow, which the core lets go of the type where it was drawn. The delete of the type is never refused. A deviation from tldraw, written in [arrows](arrows.md). Remove Type, the mark taken off, a type at an end deleted and a pill deleted take nothing along. Cut is a delete, so cutting a relationship type alone takes its end arrows, and pasting it back puts the type under its id with no ends (a `/move-to` of it leaves them). A subboard deleted with a relationship type on its board runs no handler for it (the board goes whole), so ends drawn at a pill for it on other boards stay, silent. Not taken: an end drawn at a pill on another board that is bound to the pill alone (free at its other end).
- **The loose end** (`FieldChecks.looseEnd(of:)`): one orange line, `This arrow isn’t attached at both ends.` (with the type's title for the first case), on an arrow of a relating kind that holds no `is` and no connection (it is not bound at both ends) and is bound either to a relationship type (the type's end of an arrow whose other end was freed) or, once its relationship type is gone (deleted, or moved to another board alone, which lets go of its bindings), to a type's note at its one end, with a name on it or a rule (`endRule`, only whether it holds one). An end with neither is indistinguishable from a plain arrow that lost an end, and says nothing; so does one left at a note that is no type. It is a function of the arrow's record, the marks and which notes are types, so it is right after a reopen and after an undo. A pill that names a type counts as the type at an end (`RelationshipIndex.typeAt`), so a locked end left at a pill with a name is orange too. In a file with a type and no relationship type ever, a named arrow that lost an end at a type's note says the line too: the arrow cannot say which it is, and the line is the one a deleted relationship type needs. The index names these arrows: when a mark flips (`relatingShapes(boundToAny:)`, one pass over the board's arrows) and when a note comes or goes as a type, or a pill is changed or its shape is (a note that stops being a type clears the line, one that becomes a type earns it), from `halvesAt`, the relating shapes bound to one shape and to nothing else, kept by the commits that name them (one pass over the file when it is compiled, then O(the shapes a commit names)), so no pass over a board is made for a type made, in a file with no relationship type too (the index does not return early for a membership change or for a change at a pill with such an arrow drawn at it). The cheap tests come first, so an arrow that says nothing of itself in a file with no relationship type reads only its own record.
- **A type related to itself** is two arrows, never one two-headed arrow, by each way in: two port drags (a type to the relationship type, and the relationship type back to the type: each an end, in its own step, the second stored bent apart from the first, `ArrowConnections.parallels`), `Relate to Person` from the type's words (`newRelationshipType(from:to:)` with `from == to`), and one `canvas draw` script (`edge "Person" -> "Friendship"` and `edge "Friendship" -> "Person"`, the second bent by `EdgeRequest.beside`, run again `unchanged`). A relationship between two notes of the type then fits in either direction and a drag between them takes the relationship type at once. A note shows the relation in one row where the two ends are named alike (or unnamed on both sides, named for the type: `feature`) and in two where they are not; a row lists the far note of every arrow of its side. The type's own note says `↔` for the one row and `→` and `←` for two. **An arrow from a note to itself is never made**: a port's drag cannot end on its own shape (the arrow of a free release is deleted), a row's pick refuses the note itself (`relate` answers nil and the note shakes), and a script's `edge "Ann" -> "Ann"` is refused (`no_channel`, `a connection on note-link can't end where it starts`). CompositionTests' `relationshipSelfShippedTests` and `relationshipSelfDrawTests`. Each end arrow keeps its own `endRule`, and a row merged from both ends takes the union of the rules (`RelationshipEnds.rows(of:sides:)`).

## Setting the rule

`editor.setEndRule(_:needed:onlyOne:)` (IsA, `EndRules.swift`) is the one writer of `endRule`: it passes by an arrow that is no end (`relationships.end(_:)`), writes the members named and keeps the rest (both false take the property off), and makes one step named for the first change (`Make Needed`, `Make Optional`, `Allow Only One`, `Allow Several`; several arrows at once are one step). A read-only arrow is refused by the core and shakes while the rest change; nothing is written, and no step is made, for a rule already so, and it answers true only when a commit was made (false for an end the core refused whole). The arrow's context menu (`Needed`, `Only one`, checked by what every selected end has, shown only while every selected shape is an end) and its panel (an End section in the Types tab, two checkboxes) call it; `canvas draw` writes the property (`endRule:`), merged member by member. A type related to itself has two end arrows between one pair of notes, and each keeps its own rule. Setting a rule at a type with many instances names them in `notes` and so rechecks them in its commit, like a schema edit ([benchmarks](benchmarks.md): `ruleFanOut10k`).

## Relating from a row

What a person does with a relation row (the keys and the list are in [types](types.md#typing-in-a-row)): `editor.relate(note, to: other, in: row, step:)` and `editor.unrelate(arrows, shaking:, step:)` (IsA, `FarNotes.swift`), `farVerdict(of:)` and `RelationStep` (`.own`, a plain step; `.card(key:)`, joined to an open card's).

- `relate` makes one arrow of the row's relationship type through `registry.drawConnection` and writes the `is` on it in the same transaction ("Add Relationship"; two picks are two steps). The arrow runs by the row's side (`drawSide`): from the note where the row is on the `from` side, else into it; a row on both sides takes the side the picked note does not fit (`RelationshipGraph.drawSide(of:picking:)`), so the arrow fits. Nothing is written to either note. A row whose rule is Only one (`row.rule.onlyOne`) and in which the note already has a relationship is replaced by the pick: the arrows it holds there (`relations(of:in:)`, near or far) are deleted in the same transaction by the delete `unrelate` uses, with the pills they empty (except one the new arrow is drawn to), and a locked one refuses the whole pick, so the step is still the one `Add Relationship` (or the card's) and one Undo returns the old arrow. By hand nothing is replaced or refused: a second arrow drawn at a port is the note's issue. It answers nil, with nothing changed and no step, for a note that is read-only or on a read-only board (the core refuses it and the note shakes), a note not on the board shown, the note itself, a row whose type is no relationship type, nothing that draws connections, a pick that cannot be made, or a step the core refused.
- A note on another board is related through a pill on the board shown (`FarVerdict`: `here` an arrow straight to it; `reads` a pill can stand for it as it is; `fulfils(needs:)` it is made what the pill's kind needs, `public`, in the same step, and the list says so first; `cannot` it is private and its board is read-only or it is locked, no kind can stand for it, or it is on no board). One transaction: `standIns.fulfil` on the far record (`update(inFile:)`), admission asked again as the step leaves the far note, the pill reused (`StandInRoute.existing`, `.host(note)`: the one this note already has an arrow into for it) or inserted at `StandInRoute.landing` (the rect a `canvas draw` run gives the same pill) and settled, the arrow made with `standingFor:`, and a throw on any refusal, so nothing changes and no step opens. Types learns no pill kind and no publicness: the kind, the word and the making are the stand-in kind's. One Undo returns both boards byte for byte.
- `unrelate` groups the arrows by the board they are on, adds the pills each board's delete leaves with no arrow (`StandInRoute.emptied`; a pill another arrow still runs to stays), and deletes with the core's `delete(inFile:)`, whichever board, in one step on the board shown (a delete from the far note's own row does not switch boards, and its Undo does not either). A locked or read-only arrow or pill, or a board that cannot change, refuses the whole delete: nothing goes, no step opens, the note whose row asked shakes.
- `newRelationshipType(from:to:)` takes `from == to`: a type related to itself is two arrows (one into the new type and one out of it, never a two-headed one), the second asked of the connection maker beside the first (`beside:` names it, so the two are stored bent apart: [arrows](arrows.md)), and the new type lands beside the type. It accepts one end on another board: the far type is related through a pill as above, the new type lands beside the near one (`Surroundings.near`) and the pill beyond it.
- `RelationPicker` (Form, [types](types.md#the-list-of-notes-a-row-or-a-cell-hosts)) lists the notes: `relationships.instances(for:)` (the instances, near and far, of the row's other types through the chain, less types and relationship types), less the note and the notes its row shows, less the notes `farVerdict` says `cannot`; an open side lists any note of a kind that draws rows. A note with no title or words is in it, named by its values (`FieldValues.name`), and one with nothing in it (`listingUnnamed`).

## Relating from the words (the offer)

Words never draw, and one click does. `RelateOffer.swift` (IsA) is Types' face (Selection's `shapeFaces`, registered by `registerRelateOffer` beside the rows' faces) and an item for the canvas's context menu (`TypeMenus.swift`), both asking `RelateOffers.find(at:on:in:)`; the menu and the item are `RelateOffers.menu(for:in:)` and `title(for:in:)`, and what the item does is `editor.acceptRelateOffer(_:)`.

- **Where it is offered.** A pill in the words of a type (a shape that holds `schema`, and no relationship type) that names a type that is no relationship type (`TypeIndex.canBeEmbedded`: a mention of a relationship type, a plain note or a dead pill is Mentions' and nothing else), live, on the board shown or on another that a pill can stand for (`farVerdict` is not `cannot`), where the type does not hold a `$ref` to it (the words say a part) and no relationship type already joins the two types in either direction (`RelationshipGraph.relationshipTypes(joining:and:)`, a type that builds on an end's type counting as it). A type that mentions itself ("friends with another @Person") is offered `Relate to Person`, until a relationship type joins it to itself. Not on a read-only board, not while the type's words are edited, not drawn as a skeleton (a face is never asked there, and the context-menu item is left out), not with no engine that draws connections (`registry.drawsConnections`). A locked type is offered: the click changes no record of its own, and its ports draw arrows as any.
- **The cost of being asked.** The face is asked on every pointer move over a shape ([benchmarks](benchmarks.md): `relateOfferMove`): it returns after one lookup of an added value on a note that is no type, then a few tests, then the pill under the pointer (`mentionPills`, a memo hit the second face to ask shares with Mentions'), and only on a pill the schema's bytes and the file's relationship types.
- **The click.** Types is listed after Mentions, and a face source is asked last plugin first, so Types' is asked before Mentions' and Mentions' handles every pill this one answers nil for, exactly as before. A click pops one menu under the pill (`editor.popUpMenu(_:below:highlighting:)`, so Return takes it), the item `Relate to Layer` (`TypesStyle.relate(to:)`; for a type on another board whose pill would make it public, `Relate to Company · will be made public`, as the row's list says it). The click does not begin editing; a double-click does what a click on a pill did before (`beginEditing` at the pill, or, on a type that cannot be edited because it is read-only or its kind has no editing view, follows the pill, `mentions.follow`), the second press dropping the menu the first queued; the pointer over the pill hovers the type it names while that type is on the board shown. Only the single click changes.
- **The item.** `newRelationshipType(from: the type whose words mention, to: the type mentioned)`: the writer the drag between two types calls, one step "New Relationship Type" with the name card inside it, the direction the words' ("Feature is in a Layer" gives Feature `layer → Layer` and Layer `feature ← Feature`). Neither side of either type is written, so the sync hears no change and no model is asked. A nil from the writer shakes the type (`refuseChanges`). A choice that is stale (the two were related, or one stopped being a type, after the menu was made) changes nothing and shakes nothing. A type on another board is related through a pill, as a row's far pick does. A type related to itself is two arrows (`from == to`, above). One Undo takes the type, both arrows and the name back, and the offer returns.
- A mention of a relationship type, in another type's words or in a schema, is never what a mention embeds: `TypeIndex.canBeEmbedded` is asked by the sync, the highlights and the `$ref` completion ([types](types.md#the-model)).
