# canvas-ingest

The canvas-ingest skill: a git repository drawn as boards in one command, `ingest`. A scanner reads a commit's code into the scan, the repository's lens turns the scan into a digest, and canvas-digest draws the digest. The board is a view of the code that is made again from a commit, never kept up to date in place. Nothing is written by hand for a codebase, and nothing is written into the repository but what it keeps for itself: the settings (`.canvas/ingest.json`) and its lens (`.canvas/lens.py`); what a run keeps is in a cache outside it. One fixed picture fits no team, so each repository owns its lens, and a lens must stay deterministic: the same commit, lens, app and macOS draw the same boards.

Related: [digest](digest.md) (the skill that measures, lays out and draws what `ingest` makes; its driver and `--records`), [command line](command-line.md) (`canvas`, which the driver runs), [build](build.md) (the audit knows nothing of the skill) ([every topic](../../CLAUDE.md#map)).

## Architecture

- **Vocabulary.** The scan (`scan.json`, what a scanner writes: `reference/scan.md` has its format), a scanner (`scanners/`: Swift's three scripts, and SCIP's), the lens (`<repo>/.canvas/lens.py`, a function `digest(scan, repo)` returning the digest as a dict; without one, the default lens), lenskit (`lenskit/`, the library every lens imports), the runner (`runner/`, which runs a lens twice, isolated), the settings (`<repo>/.canvas/ingest.json`), the checkout (`<cache>/checkout`, the commit's code, where the scanners run). The skill folder is `.claude/skills/canvas-ingest`: `ingest` (POSIX sh), `settings.py`, `SKILL.md` (Agent Skills: `name` is the folder's, the `description` at most 1,024 characters), `reference/scan.md` (the options, the settings, the cache, the scanners, the scan's format, the default lens's digest), `reference/lens.md` (writing a lens), `examples/orders` (the worked example), `scanners/`, `lenskit/`, `runner/`. All Python is `/usr/bin/python3` (3.9: no `match`, no `X | Y` types, no tomllib), which `ingest` runs by that path.
- **`ingest [REPO]`** draws the git repository you run it in (or `REPO`, whose top level it finds), not the one the skill lives in. It finds the digest driver beside its own folder (`<its folder>/../canvas-digest/digest`, links followed, so a skill folder linked into `~/.claude/skills` finds its neighbour next to the real one) and leaves how the driver finds `canvas` to the driver (`$CANVAS_CLI`, else the one beside the skills, else the PATH; run from a worktree of this repository, the beside-the-skills one is the worktree's own build, an app that is not the one running, so point `CANVAS_CLI` at the main checkout's `canvas`, the app that is: the user's shell runs there, [build](build.md)). Order: the options, the repository and its cache (`--where` prints the cache's folder and stops), a `spec.py` refused, the settings, the commit (resolved once to a sha, below), the lock, what to scan with (refused before the app is asked anything), `digest ready` (the app running, the board fit to be drawn, the take-back possible: asked before anything slow, so an app that isn't running is said before the scan; a refusal removes the run's folder and adds `ingest`'s own options to the driver's words, since `ingest` has no `--into` or `--replace`), the scan (the commit's, kept or made; what a partial clone lacks of the commit fetched first, below), the digest, `digest all`. The target is the board in front with `--replace` (default), `--board ID --replace`, or `--new-file PATH`; options `--commit REF`, `--mess`, `--ranks`, `--window WxH` (the driver's `--view`), `--scip INDEX`, `--scan FILE`, `--rescan`. `--skip-read` is gone (one scan kept for the repository's latest state means nothing once scans are per commit): `--scan FILE` draws from a scan given by hand, which tests and checked-in examples use.
- **The settings** (`settings.py`, which prints shell assignments for `eval`; sh never parses JSON): `scanner` (`swift` or `scip`), `scip` (the command that writes the index, run at the checkout's root with the indexer's version pinned, `{index}` the path to write, `<cache>/index/index.scip`, written bare: it is replaced by a shell-quoted path, so quotes around it would be part of the name), `prepare` (run in the checkout when a lockfile of the commit, or the command, has changed), `window` (`[width, height]`, each from 1 to 1,000,000, the driver's `--view WxH`; absent, the window's size at run time), `mess` (0 to 1), `ranks` (`rows` or `columns`). An unknown key is a warning on standard error and a bad value (a number that is infinite or NaN, as `1e400` is to a JSON reader, among them) is refused naming its key, before anything is asked of the app. `settings.py` is a program and no module (its `main()` runs only as `__main__`). An option on the command line beats its setting. With no `scanner`, a repository with a `Package.swift` scans as Swift; any other is refused, saying what to write. `--scip INDEX` still takes an index made by hand. A `<repo>/.canvas/spec.py` is **refused**, before anything else is asked, with the way on: its names go into `lens.py` as the lower-case arguments of `lenskit.default.digest` (below). The settings and the lens are read from the folder `ingest` is run in, the working tree, never from the commit drawn (so a commit from before the settings existed draws too). This repository's `.canvas/ingest.json` is `{"scanner": "swift", "window": [1322, 893], "ranks": "rows"}`, so every run lays its boards out for that room and its bands as rows, and its `lens.py` lays the root out as `Package.swift` does the module graph (the rungs stacked from app to core, the platform rung in a frame for each heading over its modules, the core rung in one row; scan.md says so).
- **The cache**, outside the repository, one per repository, shared by its worktrees: `${CANVAS_INGEST_CACHE:-$HOME/Library/Caches/InfiniteCanvas/ingest}/<name>-<hash>`, `<hash>` the first 12 hex digits of the sha256 of the resolved absolute path of `git rev-parse --git-common-dir` and `<name>` the basename of that directory's parent. It holds `checkout/` and `checkout.prepared` (below), `scans/` (the scans by the commit's code and scanner, below; each is written as `<name>.json.reading` and moved into place when whole, so a scan that stops part way never leaves one with its files and none of their uses), `index/` (Swift's index; SCIP's `index.scip`), `runs/<run>/` (`digest.json` and the driver's `out/`; the last five are kept, and a run the driver refuses leaves none), `drawn/` (the drawing records, one for each file drawn in: `digest --records`, so a proposal drawn into a new file never replaces the record of the board in front, and runs from two worktrees do not share one) and `lock`. The `PROJECT` variable is gone.
- **Whose code runs.** A repository's `prepare` and `scip` commands and its `.canvas/lens.py` are that repository's own code, run as its build would be, and not sandboxed: `prepare` and `scip` with the user's environment (each in a shell of its own at the checkout's root, none of `ingest`'s variables in it), the lens with a cleared one (below). It is the repository's trust, not `ingest`'s: an agent shows the user these commands (the settings' `prepare` and `scip`, the lens) before the first run on a repository the user didn't set up.
- **One ingest a repository at a time.** `ingest` takes `<cache>/lock` with `mkdir`, writing its pid in it, holds it for the whole run, and frees it on any exit (a trap on `EXIT`, with `INT`, `TERM` and `HUP` turned into exits). A second run refuses at once, naming the holder's pid; a lock whose pid is gone is taken over: the stale lock is moved aside whole, so of two runs that find it stale one moves it, and what was moved is looked at (if its pid isn't the stale holder's, another run had already taken the lock over and made its own: it is put back, and the lock is looked at again; if it can't be put back, the run refuses, saying so). A pid that another process has since been given reads as a live holder, and is not told apart (that would cost a process's start time): the lock is refused until that process ends or the folder is removed by hand. **A signal is acted on at once**: every long command (`prepare`, the `scip` command, the scanners, the runner, the driver) is run by `run`, in the background and waited for, since the shell holds a trapped signal until a foreground command has ended (a 40 s `prepare` held the lock 40 s past a `TERM`); on exit the command and the processes under it are sent `TERM`, and `KILL` three seconds on, before the lock is freed. A background command ignores `^C` in a shell with no job control, so this is `ingest`'s doing and no signal's.
- **The commit** is `--commit REF` (default `HEAD`), resolved once, before anything slow, by `git rev-parse --verify REF^{commit}` to a sha that every step after it names (a branch moving or a working tree changing while it runs changes nothing); a REF that is no commit is refused, with nothing asked of the app (in a shallow clone, saying it is one, whose older commits `git fetch --unshallow` fetches). The code drawn is that commit's, always: the scanners read the checkout, and the lens reads it through `repo` (`run.py --commit SHA`), never the working tree, so an uncommitted edit is never drawn. The repository `run.py` is handed is the one you run in (its objects hold the commit); the lens file is the working tree's (`.canvas/lens.py`), committed or not, so a round of art direction needs no commit and the agent leaves the lens and settings uncommitted until the user is happy and says to commit them (it never commits in a user's repository unasked: SKILL.md).
- **One checkout a repository** (`<cache>/checkout`), moved to each commit: a fresh `git archive` for each commit would have the compiler type-check every module again (the index's marks hold the sources' absolute paths) and reinstall a TypeScript project's packages every time. It is made once by `git clone --shared --no-checkout` from the repository's git directory, so it borrows the repository's objects through `objects/info/alternates` (every commit of the repository is there with no fetch). For each scan `checkout --force --detach <sha>` then `clean -ffd` (no `-x`: what git ignores, `node_modules`, `.build`, stays; what git doesn't know goes, so what `prepare` makes should be ignored). Never `git worktree add`, which would show in the user's `git worktree list`. Its git is always run as `git -C <checkout> --git-dir=.git` (a cache inside some other repository is never taken for the checkout, or its work tree), with `core.hooksPath` off and LFS's filters empty (the pointer files are what the commit holds, as `repo` reads them). **It heals**: a checkout whose move fails (the source pruned an object the checkout borrowed, a git directory gone or damaged) is deleted, with the stamp beside it, and cloned again, saying so on standard error (`the checkout in the cache is broken (<git's first line>); making it again`); a move that still fails after that is the run's failure, naming git's first line and how many more it said (`first_line`: a checkout that fails says a line a file). A checkout made again has no `node_modules`, so `prepare` runs again. **Submodules are not checked out**: their paths are empty folders, and the lens's `repo` sees no file in them. The scan's `name` is the repository's, never the checkout's: the Swift scanner takes it from `Package.swift` and otherwise, as `scip_read.py` does, from `--name`, which `ingest` passes as the cache's `<name>` (the folder that holds the git directory, the same from every worktree). Swift's index stays in `<cache>/index`, built from the checkout, whose path doesn't change between commits, so the second commit type-checks only what changed.
- **A partial clone** (`git clone --filter=blob:none`, or `tree:0`: a remote with `promisor = true`, or `extensions.partialClone`) has only some of its commits' files and folders, and git fetches the rest from that remote when they are wanted. The checkout borrows the repository's objects but not its remotes, and the lens reads the commit with a cleared environment (no credentials: a lazy fetch there would fail, or wait on a prompt), so `ingest` fetches what the commit lacks (`fetch_missing`) before the checkout moves to scan it and before a lens of the repository's own runs, which reads the commit through `repo` (the default lens reads only the scan, so a kept scan drawn with it fetches nothing; the scan's key reads the commit's top-level tree first, which git fetches itself in a treeless clone): `git rev-list --objects --missing=print --no-walk <sha>` lists it, and it is fetched as git's own lazy fetch fetches, `fetch <remote> --no-tags --no-write-fetch-head --recurse-submodules=no --filter=blob:none --stdin` (with `fetch.negotiationAlgorithm=noop`), into the repository, with the user's environment; a level a request (a treeless clone's folders, then their files), at most three, after which what is still missing is the run's failure, as a fetch that fails is (git's words above it). A commit the clone has whole (one checked out) fetches nothing.
- **`prepare`** (the setting) runs in the checkout, once it is at the commit and a scan is to be made, when a hash differs from the one in `<cache>/checkout.prepared`: the hash of the commit's lockfiles (`package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `Package.resolved`, `Gemfile.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `Cargo.lock`, `go.sum`, `composer.lock`, `gradle.lockfile` and `requirements*.txt`, at any depth: their paths and blob ids from `git ls-tree -r -z`, read by `runner/lockfiles.py`, so no path is quoted and skipped) and the command itself. What it prints goes to `<run>/prepare.log`, and only a failure says it (its last 40 lines, then the log's path: `quietly`), since an install prints a line a package (a yarn install, ten thousand) that would bury `ingest`'s own lines and fill an agent's reading of the run; the `scip` command's likewise, to `<run>/scip.log`. The stamp is written only after the command succeeded (it is removed first), so a failing one stops the run and is tried again by the next, and it goes with a checkout that is made again. A move to a commit that changes none of them leaves what the command installed as it was.
- **Scans are kept by the commit's code and the scanner**: `<cache>/scans/<code>-<scanner>-<12 hex>.json`, `<code>` 40 hex digits of the sha256 of the lines of `git ls-tree <sha>` (the commit's top-level tree) but the `.canvas` entry (`code_key` in `ingest`), `<scanner>` `swift` or `scip` (also for `--scip INDEX`), and the 12 hex digits a hash of what made it: the scanner's own files (Swift's: the three scripts and `reading.py`; SCIP's: `scip_read.py`, `scip.py`, `reading.py`) and, for SCIP, the `scip` command (or the index given by hand, by its bytes). **Why not the commit**: SKILL.md has an agent leave the lens in the working tree until the user is happy and then offer to commit it, and a commit that changes only `.canvas/` moves HEAD; keyed by the commit, every round of art direction would have rescanned (`npm ci` and indexing, minutes each). Commits that differ only in `.canvas/` share a scan; any other change (a lockfile among them, and a `.canvas` below the top level) is another, and a scanner reads nothing from the top-level `.canvas`, since a target of the code never lives in it. The `scip` command's index is removed before it runs, and a command that writes none is refused (an index left by the commit before is never read as this one's). A later run on code with a scan of that key goes straight to the lens and says so (`the scan of <sha> is kept, so nothing is scanned`), moving no checkout and running no `prepare`; `--rescan` scans it again. The scan holds nothing of the commit (its `name` is the repository's). The last 20 scans are kept (by modification time; a run that uses one touches it), the rest are removed. `--scan FILE` draws from a scan given by hand and touches none of this: no checkout, no `prepare`, no scanner, no kept scan, and not with `--scip` or `--rescan`.
- **The same boards.** A lens must stay deterministic (below), and nothing else varies: the same commit, lens, app and macOS give the same plan (`plan.json`) and the same run scripts (`runs/*.draw`), the same commit drawn twice, whatever the working tree holds, a lens committed or not. No board says which commit it shows (the line that once ended the first board's About note, `runner/stamp.py`, went with the note on 2026-10-22); a run's folder in the cache has its `digest.json`, and the scan its commit's code.
- **The codebase ingestion** is what the scanners, the lens and the driver make together; the board is what the code says. The scanner reads the code into the scan (Swift's three scripts, or `scip_read.py` with the `scip` scanner or `--scip`, on the checkout; the scan is kept by the commit's code, above; Swift's index is kept from run to run, below; an indexer reads only the files its projects take in, so `scip_read.py` says, after its counts, how many of the commit's files of the kinds the index read (an ending five of its files have, or half the commit's files with it: one `.js` config a project takes in doesn't make every script a source), tests aside, the index lacks, and the three folders most of them are in: `not_indexed`, from the checkout's `git ls-files`; and, since an import of a workspace package whose `package.json` names built files nothing built resolves to nothing, when of the dependencies the modules' own `package.json` files (the nearest at or above a module's folder, whose `name` is the module's) declare on each other, three or more, under a fifth show up as uses: `unconnected`, which says the two ways out (scan.md's Workspaces that resolve through built files); both lines start `scan:`); a target whose line in `Package.swift` ends `+ shipped`, the product and the tests of it ([build](build.md), What ships), is read two ways (`parse_package`): `deps`, what the line writes, is what the scan keeps and the board draws arrows from, so the app's card has no arrow to every plugin, and `links`, those and the modules of the plugins that ship, is what a compile of it reads, so its tests, which import plugins their line doesn't name, still type-check; a scanner also writes `name`, what the code calls itself, which is the board's title. **The Swift scanner is this repository's**: it relies on `// layer:` tags, `let ships` and `+ shipped`, and its own index build (`reference/scan.md` says so). The default lens (`lenskit/default.py`) makes the digest: bands as ranked frames, by the modules' layer tags ordered by how deep their imports go, else by import depth; modules, and the folders of a module of over 50 files, as subboards whose `text` is their description (what the module is, what it imports as mentions of their cards, how big: the card's panel shows it, and the board has no About note); a board's folders as frames; files as notes; imports and uses as edges, weighted by the names used up to 4. Then `digest all` with the target, `--records <cache>/drawn`, `--out <run>/out`, and `--mess`, `--ranks`, `--view` when set (the digest it writes has no `policy.ranks`). A note's `@[` is written `\@[` (a run of backslashes before it doubled), so a doc that shows a mention reads as text, and a description's mention of a card escapes `]` and `\` in its title (`lenskit.text.mention`). **Every title is given out once** (`lenskit.builder`'s `Titles.claim`), the ones that matter most first: modules, folder boards, bands, files, frames. One another shape has (spaces folded, case aside), or over 80 characters, gives way to the next it is offered (a band `X (layer)`, a file its whole path, a frame `X (<board>)`), then to a number after it, keeping its end behind an ellipsis when clipped; each is said on standard error and none stops the run, so no codebase's names can fail `check` after the scan (a name with half a character in it, a file's that isn't UTF-8, is given U+FFFD there, in a `source` too; a folder whose board would be named as a module is gets no board of its own, `derive.complete`). Every node says what it was made from in `source` (a path, or `{path, line}`): a file's note its path, a module's card (and a folder's) its folder, which canvas-digest accepts and ignores ([digest](digest.md)).
- **The lens** is `<repo>/.canvas/lens.py` **in the checkout you run in, never read from the commit**: a function `digest(scan, repo)` returning the digest as a dict (`{title, nodes, edges}`; a `warnings` list, if it has one, is said on standard error and taken off), or, with no such file, `lenskit.default.digest(scan, repo)`. An agent writes it for a team over rounds of feedback (SKILL.md, below; the guide is `reference/lens.md`). `scan` is a `lenskit.Scan`, `repo` a `lenskit.Repo`; the file may import `lenskit` and anything beside itself. Runs must be deterministic, so `ingest` runs it through `runner/run.py` **twice** (`REPO SCAN DIGEST [--lens FILE] [--commit SHA]`, the sha `ingest` resolved), concurrently: each run is `env -i` with only `PATH=/usr/bin:/bin`, `HOME` (a fresh empty folder, a different one each run), `TZ=UTC`, `LC_ALL=C`, `PYTHONHASHSEED` (1, then 2) and `PYTHONDONTWRITEBYTECODE=1`, started in a fresh empty folder as the current folder, as `/usr/bin/python3 -s -B runner/child.py` (not `-I` or `-E`, which drop `PYTHONHASHSEED`). `child.py` makes the clock read a different instant in each run (`time.time`, `time.time_ns`, `localtime`, `gmtime`, `ctime`, `asctime` and `strftime` without a time, `clock_gettime` of the real-time clock, `datetime`'s `now`, `utcnow` and `today`, `date.today`: 2001 in run 1, 2020 in run 2, moving on as a clock does; `datetime.date` and `datetime.datetime` are subclasses with a metaclass that answers `isinstance` and `issubclass` as the real classes do, so `isinstance(datetime.now(), datetime.date)` holds and a `default=` hook that asks it is called). What a lens can import is `lenskit` (loaded from the skill's folder, which is not on `sys.path`, and `runner/` is taken off it) and what sits beside the lens, in the folder first on the path: a helper named `settings.py` is the lens's own, and the skill's `settings`, `run` and `child` are not importable by name. It loads the lens, runs it, checks the basic shape (a dict, a non-empty `title`, `nodes` and `edges` lists, `warnings` a list of strings, everything JSON can hold) and writes the digest as `json.dumps(indent=1)` in the lens's own order. `run.py` compares the two as text: a difference is refused, naming the first node or edge that differs (its number and both) and the usual causes (a set of strings, the clock, the environment or current folder, a file read outside `repo`); a lens that raises stops the run with its traceback (the child's own, naming the lens file), before `digest all`, and no `digest.json` is left; a run over 900 seconds is stopped. On success `digest.json` is the first run's, without its warnings (the first 20 said as `lens: ...`, all of them in `lens-warnings.txt` beside the digest when there are more, `SAID`; then a summary line with the processes' CPU time). **lenskit** (`lenskit/`, no module-level state; `/usr/bin/python3` 3.9): `Scan` (`scan.modules` by name, test modules too; `scan.production`, the drawn modules' names, whose `deps` are among them; `scan.files` by `(module, path)`, production modules' only; `scan.uses` `(from, to, names)`, once a pair; `module()`, `file()`, `Scan.load`), `Repo(root, commit="HEAD")` (below; the folder is kept private, `_root`, so a lens isn't invited to read the working tree), `Digest` (`frame`, `subboard`, `note`, `add` for any kind, `edge`, each passing extra fields through as keywords; `claim(what, wanted, *others, most=80)`, a title given out once, reworded and warned as above; `warn`; `finish()`, which gathers the warnings into the digest), `text` (`as_text`, `mention`, `file_text`, `declares`, `words` per language), `default.digest(scan, repo=None, **overrides)`, `yaml` and `sql`. **The default lens's overrides** are spec.py's names as keyword arguments, taking the values those took: `title`, `bands` (`[(title, [module])]`), `purposes` (`{module: text}`), `folder_purposes`, `folder_boards` (`{module: [folder]}`), `groups` (`{board: [(title, [file], [subgroup])]}`), `by_module` (`[(module, file)]`), `layer_names`; any other keyword is a `TypeError` listing these. What they leave out is worked out and what they name that the code lacks is passed over and warned (`lens: bands name modules the code lacks...`), as spec.py's were. **`repo`** reads one commit through git and never the working tree (an uncommitted edit is not seen): `files(pattern=None)` the commit's paths sorted, matching a glob over the whole path (`*` and `?` stay in a folder's name, `**/` crosses folders and may match none, `[abc]`; no `.gitignore` rules), `read(path)` (UTF-8, U+FFFD where it isn't), `read_bytes`, `exists`, `commit` (the sha), `name` (the folder's), from `git ls-tree -r -z` once and a `git cat-file --batch` kept open (`FileNotFoundError` for a path the commit lacks; a submodule is no file). **`lenskit.yaml.load`** reads block mappings and sequences, plain scalars (`null`, `~`, `true`/`false`, integers, floats; `yes` and `on` are text), quoted strings with their escapes (one that is no character, `\U00110000`, is a `YamlError`), comments, a byte order mark (passed over), `|` and `>` block scalars (`-` strips, `+` keeps the blank lines after the text) and one-line flow `[a, b]` and `{a: b}`, and refuses with a `YamlError` naming the line anchors, aliases and `<<`, tags, a second document, `? ` keys, tabs in indentation, flow over several lines, plain scalars over several lines and a key given twice. **`lenskit.sql.tables(texts)`** (a text, or migrations in order) gives `{name: Table}` with `Column(name, type, nullable, primary_key)` from `CREATE TABLE` (a table-level `PRIMARY KEY` too), `ALTER TABLE ... ADD [COLUMN]`, `DROP COLUMN`, `RENAME COLUMN` and `RENAME TO`, `ALTER COLUMN ... SET NOT NULL | DROP NOT NULL | [SET DATA] TYPE t` (and T-SQL's `ALTER COLUMN a t [NOT NULL]`), MySQL's `MODIFY` and `CHANGE` (a column keeps its place, and its primary key), and `DROP TABLE`, skipping every other statement, a table made `AS SELECT`, a temporary table, comments, `$$` bodies and an ALTER of a table no migration made. Comments and `$$` bodies are taken out in the same pass that reads the strings, so a `'--'` or `'/*'` is a string. `KEY`, `INDEX`, `EXCLUDE`, `PERIOD`, `FULLTEXT`, `SPATIAL` and `LIKE` start a table-level constraint only as one reads (a `(`, or a name and then `(`, and not a type: `KEY idx (a)` is one, `key varchar(10)` a column); a `CHECK (x IS NOT NULL)` says nothing of the column's nullability; a name may hold any letters; `AFTER x` and `FIRST` end a type. Limits: `[x]` identifiers, nested block comments, and a type this reader has never heard of after such a word (it reads as a constraint) are not read.
- **The skill an agent follows** (`SKILL.md`, rewritten whole for any agent that reads Agent Skills: it works through `ingest`, `canvas` and plain instructions, never one agent's own tools; under 500 lines and about 3,000 tokens, the detail in `reference/`). `ingest` is the script in the skill's folder, run by its path (`"$SKILL/ingest"`, `$SKILL` the folder SKILL.md is in), never assumed to be in the repository's `.claude/skills`. In the order a doer needs it: **Before anything** (the app's state, by the canvas skill's Check the app; only an empty board in front, the board of the last ingestion, or a new file is drawn on; a commit is drawn, never the working tree). **Setting a repository up, round one**: survey (languages, package manager and workspaces, frameworks, the repository's conventions for what matters: Temporal, Lambdas, tables, controllers, jobs), list the main things with counts and evidence, confirm them with the user one question at a time and only what changes the picture, write `.canvas/ingest.json` (the scanner and its pinned command, `prepare`, and `window`, set once from `canvas boards`' `view`), write `.canvas/lens.py` (the default lens with arguments, or a lens of its own with types and relationship types for the real things, from the example), draw HEAD, read the run before the user looks (`lens:` warnings, `check`'s crowded frames and boards, the plan's line, what was made public, the typed warnings, `verify`; the run's `digest.json` and `out/plan.json` through `--where`) and fix the obvious, then show it. **Later rounds**: art direction; shapes the user points at read with `canvas query ':selected'` and mapped back to the code by `source` in the run's `digest.json`; - **Scale.** The default lens does no board's work over every file or every module: files are grouped by module once (`derive.folder_boards`, `full_groups`, and `_Build`'s indexes of a module's files, its importers and a folder's outgoing uses), and module levels (`derive.levels`) are Tarjan's with a stack of its own, so a chain of thousands of modules is no recursion (3,000 modules in 60,000 files took 27 s a run, and takes under 1). One title query lists at most 10,000 titles, and a monorepo has many thousands of files: past `NOTES_MOST` (4,000) file notes the default lens draws a folder's files as one note (`default.collapse`). It collapses folders (a folder's own files, not its subfolders'; one with two files or more) one at a time, the deepest first (a module's own files are depth 0), then the one with the most files, then by `(module, path)`, until at most 4,000 notes are left, and warns how many folders it collapsed and into how many notes (and when none are left to collapse and it is still over). A collapsed note is titled for its folder (`Module/folder/`, `Module/` for the module's own files, claimed with the files' titles), says its file and line counts and lists each file with what it declares (at most four names, cut to 60 characters, 300 files and then `+N more files`), has the folder's path as its `source`, sits in the frame of its first file that has one, and takes its files' edges: those inside the folder are dropped, the rest merged by pair of ends with their weights added up to the cap of 4. Under 4,000 files nothing changes. That bounds the digest, not a board: a board with a frame of more than 150 shapes is laid out once and not searched ([digest](digest.md), Crowded boards), and the default lens makes one of a folder of hundreds of files.
- **Swift's index** (`scanners/swift_index_build.py`, `swift_index_read.py`): which file uses which comes from the compiler's index, which the ingestion makes itself, since nothing here builds with one: every module of `Package.swift` type-checked with debug flags (`-D DEBUG`, as test.sh builds, so a test's use of a DEBUG-only hook resolves), its interface first for the modules that import it (function bodies skipped, as build.sh's interface job skips them), then its index, in a store of its own (`<cache>/index/store/<Module>`). A module is one whole-module compile (`-wmo`): left to split a module among the cores, the compiler checks much of it once a part, three times the work for the same index. **Only what changed is made again.** An interface and an index are each kept with a mark, a hash of what they were made from (`made_from`: the compiler's version, the command, the module's sources by their bytes, and the interfaces of the modules it depends on, directly or through another, by theirs), and a compile runs only when that isn't what is there now. An interface keeps its bytes through an edit inside a function or a line added above one, so such an edit makes its module again and no other; an edit to what a module declares (a private declaration too) makes every module that depends on it again. **What is kept is always whole, and always what its mark says** (`make`): a compile writes to a folder of the run's own (`index/part`), which takes the kept one's place (`mods/<Module>`, `store/<Module>`) only after a compile that worked, its mark already in it, from sources still as they were when it began (else the run fails, saying so, as build.sh does). So a compile that fails or is stopped changes nothing, a store is made anew each time (a store keeps the records of files since changed), and a compiler left running by a run that was killed writes where no run reads. **A compile reads no interface its mark doesn't cover**: its `-I` is a folder for each module `Package.swift` says it depends on, directly or through another, as build.sh has it, so an import that isn't declared fails (`no such module`), and is never an index an edit to that module would leave stale. What a module since removed left (its store, its interface) is deleted when a run starts, since the reader would take it for code that is there, and one build of an index runs at a time (a lock in `index`). The SDK is chosen as build.sh chooses one, and the choice kept (`index/sdk`, for this compiler and this `SDKROOT`): asking the compiler about an SDK it rejects takes ten seconds. The reader takes one store (Xcode's, `swift build`'s) or a folder of them and reads their records in name order, so the scan is byte for byte what one store for every module gave. `ingest` says how many modules were type-checked; deleting `index` starts over.
