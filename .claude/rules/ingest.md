# canvas-ingest

The canvas-ingest skill: a git repository drawn as boards in one command, `ingest`. A scanner reads a commit's code into the scan, the repository's lens turns the scan into a graph document keyed by the code, and canvas-digest draws the document. The board is a view of the code that is made again from a commit, never kept up to date in place; the app keeps the drawing's record by its name, so drawing again updates it by key. Nothing is written by hand for a codebase, and nothing is written into the repository but what it keeps for itself: the settings (`.canvas/ingest.json`) and its lens (`.canvas/lens.py`); what a run keeps is in a cache outside it. One fixed picture fits no team, so each repository owns its lens, and a lens must stay deterministic: the same commit, lens, app and macOS draw the same boards.

Related: [digest](digest.md) (the skill that measures, lays out and draws what `ingest` makes: `digest all`, and the graph document's format), [command line](command-line.md) (`canvas`, which the driver runs), [build](build.md) (the audit knows nothing of the skill) ([every topic](../../CLAUDE.md#map)).

## Architecture

- **Vocabulary.** The scan (`scan.json`, what a scanner writes: `reference/scan.md` has its format), a scanner (`scanners/`: Swift's three scripts, and SCIP's), the lens (`<repo>/.canvas/lens.py`, a function `digest(scan, repo)` returning the graph document as a dict; without one, the default lens), lenskit (`lenskit/`, the library every lens imports), the runner (`runner/`, which runs a lens twice, isolated), the settings (`<repo>/.canvas/ingest.json`), the checkout (`<cache>/checkout`, the commit's code, where the scanners run). The skill folder is `.claude/skills/canvas-ingest`: `ingest` (POSIX sh), `settings.py`, `SKILL.md` (Agent Skills: `name` is the folder's, the `description` at most 1,024 characters), `reference/scan.md` (the options, the settings, the cache, the scanners, the scan's format, the default lens's document), `reference/lens.md` (writing a lens), `examples/bookshelf` and `examples/orders` (the worked examples), `scanners/`, `lenskit/`, `runner/`. All Python is `/usr/bin/python3` (3.9: no `match`, no `X | Y` types, no tomllib), which `ingest` runs by that path.
- **`ingest [REPO]`** draws the git repository you run it in (or `REPO`, whose top level it finds), not the one the skill lives in. It finds the digest driver beside its own folder (`<its folder>/../canvas-digest/digest`, links followed, so a skill folder linked into `~/.claude/skills` finds its neighbour next to the real one) and leaves how the driver finds `canvas` to the driver (`$CANVAS_CLI`, else the one beside the skills, else the PATH; run from a worktree of this repository, the beside-the-skills one is the worktree's own build, an app that is not the one running, so point `CANVAS_CLI` at the main checkout's `canvas`, the app that is: the user's shell runs there, [build](build.md)). This repository's `mise run ingest` ([build](build.md), The tasks) runs the main checkout's `ingest` on the main checkout, as it is, from any checkout; a worktree's own lens or `ingest` is drawn by running that worktree's `ingest` with `CANVAS_CLI` so. Order: the options, the repository and its cache (`--where` prints the cache's folder and stops), a `spec.py` refused, the settings, the commit (resolved once to a sha, below), the lock, what to scan with (refused before the app is asked anything), the scan (the commit's, kept or made; what a partial clone lacks of the commit fetched first, below), the graph document (`runner/run.py`), then `digest all GRAPH --out <run>/out [--on NAME] [--view WxH]`. `ingest` asks the app nothing itself: an app that isn't running is said by `digest all` once the document is made (the scan is kept, so the next run costs the lens and the drawing only). It keeps no drawing record and has no take-back: the app keeps the record by the drawing's name (the settings' `drawing`, `--drawing`, else the lens's, else the repository's folder name, the same from every worktree), and `canvas apply` updates the drawing by key ([digest](digest.md)). Options: `--commit REF`, `--board ID` (the file, as `canvas boards` names it, handed to the driver; left out, the file in front), `--on NAME` (the board: a subboard's title, path or `#id`; left out, the root of the file, or where the file's drawing of that name was drawn), `--drawing NAME`, `--mess`, `--ranks` (both written by the runner into the document's top-level `layout`, over the lens's), `--window WxH` (the driver's `--view`), `--scip INDEX`, `--scan FILE`, `--rescan`, `--where`. `--new-file`, `--replace` and `--records` are gone with the drawing records: a new file is `canvas new PATH` first (its `id` then `--board`'s), a proposal a second drawing name. `--scan FILE` draws from a scan given by hand, which tests and checked-in examples use.
- **The settings** (`settings.py`, which prints shell assignments for `eval`; sh never parses JSON): `scanner` (`swift` or `scip`), `scip` (the command that writes the index, run at the checkout's root with the indexer's version pinned, `{index}` the path to write, `<cache>/index/index.scip`, written bare: it is replaced by a shell-quoted path, so quotes around it would be part of the name), `prepare` (run in the checkout when a lockfile of the commit, or the command, has changed), `window` (`[width, height]`, each from 1 to 1,000,000, the driver's `--view WxH`; absent, the window's size at run time), `mess` (0 to 1), `ranks` (`rows` or `columns`), `drawing` (the drawing's name). An unknown key is a warning on standard error and a bad value (a number that is infinite or NaN, as `1e400` is to a JSON reader, among them) is refused naming its key, before anything is asked of the app. `settings.py` is a program and no module (its `main()` runs only as `__main__`). An option on the command line beats its setting. With no `scanner`, a repository with a `Package.swift` scans as Swift; any other is refused, saying what to write. `--scip INDEX` still takes an index made by hand. A `<repo>/.canvas/spec.py` is **refused**, before anything else is asked, with the way on: its names go into `lens.py` as the lower-case arguments of `lenskit.default.digest` (below). The settings and the lens are read from the folder `ingest` is run in, the working tree, never from the commit drawn (so a commit from before the settings existed draws too). This repository's `.canvas/ingest.json` is `{"scanner": "swift", "window": [1322, 893], "ranks": "rows"}`, so every run lays its boards out for that room and its bands as rows, and its `lens.py` lays the root out as `Package.swift` does the module graph (the rungs stacked from product to core, the platform rung in a frame for each heading over its modules, the core rung in two rows, its libraries above its private modules; scan.md says so), types every file's note File (its `path` and `lines` as values, its words the doc and what it declares, `file_text(.., length=False)`; no `$color`, so files keep a note's yellow), and draws the plugin system in types: every plugin (the core among them), extension point, kind and added property a note of its type (Plugin, Extension point, Kind, Property, each with a `$color`) in a frame `Plugin system` on the board that holds the note of the file it is declared in, and arrows of four relationship types (a plugin declares the points it owns, the kinds it defines and the properties it adds, a plugin fills a point, a kind holds a property, and each thing is `declared in` its file, an arrow to that file's note, which a File gets a row `defines` for: before it, the frame of things on a module's board had no line to its files), with the types, File's among them, in a frame `Code types` at the bottom of the root (rules files-are-typed and things-in-their-files, round 5). Its things are keyed `plugin:<id>`, `extension-point:<Name>`, `kind:<kind>`, `property:<key>` and titled by their names (a plugin's type, a point's name), its types `type:<Title>`, its frames `frame:Code types`, `frame:Plugin system:<card key>` and `group:<heading>`, and a thing's board is found by following its file's note (`file:<path>`, else the `files:` note of a folder drawn as one) up to the card. Who declares, fills and holds what is the registry report in `docs/plugin-system.md` (ShippedTests holds it to the registry), each line placed on the point whose `summary` words fit it best (or the core's words for its own points, in `Registry.swift`'s `RawContribution`); what a thing is (a plugin's id, a point's owner, keys and scope, a kind's props, definition and capabilities, a property's type, each one's doc comment) is the Swift declarations, read through `repo`. A line, a kind or a property it can't place is warned (`lens:`), never guessed. A change to how a point words its contributions, to the report's lead line, or to how plugins, points, kinds and properties are declared reaches this lens: run it (`ingest`, or the lens by hand with `lenskit`'s `Scan` and `Repo`) and read its warnings.
- **The cache**, outside the repository, one per repository, shared by its worktrees: `${CANVAS_INGEST_CACHE:-$HOME/Library/Caches/InfiniteCanvas/ingest}/<name>-<hash>`, `<hash>` the first 12 hex digits of the sha256 of the resolved absolute path of `git rev-parse --git-common-dir` and `<name>` the basename of that directory's parent. It holds `checkout/` and `checkout.prepared` (below), `scans/` (the scans by the commit's code and scanner, below; each is written as `<name>.json.reading` and moved into place when whole, so a scan that stops part way never leaves one with its files and none of their uses), `index/` (Swift's index; SCIP's `index.scip`), `runs/<run>/` (`graph.json` and the driver's `out/`; the last five are kept) and `lock`. The `PROJECT` variable is gone.
- **Whose code runs.** A repository's `prepare` and `scip` commands and its `.canvas/lens.py` are that repository's own code, run as its build would be, and not sandboxed: `prepare` and `scip` with the user's environment (each in a shell of its own at the checkout's root, none of `ingest`'s variables in it), the lens with a cleared one (below). It is the repository's trust, not `ingest`'s: an agent shows the user these commands (the settings' `prepare` and `scip`, the lens) before the first run on a repository the user didn't set up.
- **One ingest a repository at a time.** `ingest` takes `<cache>/lock` with `mkdir`, writing its pid in it, holds it for the whole run, and frees it on any exit (a trap on `EXIT`, with `INT`, `TERM` and `HUP` turned into exits). A second run refuses at once, naming the holder's pid; a lock whose pid is gone is taken over: the stale lock is moved aside whole, so of two runs that find it stale one moves it, and what was moved is looked at (if its pid isn't the stale holder's, another run had already taken the lock over and made its own: it is put back, and the lock is looked at again; if it can't be put back, the run refuses, saying so). A pid that another process has since been given reads as a live holder, and is not told apart (that would cost a process's start time): the lock is refused until that process ends or the folder is removed by hand. **A signal is acted on at once**: every long command (`prepare`, the `scip` command, the scanners, the runner, the driver) is run by `run`, in the background and waited for, since the shell holds a trapped signal until a foreground command has ended (a 40 s `prepare` held the lock 40 s past a `TERM`); on exit the command and the processes under it are sent `TERM`, and `KILL` three seconds on, before the lock is freed. A background command ignores `^C` in a shell with no job control, so this is `ingest`'s doing and no signal's.
- **The commit** is `--commit REF` (default `HEAD`), resolved once, before anything slow, by `git rev-parse --verify REF^{commit}` to a sha that every step after it names (a branch moving or a working tree changing while it runs changes nothing); a REF that is no commit is refused, with nothing asked of the app (in a shallow clone, saying it is one, whose older commits `git fetch --unshallow` fetches). The code drawn is that commit's, always: the scanners read the checkout, and the lens reads it through `repo` (`run.py --commit SHA`), never the working tree, so an uncommitted edit is never drawn. The repository `run.py` is handed is the one you run in (its objects hold the commit); the lens file is the working tree's (`.canvas/lens.py`), committed or not, so a round of art direction needs no commit and the agent leaves the lens and settings uncommitted until the user is happy and says to commit them (it never commits in a user's repository unasked: SKILL.md).
- **One checkout a repository** (`<cache>/checkout`), moved to each commit: a fresh `git archive` for each commit would have the compiler type-check every module again (the index's marks hold the sources' absolute paths) and reinstall a TypeScript project's packages every time. It is made once by `git clone --shared --no-checkout` from the repository's git directory, so it borrows the repository's objects through `objects/info/alternates` (every commit of the repository is there with no fetch). For each scan `checkout --force --detach <sha>` then `clean -ffd` (no `-x`: what git ignores, `node_modules`, `.build`, stays; what git doesn't know goes, so what `prepare` makes should be ignored). Never `git worktree add`, which would show in the user's `git worktree list`. Its git is always run as `git -C <checkout> --git-dir=.git` (a cache inside some other repository is never taken for the checkout, or its work tree), with `core.hooksPath` off and LFS's filters empty (the pointer files are what the commit holds, as `repo` reads them). **It heals**: a checkout whose move fails (the source pruned an object the checkout borrowed, a git directory gone or damaged) is deleted, with the stamp beside it, and cloned again, saying so on standard error (`the checkout in the cache is broken (<git's first line>); making it again`); a move that still fails after that is the run's failure, naming git's first line and how many more it said (`first_line`: a checkout that fails says a line a file). A checkout made again has no `node_modules`, so `prepare` runs again. **Submodules are not checked out**: their paths are empty folders, and the lens's `repo` sees no file in them. The scan's `name` is the repository's, never the checkout's: the Swift scanner takes it from `Package.swift` and otherwise, as `scip_read.py` does, from `--name`, which `ingest` passes as the cache's `<name>` (the folder that holds the git directory, the same from every worktree). Swift's index stays in `<cache>/index`, built from the checkout, whose path doesn't change between commits, so the second commit type-checks only what changed.
- **A partial clone** (`git clone --filter=blob:none`, or `tree:0`: a remote with `promisor = true`, or `extensions.partialClone`) has only some of its commits' files and folders, and git fetches the rest from that remote when they are wanted. The checkout borrows the repository's objects but not its remotes, and the lens reads the commit with a cleared environment (no credentials: a lazy fetch there would fail, or wait on a prompt), so `ingest` fetches what the commit lacks (`fetch_missing`) before the checkout moves to scan it and before a lens of the repository's own runs, which reads the commit through `repo` (the default lens reads only the scan, so a kept scan drawn with it fetches nothing; the scan's key reads the commit's top-level tree first, which git fetches itself in a treeless clone): `git rev-list --objects --missing=print --no-walk <sha>` lists it, and it is fetched as git's own lazy fetch fetches, `fetch <remote> --no-tags --no-write-fetch-head --recurse-submodules=no --filter=blob:none --stdin` (with `fetch.negotiationAlgorithm=noop`), into the repository, with the user's environment; a level a request (a treeless clone's folders, then their files), at most three, after which what is still missing is the run's failure, as a fetch that fails is (git's words above it). A commit the clone has whole (one checked out) fetches nothing.
- **`prepare`** (the setting) runs in the checkout, once it is at the commit and a scan is to be made, when a hash differs from the one in `<cache>/checkout.prepared`: the hash of the commit's lockfiles (`package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `Package.resolved`, `Gemfile.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `Cargo.lock`, `go.sum`, `composer.lock`, `gradle.lockfile` and `requirements*.txt`, at any depth: their paths and blob ids from `git ls-tree -r -z`, read by `runner/lockfiles.py`, so no path is quoted and skipped) and the command itself. What it prints goes to `<run>/prepare.log`, and only a failure says it (its last 40 lines, then the log's path: `quietly`), since an install prints a line a package (a yarn install, ten thousand) that would bury `ingest`'s own lines and fill an agent's reading of the run; the `scip` command's likewise, to `<run>/scip.log`. The stamp is written only after the command succeeded (it is removed first), so a failing one stops the run and is tried again by the next, and it goes with a checkout that is made again. A move to a commit that changes none of them leaves what the command installed as it was.
- **Scans are kept by the commit's code and the scanner**: `<cache>/scans/<code>-<scanner>-<12 hex>.json`, `<code>` 40 hex digits of the sha256 of the lines of `git ls-tree <sha>` (the commit's top-level tree) but the `.canvas` entry (`code_key` in `ingest`), `<scanner>` `swift` or `scip` (also for `--scip INDEX`), and the 12 hex digits a hash of what made it: the scanner's own files (Swift's: the three scripts and `reading.py`; SCIP's: `scip_read.py`, `scip.py`, `reading.py`) and, for SCIP, the `scip` command (or the index given by hand, by its bytes). **Why not the commit**: SKILL.md has an agent leave the lens in the working tree until the user is happy and then offer to commit it, and a commit that changes only `.canvas/` moves HEAD; keyed by the commit, every round of art direction would have rescanned (`npm ci` and indexing, minutes each). Commits that differ only in `.canvas/` share a scan; any other change (a lockfile among them, and a `.canvas` below the top level) is another, and a scanner reads nothing from the top-level `.canvas`, since a target of the code never lives in it. The `scip` command's index is removed before it runs, and a command that writes none is refused (an index left by the commit before is never read as this one's). A later run on code with a scan of that key goes straight to the lens and says so (`the scan of <sha> is kept, so nothing is scanned`), moving no checkout and running no `prepare`; `--rescan` scans it again. The scan holds nothing of the commit (its `name` is the repository's). The last 20 scans are kept (by modification time; a run that uses one touches it), the rest are removed. `--scan FILE` draws from a scan given by hand and touches none of this: no checkout, no `prepare`, no scanner, no kept scan, and not with `--scip` or `--rescan`.
- **The same boards.** A lens must stay deterministic (below), and nothing else varies: the same commit, lens, app and macOS give the same plan (`plan.json`) and the same apply document, the same commit drawn twice, whatever the working tree holds, a lens committed or not. No board says which commit it shows (the line that once ended the first board's About note, `runner/stamp.py`, went with the note on 2026-10-22); a run's folder in the cache has its `graph.json`, and the scan its commit's code.
- **The codebase ingestion** is what the scanners, the lens and the driver make together; the board is what the code says. The scanner reads the code into the scan (Swift's three scripts, or `scip_read.py` with the `scip` scanner or `--scip`, on the checkout; the scan is kept by the commit's code, above; Swift's index is kept from run to run, below; an indexer reads only the files its projects take in, so `scip_read.py` says, after its counts, how many of the commit's files of the kinds the index read (an ending five of its files have, or half the commit's files with it: one `.js` config a project takes in doesn't make every script a source), tests aside, the index lacks, and the three folders most of them are in: `not_indexed`, from the checkout's `git ls-files`; and, since an import of a workspace package whose `package.json` names built files nothing built resolves to nothing, when of the dependencies the modules' own `package.json` files (the nearest at or above a module's folder, whose `name` is the module's) declare on each other, three or more, under a fifth show up as uses: `unconnected`, which says the two ways out (scan.md's Workspaces that resolve through built files); both lines start `scan:`); a target whose line in `Package.swift` ends `+ shipped`, the product and the tests of it ([build](build.md), What ships), is read two ways (`parse_package`): `deps`, what the line writes, is what the scan keeps and the board draws arrows from, so the app's card has no arrow to every plugin, and `links`, those and the modules of the plugins that ship, is what a compile of it reads, so its tests, which import plugins their line doesn't name, still type-check; a scanner also writes `name`, what the code calls itself (a lens may use it; the drawing's name is the repository's, not the scan's). **The Swift scanner is this repository's**: it relies on `// layer:` tags, `let ships` and `+ shipped`, and its own index build (`reference/scan.md` says so). The default lens (`lenskit/default.py`) makes the graph document: bands as ranked frames (`layout.rank`), by the modules' layer tags ordered by how deep their imports go, else by import depth; modules, and the folders of a module of over 50 files, as subboards whose `description` is what the module is and how big, and a folder's its module and the other folders it uses, as mentions of their cards by key (the card's panel shows it, and the board has no About note; a module's imports are its arrows and never mentions, which would crowd the card's mentions, a ⌃⌥ hover's, with what its arrows show); a board's folders as frames; files as notes, plain (the default lens types nothing: a lens that types its files, as setup usually recommends, does it on `default.build`'s nodes, `reference/lens.md`'s Files as a type); imports and uses as edges, weighted by the names used up to 4 (`layout.weight`). Then `digest all <run>/graph.json --out <run>/out`, with `--on` and `--view` when set. A note's `@[` is written `\@[` (a run of backslashes before it doubled), so a doc that shows a mention reads as text, and a mention of a node escapes `]` and `\` in its key (`lenskit.text.mention`). **Every node is keyed by the code and titled by what the code calls it.** The key is the same from commit to commit, which is how the app keeps the drawing: `module:<name>` (a folder board's `module:<module>/<folder>`), `dir:<path>` for a folder's frame, `file:<path>`, `files:<path>` for a folder drawn as one note, `band:<title>`; a lens of its own adds `table:<name>`, `workflow:<path>#<name>`, `type:<Title>` and so on. A title is `props["title"]` and nothing makes it unique: two `index.ts` are two notes both titled `index.ts` and two boards each have a frame `src`, and the lens renames, numbers and clips nothing (no `claim`, no ids, no naming report; those went with the app's own record of the drawing). A key two things come to gets `#2` after it (`_Build.free`); a name with half a character in it, a file's that isn't UTF-8, is given U+FFFD in a title and a key (`lenskit.text.whole`); a folder whose board would be named as a module is gets no board of its own (`derive.complete`). The builder (`lenskit.Graph`) holds no rule about kinds, attributes or titles and passes every field through; it refuses a duplicate key, an `in` or an end that names no node and an `in` in a circle, which are structure. What a kind takes is the app's to say (`digest check` and `canvas apply` ask it), and `layout` (`rank`, `pill`, `direct`, `weight`) is the render layer's hints, never placement. No node carries a `source`: the key says what it was made from.
- **The lens** is `<repo>/.canvas/lens.py` **in the checkout you run in, never read from the commit**: a function `digest(scan, repo)` returning the graph document as a dict (`{drawing?, layout?, nodes, edges}`; a `warnings` list, if it has one, is said on standard error and taken off), or, with no such file, `lenskit.default.digest(scan, repo)`. An agent writes it for a team over rounds of feedback (SKILL.md, below; the guide is `reference/lens.md`). `scan` is a `lenskit.Scan`, `repo` a `lenskit.Repo`; the file may import `lenskit` and anything beside itself. Runs must be deterministic, so `ingest` runs it through `runner/run.py` **twice** (`REPO SCAN GRAPH [--lens FILE] [--commit SHA] [--drawing NAME] [--drawing-default NAME] [--mess N] [--ranks WAY]`, the sha `ingest` resolved), concurrently: each run is `env -i` with only `PATH=/usr/bin:/bin`, `HOME` (a fresh empty folder, a different one each run), `TZ=UTC`, `LC_ALL=C`, `PYTHONHASHSEED` (1, then 2) and `PYTHONDONTWRITEBYTECODE=1`, started in a fresh empty folder as the current folder, as `/usr/bin/python3 -s -B runner/child.py` (not `-I` or `-E`, which drop `PYTHONHASHSEED`). `child.py` makes the clock read a different instant in each run (`time.time`, `time.time_ns`, `localtime`, `gmtime`, `ctime`, `asctime` and `strftime` without a time, `clock_gettime` of the real-time clock, `datetime`'s `now`, `utcnow` and `today`, `date.today`: 2001 in run 1, 2020 in run 2, moving on as a clock does; `datetime.date` and `datetime.datetime` are subclasses with a metaclass that answers `isinstance` and `issubclass` as the real classes do, so `isinstance(datetime.now(), datetime.date)` holds and a `default=` hook that asks it is called). What a lens can import is `lenskit` (loaded from the skill's folder, which is not on `sys.path`, and `runner/` is taken off it) and what sits beside the lens, in the folder first on the path: a helper named `settings.py` is the lens's own, and the skill's `settings`, `run` and `child` are not importable by name. It loads the lens, runs it, checks the document's structure (a dict, `nodes` and `edges` lists, every node a non-empty string `key` no other has, every `in` and edge end a node's key, `warnings` a list of strings, everything JSON can hold) and writes the document as `json.dumps(indent=1)` in the lens's own order. `run.py` compares the two as text: a difference is refused, naming the first node or edge that differs (its number and both) and the usual causes (a set of strings, the clock, the environment or current folder, a file read outside `repo`); a lens that raises stops the run with its traceback (the child's own, naming the lens file), before `digest all`, and no `graph.json` is left; a run over 900 seconds is stopped. On success `graph.json` is the first run's, without its warnings (the first 20 said as `lens: ...`, all of them in `lens-warnings.txt` beside it when there are more, `SAID`; then a summary line with the node counts by kind and the processes' CPU time), and with the runner's two additions made after the comparison: the drawing's name (`--drawing`, the settings' or the option's, else the lens's, else `--drawing-default`, the repository's) and `--mess` and `--ranks` in the top-level `layout`, over the lens's. **lenskit** (`lenskit/`, no module-level state; `/usr/bin/python3` 3.9): `Scan` (`scan.modules` by name, test modules too; `scan.production`, the drawn modules' names, whose `deps` are among them; `scan.files` by `(module, path)`, production modules' only; `scan.uses` `(from, to, names)`, once a pair; `module()`, `file()`, `Scan.load`), `Repo(root, commit="HEAD")` (below; the folder is kept private, `_root`, so a lens isn't invited to read the working tree), `Graph` (`node(key, kind, props=None, *, in_=None, layout=None, **more)` for any kind, `edge(source, target, props=None, *, key=None, layout=None, **more)` between nodes or keys, `get(key)`, `warn`, `finish()`, which checks the structure and gathers the warnings into the document;
