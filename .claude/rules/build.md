# Building, the module graph and the audit

How `build.sh` builds and runs, and which app a build is to macOS (a worktree's is a copy of the app, an app of its own); what `Package.swift` declares, the layers and what each may import; what ships and how the product is made of it; the parts a large module is split into and how the build holds them apart; and what the audit refuses.

Related: [benchmarks](benchmarks.md), [testing](testing.md), [plugins and kinds](plugins-and-kinds.md), [host slots](host-slots.md), [Quick Look](quick-look.md), [types](types.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [The module graph](../../docs/plugin-system.md#the-module-graph), [Horizontal and vertical](../../docs/plugin-system.md#horizontal-and-vertical).

## Building

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`, as many at once as there are cores (`BUILD_JOBS=N`), each once its dependencies are built, and only when what it's built from changed: its sources, its command, its dependencies' `.swiftmodule`s. A module's `.swiftmodule` is a job of its own (function bodies skipped, as in the job swiftc splits off itself), so what imports it starts compiling long before its code is done, and in release other modules can't inline its functions whatever cross-module optimization makes of them (nothing is `@inlinable`, and the benchmarks measured no difference). A module's code compiles to an object per source at fixed paths (`-num-threads 4`, through an output file map), so the same inputs make the same bytes, and what comes out the same isn't replaced: an edit inside a function recompiles only its module and links the executables again, and a touch or a checkout that changes nothing links nothing. In debug an executable's object job emits its module too, which its link hands the debugger (`-add_ast_path`), as a one-step `swiftc -g` does. A build fails, saying so, if a module's sources change while it builds (an interface and an object from different edits would link). Builds of one configuration wait for each other (`build/.debug.lock`), and however build.sh or test.sh ends (^C, a TERM), what it started stops with it. The app bundle's files change only when they do: macOS checks each new executable the first time it runs (about 0.3 s each, one at a time). The app carries its command line, `canvas` (`Contents/Helpers/canvas`; `build/canvas` links to it): with the app open, `build/canvas help`. It carries the skills for agents too (`Contents/Resources/agents`, below). It carries its Quick Look extensions too (`Contents/PlugIns`: `QuickLookPreview.appex` and `QuickLookThumbnail.appex`, both the executable the app carries, linked to start in `NSExtensionMain`, each with an Info.plist `build.sh` writes and signed ad hoc with the sandbox entitlement Quick Look requires, in a copy, so what didn't change isn't replaced; [Quick Look](quick-look.md)). A build that changed the bundle, and a checkout's first, also unregisters the copies of the app whose folders are gone (a removed worktree's build stays registered with macOS, and when Quick Look is handed that one's extensions, a board file shows as JSON), and its own bundle where macOS has it as another app (below), which takes a second; a build that changed nothing skips it.
- **The skills for agents** (`Contents/Resources/agents`), put together by `./build.sh agents DIR` (a mode of its own, which the app build calls, so a test runs it without building the app; it compiles and audits nothing, and empties DIR first only if DIR is an agents folder this build made, the `infinite-canvas` marketplace with a `build-id` at its root, refusing any other folder with files in it, someone's own marketplace checkout included; an empty DIR and `/` are refused). The folder is a Claude Code plugin marketplace: `.claude-plugin/marketplace.json` (name `infinite-canvas`, an owner, one plugin, `canvas`, at `./canvas`), `canvas/.claude-plugin/plugin.json` (it and the marketplace's entry say the build id as `version`: Claude Code may keep a versioned cache of a plugin, so each build must be another version), and `canvas/skills/<skill>/` for each skill in `AGENT_SKILLS` (build.sh, near its top: `canvas`, `canvas-digest` and `canvas-ingest`; a listed skill whose `.claude/skills/<name>/SKILL.md` is missing stops the build, saying which). Each is a copy of its folder in `.claude/skills` without the paths in `AGENT_SKILL_LEFT_OUT` (canvas-digest's `tool/test`), without dotfiles and Python's caches (`tool/vendor` stays, and so does `canvas-ingest/examples/*/.canvas`, one folder under an example and no deeper: an example repository keeps its settings and lens there as every repository does, [ingest](ingest.md); a `.canvas` anywhere else in the skills goes with the other dotfiles, AgentsTests' "keeps a .canvas folder only in canvas-ingest's examples"), plus a `build-id` file. Claude Code names the plugin's skills `canvas:canvas`, `canvas:canvas-digest`, so they never hide a project's own skill of the same name (it ranks personal skills above project skills, and this repository has skills of these names); whether Claude Code reads a plugin of a local marketplace in place or from a versioned cache of its own is not established (its binary mentions the cache), so `canvas install` refreshes the marketplace and updates the plugin on every run ([command line](command-line.md)). `canvas install` ([command line](command-line.md)) copies the same skills into `~/.agents/skills`, where agents that follow the Agent Skills standard (agentskills.io) look. The skills say `canvas`, never `build/canvas` (but for the one sentence in the canvas skill that says where `canvas` is), true in the bundle and in this repository; SkillTests (`every skill the app carries …`) hold each shipped skill to the standard (the frontmatter `name` is its folder's, at most 64 letters, digits and hyphens; the description at most 1,024 characters; SKILL.md under 500 lines) and AgentsTests (CanvasCLITests) hold the folder.
- **The build id** (`build_id` in build.sh): the git commit (12 characters), and, if the tree has changes, `-dirty-` and 8 characters of a hash of `git status` and `git diff HEAD` (`unknown` with no git); the hash covers the files git doesn't track and doesn't ignore by their contents too (`git ls-files -o --exclude-standard`), and git runs with `--no-optional-locks`. The app carries it as `InfiniteCanvasBuild` in its Info.plist (`canvas status` and `describe` say it: [command line](command-line.md)), the agents folder as `build-id` at its root and in each skill, and a copy `canvas install` makes keeps it in its marker. The build's last line says it.
- **Which app a build is.** A checkout's build is the app: `com.example.InfiniteCanvas`, "Infinite Canvas", which owns board files (`LSHandlerRank` `Owner`) and exports their type. A linked git worktree's build (its `git rev-parse --git-dir` isn't its `--git-common-dir`) is a copy of the app, an app of its own to macOS: `com.example.InfiniteCanvas.worktree.<name>`, "Infinite Canvas (<name>)", the name what git calls the worktree (its folder in the repository's `worktrees`, which no two share; what an identifier can't hold becomes a hyphen), with board files claimed as an `Alternate`: it opens them (`open -a <worktree>/build/InfiniteCanvas.app <file>`, Open With, a drag onto it), and a double-click, or `open <file>`, opens the app. The build's last line says which it built. A clone is no copy, nor is a folder with no git: either builds the app (macOS offers no app under `/private/tmp`, for a file or by its identifier, so a clone in a scratchpad doesn't compete; one elsewhere would).
  - Why: every checkout's build was the one app once, and of several registered under one identifier macOS opens whichever it picks, by no rule that was found (`osascript -e 'POSIX path of (path to application id "com.example.InfiniteCanvas")'` says which): board files opened in an old build in some worktree. Having each build unregister the others was turned down: opening a copy registers it again.
  - What macOS does with the two, traced with bundles in a namespace of their own (nothing documents it): of an owner and an alternate that have each been opened, the owner opens the file, whichever was opened or registered last and whether the alternate imports or exports the type; an app only registered (`lsregister -f`) and never opened loses to one that was opened, whatever their ranks, so with the app unregistered or never opened a copy opens board files. `NSWorkspace.shared.urlForApplication(toOpen:)` answers without opening anything.
  - The same in every copy: the types' identifiers, which the sources spell (the board's, the pasteboard's, the mention text's, the table of contents' rows'), so files, the pasteboard and drags pass between copies. The app exports the two it declares; a copy imports the board's (`UTImportedTypeDeclarations`), so the app's declaration is the one macOS goes by, and exports the rows' as the app does: the sources make it with `UTType(exportedAs:)`, which in an app that only imports it logs `Type … was expected to be exported in the Info.plist …, but it was imported instead` at each launch (the type works all the same). And what's kept by path, not by identifier: the Anthropic key ([language models](language-models.md)), which a copy reads and Settings in any copy writes, and the command line's socket ([command line](command-line.md)): `canvas` reaches whichever app took the socket first, the app's or a copy's, as it did (a second app gives up; `CANVAS_SOCKET`, a path of at most 103 bytes, gives one its own).
  - A copy's own, by its identifier: its preferences (`UserDefaults.standard`: the view memory, the spelling settings, and AppKit's, window frames and Open Recent among them), so a worktree's build starts with none of the app's; its Quick Look extensions' identifiers and their containers ([Quick Look](quick-look.md)). `~/Library/Preferences/<identifier>.plist` and the containers stay when the worktree is removed. The app's menu says the bundle's name (`CFBundleName`, which `canvas status` says too); the Finder calls every copy InfiniteCanvas, its file's name.
  - A worktree's build from before this, registered as the app, is still picked from until it's rebuilt with this or unregistered. A build that finds its own bundle registered under another identifier unregisters it (`forget_copies_gone`; until a rebuilt bundle is opened macOS keeps what it registered), and opening it registers what it is. By hand: `lsregister -u <worktree>/build/InfiniteCanvas.app`.

## The module graph and the audit

- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the rungs and what each may use (core, platform, product and app, below in Layers; and testsupport and test, which say what kind of target a line is): the app uses the core and its own modules (the window, CanvasUI) and names no plugin, and so does an executable the app carries, an app extension macOS runs on its own (`// layer: app of InfiniteCanvas`: CanvasQuickLook, Quick Look's). Before the targets is the table of what ships (below, What ships), and a line may end `+ shipped`. A test target named after a module, `<M>Tests`, may use only M, what M uses, testsupport modules and the window, and so may one named after a plugin of M that says so, `// layer: test of M` (ArrowPortsTests, of Arrows; TitleQueriesTests, of Titles); an `of` on any layer but test and app is refused, and an app's names the app itself, `// layer: app of InfiniteCanvas`. Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. What it reads of each module is kept in `build/audit` and read again only for a module that changed, and a pass is kept by every input's name, size and mtime, so auditing what already passed costs one stat. It fails on a cycle or a forbidden layer edge, or on the wire importing anything or the command line anything but the wire (by name: `WIRE_MODULE`, `CLI_MODULE`); on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies (what `+ shipped` adds to a line is linked, not imported: the app and its extension may import none of it, the tests of what ships and their support whichever they call); on a line of what ships that isn't a public struct of that module that is a `ListedPlugin`, or that ships twice, or whose module isn't platform or product; on a product that declares no `ShapeKind` (read from its non-test sources); on `+ shipped` anywhere but the app, its extension, a test or a test-support module, or missing from what depends on a library that says it; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` or `Span` (either would shadow Swift's in every importer: a query's place in its text is a `QuerySpan`); and on a module writing another module's `ShapeKind`, `PluginID`, `ToolID`, `PropertyKey`, `ChannelID` (Connections') or `EdgeTypeID` (Topology's) string without depending on it (a string two modules declare is both's, so an id that must equal another module's is made from that module's constant, as a channel's edge type from the channel's `id`; a name in a property list, `Property("…")`, is exempt, and so is a JSON member named by a JSON Schema keyword, a subscript's key, `json["title"]`, or a key before a colon where a member's name starts, but not in a `case`'s patterns or `where` or a ternary, even across lines: the `title` keyword is also Titles' property key; any other member's name, `json["locked"]`, counts; `frame`, the core's own member every box has, which Frames' kind is spelled as, and `schema`, a board's own member that once listed its kinds' versions (and `canvas kinds --schema`'s answer), which Types' property is spelled as, and `is`, an English word every message uses, which Types' property is spelled as, and `color`, a word any test's or message's data may hold (a field called color), which Colors' property is spelled as, are ordinary words that no module owns, `ORDINARY_IDS`). The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool, plugin, property, channel or edge type id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the window (CanvasUI), testsupport and test modules may import it; loading the list of what ships whole is `@_spi(Product)`, and only the app and its extension may.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph: each line's own dependencies (` + shipped` said, never spelled out), and `graph` prints the list of what ships after the modules, since what ships is membership in the product, not a module depending on another.
- **The product's text files** (`Shipped/*.txt`, with a README): what the product says in a file, not in a module. `build.sh` puts each, and the list of what ships as text (`build/shipped/plugins.txt`, written from the table; no file here may be called `plugins.txt`), in every executable that is the product (`is_product`: one whose line ends `+ shipped`, so the app, CanvasQuickLook, CompositionTests and BenchmarkTests), at its link (`-sectcreate __TEXT __<name> <file>`, the section named for the file, `-` as `_`; the files are the link's inputs, so an edit links those executables again and compiles nothing), and the core reads one back by name, `ShippedText.named("ask-prompt")` (Canvas: the process's own executable's section, nil in an executable that isn't the product or for a name with no file), so nothing looks for a file at run time and no module holds the text. A file's name is lowercase letters, digits and hyphens, at most 14 characters (a section's name is at most 16), which every build.sh mode checks. Shipped: `ask-prompt.txt` and `ask-rule.txt`, which `QueryTranslationPlugin()` reads ([language models](language-models.md)).

## What ships

- **The list.** Which plugins the product is made of, in which order (the toolbar's, the order overlays draw in, and each after the plugins whose points it fills), is one table in `Package.swift`, before the targets: `let ships = [` on a line of its own, then lines of `"Module.Type",` entries (several a line), comments on lines of their own saying why each sits where it does, and `]`. It's the only list: no module imports the plugins to make it (Composition, which did, is gone). `build.sh` reads it as text, as it reads the targets (`SHIPPED_PLUGINS`, `SHIPPED_MODULES`, the modules once each in the list's order), and `Package.swift` computes `shipped`, those modules as dependencies, from the same array, which the SwiftPM check holds equal.
- **`+ shipped`.** A target line whose dependencies end `+ shipped` is the product, or the tests of it: every module the list names links into it, though nothing need import them (`SHIPS`, `LITERAL`, a line's own dependencies; `DEPS` and `CLOSURE` have both). Five say it: InfiniteCanvas and CanvasQuickLook, which import none of those modules and compile against none (`VISIBLE`: the include path, and what the id check lets a module name, are their own dependencies' closures); ShippedTesting, CompositionTests and BenchmarkTests, which import the ones they call. A line may not also list a module the list names.
- **Made by name** (Canvas, `Sources/Canvas/Plugins/ShippedList.swift`). A plugin a list can name is a `ListedPlugin`: a `CanvasPlugin` with an `init()`; every shipped plugin is one, and a plugin that takes arguments stays a `CanvasPlugin`. `ShippedList.names` is the list as the executable carries it (`ShippedText.named("plugins")`, nil in one that isn't the product), and `ShippedList.plugins(named:supplying:)` makes a list's plugins: each line's type found in the binary by its mangled name (`_typeByName("6Boards12BoardsPluginV")`, a struct's, a class's or an enum's: the standard library's, underscored, so not documented API; every library links whole, so the type is there whether or not anything names it), cast to `ListedPlugin`, and made. `ShippedListError`: `notTheProduct`, `malformed(line)`, `notFound(name)`, `notListed(name)`, `notSupplied(names)`, `notInList(names)`, each saying the line.
- **What reaches outside the process.** A listed plugin that, made from nothing, reaches the network or the user's pasteboard is an `OutwardPlugin`: `LanguageModelsPlugin()` (Claude over the network, the key from Settings) and `ClipboardPlugin()` (the system's pasteboard). `ShippedList.plugins()`, which makes them as they come, is `@_spi(Product)`: the app's and its extension's alone, by the audit. Anything else calls `ShippedList.plugins(supplying:)`, which takes the caller's plugins in the listed ones' places (matched by type, `String(reflecting:)`), refuses to load while an outward one isn't supplied (`notSupplied`), and refuses one the list hasn't (`notInList`); any listed plugin may be supplied (a translator that asks another way).
- **Tests** of what ships get the plugins from ShippedTesting (`Tests/ShippedTesting`, test support, `+ shipped`): `ShippedPlugins.plugins(pasteboard:model:)`, `registry(pasteboard:model:)` and `makeEditor(document:scheduler:pasteboard:model:)`, the list with a `ClipboardPlugin` on the test's pasteboard (the system's unless it passes one) and a `LanguageModelsPlugin` with the test's model, whose `model` has no default. So a test checks exactly what ships.
- **Shipping a plugin** is its line in the table, where its order belongs, and `public struct XPlugin: ListedPlugin` with a `public init() {}` in its module. Leaving one out is deleting its line.
- **Testing.** CanvasTests' `registryTests` hold the loader with plugins of their own, found in the test executable by name (`CanvasTests.FirstListed`): a list's order, each refusal, an outward plugin refused until it's handed over and the one handed over taken, any listed plugin swapped, and no list in an executable that isn't the product. CompositionTests' `shippedTests` hold the product's: the list in the executable, every line a plugin of that type in order, the registry it makes, and the list refusing to load without a clipboard's and a model's plugin of the caller's own.

## The parts of a module

- **What a part is.** A module too large to hold in mind is split into parts, each a folder of its directory, with the rule between them that holds between modules: a part uses only the parts its line names. They are parts and not modules by the rule at the end of Layers (nothing must build without the others, and no rung forbids an import), and because what one part shares with the next stays internal to the module: as modules, every such name would be public to every importer. Types is the one module in parts ([types](types.md), "The parts"); a module with folders and no line in the table (Canvas) has none.
- **The table** is in `Package.swift`, after what ships: `let parts: KeyValuePairs<String, [String]> = [` on a line of its own, then a line a part, `"Module/Part": ["A", "B"],`, comments on lines of their own, and `]`. `build.sh` reads it as text (`PARTED`, `PARTS`, `PART_USES`), and SwiftPM makes nothing of it. The lines are in an order the parts could be built in: a part uses only parts written above it, so there is no cycle, and names all of what those use, so a line says everything its part compiles with. Every folder directly in a module that has parts is a part; the sources beside the folders are the module's own (its plugin values, which install every part) and may use them all. Every mode refuses a table that breaks one of these, a part with no folder or no sources, and a folder that is no part.
- **The check** is the compiler's: for a module that has parts the build runs one job more, `<Module>:parts`, which type-checks each part, in the table's order, with only its own sources and those of the parts its line names (the module's flags and include path, `-typecheck`, nothing made), and stops at the first that fails, with the compiler's errors at the names it could not find and a line saying which part reached out of its own. So a part that names anything else of the module doesn't compile, as a module that names one it doesn't depend on doesn't. It needs the module's dependencies built, so it is a job of the build and of `./test.sh`, not of `./build.sh audit`; it waits for the dependencies' interfaces and nothing waits for it; and a part is checked again only when a source it compiles with, or a dependency's interface, changed (a stamp a part, `build/<config>/<Module>/.part.<Part>`). Types' nine take about seven seconds of one core in all, beside the module's own compile.
- **Changing them.** A file moved to another part, a new part, or a part given another to use is its folder and its line. When the check refuses a name, the choice is the one a forbidden import between modules gives: move the declaration down to the part both can use, have the lower part take a closure the higher one registers (as `TypeIndex.onChange` is used), or say the use on the line if the order allows it. `./build.sh graph` prints each module's parts, with what each uses, after the list of what ships.

## Layers

- **Four rungs.** Every module is on one of four rungs and imports only from its own rung or those below it, and the graph has no cycle. They replaced twelve layers (wire, foundation, ui, surface, concern, feature, language, vertical, app and cli, with the tests' two) on 2026-10-14: the owner found that many too many to hold in mind, each layer's purpose and how it differed from the next. The guide's [Horizontal and vertical](../../docs/plugin-system.md#horizontal-and-vertical) tells it with the examples.
  - **Core** (`core`): the canvas and plain libraries, which know no plugin. Canvas, the core, holds what a window puts around its canvas and what the app takes from the plugins besides, points of the core's that plugins fill and the window and the app read, since the app may import only the core and its own modules and no plugin may import the window ([host slots](host-slots.md)); for them it imports SwiftUI and the wire, CanvasRPC (what the app and its command line say to each other), whose types the commands the app's server runs are said in. Geometry beside it, and five libraries beneath the plugins that know no canvas, registry or plugin: DrawScript and QueryLanguage, the languages `canvas draw` and `canvas query` read, and draw's solver with the grid its obstacles are filed in, pure, which Draw's placement for plugins places shapes with too; TextEditing, the text view and caret list every editable text is built on; FuzzyMatching, which every list that ranks typed text, Find and Jump To are built on; and Palette, the color math ([palette](palette.md)), which the core imports too, for the one test of a dark appearance.
  - **Platform** (`platform`): what every shape gets, whatever its kind; its modules build on one another. `Package.swift` and the docs group them under headings, which nothing checks. Horizontals are the interfaces verticals plug into, something a shape shows up on in the window (Keyboard, Selection, DetailPanel, ContextMenus, SlashCommands, TableOfContents, Adornments, Find) or has as a trait (Topology, Validation, Titles, Locking, Connections, Mentions, Publishing, Boards, Transform, Colors, Types, References). Things you do are a palette, a command or a gesture that no kind opts into and nothing builds on (Clipboard, Snapping, JumpTo, Moving, Reordering). Engines are what any plugin may run or ask (LanguageModels, ProseMaps, Queries, Draw, QueryTranslation, Neighbors). And what agents speak is where their request arrives over the wire and is answered (Automation, QueryCommands). References is platform though it is a kind, the one platform module that declares a `ShapeKind`: any public shape can be stood for, a kind written after it too, and a pill holds nothing of its own, only another shape shown in a second place.
  - **Product** (`product`): the verticals, shapes that hold something of their own (a note's text, an arrow's ends and label, a frame's region, a subboard's board): Arrows, StickyNotes, Subboards and Frames. Each declares a `ShapeKind`, and nothing imports one (a test and `+ shipped` aside), so no product knows another.
  - **App** (`app`): the window around the canvas (CanvasUI: the AppKit view, the SwiftUI toolbar, the chrome around the canvas, `CanvasFocus`, the Settings window and the command line's server), the command line (CanvasCLI, `canvas`) and the product's executables (InfiniteCanvas, and CanvasQuickLook, `of` it). It imports only the core and its own modules, and the app gets its plugins from the list of what ships, never by import.
  - Test targets keep their two tags, `testsupport` and `test`, which say what kind of target a line is, not where it sits.
- **Four rules by name**, from layers there were before the rungs (`build.sh`'s `WIRE_MODULE`, `CLI_MODULE`, `WINDOW_MODULE` and `APP_MODULE`): the wire imports nothing, and the command line only the wire, so `canvas` builds without the app; `@_spi(Host)`, the editor's host API, may be imported only by the window, testsupport and test modules; `@_spi(Product)`, loading the list whole, only by the app and its extension; and a plugin that ships is in a platform or a product module.
- **Which way an edge between two platform modules goes** is the meaning's: the module that owns a meaning imports what it builds on and what shows it, and the graph having no cycle holds the direction once an edge is drawn (Titles imports Queries, so Queries can never import Titles). The rest, which layers held before, conventions hold, and a review. Among them: the wire is core, so any plugin may import its types, where once only what agents speak (Automation, QueryCommands) could; still, only those answer a request over it.
  - An engine knows no meaning a horizontal owns. A word in a language is given by the module that owns its meaning, as a plugin value of its own, through the engine's points; when the owner sits below the engine, the engine's module gives it. The draw engine (Draw; Automation is the command line over it) takes what shapes are called, what an edge is, what's wrong with a shape drawn and what a mention's text is from its points, and the owners fill them, Draw knowing none of them: Titles gives `canvas draw` names, Connections edges, Validation warnings, Mentions text and Types types' names (`TitleNamesPlugin`, `PortEdgesPlugin`, `ValidationChecksPlugin`, `MentionTextsPlugin`, `TypeNamesPlugin`), a plugin value for each, so a list without one leaves its words out. The query engine, Queries, whose points are `canvas query`'s words, knows none either: Titles gives it names, Boards boards' names, Mentions its words and text, Validation and Types their words, and Queries itself the selection's, Selection being below it (`TitleQueriesPlugin`, `BoardQueriesPlugin`, `MentionQueriesPlugin`, `ValidationQueriesPlugin`, `TypeQueriesPlugin`, `SelectionQueriesPlugin`). The points stay points though one module fills each: AutomationTests and QueriesTests fill them with fixtures of their own. `--ask`'s prompt is in no module: its examples name the shipped kinds (`sticky-note`, `subboard`), which no module knows all of, so it's a text file of the product's (`Shipped/ask-prompt.txt`; above, the product's text files).
  - A horizontal imports the horizontals that show it (Validation imports DetailPanel and TableOfContents, for its Issues tab and its rows' dots, as Titles imports them for its header and its rows' names), one may build on another (Titles and Mentions import Validation, for the rules they add), and a face a plugin list should be able to leave out is a plugin value of its own in the owner's module (`ValidationDetailsPlugin`, `ValidationContentsPlugin`, `MentionValidationPlugin`, `TitleValidationPlugin`, `TypeValidationPlugin`, `TypeDetailsPlugin`, and Find's contributors `TitleFindPlugin` and `MentionFindPlugin`, Neighbors' lights `ArrowLightsPlugin`, `MentionLightsPlugin` and its Connections tab `NeighborDetailsPlugin`, the detail panel's overview and takeover `ContentsOverviewPlugin`, `FindPanelPlugin`, and Boards' headings over the table of contents and Find's list `BoardContentsPlugin`, `BoardFindPlugin`): the registry refuses a contribution whose point's owner isn't installed, so a list with Validation and no panel installs `ValidationPlugin()` alone.
  - No module joins two others (there are no bridges), and none lists the plugins: what ships is `Package.swift`'s table (What ships, above), the commands are Automation's, through a host slot, and `--ask`'s prompt is a text file.

- **A module is its own**, apart from another, only when something must build without the other (the command line without the app) or a rung forbids an import the merged module would need. What other plugins build on can't be a product, so ports and channels are Connections', on the platform, and the arrow that draws them is Arrows', a product: notes and subboards declare their channels without importing a kind. The host slots are the core's points, so Canvas declares them.
