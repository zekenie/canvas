# Building, the module graph and the audit

How `build.sh` builds and runs, and which app a build is to macOS (a worktree's is a copy of the app, an app of its own); what `Package.swift` declares, the layers and what each may import; what ships and how the product is made of it; the parts a large module is split into and how the build holds them apart; and what the audit refuses.

Related: [benchmarks](benchmarks.md), [testing](testing.md), [plugins and kinds](plugins-and-kinds.md), [host slots](host-slots.md), [Quick Look](quick-look.md), [types](types.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [The module graph](../../docs/plugin-system.md#the-module-graph), [Horizontal and vertical](../../docs/plugin-system.md#horizontal-and-vertical).

## Building

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`, as many at once as there are cores (`BUILD_JOBS=N`), each once its dependencies are built, and only when what it's built from changed: its sources, its command, its dependencies' `.swiftmodule`s. A module's `.swiftmodule` is a job of its own (function bodies skipped, as in the job swiftc splits off itself), so what imports it starts compiling long before its code is done, and in release other modules can't inline its functions whatever cross-module optimization makes of them (nothing is `@inlinable`, and the benchmarks measured no difference). A module's code compiles to an object per source at fixed paths (`-num-threads 4`, through an output file map), so the same inputs make the same bytes, and what comes out the same isn't replaced: an edit inside a function recompiles only its module and links the executables again, and a touch or a checkout that changes nothing links nothing. In debug an executable's object job emits its module too, which its link hands the debugger (`-add_ast_path`), as a one-step `swiftc -g` does. A build fails, saying so, if a module's sources change while it builds (an interface and an object from different edits would link). Builds of one configuration wait for each other (`build/.debug.lock`), and however build.sh or test.sh ends (^C, a TERM), what it started stops with it. The app bundle's files change only when they do: macOS checks each new executable the first time it runs (about 0.3 s each, one at a time). The app carries its command line, `canvas` (`Contents/Helpers/canvas`; `build/canvas` links to it): with the app open, `build/canvas help`. It carries its Quick Look extensions too (`Contents/PlugIns`: `QuickLookPreview.appex` and `QuickLookThumbnail.appex`, both the executable the app carries, linked to start in `NSExtensionMain`, each with an Info.plist `build.sh` writes and signed ad hoc with the sandbox entitlement Quick Look requires, in a copy, so what didn't change isn't replaced; [Quick Look](quick-look.md)). A build that changed the bundle, and a checkout's first, also unregisters the copies of the app whose folders are gone (a removed worktree's build stays registered with macOS, and when Quick Look is handed that one's extensions, a board file shows as JSON), and its own bundle where macOS has it as another app (below), which takes a second; a build that changed nothing skips it.
- **Which app a build is.** A checkout's build is the app: `com.example.InfiniteCanvas`, "Infinite Canvas", which owns board files (`LSHandlerRank` `Owner`) and exports their type. A linked git worktree's build (its `git rev-parse --git-dir` isn't its `--git-common-dir`) is a copy of the app, an app of its own to macOS: `com.example.InfiniteCanvas.worktree.<name>`, "Infinite Canvas (<name>)", the name what git calls the worktree (its folder in the repository's `worktrees`, which no two share; what an identifier can't hold becomes a hyphen), with board files claimed as an `Alternate`: it opens them (`open -a <worktree>/build/InfiniteCanvas.app <file>`, Open With, a drag onto it), and a double-click, or `open <file>`, opens the app. The build's last line says which it built. A clone is no copy, nor is a folder with no git: either builds the app (macOS offers no app under `/private/tmp`, for a file or by its identifier, so a clone in a scratchpad doesn't compete; one elsewhere would).
  - Why: every checkout's build was the one app once, and of several registered under one identifier macOS opens whichever it picks, by no rule that was found (`osascript -e 'POSIX path of (path to application id "com.example.InfiniteCanvas")'` says which): board files opened in an old build in some worktree. Having each build unregister the others was turned down: opening a copy registers it again.
  - What macOS does with the two, traced with bundles in a namespace of their own (nothing documents it): of an owner and an alternate that have each been opened, the owner opens the file, whichever was opened or registered last and whether the alternate imports or exports the type; an app only registered (`lsregister -f`) and never opened loses to one that was opened, whatever their ranks, so with the app unregistered or never opened a copy opens board files. `NSWorkspace.shared.urlForApplication(toOpen:)` answers without opening anything.
  - The same in every copy: the types' identifiers, which the sources spell (the board's, the pasteboard's, the mention text's, the table of contents' rows'), so files, the pasteboard and drags pass between copies. The app exports the two it declares; a copy imports the board's (`UTImportedTypeDeclarations`), so the app's declaration is the one macOS goes by, and exports the rows' as the app does: the sources make it with `UTType(exportedAs:)`, which in an app that only imports it logs `Type … was expected to be exported in the Info.plist …, but it was imported instead` at each launch (the type works all the same). And what's kept by path, not by identifier: the Anthropic key ([language models](language-models.md)), which a copy reads and Settings in any copy writes, and the command line's socket ([command line](command-line.md)): `canvas` reaches whichever app took the socket first, the app's or a copy's, as it did (a second app gives up; `CANVAS_SOCKET`, a path of at most 103 bytes, gives one its own).
  - A copy's own, by its identifier: its preferences (`UserDefaults.standard`: the view memory, the spelling settings, and AppKit's, window frames and Open Recent among them), so a worktree's build starts with none of the app's; its Quick Look extensions' identifiers and their containers ([Quick Look](quick-look.md)). `~/Library/Preferences/<identifier>.plist` and the containers stay when the worktree is removed. The app's menu says the bundle's name (`CFBundleName`, which `canvas status` says too); the Finder calls every copy InfiniteCanvas, its file's name.
  - A worktree's build from before this, registered as the app, is still picked from until it's rebuilt with this or unregistered. A build that finds its own bundle registered under another identifier unregisters it (`forget_copies_gone`; until a rebuilt bundle is opened macOS keeps what it registered), and opening it registers what it is. By hand: `lsregister -u <worktree>/build/InfiniteCanvas.app`.

## The module graph and the audit

- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (wire, foundation, ui, surface, concern, feature, language, vertical, app, cli, testsupport, test): the app uses the foundation, the ui layer and the wire, and names no plugin, and so does an executable the app carries, an app extension macOS runs on its own (`// layer: app of InfiniteCanvas`: CanvasQuickLook, Quick Look's). Before the targets is the table of what ships (below, What ships), and a line may end `+ shipped`. A test target named after a module, `<M>Tests`, may use only M, what M uses, and testsupport and ui modules, and so may one named after a plugin of M that says so, `// layer: test of M` (ArrowsTests, of Connections; TitleQueriesTests, of Titles); an `of` on any layer but test and app is refused, and an app's names the app itself, `// layer: app of InfiniteCanvas`. Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. What it reads of each module is kept in `build/audit` and read again only for a module that changed, and a pass is kept by every input's name, size and mtime, so auditing what already passed costs one stat. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies (what `+ shipped` adds to a line is linked, not imported: the app and its extension may import none of it, the tests of what ships and their support whichever they call); on a line of what ships that isn't a public struct of that module that is a `ListedPlugin`, or that ships twice, or whose module isn't a plugin's layer; on a module whose code doesn't fit its layer, read from non-test sources as declarations of a `ShapeKind`, a `PropertyKey` and a conformance to `ExtensionPoint` or `KeyedExtensionPoint` (a vertical that declares no `ShapeKind`; a feature that declares a `ShapeKind`, an extension point or a `PropertyKey`; a concern that declares neither a point nor a `PropertyKey`; a surface that declares no point and that no plugin module imports); on `+ shipped` anywhere but the app, its extension, a test or a test-support module, or missing from what depends on a library that says it; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` or `Span` (either would shadow Swift's in every importer: a query's place in its text is a `QuerySpan`); and on a module writing another module's `ShapeKind`, `PluginID`, `ToolID`, `PropertyKey`, `ChannelID` (Connections') or `EdgeTypeID` (Topology's) string without depending on it (a string two modules declare is both's, so an id that must equal another module's is made from that module's constant, as a channel's edge type from the channel's `id`; a name in a property list, `Property("…")`, is exempt, and so is a JSON member named by a JSON Schema keyword, a subscript's key, `json["title"]`, or a key before a colon where a member's name starts, but not in a `case`'s patterns or `where` or a ternary, even across lines: the `title` keyword is also Titles' property key; any other member's name, `json["locked"]`, counts; `frame`, the core's own member every box has, which Frames' kind is spelled as, and `schema`, a board's own member that once listed its kinds' versions (and `canvas kinds --schema`'s answer), which Types' property is spelled as, and `is`, an English word every message uses, which Types' property is spelled as, and `color`, a word any test's or message's data may hold (a field called color), which Colors' property is spelled as, are ordinary words that no module owns, `ORDINARY_IDS`). The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool, plugin, property, channel or edge type id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it; loading the list of what ships whole is `@_spi(Product)`, and only the app and its extension may.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph: each line's own dependencies (` + shipped` said, never spelled out), and `graph` prints the list of what ships after the modules, since what ships is membership in the product, not a module depending on another.
- **The product's text files** (`Shipped/*.txt`, with a README): what the product says in a file, not in a module. `build.sh` puts each, and the list of what ships as text (`build/shipped/plugins.txt`, written from the table; no file here may be called `plugins.txt`), in every executable that is the product (`is_product`: one whose line ends `+ shipped`, so the app, CanvasQuickLook, CompositionTests and BenchmarkTests), at its link (`-sectcreate __TEXT __<name> <file>`, the section named for the file, `-` as `_`; the files are the link's inputs, so an edit links those executables again and compiles nothing), and the core reads one back by name, `ShippedText.named("ask-prompt")` (Canvas: the process's own executable's section, nil in an executable that isn't the product or for a name with no file), so nothing looks for a file at run time and no module holds the text. A file's name is lowercase letters, digits and hyphens, at most 14 characters (a section's name is at most 16), which every build.sh mode checks. Shipped: `ask-prompt.txt` and `ask-rule.txt`, which `QueryTranslationPlugin()` reads ([language models](language-models.md)).

## What ships

- **The list.** Which plugins the product is made of, in which order (the toolbar's, the order overlays draw in, and each after the plugins whose points it fills), is one table in `Package.swift`, before the targets: `let ships = [` on a line of its own, then lines of `"Module.Type",` entries (several a line), comments on lines of their own saying why each sits where it does, and `]`. It's the only list: no module imports the plugins to make it (Composition, which did, is gone). `build.sh` reads it as text, as it reads the targets (`SHIPPED_PLUGINS`, `SHIPPED_MODULES`, the modules once each in the list's order), and `Package.swift` computes `shipped`, those modules as dependencies, from the same array, which the SwiftPM check holds equal.
- **`+ shipped`.** A target line whose dependencies end `+ shipped` is the product, or the tests of it: every module the list names links into it, though nothing need import them (`SHIPS`, `LITERAL`, a line's own dependencies; `DEPS` and `CLOSURE` have both). Five say it: InfiniteCanvas and CanvasQuickLook, which import none of those modules and compile against none (`VISIBLE`: the include path, and what the id check lets a module name, are their own dependencies' closures); ShippedTesting, CompositionTests and BenchmarkTests, which import the ones they call. A line may not also list a module the list names.
- **Made by name** (Canvas, `Sources/Canvas/Plugins/ShippedList.swift`). A plugin a list can name is a `ListedPlugin`: a `CanvasPlugin` with an `init()`; every shipped plugin is one, and a plugin that takes arguments stays a `CanvasPlugin`. `ShippedList.names` is the list as the executable carries it (`ShippedText.named("plugins")`, nil in one that isn't the product), and `ShippedList.plugins(named:supplying:)` makes a list's plugins: each line's type found in the binary by its mangled name (`_typeByName("6Boards12BoardsPluginV")`, a struct's, a class's or an enum's: the standard library's, underscored, so not documented API; every library links whole, so the type is there whether or not anything names it), cast to `ListedPlugin`, and made. `ShippedListError`: `notTheProduct`, `malformed(line)`, `notFound(name)`, `notListed(name)`, `notSupplied(names)`, `notInList(names)`, each saying the line.
- **What reaches outside the process.** A listed plugin that, made from nothing, reaches the network or the user's pasteboard is an `OutwardPlugin`: `LanguageModelsPlugin()` (Claude over the network, the key from Settings) and `ClipboardPlugin()` (the system's pasteboard). `ShippedList.plugins()`, which makes them as they come, is `@_spi(Product)`: the app's and its extension's alone, by the audit. Anything else calls `ShippedList.plugins(supplying:)`, which takes the caller's plugins in the listed ones' places (matched by type, `String(reflecting:)`), refuses to load while an outward one isn't supplied (`notSupplied`), and refuses one the list hasn't (`notInList`); any listed plugin may be supplied (a translator that asks another way).
- **Tests** of what ships get the plugins from ShippedTesting (`Tests/ShippedTesting`, test support, `+ shipped`): `ShippedPlugins.plugins(pasteboard:model:)`, `registry(pasteboard:model:)` and `makeEditor(document:scheduler:pasteboard:model:)`, the list with a `ClipboardPlugin` on the test's pasteboard (the system's unless it passes one) and a `LanguageModelsPlugin` with the test's model, whose `model` has no default. So a test checks exactly what ships.
- **Shipping a plugin** is its line in the table, where its order belongs, and `public struct XPlugin: ListedPlugin` with a `public init() {}` in its module. Leaving one out is deleting its line.
- **Testing.** CanvasTests' `registryTests` hold the loader with plugins of their own, found in the test executable by name (`CanvasTests.FirstListed`): a list's order, each refusal, an outward plugin refused until it's handed over and the one handed over taken, any listed plugin swapped, and no list in an executable that isn't the product. CompositionTests' `shippedTests` hold the product's: the list in the executable, every line a plugin of that type in order, the registry it makes, and the list refusing to load without a clipboard's and a model's plugin of the caller's own.

## The parts of a module

- **What a part is.** A module too large to hold in mind is split into parts, each a folder of its directory, with the rule between them that holds between modules: a part uses only the parts its line names. They are parts and not modules by the rule at the end of Layers (nothing must build without the others, and no layer forbids an import), and because what one part shares with the next stays internal to the module: as modules, every such name would be public to every importer. Types is the one module in parts ([types](types.md), "The parts"); a module with folders and no line in the table (Canvas) has none.
- **The table** is in `Package.swift`, after what ships: `let parts: KeyValuePairs<String, [String]> = [` on a line of its own, then a line a part, `"Module/Part": ["A", "B"],`, comments on lines of their own, and `]`. `build.sh` reads it as text (`PARTED`, `PARTS`, `PART_USES`), and SwiftPM makes nothing of it. The lines are in an order the parts could be built in: a part uses only parts written above it, so there is no cycle, and names all of what those use, so a line says everything its part compiles with. Every folder directly in a module that has parts is a part; the sources beside the folders are the module's own (its plugin values, which install every part) and may use them all. Every mode refuses a table that breaks one of these, a part with no folder or no sources, and a folder that is no part.
- **The check** is the compiler's: for a module that has parts the build runs one job more, `<Module>:parts`, which type-checks each part, in the table's order, with only its own sources and those of the parts its line names (the module's flags and include path, `-typecheck`, nothing made), and stops at the first that fails, with the compiler's errors at the names it could not find and a line saying which part reached out of its own. So a part that names anything else of the module doesn't compile, as a module that names one it doesn't depend on doesn't. It needs the module's dependencies built, so it is a job of the build and of `./test.sh`, not of `./build.sh audit`; it waits for the dependencies' interfaces and nothing waits for it; and a part is checked again only when a source it compiles with, or a dependency's interface, changed (a stamp a part, `build/<config>/<Module>/.part.<Part>`). Types' nine take about seven seconds of one core in all, beside the module's own compile.
- **Changing them.** A file moved to another part, a new part, or a part given another to use is its folder and its line. When the check refuses a name, the choice is the one a forbidden import between modules gives: move the declaration down to the part both can use, have the lower part take a closure the higher one registers (as `TypeIndex.onChange` is used), or say the use on the line if the order allows it. `./build.sh graph` prints each module's parts, with what each uses, after the list of what ships.

A module is its own, apart from another, only when something must build without the other (the command line without the app) or a layer forbids an import the merged module would need: the host slots are the core's points, so Canvas declares them.
