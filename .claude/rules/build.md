# Building, the module graph and the audit

How `build.sh` builds and runs; what `Package.swift` declares, the layers and what each may import; and what the audit refuses.

Related: [benchmarks](benchmarks.md), [testing](testing.md), [plugins and kinds](plugins-and-kinds.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [The module graph](../../docs/plugin-system.md#the-module-graph), [Horizontal and vertical](../../docs/plugin-system.md#horizontal-and-vertical).

## Building

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`, as many at once as there are cores (`BUILD_JOBS=N`), each once its dependencies are built, and only when what it's built from changed: its sources, its command, its dependencies' `.swiftmodule`s. A module's `.swiftmodule` is a job of its own (function bodies skipped, as in the job swiftc splits off itself), so what imports it starts compiling long before its code is done, and in release other modules can't inline its functions whatever cross-module optimization makes of them (nothing is `@inlinable`, and the benchmarks measured no difference). A module's code compiles to an object per source at fixed paths (`-num-threads 4`, through an output file map), so the same inputs make the same bytes, and what comes out the same isn't replaced: an edit inside a function recompiles only its module and links the executables again, and a touch or a checkout that changes nothing links nothing. In debug an executable's object job emits its module too, which its link hands the debugger (`-add_ast_path`), as a one-step `swiftc -g` does. A build fails, saying so, if a module's sources change while it builds (an interface and an object from different edits would link). Builds of one configuration wait for each other (`build/.debug.lock`), and however build.sh or test.sh ends (^C, a TERM), what it started stops with it. The app bundle's files change only when they do: macOS checks each new executable the first time it runs (about 0.3 s each, one at a time). The app carries its command line, `canvas` (`Contents/Helpers/canvas`; `build/canvas` links to it): with the app open, `build/canvas help`.

## The module graph and the audit

- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (wire, foundation, ui, surface, concern, language, lexicon, vertical, composition, app, cli, testsupport, test). A test target named after a module, `<M>Tests`, may use only M, what M uses, and testsupport and ui modules, and so may one named after a plugin of M that says so, `// layer: test of M` (ArrowsTests, of Connections; TitleQueriesTests, of QueryLexicon). Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. What it reads of each module is kept in `build/audit` and read again only for a module that changed, and a pass is kept by every input's name, size and mtime, so auditing what already passed costs one stat. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` or `Span` (either would shadow Swift's in every importer: a query's place in its text is a `QuerySpan`); and on a module writing another module's `ShapeKind`, `PluginID`, `ToolID`, `PropertyKey`, `ChannelID` (Connections') or `EdgeTypeID` (Topology's) string without depending on it (a string two modules declare is both's, so an id that must equal another module's is made from that module's constant, as a channel's edge type from the channel's `id`; a name in a property list, `Property("…")`, is exempt, and so is a JSON member named by a JSON Schema keyword, a subscript's key, `json["title"]`, or a key before a colon where a member's name starts, but not in a `case`'s patterns or `where` or a ternary, even across lines: the `title` keyword is also Titles' property key; any other member's name, `json["locked"]`, counts; `frame`, the core's own member every box has, which Frames' kind is spelled as, is an ordinary word that no module owns, `ORDINARY_IDS`). The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool, plugin, property, channel or edge type id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph.

## Layers

- Layers: horizontals, the plugins any kind can opt into, declare extension points and import no vertical, and are four layers that say which way an edge between two of them goes, each using the foundation too: surfaces (Keyboard, Selection, DetailPanel, ContextMenus, SlashCommands, TableOfContents, Adornments, LanguageModels, Topology), what the others show themselves on or build on, use only surfaces; concerns (Validation, Clipboard, Titles, Locking, Connections, Mentions, Boards, Snapping), a meaning a kind opts into, use surfaces and concerns; languages (Automation, Queries, QueryCommands), what agents read and write the canvas in, use surfaces, languages and the wire, never a concern; and lexicons (DrawLexicon, QueryLexicon), a language's words for the concerns (below), use surfaces, concerns and languages. One may build on another (Queries on Topology; QueryCommands on Automation, LanguageModels and Queries, and the wire; DrawLexicon on Automation, Connections, Titles and Validation; QueryLexicon on Queries, Boards, Mentions, Selection, Titles, Topology and Validation; Boards on ContextMenus, DetailPanel, Keyboard, Selection, TableOfContents and Titles; Clipboard on Keyboard, Selection and ContextMenus; Locking on Adornments, ContextMenus, Selection, SlashCommands and TableOfContents; Connections on Selection, TableOfContents, TextEditing and Topology; Mentions on ContextMenus, DetailPanel, Selection, SlashCommands, TableOfContents, TextEditing, Titles, Topology and Validation; Titles on Adornments, DetailPanel, SlashCommands, TableOfContents and Validation; Validation on DetailPanel and TableOfContents; Adornments, DetailPanel, ContextMenus and TableOfContents on Selection; DetailPanel and SlashCommands also on TextEditing; Selection on Keyboard); verticals (StickyNotes, Schemas, Subboards, Frames, Reordering) use surfaces and concerns, and import no other vertical (StickyNotes and Schemas import TextEditing, for the text view their editors are; StickyNotes and Schemas import Connections, each for a channel of its own, and StickyNotes, Subboards, Frames and Schemas import Mentions, notes and schema cards to hold mentions and all four to be mentioned; Subboards builds on Boards; Frames on Selection, for its marquee and its resizing); no module joins two others but a lexicon (there are no bridges), and `build.sh` refuses an edge the layers don't allow: a surface importing a concern, a concern or a vertical importing a language, a language importing a concern. A language (Automation's `canvas draw`, Queries) takes what shapes are called, what an edge is, what's wrong with a shape drawn, what a board is called and what more a query may ask from its points, and the app's words for them are a lexicon, which imports the language and the concerns, neither of which knows the other. DrawLexicon gives `canvas draw` Titles' names, Connections' edges and Validation's warnings (`TitleNamesPlugin`, `PortEdgesPlugin`, `ValidationChecksPlugin`), and QueryLexicon gives `canvas query` Titles' names, Boards' names, Mentions' words and text, and Validation's and Selection's words (`TitleQueriesPlugin`, `BoardQueriesPlugin`, `MentionQueriesPlugin`, `ValidationQueriesPlugin`, `SelectionQueriesPlugin`), a plugin value for each concern, so a list without a concern leaves its words out. The points stay points though one module fills each: AutomationTests and QueriesTests fill them with fixtures of their own. `QueryPrompt`, `--ask`'s prompt, stays in Composition: its examples name the shipped kinds (`sticky-note`, `subboard`), and only Composition depends on all of them. A horizontal may own the one kind its concern is drawn as (Connections' arrow): Connections holds ports, channels and the arrow, `ArrowPortsPlugin` making arrows the connector (the only code in it that knows both arrows and channels), and being a concern it lets notes and schema cards declare their channels without importing a vertical. A concern imports the surfaces that show it (so Validation imports DetailPanel and TableOfContents, for its Issues tab and its rows' dots, as Titles imports them for its header and its rows' names), and a concern may build on another (Titles and Mentions import Validation, for the rules they add), and a face a plugin list should be able to leave out is a plugin value of its own in the owner's module (`ValidationDetailsPlugin`, `ValidationContentsPlugin`, `MentionValidationPlugin`, `TitleValidationPlugin`): the registry refuses a contribution whose point's owner isn't installed, so a list with Validation and no panel installs `ValidationPlugin()` alone. The foundation is Geometry, Canvas, DrawScript, QueryLanguage and TextEditing (the last three libraries beneath the plugins that know no canvas, registry or plugin: the languages `canvas draw` and `canvas query` read, and draw's solver, pure; and the app's text editing, the text view and caret list every editable text is built on). The shipped list is `ShippedPlugins.plugins(pasteboard:model:)` in Composition (and `registry(pasteboard:model:)`, `makeEditor(document:scheduler:pasteboard:model:)`); the app passes `ShippedPlugins.anthropicModel`.
