# Building, the module graph and the audit

How `build.sh` builds and runs; what `Package.swift` declares, the layers and what each may import; and what the audit refuses.

Related: [benchmarks](benchmarks.md), [testing](testing.md), [plugins and kinds](plugins-and-kinds.md), [Quick Look](quick-look.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [The module graph](../../docs/plugin-system.md#the-module-graph), [Horizontal and vertical](../../docs/plugin-system.md#horizontal-and-vertical).

## Building

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`, as many at once as there are cores (`BUILD_JOBS=N`), each once its dependencies are built, and only when what it's built from changed: its sources, its command, its dependencies' `.swiftmodule`s. A module's `.swiftmodule` is a job of its own (function bodies skipped, as in the job swiftc splits off itself), so what imports it starts compiling long before its code is done, and in release other modules can't inline its functions whatever cross-module optimization makes of them (nothing is `@inlinable`, and the benchmarks measured no difference). A module's code compiles to an object per source at fixed paths (`-num-threads 4`, through an output file map), so the same inputs make the same bytes, and what comes out the same isn't replaced: an edit inside a function recompiles only its module and links the executables again, and a touch or a checkout that changes nothing links nothing. In debug an executable's object job emits its module too, which its link hands the debugger (`-add_ast_path`), as a one-step `swiftc -g` does. A build fails, saying so, if a module's sources change while it builds (an interface and an object from different edits would link). Builds of one configuration wait for each other (`build/.debug.lock`), and however build.sh or test.sh ends (^C, a TERM), what it started stops with it. The app bundle's files change only when they do: macOS checks each new executable the first time it runs (about 0.3 s each, one at a time). The app carries its command line, `canvas` (`Contents/Helpers/canvas`; `build/canvas` links to it): with the app open, `build/canvas help`. It carries its Quick Look extensions too (`Contents/PlugIns`: `QuickLookPreview.appex` and `QuickLookThumbnail.appex`, both the appex layer's one executable, linked to start in `NSExtensionMain`, each with an Info.plist `build.sh` writes and signed ad hoc with the sandbox entitlement Quick Look requires, in a copy, so what didn't change isn't replaced; [Quick Look](quick-look.md)).

## The module graph and the audit

- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (wire, foundation, ui, surface, concern, language, lexicon, vertical, composition, app, appex, cli, testsupport, test): an appex is an app extension, an executable the app carries that macOS runs on its own (CanvasQuickLook, Quick Look's), and uses what the app does but the wire. A test target named after a module, `<M>Tests`, may use only M, what M uses, and testsupport and ui modules, and so may one named after a plugin of M that says so, `// layer: test of M` (ArrowsTests, of Connections; TitleQueriesTests, of QueryLexicon). Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. What it reads of each module is kept in `build/audit` and read again only for a module that changed, and a pass is kept by every input's name, size and mtime, so auditing what already passed costs one stat. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` or `Span` (either would shadow Swift's in every importer: a query's place in its text is a `QuerySpan`); and on a module writing another module's `ShapeKind`, `PluginID`, `ToolID`, `PropertyKey`, `ChannelID` (Connections') or `EdgeTypeID` (Topology's) string without depending on it (a string two modules declare is both's, so an id that must equal another module's is made from that module's constant, as a channel's edge type from the channel's `id`; a name in a property list, `Property("…")`, is exempt, and so is a JSON member named by a JSON Schema keyword, a subscript's key, `json["title"]`, or a key before a colon where a member's name starts, but not in a `case`'s patterns or `where` or a ternary, even across lines: the `title` keyword is also Titles' property key; any other member's name, `json["locked"]`, counts; `frame`, the core's own member every box has, which Frames' kind is spelled as, and `schema`, a board's own member that once listed its kinds' versions (and `canvas kinds --schema`'s answer), which Types' property is spelled as, and `is`, an English word every message uses, which Types' property is spelled as, are ordinary words that no module owns, `ORDINARY_IDS`). The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool, plugin, property, channel or edge type id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph.

## Layers

- Layers: horizontals, the plugins any kind can opt into, declare extension points and import no vertical, and are four layers that say which way an edge between two of them goes, each using the foundation too: surfaces (Keyboard, Selection, DetailPanel, ContextMenus, SlashCommands, TableOfContents, Adornments, LanguageModels, ProseMaps, Topology, Find, Queries, QueryTranslation, Neighbors, Placing) what the others show themselves on or build on, use only surfaces (the query engine is a surface every plugin may run, and QueryTranslation turns English into a query for the command line and the app alike; the language agents write is `canvas query` and the lexicon's words, so any concern may now contribute a query word directly, which the convention, words for a concern through QueryLexicon, leaves to the lexicon, and the audit does not yet enforce); concerns (Validation, Clipboard, Titles, Locking, Publishing, Connections, Mentions, Boards, Snapping, Transform, Types), a meaning a kind opts into, use surfaces and concerns; languages (Automation, QueryCommands), what agents read and write the canvas in, use surfaces, languages and the wire, never a concern; and lexicons (DrawLexicon, QueryLexicon), a language's words for the concerns (below), use surfaces, concerns and languages. One may build on another (Queries on Topology; ProseMaps and QueryTranslation on LanguageModels, QueryTranslation on Queries too; Automation on Queries, to check a query a property holds, and on Topology, to read which kinds stand in for others and can be made to stand for a shape, as an edge to a shape on another board goes through one, and on Adornments, to say how far a shape's title row reaches above it (`canvas measure`); QueryCommands on Automation, Queries, QueryTranslation and the wire; DrawLexicon on Automation, Connections, Mentions, Titles, Types and Validation; QueryLexicon on Queries, Boards, Mentions, Selection, Titles, Topology, Types and Validation; Boards on ContextMenus, DetailPanel, Keyboard, Selection, TableOfContents and Titles; Clipboard on Keyboard, Selection and ContextMenus; Locking on Adornments, ContextMenus, SlashCommands and TableOfContents; Publishing on Adornments, ContextMenus, DetailPanel, Selection, SlashCommands, TableOfContents, Titles and Topology; Connections on Mentions, Neighbors, Publishing, Selection, TableOfContents, TextEditing and Topology, and on Types, so an arrow opts into being an instance of a type (Types never imports Connections); Mentions on ContextMenus, DetailPanel, Find, FuzzyMatching, Neighbors, Selection, SlashCommands, TableOfContents, TextEditing, Titles, Topology and Validation; Titles on Adornments, DetailPanel, Find, SlashCommands, TableOfContents and Validation; Transform on ContextMenus and SlashCommands; Types on Adornments, ContextMenus (Is a ▸), DetailPanel, Find (a note that is one has its values found: `FieldFindPlugin`), LanguageModels, Placing (to put a new type beside the shape that asked for it), ProseMaps, Selection, SlashCommands, TextEditing (the rows' one-line field) and Topology, and on Mentions, Titles and Validation (a type's words are mention text, its name is its title, its rules are Validation's, its chips are Adornments', and what a shape is makes an edge in Topology's graph); Validation on DetailPanel and TableOfContents; Adornments, DetailPanel, ContextMenus and TableOfContents on Selection; Find on DetailPanel, FuzzyMatching, Geometry, Keyboard, Selection and Topology; Neighbors, what an edge's owner shows its edges on when a shape is hovered, on Queries, to ask the questions its lights are, Selection, for the hover it follows (the canvas's, and the one a list sets for a shape the canvas doesn't show), and Topology, for when a shape's edges change: where a shape on another board is drawn is the file's, and the lights are Connections' and Mentions', which import it; DetailPanel and SlashCommands also on FuzzyMatching and TextEditing; Selection on Keyboard); verticals (StickyNotes, Subboards, Frames, JumpTo, References, Moving, Reordering) use surfaces and concerns, and import no other vertical (StickyNotes imports TextEditing, for the text view its editor is, and Types, the concern a note opts into to be a type; StickyNotes and Subboards import Connections, each for a channel of its own (Subboards for ports on every channel too), and References for ports on every channel and the arrows attached to a pill, and StickyNotes, Subboards and Frames import Mentions, notes to hold mentions and all three to be mentioned; Subboards builds on Boards; Frames on Selection, for its marquee and its resizing, and on ContextMenus, for Create Frame; Subboards and Frames import Transform, Frames to offer the container channel and Subboards to take it, which is how a frame turns into a subboard though neither names the other; JumpTo, a feature no kind opts into and nothing imports, as Reordering is one, on Boards, for how a pick follows a shape, Titles and Topology, for what it lists (a row's tint is its kind's, the core's `registry.label(of:)`), and Keyboard and TextEditing, for ⌘K and its field and list; References on Queries and QueryLanguage, to ask what a dynamic reference's query finds, QueryTranslation and LanguageModels, to turn its typed words into a query, and Validation, to warn of a query it can't read; Moving, a feature no kind opts into and nothing imports, as JumpTo and Reordering are, on SlashCommands, for `/move-to` and `/move-near`, TableOfContents, for the drops that move shapes (`ContentsMoves`), Placing, to place a shape as `canvas draw` places one (Placing is that solver, DrawScript's `LayoutProblem` and `ObstacleGrid`, over a board read in place, a surface any plugin may use); no module joins two others but a lexicon (there are no bridges), and `build.sh` refuses an edge the layers don't allow: a surface importing a concern, a concern or a vertical importing a language, a language importing a concern. A language (Automation's `canvas draw`, and the query engine, Queries, though it is a surface) takes what shapes are called, what an edge is, what's wrong with a shape drawn, what a board is called and what more a query may ask from its points, and the app's words for them are a lexicon, which imports the language and the concerns, neither of which knows the other. DrawLexicon gives `canvas draw` Titles' names, Connections' edges, Validation's warnings, Mentions' text and Types' names (`TitleNamesPlugin`, `PortEdgesPlugin`, `ValidationChecksPlugin`, `MentionTextsPlugin`, `TypeNamesPlugin`), and QueryLexicon gives `canvas query` Titles' names, Boards' names, Mentions' words and text, and Validation's, Selection's and Types' words (`TitleQueriesPlugin`, `BoardQueriesPlugin`, `MentionQueriesPlugin`, `ValidationQueriesPlugin`, `SelectionQueriesPlugin`, `TypeQueriesPlugin`), a plugin value for each concern, so a list without a concern leaves its words out. The points stay points though one module fills each: AutomationTests and QueriesTests fill them with fixtures of their own. `QueryPrompt`, `--ask`'s prompt, stays in Composition: its examples name the shipped kinds (`sticky-note`, `subboard`), and only Composition depends on all of them. A horizontal may own the one kind its concern is drawn as (Connections' arrow): Connections holds ports, channels and the arrow, `ArrowPortsPlugin` making arrows the connector (the only code in it that knows both arrows and channels), and being a concern it lets notes declare their channel without importing a vertical. A concern imports the surfaces that show it (so Validation imports DetailPanel and TableOfContents, for its Issues tab and its rows' dots, as Titles imports them for its header and its rows' names), and a concern may build on another (Titles and Mentions import Validation, for the rules they add), and a face a plugin list should be able to leave out is a plugin value of its own in the owner's module (`ValidationDetailsPlugin`, `ValidationContentsPlugin`, `MentionValidationPlugin`, `TitleValidationPlugin`, `TypeValidationPlugin`, `TypeDetailsPlugin`, and Find's contributors `TitleFindPlugin` and `MentionFindPlugin`, and Neighbors' lights `ArrowLightsPlugin`, `MentionLightsPlugin`): the registry refuses a contribution whose point's owner isn't installed, so a list with Validation and no panel installs `ValidationPlugin()` alone. The foundation is Geometry, Canvas, DrawScript, QueryLanguage, TextEditing and FuzzyMatching (the last four libraries beneath the plugins that know no canvas, registry or plugin: the languages `canvas draw` and `canvas query` read, and draw's solver with the grid its obstacles are filed in, pure, which Placing places shapes with; the app's text editing, the text view and caret list every editable text is built on; and fuzzy matching, which every list that ranks typed text, Find and Jump To are built on). The shipped list is `ShippedPlugins.plugins(pasteboard:model:)` in Composition (and `registry(pasteboard:model:)`, `makeEditor(document:scheduler:pasteboard:model:)`); the app passes `ShippedPlugins.anthropicModel`.
