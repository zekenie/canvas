# Building, the module graph and the audit

How `build.sh` builds and runs; what `Package.swift` declares, the layers and what each may import; what ships and how the product is made of it; and what the audit refuses.

Related: [benchmarks](benchmarks.md), [testing](testing.md), [plugins and kinds](plugins-and-kinds.md), [host slots](host-slots.md), [Quick Look](quick-look.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [The module graph](../../docs/plugin-system.md#the-module-graph), [Horizontal and vertical](../../docs/plugin-system.md#horizontal-and-vertical).

## Building

- `./build.sh && open build/InfiniteCanvas.app`. It calls `swiftc` directly and wraps the binary in an `.app`, because SwiftPM (`swift build`) is broken with this machine's Command Line Tools. Each module is compiled with only its dependency closure on `-I`, as many at once as there are cores (`BUILD_JOBS=N`), each once its dependencies are built, and only when what it's built from changed: its sources, its command, its dependencies' `.swiftmodule`s. A module's `.swiftmodule` is a job of its own (function bodies skipped, as in the job swiftc splits off itself), so what imports it starts compiling long before its code is done, and in release other modules can't inline its functions whatever cross-module optimization makes of them (nothing is `@inlinable`, and the benchmarks measured no difference). A module's code compiles to an object per source at fixed paths (`-num-threads 4`, through an output file map), so the same inputs make the same bytes, and what comes out the same isn't replaced: an edit inside a function recompiles only its module and links the executables again, and a touch or a checkout that changes nothing links nothing. In debug an executable's object job emits its module too, which its link hands the debugger (`-add_ast_path`), as a one-step `swiftc -g` does. A build fails, saying so, if a module's sources change while it builds (an interface and an object from different edits would link). Builds of one configuration wait for each other (`build/.debug.lock`), and however build.sh or test.sh ends (^C, a TERM), what it started stops with it. The app bundle's files change only when they do: macOS checks each new executable the first time it runs (about 0.3 s each, one at a time). The app carries its command line, `canvas` (`Contents/Helpers/canvas`; `build/canvas` links to it): with the app open, `build/canvas help`. It carries its Quick Look extensions too (`Contents/PlugIns`: `QuickLookPreview.appex` and `QuickLookThumbnail.appex`, both the executable the app carries, linked to start in `NSExtensionMain`, each with an Info.plist `build.sh` writes and signed ad hoc with the sandbox entitlement Quick Look requires, in a copy, so what didn't change isn't replaced; [Quick Look](quick-look.md)). A build that changed the bundle, and a checkout's first, also unregisters the copies of the app whose folders are gone (a removed worktree's build stays registered with macOS, and when Quick Look is handed that one's extensions, a board file shows as JSON), which takes a second; a build that changed nothing skips it.

## The module graph and the audit

- `Package.swift` is the module graph: one target per line, each tagged `// layer:`. Its header lists the layers and what each may use (wire, foundation, ui, surface, concern, feature, language, vertical, app, cli, testsupport, test): the app uses the foundation, the ui layer and the wire, and names no plugin, and so does an executable the app carries, an app extension macOS runs on its own (`// layer: app of InfiniteCanvas`: CanvasQuickLook, Quick Look's). Before the targets is the table of what ships (below, What ships), and a line may end `+ shipped`. A test target named after a module, `<M>Tests`, may use only M, what M uses, and testsupport and ui modules, and so may one named after a plugin of M that says so, `// layer: test of M` (ArrowsTests, of Connections; TitleQueriesTests, of Titles); an `of` on any layer but test and app is refused, and an app's names the app itself, `// layer: app of InfiniteCanvas`. Non-test modules live in `Sources/X`, or `Examples/X` with `path:`; test modules in `Tests/X`.
- Every build.sh mode audits first; `./build.sh audit` does only that. What it reads of each module is kept in `build/audit` and read again only for a module that changed, and a pass is kept by every input's name, size and mtime, so auditing what already passed costs one stat. It fails on a cycle or a forbidden layer edge; on any difference between that table and SwiftPM's own evaluation of `Package.swift`; on a module whose imports, as the compiler parses them, aren't exactly its declared dependencies (what `+ shipped` adds to a line is linked, not imported: the app and its extension may import none of it, the tests of what ships and their support whichever they call); on a line of what ships that isn't a public struct of that module that is a `ListedPlugin`, or that ships twice, or whose module isn't a plugin's layer; on a module whose code doesn't fit its layer, read from non-test sources as declarations of a `ShapeKind`, a `PropertyKey` and a conformance to `ExtensionPoint` or `KeyedExtensionPoint` (a vertical that declares no `ShapeKind`; a feature that declares a `ShapeKind`, an extension point or a `PropertyKey`; a concern that declares neither a point nor a `PropertyKey`; a surface that declares no point and that no plugin module imports); on `+ shipped` anywhere but the app, its extension, a test or a test-support module, or missing from what depends on a library that says it; on an import inside `#if`, `canImport(<project module>)`, `@_exported`, `@_implementationOnly` or `@testable`; on a public type named like a module, or `Task` or `Span` (either would shadow Swift's in every importer: a query's place in its text is a `QuerySpan`); and on a module writing another module's `ShapeKind`, `PluginID`, `ToolID`, `PropertyKey`, `ChannelID` (Connections') or `EdgeTypeID` (Topology's) string without depending on it (a string two modules declare is both's, so an id that must equal another module's is made from that module's constant, as a channel's edge type from the channel's `id`; a name in a property list, `Property("…")`, is exempt, and so is a JSON member named by a JSON Schema keyword, a subscript's key, `json["title"]`, or a key before a colon where a member's name starts, but not in a `case`'s patterns or `where` or a ternary, even across lines: the `title` keyword is also Titles' property key; any other member's name, `json["locked"]`, counts; `frame`, the core's own member every box has, which Frames' kind is spelled as, is an ordinary word that no module owns, `ORDINARY_IDS`). The graph (the `-I` closure plus MemberImportVisibility) keeps the core from referencing plugin types; the id check keeps any module from writing another module's kind, tool, plugin, property, channel or edge type id as a literal. The editor's host API (input, cursor, drawing, delegate) is `@_spi(Host)`, and only the ui, testsupport and test layers may import it; loading the list of what ships whole is `@_spi(Product)`, and only the app and its extension may.
- `./build.sh graph`, `dot`, and `api <Module>` (a module's public interface) are for reading the graph: each line's own dependencies (` + shipped` said, never spelled out), and `graph` prints the list of what ships after the modules, since what ships is membership in the product, not a module depending on another.
- **The product's text files** (`Shipped/*.txt`, with a README): what the product says in a file, not in a module. `build.sh` puts each, and the list of what ships as text (`build/shipped/plugins.txt`, written from the table; no file here may be called `plugins.txt`), in every executable that is the product (`is_product`: one whose line ends `+ shipped`, so the app, CanvasQuickLook, CompositionTests and BenchmarkTests), at its link (`-sectcreate __TEXT __<name> <file>`, the section named for the file, `-` as `_`; the files are the link's inputs, so an edit links those executables again and compiles nothing), and the core reads one back by name, `ShippedText.named("ask-prompt")` (Canvas: the process's own executable's section, nil in an executable that isn't the product or for a name with no file), so nothing looks for a file at run time and no module holds the text. A file's name is lowercase letters, digits and hyphens, at most 14 characters (a section's name is at most 16), which every build.sh mode checks. Shipped: `ask-prompt.txt` and `ask-rule.txt`, which `QueryTranslationPlugin()` reads ([language models](language-models.md)).

## What ships

- **The list.** Which plugins the product is made of, in which order (the toolbar's, the order overlays draw in, and each after the plugins whose points it fills), is one table in `Package.swift`, before the targets: `let ships = [` on a line of its own, then lines of `"Module.Type",` entries (several a line), comments on lines of their own saying why each sits where it does, and `]`. It's the only list: no module imports the plugins to make it (Composition, which did, is gone). `build.sh` reads it as text, as it reads the targets (`SHIPPED_PLUGINS`, `SHIPPED_MODULES`, the modules once each in the list's order), and `Package.swift` computes `shipped`, those modules as dependencies, from the same array, which the SwiftPM check holds equal.
- **`+ shipped`.** A target line whose dependencies end `+ shipped` is the product, or the tests of it: every module the list names links into it, though nothing need import them (`SHIPS`, `LITERAL`, a line's own dependencies; `DEPS` and `CLOSURE` have both). Five say it: InfiniteCanvas and CanvasQuickLook, which import none of those modules and compile against none (`VISIBLE`: the include path, and what the id check lets a module name, are their own dependencies' closures); ShippedTesting, CompositionTests and BenchmarkTests, which import the ones they call. A line may not also list a module the list names.
- **Made by name** (Canvas, `Sources/Canvas/Plugins/ShippedList.swift`). A plugin a list can name is a `ListedPlugin`: a `CanvasPlugin` with an `init()`; every shipped plugin is one, and a plugin that takes arguments stays a `CanvasPlugin`. `ShippedList.names` is the list as the executable carries it (`ShippedText.named("plugins")`, nil in one that isn't the product), and `ShippedList.plugins(named:supplying:)` makes a list's plugins: each line's type found in the binary by its mangled name (`_typeByName("6Boards12BoardsPluginV")`, a struct's, a class's or an enum's: the standard library's, underscored, so not documented API; every library links whole, so the type is there whether or not anything names it), cast to `ListedPlugin`, and made. `ShippedListError`: `notTheProduct`, `malformed(line)`, `notFound(name)`, `notListed(name)`, `notSupplied(names)`, `notInList(names)`, each saying the line.
- **What reaches outside the process.** A listed plugin that, made from nothing, reaches the network or the user's pasteboard is an `OutwardPlugin`: `LanguageModelsPlugin()` (Claude over the network, the key from Settings) and `ClipboardPlugin()` (the system's pasteboard). `ShippedList.plugins()`, which makes them as they come, is `@_spi(Product)`: the app's and its extension's alone, by the audit. Anything else calls `ShippedList.plugins(supplying:)`, which takes the caller's plugins in the listed ones' places (matched by type, `String(reflecting:)`), refuses to load while an outward one isn't supplied (`notSupplied`), and refuses one the list hasn't (`notInList`); any listed plugin may be supplied (a translator that asks another way).
- **Tests** of what ships get the plugins from ShippedTesting (`Tests/ShippedTesting`, test support, `+ shipped`): `ShippedPlugins.plugins(pasteboard:model:)`, `registry(pasteboard:model:)` and `makeEditor(document:scheduler:pasteboard:model:)`, the list with a `ClipboardPlugin` on the test's pasteboard (the system's unless it passes one) and a `LanguageModelsPlugin` with the test's model, whose `model` has no default. So a test checks exactly what ships.
- **Shipping a plugin** is its line in the table, where its order belongs, and `public struct XPlugin: ListedPlugin` with a `public init() {}` in its module. Leaving one out is deleting its line.
- **Testing.** CanvasTests' `registryTests` hold the loader with plugins of their own, found in the test executable by name (`CanvasTests.FirstListed`): a list's order, each refusal, an outward plugin refused until it's handed over and the one handed over taken, any listed plugin swapped, and no list in an executable that isn't the product. CompositionTests' `shippedTests` hold the product's: the list in the executable, every line a plugin of that type in order, the registry it makes, and the list refusing to load without a clipboard's and a model's plugin of the caller's own.

## Layers

- Layers: horizontals, the plugins that cut across kinds, import no vertical and no feature, and are four layers that say which way an edge between two of them goes, each using the foundation too: surfaces (Keyboard, Selection, DetailPanel, ContextMenus, SlashCommands, TableOfContents, Adornments, LanguageModels, ProseMaps, Topology, Find, Queries, Draw, QueryTranslation, Neighbors), what the others show themselves on or build on, declare extension points or are built on by other plugins, and use only surfaces (the query engine, Queries, and the draw engine, Draw, are surfaces every plugin may run, and QueryTranslation turns English into a query for the command line and the app alike); concerns (Validation, Clipboard, Titles, Locking, Publishing, Connections, Mentions, Boards, Transform), a meaning shapes carry or kinds opt into, declare extension points (or a property) and use surfaces and concerns; features (JumpTo, Moving, Snapping, Reordering), a cross-cutting behavior the person uses that nothing builds on, horizontal in reach and a leaf in the graph, declare no kind, no extension point and no property, use surfaces and concerns, and are imported by no plugin (JumpTo on Boards, for how a pick follows a shape, Titles and Topology, for what it lists (a row's tint is its kind's, the core's `registry.label(of:)`), and Keyboard and TextEditing, for ⌘K and its field and list; Moving on SlashCommands, for `/move-to` and `/move-near`, TableOfContents, for the drops that move shapes (`ContentsMoves`), and DrawScript and Geometry, to place a shape as `canvas draw` places one, with its solver and `ObstacleGrid`); languages (Automation, QueryCommands), what agents read and write the canvas in, use surfaces, languages and the wire, never a concern. One may build on another (Queries on Selection and Topology; ProseMaps and QueryTranslation on LanguageModels, QueryTranslation on Queries too; Draw on Queries, to check a query a property holds, and on Topology, to read which kinds stand in for others and can be made to stand for a shape, as an edge to a shape on another board goes through one, and on Adornments, to say how far a shape's title row reaches above it (`canvas measure`); Automation on Draw, for the commands over it; QueryCommands on Automation, Queries, QueryTranslation and the wire; Boards on ContextMenus, DetailPanel, Find, Keyboard, Queries, Selection, TableOfContents and Titles (the table of contents and Find for the board names it heads their lists with); Clipboard on Keyboard, Selection and ContextMenus; Locking on Adornments, ContextMenus, SlashCommands and TableOfContents; Publishing on Adornments, ContextMenus, DetailPanel, Selection, SlashCommands, TableOfContents, Titles and Topology; Connections on Draw, Find, Neighbors, Publishing, Selection, TableOfContents, TextEditing and Topology; Mentions on ContextMenus, DetailPanel, Draw, Find, FuzzyMatching, Neighbors, Queries, Selection, SlashCommands, TableOfContents, TextEditing, Titles, Topology and Validation; Titles on Adornments, DetailPanel, Draw, Find, Queries, SlashCommands, TableOfContents and Validation; Transform on ContextMenus and SlashCommands; Validation on DetailPanel, Draw, Queries and TableOfContents; Adornments, DetailPanel, ContextMenus and TableOfContents on Selection, TableOfContents on DetailPanel too, whose overview its list is; Find on DetailPanel, FuzzyMatching, Geometry, Keyboard, Selection and Topology; Neighbors, what an edge's owner shows its edges on when a shape is hovered, on Queries, to ask the questions its lights are, Selection, for the hover it follows (the canvas's, and the one a list sets for a shape the canvas doesn't show), and Topology, for when a shape's edges change: where a shape on another board is drawn is the file's, and the lights are Connections' and Mentions', which import it; DetailPanel and SlashCommands also on FuzzyMatching and TextEditing; Selection on Keyboard); verticals (StickyNotes, Schemas, Subboards, Frames, References), each a shape kind, use surfaces and concerns, and import no other vertical (StickyNotes and Schemas import TextEditing, for the text view their editors are; Schemas imports ProseMaps, whose map of its description into its schema its highlights are; StickyNotes, Subboards and Schemas import Connections, each for a channel of its own (Subboards for ports on every channel too), and References for ports on every channel and the arrows attached to a pill, and StickyNotes, Subboards, Frames and Schemas import Mentions, notes and schema cards to hold mentions and all four to be mentioned; Subboards builds on Boards; Frames on Selection, for its marquee and its resizing, and on ContextMenus, for Create Frame; Subboards and Frames import Transform, Frames to offer the container channel and Subboards to take it, which is how a frame turns into a subboard though neither names the other; References on Queries and QueryLanguage, to ask what a dynamic reference's query finds, QueryTranslation and LanguageModels, to turn its typed words into a query, and Validation, to warn of a query it can't read); no module joins two others (there are no bridges), and `build.sh` refuses an edge the layers don't allow: a surface importing a concern, a concern, a feature or a vertical importing a language, a language importing a concern, a plugin importing a feature or a vertical. The draw engine (Draw, a surface; Automation is the command line over it) takes what shapes are called, what an edge is, what's wrong with a shape drawn and what a mention's text is from its points, and the concerns fill them, Draw knowing none of them: Titles gives `canvas draw` names, Connections edges, Validation warnings and Mentions text (`TitleNamesPlugin`, `PortEdgesPlugin`, `ValidationChecksPlugin`, `MentionTextsPlugin`), a plugin value for each, so a list without a concern leaves its words out. A word in a language is given by the module that owns its meaning, as a plugin value of its own, through the engine's points; when the owner sits below the engine, the engine's module gives it, so the query engine, Queries (a surface, whose points are `canvas query`'s words), knows no concern, and Titles gives it names, Boards boards' names, Mentions its words and text, Validation its words, and Queries itself the selection's, Selection being below it (`TitleQueriesPlugin`, `BoardQueriesPlugin`, `MentionQueriesPlugin`, `ValidationQueriesPlugin`, `SelectionQueriesPlugin`). The points stay points though one module fills each: AutomationTests and QueriesTests fill them with fixtures of their own. `--ask`'s prompt is in no module: its examples name the shipped kinds (`sticky-note`, `subboard`), which no module knows all of, so it's a text file of the product's (`Shipped/ask-prompt.txt`; below, the product's text files). A horizontal may own the one kind its concern is drawn as (Connections' arrow): Connections holds ports, channels and the arrow, `ArrowPortsPlugin` making arrows the connector (the only code in it that knows both arrows and channels), and being a concern it lets notes and schema cards declare their channels without importing a vertical. A concern imports the surfaces that show it (so Validation imports DetailPanel and TableOfContents, for its Issues tab and its rows' dots, as Titles imports them for its header and its rows' names), and a concern may build on another (Titles and Mentions import Validation, for the rules they add), and a face a plugin list should be able to leave out is a plugin value of its own in the owner's module (`ValidationDetailsPlugin`, `ValidationContentsPlugin`, `MentionValidationPlugin`, `TitleValidationPlugin`, Find's contributors `TitleFindPlugin`, `MentionFindPlugin`, `ArrowFindPlugin`, Neighbors' lights `ArrowLightsPlugin`, `MentionLightsPlugin`, the detail panel's overview and takeover `ContentsOverviewPlugin`, `FindPanelPlugin`, and Boards' headings over the table of contents and Find's list `BoardContentsPlugin`, `BoardFindPlugin`): the registry refuses a contribution whose point's owner isn't installed, so a list with Validation and no panel installs `ValidationPlugin()` alone. The foundation is Geometry, Canvas, DrawScript, QueryLanguage, TextEditing and FuzzyMatching (the core holds what a window puts around its canvas and what the app takes from the plugins besides, points of the core's that plugins fill and CanvasUI and the app read, since the app and CanvasUI may import only the foundation and the wire and no plugin may import CanvasUI: [host slots](host-slots.md); for them it imports SwiftUI and the wire, CanvasRPC, whose types the commands the app's server runs are said in; the last four are libraries beneath the plugins that know no canvas, registry or plugin: the languages `canvas draw` and `canvas query` read, and draw's solver with the grid its obstacles are filed in, pure, which Moving places shapes with too; the app's text editing, the text view and caret list every editable text is built on; and fuzzy matching, which every list that ranks typed text, Find and Jump To are built on). No module lists the plugins or joins two of them: what ships is `Package.swift`'s table (What ships, below), the welcome board is StickyNotes' and the commands Automation's, each through a host slot, and `--ask`'s prompt is a text file. A module is its own, apart from another, only when something must build without the other (the command line without the app) or a layer forbids an import the merged module would need: the host slots are the core's points, so Canvas declares them.
