# Validation

Validation: rules and their issues, the schema rule, what each commit re-checks, rings on the canvas, and where issues show.

Related: [properties and schemas](properties-and-schemas.md), [titles](titles.md), [mentions](mentions.md), [detail panel](detail-panel.md), [table of contents](table-of-contents.md), [queries](queries.md), [command line](command-line.md), [adornments](adornments.md), [drawing](drawing.md) ([every topic](../../CLAUDE.md#map)).

## Architecture

- Validation (a concern) is ESLint's model: rules (`x.validate { shape, context in … }`, `registrar.validate(P.self)`, `validateEveryShape`) find issues on a shape, each `.error` or `.warning`, two channels of one thing; an error makes a shape invalid. Validation's own rule, for every kind, checks each shape against its kind's schema (`registry.schemaViolations(of:)`): each violation is a warning about the property it's in ("Title is 95 characters long, and should be at most 80.", `field: "title"`). The overlay outlines a shape red with an error, orange with warnings alone, and not at all without issues, nor while it's being edited (`editingShapeID`: what it says is still being written), at every zoom. In full, each ring is stroked alone and follows the shape's outline, 3 view points outside where the canvas strokes that: a closed shape's outline stands off its edge `editor.outlineGap` (4) view points ([the editor](editor.md)), so its ring is 7 out of the edge and clear of a selected shape's accent line, the same for every kind, and outside the rings of tinted outlines the core draws round it (Neighbors' lights: `OverlayContext.tintedOutset(of:)`, 4 view points for each ring past the first, counting a selected shape's tint a ring further out and none for an open shape, so a shape two lights outline has its ring 7 + 4 = 11 out, and the overlay grows what it culls by `greatestTintedOutset`), and an open shape's (an arrow's) is on its line, so its ring is 3 out of it (its kind's `indicatorPath`, read through the core's `registry.indicatorPath(of:in:)`, grown by `CGPath.grownOutward(by:isClosed:)`, the core's path arithmetic, which also stands any outline that isn't a rect off its shape, and kept per shape until the shape or its outline changes, or the zoom by more than a tenth, or the standoff, or the tinted outset, `ValidationRings`), and is a rounded rect around the bounds, grown the same, for a shape under 32 points on screen; zoomed out (`OverlayContext.drawsSkeletons`), a map of where the problems are among thousands, each is a ring around the bounds with square corners, grown from no outline (and by the tinted outset, 3 + 4 out of the frame for a shape two lights outline), a run of one color filled as one path in paint order, so a front shape's still covers a back one's (rects in one path cost a fraction of stroking each, 4,800 at 10% in 2.7 ms against 21, while rounded outlines in one path cost ten times each stroked alone); `ValidationResult.worst` allocates nothing, since the overlay reads it for every shape in view. Rules see other shapes only through `ValidationContext` (`context.shape(_:)`, a lookup it notes, and `context.registry`, for a rule over every kind that asks about kinds, which is no lookup; `context.service(_:)` for a rule over what a plugin keeps across the file, nil where shapes are checked without an editor); `ValidationEngine` re-checks the shapes each commit's `ChangeSet` names, those whose rules looked one up, and those a rule's `affected` names (`affected: { changes, editor in … }` on the same three and `ValidationRule`: for a rule that reads a service, the shapes a commit may change the issues of without changing them, on any board, O(changed), asked as the engine hears each commit; on a board it keeps, they're checked once it's taken back). `engine.affected(by:)` is what a commit may change the issues of beyond what it changed (`dependents(of:)` and what the rules named; given `elsewhere`, the table of contents' catch-up on going back, what they named there meanwhile): what `ValidationContentsPlugin`'s marks read again. A rule whose issues follow from what shapes are, never where, says so (`ignoringMoves: true`, on `x.validate`, `registrar.validate(P.self, …)`, `validateEveryShape` and `ValidationRule`; never a rule that measures distances or finds overlaps): a commit that only moves shapes (`ChangeSet.moved`, the shapes a commit only moved with `Transaction.moveBox`, which a drag and `translate` use: a drag moves every shape it drags, every event) runs it for none of them, neither those it moved nor those whose rule looked one of them up, each keeping what it found (kept per shape and per rule, so issues stay in the rules' order), while the other rules run as ever. Validation's schema rule ignores moves (and keeps each shape's verdict until the shape changes other than by moving, for the re-checks a lookup brings), and so does Mentions' (`MentionValidationPlugin`), so a drag of a subboard 100 notes mention re-checks none of them. It checks the board shown (a board never shown isn't checked: its issues show once you enter it), and keeps what it found (issues, lookups, what's left to check) per board in a `BoardStash`, so going back to a board checks nothing. `registry.validationIssues(of:in:editor:)` runs a shape's rules against any `ShapeContext` (a transaction's: `canvas draw`'s warnings, through DrawLexicon's `ValidationChecksPlugin`, with no editor), with schema verdicts of its own, and the editor's services if given one (QueryLexicon's `ValidationQueriesPlugin` passes it). `engine.cachedResult(for:)` is a verdict as the engine holds it, checking nothing (`CachedVerdict`: `.current(result)`, nil for no issues, for a shape on the board shown once the engine has heard every commit and read that board, while the shape isn't waiting to be checked again; else `.unknown`): it never runs a rule, for a reader that mustn't make the engine read a board (a query's `:invalid`, through QueryLexicon's `ValidationQueriesPlugin`, which runs the rules itself where it's unknown). Validation shows the issues itself, in plugin values of its own that a list may leave out (it imports DetailPanel and TableOfContents for them): `ValidationDetailsPlugin` in the panel's Issues tab (worst first; the footer stays empty), `ValidationContentsPlugin` as the dot on a row in the table of contents; and a module that imports Validation may add rules, as Mentions' `MentionValidationPlugin` warns about mentions that can't work ([mentions](mentions.md)) and Titles' `TitleValidationPlugin` about titles two shapes share ([titles](titles.md)).
