# Validation

Validation: rules and their issues, the schema rule, what each commit re-checks, rings on the canvas, a rule's place in a value and rechecking shapes no commit named, and where issues show.

Related: [properties and schemas](properties-and-schemas.md), [titles](titles.md), [mentions](mentions.md), [detail panel](detail-panel.md), [table of contents](table-of-contents.md), [queries](queries.md), [command line](command-line.md), [adornments](adornments.md), [drawing](drawing.md), [types](types.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [A tab of status lines: Validation's Issues tab](../../docs/plugin-system.md#a-tab-of-status-lines-validations-issues-tab), [Marks: Validation's dots](../../docs/plugin-system.md#marks-validations-dots).

## Architecture

- Validation (a concern) is ESLint's model: rules (`x.validate { shape, context in … }`, `registrar.validate(P.self)`, `validateEveryShape`) find issues on a shape, each `.error`, `.warning` or `.incomplete` (`Severity`, in that order of worth): an error makes a shape invalid, a warning only flags it, and the third, under a warning, says the shape still needs something (a value its type calls needed, left empty; any rule may say it) and **shows nowhere on the board** (below). Validation's own rule, for every kind, checks each shape against its kind's schema (`registry.schemaViolations(of:)`): each violation is a warning about the property it's in ("Title is 95 characters long, and should be at most 80.", `field: "title"`). The overlay outlines a shape red with an error, orange with warnings alone, and not at all without issues that show (an `.incomplete` one is not among them), nor while it's being edited (`editingShapeID`: what it says is still being written), at every zoom. In full, each ring is stroked alone and follows the shape's outline, 3 view points outside where the canvas strokes that: a closed shape's outline stands off its edge `editor.outlineGap` (4) view points ([the editor](editor.md)), so its ring is 7 out of the edge and clear of a selected shape's accent line, the same for every kind, and outside the rings of tinted outlines the core draws round it (Neighbors' lights: `OverlayContext.tintedOutset(of:)`, 4 view points for each ring past the first, counting a selected shape's tint a ring further out and none for an open shape, so a shape two lights outline has its ring 7 + 4 = 11 out, and the overlay grows what it culls by `greatestTintedOutset`), and an open shape's (an arrow's) is on its line, so its ring is 3 out of it (its kind's `indicatorPath`, read through the core's `registry.indicatorPath(of:in:)`, grown by `CGPath.grownOutward(by:isClosed:)`, the core's path arithmetic, which also stands any outline that isn't a rect off its shape, and kept per shape until the shape or its outline changes, or the zoom by more than a tenth, or the standoff, or the tinted outset, `ValidationRings`), and is a rounded rect around the bounds, grown the same, for a shape under 32 points on screen; zoomed out (`OverlayContext.drawsSkeletons`), a map of where the problems are among thousands, each is a ring around the bounds with square corners, grown from no outline (and by the tinted outset, 3 + 4 out of the frame for a shape two lights outline), a run of one color filled as one path in paint order, so a front shape's still covers a back one's (rects in one path cost a fraction of stroking each, 4,800 at 10% in 2.7 ms against 21, while rounded outlines in one path cost ten times each stroked alone); `ValidationResult.worst` allocates nothing, since the overlay reads it for every shape in view; it and `worstFirst` (the lists' order) are of the issues that show (`Severity.shows`: an error or a warning), so a shape whose issues are all `.incomplete` has no `worst` and an empty `worstFirst`, and `isValid` is true of it. The engine keeps such a shape's issues like any (its cache, its lookups, what a commit re-checks, `recheck`, `affected`, `touches`, `cachedResult`), and whoever asks for them reads `ValidationResult.issues`. A `ValidationIssue` may say where in its field's value it is (`path`, a JSON Pointer, `.error(_:field:path:)`; nil for the field as a whole), which the engine keeps with the issue and `validationIssues(of:in:)` returns. Rules see other shapes only through `ValidationContext` (`context.shape(_:)`, a lookup it notes, `context.reading`, the file as the shapes read it: the editor's committed one, a transaction's mid-way, nil where nothing is laid out, for a rule that answers from a service's kept state and must not where the file isn't the committed one (`reading.isChanged`), no lookup noted, and `context.registry`, for a rule over every kind that asks about kinds, which is no lookup; `context.service(_:)` for a rule over what a plugin keeps across the file, nil where shapes are checked without an editor); `ValidationEngine` re-checks the shapes each commit's `ChangeSet` names, those whose rules looked one up, and those a rule's `affected` names (`affected: { changes, editor in … }` on the same three and `ValidationRule`: for a rule that reads a service, the shapes a commit may change the issues of without changing them, on any board, O(changed), asked as the engine hears each commit; on a board it keeps, they're checked once it's taken back). `engine.recheck(ids)` checks shapes again though no commit named them, for a rule that reads state outside the shape and the shapes it looks up that changed (a service's: a field's caret left, a type was edited): on the board shown they are unchecked now and the ring redrawn, on a board it keeps they are filed for when it is taken back; it tells the table of contents itself (`contentsDidChange(for:)`, a no-op where there is none, because the table of contents hears a commit and asks `affected(by:)` before a service later in the list can name its shapes), and adds the ids to what `affected(by:)` names for the current revision; nothing for none. `engine.affected(by:)` is what a commit may change the issues of beyond what it changed (`dependents(of:)` and what the rules named; given `elsewhere`, the table of contents' catch-up on going back, what they named there meanwhile): what `ValidationContentsPlugin`'s marks read again. A rule whose issues follow from what shapes are, never where, says so (`ignoringMoves: true`, on `x.validate`, `registrar.validate(P.self, …)`, `validateEveryShape` and `ValidationRule`; never a rule that measures distances or finds overlaps): a commit that only moves shapes (`ChangeSet.moved`, the shapes a commit only moved with `Transaction.moveBox`, which a drag and `translate` use: a drag moves every shape it drags, every event) runs it for none of them, neither those it moved nor those whose rule looked one of them up, each keeping what it found (kept per shape and per rule, so issues stay in the rules' order), while the other rules run as ever. Validation's schema rule ignores moves (and keeps each shape's verdict until the shape changes other than by moving, for the re-checks a lookup brings), and so does Mentions' (`MentionValidationPlugin`), so a drag of a subboard 100 notes mention re-checks none of them. It checks the board shown (a board never shown isn't checked: its issues show once you enter it), and keeps what it found (issues, lookups, what's left to check) per board in a `BoardStash`, so going back to a board checks nothing. `registry.validationIssues(of:in:editor:)` runs a shape's rules against any `ShapeContext` (a transaction's), with schema verdicts of its own, and the editor's services if given one (Validation's `ValidationQueriesPlugin` passes it). `engine.cachedResult(for:)` is a verdict as the engine holds it, checking nothing (`CachedVerdict`: `.current(result)`, nil for no issues, for a shape on the board shown once the engine has heard every commit and read that board, while the shape isn't waiting to be checked again; else `.unknown`): it never runs a rule, for a reader that mustn't make the engine read a board (a query's `:invalid` and `:warned`, through Validation's `ValidationQueriesPlugin`, which runs the rules itself where it's unknown). Validation shows the issues itself, in plugin values of its own that a list may leave out (it imports DetailPanel and TableOfContents for them): `ValidationDetailsPlugin` in the panel's Issues tab (worst first; the footer stays empty), `ValidationContentsPlugin` as the dot on a row in the table of contents; and a module that imports Validation may add rules, as Mentions' `MentionValidationPlugin` warns about mentions that can't work ([mentions](mentions.md)) and Titles' `TitleValidationPlugin` about titles two shapes share ([titles](titles.md)). Its three callers are Types': the caret leaving a field (`FieldChecks.typing`, which Types' wrong-value rule leaves out while it is set), a type's edit (`TypeIndex.onChange`), which a rule's `affected:` cannot serve since it hears a commit before the index does, and a change of relationships (`RelationshipIndex.onChange`: the arrows and notes whose ends, fit or marks moved, so an arrow that no commit touched is a misfit or fits again). The rule over added values (`TypeValidationPlugin`, [types](types.md#checks)) makes a wrong value an error and a needed one an issue of the third level (`.incomplete`: no ring, no Issues line, no dot, not `:invalid`, valid, and `:incomplete`); the Issues tab is made when the panel is, so it shows a caret's leaving the next time, and the ring waits for editing to end, as for any shape.
- Types' value rule also says a note's relationship rows: more than one where a row allows one is an error on the note (`field` the row's name), a Needed row left empty one of the third level, at the row's name ([relationships](relationships.md#the-check-on-a-notes-rows)); the index names the notes whose verdict moved and the check's `recheck` reaches them, and the check makes again the notes whose kept Only one issue says a row name the row is not called now (`rowErrors`), and marks stale the words of those whose kept Needed issue says it (`rowNeeded`, `recheckWords` below), since Validation keeps the words of each issue it holds.
- **What writes touch before they commit.** A rule's `affected` is asked of a commit; a run (`canvas draw`'s, which may never commit) is asked the same of writes still in a transaction: `touches: { changes, shapes in … }` (beside `affected:` on `x.validate`, `registrar.validate(P.self, …)`, `validateEveryShape` and `ValidationRule`), given what the writes did (`transaction.pending`, a `ChangeSet`: added, changed, `moved`, removed, and `elsewhere` for other boards) and the shapes as the writer has them (`transaction.shapes`: its `reading` is the file mid-way, `reading.service(_:)` and `shapes.service(_:)` the editor's services, committed), answers the other shapes, on any board of the file, whose issues the rule may now find differently. It may name more shapes than change (whoever asks compares each one's issues before and after) and never fewer, and it costs what was written and what that reaches, never the board. `registry.validationTouched(by:in:)` is the one function that answers for every rule: each rule's `touches`, and, where the context is an editor's or a transaction's and the engine has checked the board shown, the shapes whose rules looked a written shape up (`engine.dependents(on: changes)`: what the commit would check again, a shape that only moved counting for the rules that don't ignore moves alone), never one of the written shapes themselves. `transaction.pending` is what the commit would hand services, so a board the transaction takes (a subboard's delete) puts every shape the board held in `elsewhere`: a rule reaches what those shapes' going breaks (a relationship that ran to a note on the board, a type root notes were of). A rule that reads which shapes the run leaves (Titles' count of holders of a title) reads them through `reading.shape(inFile:)`, which has none of a board taken. So a rule that reaches other shapes through `context.shape(_:)` alone needs no `touches` (Mentions': a target a run changes so that it cannot be mentioned where it is reaches its mentioners through the kept lookups; a target deleted is no issue, its pill says so); one that reads a service does (Types' and Titles', below). Its caller is `ValidationChecksPlugin`, for `canvas draw`. ValidationTests' `touchesTests` hold it over fixture rules: what a rule names, the engine's lookups (none before it has checked the board, a move reaching only rules that read where shapes are, a shape the delete wrote too left to the writer), a board not shown both ways with its shape checked over `shapes.over(document)`, nothing for a write that reaches nothing, a part of the writes asked alone, and each rule asked once whatever the board holds.
- **Every shipped rule, and what a run can bring to a shape it did not write.** Validation's schema rule: nothing (a shape's own properties against its kind's schema). Types' schema-text rule (`SchemaReadings.issues`): nothing (the type's own text). Types' rule over values and relationships: `touches` is `FieldChecks.touched(by:reading:)` ([types](types.md#checks), [relationships](relationships.md#what-a-runs-writes-reach)): a type restated reaches its instances, a relationship drawn or deleted the notes at its ends, an end drawn or ruled its end types' notes. Types' rule over a type's own warnings (a `$ref` to a type that is gone, a `$title` that titles nothing): it answers over a run's reading (`FieldChecks.typeWarnings(of:reading:)`), and the types it reaches (those that refer to or build on a type written) are named by the rule over values. Mentions' rule: the kept lookups, above. Titles' rule: `touches` names the other holders of a title a run's writes give a shape or take from one, and the rule answers over the run's reading (`TitleIndex.isShared(_:by:in:)`: [titles](titles.md)). References' rule (a pill's query the engine cannot read): nothing (the pill's own query; a shape deleted or made private that a pill stands for is no issue of the pill's, which shows it; an arrow of a relationship type drawn at such a pill is Types').
- `ValidationChecksPlugin` (`ValidationChecks.swift`, Validation's own, filling Draw's `DrawChecks`) gives `canvas draw` the issues a shape it drew would show, checked with no editor, and, of what a run wrote, the other shapes to look at (`validationTouched(by:in:)`) with the command that lists what a run brought to more shapes than it says (`canvas query ":invalid, :warned, :incomplete"`: an error, a warning or what a shape still needs, since a run's count is of all three); a list without Draw leaves it out ([command line](command-line.md)).
- **Who reads a level, and what each does with `.incomplete`.** The rule is that an issue of the third level does what no issue does, everywhere a person looks, and is read where an agent asks. The overlay's ring and its color (`worst`; a shape's ring is let go once only such issues are left) and the zoomed-out ring: none. The Issues tab (`ValidationDetailsPlugin`: `worstFirst`, and `DetailStatus.Tone.init?(_:)`, nil for it) and so the tab's alert in the strip: no line, no tab. The table of contents' dot (`ValidationContentsPlugin`: `worst`, `worstFirst` for its tooltip): none, and a shape with a warning too lists the warning alone. `Severity.color`: clear, never asked. `isValid`: true. Draw's check (`ValidationChecksPlugin`, `DrawIssue.Level`): carried as `.incomplete`; Draw says it only of a shape its run did not write ([command line](command-line.md#what-a-run-brings-to-shapes-it-did-not-write)). The query words (`ValidationQueriesPlugin`): `:invalid`, `:warned` and `:incomplete` are each of their own level alone, so a shape that only needs something is neither of the first two, and an `:incomplete` row lists its issues of that level as `problems` (`class` `needed`). A reader of `results` for the words of an issue of the third level (it may say a name that was just changed: a Needed row's end renamed, a keystroke a key) asks `result(for:)`, which has them current; `recheckWords(_:)` (Types calls it for the notes whose Needed row was renamed) marks a shape's words stale and checks nothing, so a keystroke in an end's label costs no frame the check of every empty note, `cachedResult(for:)` is unknown for it (a query runs the rules) and the shape is checked again by the next commit that names it, by `result(for:)`, or by a commit that only moves it (which checks it with every rule once, as a commit to a stale shape does, so the old words never come back as current). Types' own sources of issues for a type (the Schema tab's status lines read `SchemaReadings.issues`, not this engine) never make one. ValidationTests' `incompleteTests` hold each over a fixture rule of a plugin that is not Types, and AutomationTests' `drawIncompleteTests` Draw's part.
