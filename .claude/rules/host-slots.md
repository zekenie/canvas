# Host slots

What a board's window puts around its canvas, and what the app takes from the plugins besides, said by plugins and placed by the host: views over the canvas, the sidebar, the inspector, the window's subtitle, settings panes, tool tips, the Keyboard Shortcuts window's rows, the menu bar's commands and the keys menus show, what Copy as Image draws and the commands the app's server runs; CanvasUI's `BoardChrome`, the inspector's rule, the panes, the Settings window, the Keyboard Shortcuts window and the menu bar.

Related: [build](build.md), [command line](command-line.md), [detail panel](detail-panel.md), [boards](boards.md), [jump to](jump-to.md), [keyboard](keyboard.md), [language models](language-models.md), [decision models](decision-models.md), [find](find.md), [editor](editor.md), [plugins and kinds](plugins-and-kinds.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Host slots](../../docs/plugin-system.md#host-slots).

## Architecture

- **Why it exists.** A plugin can't import the window (CanvasUI), and the app and CanvasUI may import only the core, so neither can hand the other a view. A module that imported every plugin, Composition, used to join them (`boardChrome`, `detailPanel`, `boardPath`, `coveredTop`, `boardName`, `settings`, `help` and `commands(in:)`); it's gone, and nothing joins them now. The core (`Sources/Canvas/Plugins/HostSlots.swift`, which imports SwiftUI, since its slots hold views, and the wire, whose types the commands are said in) declares what passes between them: eleven extension points, each the core's (`owner` is `.core`, so always installed), each conformed in an extension with a `summary`. A plugin contributes from its own `register`, with no plugin value of its own for it (nothing can be missing), and a list without the plugin is a window without its piece. It knows no plugin and no window.
- **The eleven slots**, what a plugin says and what the host reads (all `Registry` extensions, public):
  - Views over the canvas (`HostOverlays`, a list in plugin order, a later one over an earlier; the report's `host overlay`): `registrar.hostOverlay(alignment:coveredTop:) { editor, onExit in … }` (`alignment` `.center` and `coveredTop` zero by default). Read as `registry.hostOverlays` (`HostOverlay`: `alignment`, `coveredTop`, `view(for:onExit:)`) and `registry.hostCoveredTop(on:)`, the most any says for a board. Not a `CanvasOverlay`, which the canvas draws into itself in the world. Shipped: Boards' path (`.top`, covering `BoardPath.coveredHeight(on:)`), then Jump To's palette, over it.
  - The sidebar (`HostSidebars`, keyed, at most one, a second `RegistryError.conflict`; `host sidebar`): `registrar.hostSidebar(keyboardEntry:) { editor, onExit in … }`: the view, and the view in it that takes the keyboard when the window gives the sidebar the keyboard (none named by default: the window then looks for one). Read as `registry.hostSidebar` (`HostSidebar`: `keyboardEntry`, `view(for:onExit:)`). Shipped: the table of contents' list (`TableOfContentsPlugin`, from its own `register`, its outline the entry: [table of contents](table-of-contents.md)).
  - The inspector (`HostInspectors`, keyed, at most one, a second `RegistryError.conflict`; `host inspector`): `registrar.hostInspector(shownWhile:isRequested:onDismiss:keyboardEntry:) { editor, onExit in … }` (`shownWhile`, whether it has something to show now, read in a view's body, always by default; never requested, nothing on dismissal and no entry named, by default). Read as `registry.hostInspector` (`HostInspector`: `shownWhile`, `isRequested`, `onDismiss`, `keyboardEntry`, `view(for:onExit:)`). Shipped: the detail panel (`DetailPanelPlugin`), with something to show while shapes are selected, requested while a takeover or a band is active (`registry.activeDetailTakeover(in:)`, `activeDetailBand(in:)`), dismissal running that takeover's `onEscape`, then the band's `onCancel`.
  - The window's subtitle (`WindowSubtitles`, keyed, at most one; `window subtitle`): `registrar.windowSubtitle { editor in … }`, nil for none. Read as `registry.windowSubtitle(for:)`. Shipped: Boards, the board shown's crumb's title, none on the root.
  - Settings panes (`SettingsPanes`, keyed by title, in plugin order; `settings pane Claude`): `registrar.settingsPane(title) { … }`, the view made each time the window opens, handed no editor. Read as `registry.settingsPanes` (`SettingsPane`: `title`, `view()`). Shipped: the sign-in's, Claude, which `LanguageModelsPlugin(model:)` adds only when its model is a `SignedInModel`, over that model's account, so the pane and the model read one way, one key and one Claude Code, and a registry built with a test's `ScriptedLanguageModel` has no pane and never points at the app's files ([language models](language-models.md)); then the TypeSafe key's, which `DecisionModelsPlugin(model:)` adds only when its model is a `JevModel` ([decision models](decision-models.md)). The window tells each pane whether it's the first (`EnvironmentValues.settingsPaneTakesFocus`, the core's, true by default), and only the first takes the keyboard as it opens.
  - Tool tips (`ToolTips`, keyed, at most one; `tool tips`): `registrar.toolTips { tool, registry in … }`. Read as `registry.toolTip(for:)`, the tool's label without one. Shipped: Keyboard, `registry.help(for:)` ("Note (N)").
  - The Keyboard Shortcuts window's rows (`KeyboardHelp`, keyed, at most one; `keyboard help`): `registrar.keyboardHelp { registry in … }`, `[KeyboardHelpRow]` (`keys` as they're written, `title`, `place`: `.tool`, `.command(c)`, `.canvas`, `.pointer`, `.text`), read off the built registry. And key hints (`KeyHints`, a list in plugin order; `key hint ⌥ Drag Drag a Copy`): `registrar.keyHint(keys, title, while: .pointer | .text)`, a key no shortcut has, said beside the code that reads it. Read together as `registry.keyboardHelp`, the list's rows then the hints, each row once; none with neither. Shipped: Keyboard's rows (`keyboardHelpRows`) and every plugin's hints ([keyboard](keyboard.md)).
  - The menu bar's commands, and the keys menus show (`MenuKeys`, keyed, at most one; `menu keys`): a command a plugin declares in a section (`registrar.command(… in:placed:…)`, the core's Commands point: [editor](editor.md)) is in the menu bar, read as `registry.menuBarCommands` (`MenuBarCommand`: `command`, `title`, `section`, the `MenuBarSection` it's in, `placement`, its place among the section's items, `menu`, the section's menu as a `MenuPath`, and `key`, a `MenuKey`, in plugin order), which the window arranges with its own items, section by section ([keyboard](keyboard.md), the menu bar); the keys an item has for a command are the plugin's that keeps the keys, `registrar.menuKeys { command, registry in … }` (`[MenuKey]`, each the key equivalent as a menu item takes it and the `Modifiers`, `modifierFlags` for the item, the one the item shows first), read as `registry.menuKey(of:)`, the first, nil for none, which a context menu's items read too, and `registry.menuKeys(of:)`, all of them, whose others held with ⌘ or ⌃ the menu bar answers through hidden items ([keyboard](keyboard.md)). Shipped: Keyboard, every key registered to run the command, in the order registered (`KeyChord.menuKey`).
  - What Copy as Image draws (`ImageSources`, keyed, at most one, a second `RegistryError.conflict`; `image source`): `registrar.imageSource(isAvailable:_:)`: `isAvailable: (CanvasEditor) -> Bool`, asked as the menu item is validated, so cheap, and the shapes, `(CanvasEditor) -> [ShapeID]`, those of the board shown to draw, back to front, none for nothing. Read as `registry.imageSource` (`ImageSource`: `isAvailable`, `shapes(for:)`), nil where no plugin says. Shipped: Clipboard, over `editor.canCopyAsImage` and `editor.imageShapes()`: the shapes a copy of the selection would take, or every copyable shape of the board shown with nothing selected ([clipboard](clipboard.md)).
  - The commands (`HostCommands`, keyed, at most one; `host commands`): `registrar.hostCommands(specs:run:)`, what the command line shows of each command and how to run one by name, both handed the frozen registry (the commands are every plugin's, known only once it's built). Read as `registry.hostCommands`, `(specs, run)`: no specs, and every name `unknown_command`, where no plugin gives any. The one slot said in the wire's types (`CommandSpec`, `JSON`, `RPCError`). Shipped: Automation, over `automationCommands` and `runAutomationCommand` ([command line](command-line.md)).
- **A view a plugin gives** is made for a window's canvas: handed that board's editor and `onExit`, which gives the keyboard back to the canvas (`CanvasFocus.take`), and it follows the editor by itself. A view over the canvas is over the whole of it and takes clicks only where it draws.
- **The window's side** (CanvasUI, which knows no plugin):
  - `BoardChrome(editor:showsSidebar:showsInspector:onExit:)` (`Sources/CanvasUI/BoardChrome.swift`), a public view modifier the app applies to its `CanvasRepresentable` after its frame and toolbar: each registered overlay folded onto the canvas with `.overlay(alignment:)`, in plugin order, then, if an inspector is registered, SwiftUI's `.inspector(isPresented:)` on the canvas with its toolbar button (Inspector, `sidebar.trailing`, its tooltip "Show Inspector" or "Hide Inspector": `ChromeStyle`; disabled while `!canToggle`). With a sidebar registered the canvas, with its overlays and its inspector, is the detail column of SwiftUI's `NavigationSplitView(columnVisibility:)` and the slot's view the sidebar column, shown while `showsSidebar` (`.all` or `.detailOnly`), with a toolbar button at the toolbar's leading end (`.navigation` placement, where it stays while the sidebar is hidden: Sidebar, `sidebar.leading`, its tooltip "Show Sidebar" or "Hide Sidebar"). No sidebar registered, no split view; no inspector, no `.inspector`. A view in the sidebar that has the keyboard as it hides gives it back to the canvas itself, as the inspector's does (the table of contents' list says when it is hidden: `onHide`). `BoardViewState.showsSidebar` (true by default) is remembered per file with `showsDetails` and `showsMinimap` (`BoardViewMemory.View.showsSidebar`; an entry from before reads as true: [boards on disk](boards-on-disk.md)), and the app's `ContentView` binds it (`showsSidebar: $view.showsSidebar`).
  - The inspector's rule, public API on `HostInspector` (CanvasUI's `BoardChrome.swift`), shared by the toolbar button and the View menu: `isShown(in:chosen:)` is `isRequested || (chosen && shownWhile)`; `canToggle(in:chosen:)` is `isShown || shownWhile`; `toggle(in:chosen:onExit:)` hides what shows (`chosen` becomes false, and if something wanted it, `onDismiss` then `onExit`) and shows what doesn't (`chosen` becomes true). `chosen` is the window's `showsDetails`, the person's choice. A request (Find's takeover) shows the inspector by the rule without changing the person's choice, and when it ends the inspector is as they chose (and as there is something to show). It slides in beside the canvas, narrowing it, as a shape is selected; the core keeps what was just revealed or selected in view meanwhile ([editor](editor.md), a view kept while the view settles). The body reads the rule, so the window follows the selection and a takeover, and the `.inspector`'s binding sets through `toggle` too, as AppKit hiding the column does. Generic over whatever requests it: the window has never heard of Find, whose ⌘F shows a hidden inspector through the detail panel's takeover ([find](find.md), [detail panel](detail-panel.md)).
  - What the canvas covers: `BoardDocument` sets each board's `editor.coveredTop` to `registry.hostCoveredTop(on:)` (host API, [editor](editor.md)), so a fit leaves the path's pill clear. A headless editor is told nothing and covers nothing, which is why this stays the window's to say and isn't a core point the editor reads.
  - The subtitle: `BoardWindowController` reads `registry.windowSubtitle(for:)` observed, so it follows a switch of board or a rename; with no plugin saying one it reads nothing, and is never read again.
  - `SettingsWindow` (moved here from Composition): `SettingsWindow(registry:)` hosts `registry.settingsPanes` one under another (`SettingsPanesView`), unheaded, since a pane says what it is itself; `init(autosaveName:content:)` hosts any view. Made afresh each time it opens, sized before it goes in. It and the Keyboard Shortcuts window are a `SecondaryWindow` (`SecondaryWindow.swift`, an `NSWindow` whose `cancelOperation:` is Close), so Escape and ⌘. close them when nothing inside took the key (P5, P6). A key's rows (LanguageModels' `KeyRows`: the Claude pane's on the API key's way, and every `KeySettingsView`'s, TypeSafe's pane) put the keyboard in the field as the pane appears when it's the window's first (`@FocusState`, `settingsPaneTakesFocus`), make Save the default action while the field has the keyboard (Return saves the key typed there), say each status as it changes (`KeySettings.announce`, an announcement; tests set it) and give the status line `statusHelp` as its accessibility hint; Tab goes down from one pane's field to the next.
  - `ToolPicker(editor:)` reads `registry.toolTip(for:)`; it takes no `help:` closure. It shows the tool lock on the selected segment ([keyboard](keyboard.md)).
  - The menu bar: `BoardMenus.make(appName:registry:editor:)` (the app's `BoardMenus.install(appName:registry:)`), the window's own items and the commands placed in it, each item carrying its command (`BoardMenus.command(of:)`), followed by a hidden item for each other key of its command held with ⌘ or ⌃ (`BoardMenus.addOtherKeys`: Go › Back's ⌃-), and sending `BoardWindowController.runCommand:`, the controller's one action for every command, whose one validation dims an item while `editor.canPerform` says no and while text has the keyboard for a `.whenIdle` command, and retitles it by `editor.menuTitle(of:)`. Edit's Undo, Redo, Cut, Copy, Paste, Delete and Select All are AppKit's own, run on the board as the commands that answer them (`editor.perform(answering:)`): the window's `undo:` and `redo:`, the controller's `cut:`, `copy:` and `paste:`, the canvas's `delete:` and `selectAll:` ([keyboard](keyboard.md)).
  - Panes (P1, P3 of [keyboard navigation](keyboard-navigation.md)). `HostSidebar.keyboardEntry` and `HostInspector.keyboardEntry` (optional, `registrar.hostSidebar(keyboardEntry:)` and `registrar.hostInspector(keyboardEntry:)`) are the views each says takes the keyboard now (the table of contents declares its outline, the detail panel its header's field). View › Focus Sidebar (⌥⌘S, `focusSidebar:`, enabled with a `hostSidebar`) shows a hidden sidebar and gives the keyboard to `sidebarKeyView()`: the declared entry, else by kind among the window content's views before the canvas; with nothing there to take it (an empty board's list) it leaves the keyboard where it is. View › Focus Inspector (⌥⌘I, `focusInspector:`) is enabled while `canToggle`, shows the inspector by the person's choice if the rule doesn't show it, and gives the keyboard to `inspectorKeyView()`: the declared entry, else by kind among the views after the canvas, never the sidebar's list, and when the panel has none at all (after the retries a just-shown inspector needs) to the window's hosting view, so Tab enters the loop: it never stops silently. By kind is `keyView(in:)`: of the window content's views that are shown, accept first responder, aren't scroll or clip views and are on that side of the canvas (`side(of:canvas:)`; what's over the canvas, the path's crumbs, is inside its frame), a table (`NSTableView`), text field or text view before any other control, the topmost then the leftmost of its kind; both try again each 16 ms for up to 30 turns while a pane just shown has no views yet (`InspectorFocusStyle`, `editor.scheduler`). View › Focus Next Pane (F6) and Focus Previous Pane (⇧F6) are `BoardWindowController`'s (`focusNextPane:`, `focusPreviousPane:`, placed after the inspector tabs) and move the keyboard round the panes shown (`Pane`: `.canvas`, `.inspector`, `.toolbar`, `.sidebar`; `shownPanes()`: the canvas; the inspector while the rule shows it; the toolbar while it is visible and one of its items' views, or a view in one, takes the keyboard; the sidebar while it is shown and a host sidebar exists), so F6 goes canvas, inspector, toolbar, sidebar and round, and ⇧F6 is the exact inverse. `currentPane()` reads where the keyboard is by the first responder: the toolbar's views are the toolbar's pane; of the window's content, a view is in the pane its middle is in (`side(of:canvas:)`): in the canvas's frame the canvas's (so a view the window puts over the canvas, the board path or Jump To's field, is the canvas's pane), before the canvas the sidebar's, after it the inspector's; the content (hosting) view itself, where Focus Inspector's last resort leaves it, the inspector's; nowhere, on the window itself: F6 then goes to the second pane, ⇧F6 to the last. A shape being edited ends first, and the way back to the canvas is `CanvasFocus.take`. Escape in the toolbar, which takes no text, or on the bare hosting view, gives the keyboard back to the canvas (`BoardWindow.escapeToCanvas`, the selection kept), with Caps Lock on too (`Modifiers(event.modifierFlags)`, the four that change a key). Ctrl-F6 is the system's floating-window key and F6 may need fn on a laptop, which is why the items name F6 in the window. The toolbar's item views exist only once the window is on screen, so CompositionTests' `inspectorFocusShippedTests` put a segmented control into the unshown toolbar's item view.
  - `BoardWindowController`'s own items, with no command: Edit › Copy as Image (⇧⌘C, `copyAsImage:`) is dimmed unless `registry.imageSource?.isAvailable` and otherwise draws `source.shapes(for:)` from the board's own file with `BoardPicture(file: editor.file, registry:, board: editor.board, showing:)` (the whole file in the picture's editor, as opening it reads it, so the file's own colors, the types notes are of and what mentions name are there to read, wherever they are; only those shapes drawn, the core's `editor.drawnShapes`, and fitted; a big file costs what opening it does; `picture.inset = ImageCopyStyle.inset`, 32 points of margin in all; `pngData(within: ImageCopyStyle.limit, scale: ImageCopyStyle.scale, appearance:)`: at most 2048 × 2048 points, 2 pixels to a point, in the window's `effectiveAppearance`, the PNG's resolution saying so) and writes the PNG to `BoardConfiguration.imagePasteboard` (`.general` in the app, so `BoardConfiguration(registry:imagePasteboard:content:)`; a test passes its own, as CompositionTests' `configureBoards(pasteboard:)` does, and no test reads or writes the general one); View › Show Sidebar (⌃⌘S, `toggleSidebarShown:`, titled Show or Hide Sidebar, enabled with a `hostSidebar`) and Focus Sidebar (⌥⌘S); View › Show Inspector (⌃⌘I, `toggleDetails:`), the rule's `toggle`, titled by `isShown` and enabled while `canToggle` (so dimmed with nothing selected and nothing wanting the inspector), and Focus Inspector (⌥⌘I), enabled likewise: how each gives the keyboard is the panes' above. Escape from the sidebar or the inspector gives the keyboard back to the canvas through the view's `onExit` ([detail panel](detail-panel.md), [table of contents](table-of-contents.md)).
  - `KeyboardShortcutsWindow(registry:menu:autosaveName:)`: Help › Keyboard Shortcuts (⌥⌘/), `registry.keyboardHelp` and the menu bar filed into sections (`KeyboardShortcutSection.sections(menu:rows:)`, [keyboard](keyboard.md)), made afresh each time it opens, as Settings is: its rows read again and its list a new view under an identity per opening (`KeyboardShortcutsView.opening`; a hosting controller keeps its root's state when the root is replaced), so nothing typed last time stays, and the search is given the keyboard again (AppKit does it only as a window is first shown). It opens with a search field focused (`KeyboardShortcutSection.filtered(_:by:)`: `FuzzyMatcher` over a row's title and each of its keys, best first, a section with no match gone); a row is one accessibility element reading "Title, keys" (`Row.spoken`) and a section title is a header; the rows are still generated, never written by hand (P6, P9).
  - `BoardConfiguration(registry:content:)` has no `coveredTop` or `boardName`: both come with the registry.
  - `CommandServer.Commands(registry:)` is `registry.hostCommands`, what the server runs beyond its own.
- **The app** (`Sources/InfiniteCanvas/InfiniteCanvasApp.swift`) imports Canvas and CanvasUI, and no plugin: it builds the registry from the product's list, each plugin made by its name (`Registry(plugins: ShippedList.plugins())`, [build](build.md), What ships), hands it to `BoardConfiguration`, `SettingsWindow(registry:)`, `KeyboardShortcutsWindow(registry:)`, `BoardMenus.install(appName:registry:)` and `CommandServer.Commands(registry:)`, opens a new, empty board when it's launched with nothing to open, and its `ContentView` is the canvas, the toolbar's `ToolPicker`, and `BoardChrome`.
- **Adding a slot**: a point in `HostSlots.swift` owned by `.core`, its sugar on `PluginRegistrar`, a public reader on `Registry`, and the window's use of it in CanvasUI. Never a module that imports both sides, and never a plugin's type in CanvasUI or the app.
