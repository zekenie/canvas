# The detail panel

The detail panel: sections, tabs and status lines (one tab drawn on its own: `DetailTabView`), headers, bindings, read-only shapes, text boxes, list rows (a row, a group's header, a search field, the list with a highlight in its caller's binding, pages of its own, a share of the panel's height and a click of its own), the code editor with its completions, board headings (what a board's shapes list is headed by, from the plugin that names boards), and its takeovers and bands (what it shows in place of a shape's details or over them, from other plugins, the shipped ones' contributors, and where Escape and ⌘. go, told apart).

Related: [fuzzy matching](fuzzy-matching.md), [table of contents](table-of-contents.md), [find](find.md), [text editing](text-editing.md), [titles](titles.md), [validation](validation.md), [mentions](mentions.md), [neighbors](neighbors.md), [boards](boards.md), [types](types.md), [locking](locking.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [The detail panel](../../docs/plugin-system.md#the-detail-panel).

## Architecture

- The detail panel (DetailPanel, platform, a horizontal in the window) lays out a header, tabs, sections and a footer; plugins fill them with `x.details { DetailSection("…", in: SomeTab.self) { $x in … } }` and `scope.detailStatus` (on the kinds a scope reaches: [plugins and kinds](plugins-and-kinds.md)): status lines, the shape's state rather than its settings, in the footer, or with `in: SomeTab.self` in a tab that shows only while the shape has lines there (Validation's Issues tab, `ValidationDetailsPlugin`), and whose title in the strip follows its worst line's symbol while that warns or errs (`layout.alert(in:)`); a line may carry buttons (`DetailStatus.actions`, `DetailStatusAction`s, drawn under it by `StatusList` as a `DetailStatusLine`'s: Validation's issues' Ignore and Show Rule), and two lines are the same when their text, tone and buttons' titles are (`==` and `hash` by hand), so the panel draws a shape again for a button that comes or goes and not for a closure made anew. A tab is a type (`DetailTab`) any plugin may declare, and its `order` (an `Order`, [plugins and kinds](plugins-and-kinds.md)) says where it goes among a shape's tabs: by default where it first appears (a kind's own contributions first, then the rest in plugin order: Types' Types tab, then Neighbors' Connections, on every shape, always: [neighbors](neighbors.md)); a kind's own tabs are `.first` (a reference's Reference, a subboard's Description, before the Types tab a typed subboard has, so a typed subboard's tabs are Description, Types, Connections and Style and a typed frame's open on Types), so a feature's tab that its opt-in brings from the kind's own `register`, saying nothing, still goes after them; `StyleTab` is `.last`, as a shared tab trails in Keynote; Types' Schema is `.after(NeighborsTab.self)`, so a type's panel opens on what is connected to it ([types](types.md)); Validation's Issues, a tab of the shape's state that comes and goes, is `.after(StyleTab.self)`, so the others keep their places. The report names the tabs a contribution's sections fill, each with its order if it says one (`ShapeDetails in Schema after Connections → every shape holding schema`, `DetailStatuses in Issues after Style → every shape`), and the registry refuses tabs placed beside each other in a circle. A section with no title, one row whose own label says what it is, names its undo steps with `.named("Color")` ("Change Color"; without it a headerless section's steps are named for the kind): Colors' row in the Style tab, which so costs the panel one line. A section whose showing is the shape's state says when with `.shownWhile { shape, context in … }` (Types' Fields: while the shape's types give it a field or it holds a value; a reference's Matches: while its query has found shapes), asked on every commit beside the status lines, whatever the commit changed, so it reads a service's cached state, O(1), and only the sections that have one are asked (found once per kind); a tab shows only while it has a section shown or status lines, and the shape's panel draws again only when its record, whether it can change, its status lines or the sections `shownWhile` hides change (`panelsDrawn`, debug builds, counts it drawn). A titled section few people need is collapsed until the person opens it (`.collapsedUntilOpened()`, as Finder's Get Info keeps Sharing & Permissions folded: Types' Advanced, the box that turns off filling a note's fields from its words), then is as they leave it: `DetailPanelState` remembers what the person collapsed and opened by key (`isCollapsed`, `setCollapsed`), a section they haven't touched as it starts, and a headerless one never collapses (DetailPanelTests' `stateTests`). `scope.details { DetailSection<AnyShapeRecord> … }` puts sections on every shape of the kinds a scope reaches, over the whole record (`ShapeBinding<AnyShapeRecord>.record`): `registrar.forShapes(holding: ColorProperty.self) { $0.details { … } }`, Colors' row on the kinds that have colors, and `forEveryShape`, Neighbors' Connections; a section that shows only in some state says so with `shownWhile` (both `ShapeDetails` and `DetailStatuses` take scopes, so a section or a line for every kind with none is refused). Beside it is `detailsForEveryBox`, on the kinds whose shapes are boxes (`.adopting(.box)`). `DetailCheckbox(_:isOn:)` (a label-hidden `Toggle` and a `Text` that toggles on click, `smallSpacing` apart, the text hidden from assistive apps, which read the title as the toggle's) is a `LabeledContent` row's checkbox that reads "Label [] Title" on macOS 14 and 15; `DetailShapeRow(symbol:tint:name:detail:detailTruncation:place:lines:dimmed:)` is a list row for a shape on `DetailStyle`'s own internal metrics (status icon column, 11 pt name, 10 pt secondary detail, cut at its start when too long (`detailTruncation: .head`, for a path), or, for an address given as `place` (`PlaceStep`s), folded in the room the name leaves it, a share of the row at least (`DetailStyle.placeShare`), as every address is (`PlaceFold`, in `DetailPlaceText`: boards semibold, an untitled container's name and the marks fainter; the row's width is read by a `GeometryReader` into its state, all of it until then) or at its end (`.tail`, for a value read from its start: the issue list's first value), and up to two lines, `dimmed` dims the whole row); `DetailGroupHeader(_:count:tint:isCollapsed:isRow:toggle:)` is the head of a list of rows inside a section, which folds it (one borderless button, or with `isRow` a plain line, a row of a `DetailRowList`, at a section header's height: a disclosure triangle, a dot in `tint` when the list has a color of its own, the title and, if given, the count; the caller keeps whether it's folded and leaves the rows out while it is); `DetailSearchField(_:text:list:)` is a field that searches such a list (a magnifying glass, the text typed as keyed, nothing corrected, and once there's text a button that clears it, a list row's height; ↓ goes into the list its `DetailListHandle` names, and Escape clears the text first); all of them, and `DetailRowList`, in `ListRows.swift` (DetailPanelTests' ListRowTests). A horizontal's feature is opt-in sugar on `ShapeRegistrar` that contributes to its own point and may call `details`, so opting in can bring a tab (Types' Types tab, over `is`; `x.opensBoard(…)` brings none). An added property's sections are over its value: `x.details(of: P.self) { DetailSection(…) { $value in … } }`, or on `PluginRegistrar` for every shape that has it (scoped `.holding(P)`: the report's `ShapeDetails → every shape holding schema`, Types' Schema tab); a kind's own sections and header read added values through `$x.shape`, the whole record (`$note.shape[TitleProperty.self]`), and bind one, nil while the shape has none, with `$x[P.self]` (a `Binding<P.Value?>`, as `TitleHeader($x)` does; the bindings one `$x` makes of its added properties read back the last write through any of them; on a kind that doesn't opt in, it reads nil and drops writes, and `$x.holds(P.self)` says which, so `TitleHeader($x)` on a kind that doesn't opt into titles stops a debug build). `DetailCommandButton(command:title:systemImage:)` (or `command:label:`, a view of its own as the label, a band's count) runs a declared command (`editor.perform`, on the selection, which is what the panel shows), dimmed while `editor.canPerform` says no, titled as the command is (`registry.title(of:)`) unless `title` says otherwise, its tooltip the title and the command's key (Keyboard's `registry.help(_:forCommand:)`, which DetailPanel imports Keyboard for; none for a command with no key, whose label says it all); **a button that has the keyboard is never disabled under it**: its command may turn off while the keyboard is on it (End Issue Walk in the update that takes a band's Done away, a step when a drag begins on the canvas, Issue List when Find opens), and a disabled control that has the keyboard hands it to the window in the middle of that update (an AttributeGraph cycle, and with Keyboard navigation on the keyboard left on the window). So while it has the keyboard it stays enabled, its press doing nothing while the command can't run (`perform` refuses), drawn at `dimmedRow` strength and spoken with the value "dimmed", and it is dimmed for real once the keyboard leaves it. It asks AppKit as its body is made (`ButtonKeyboard.holds`: the window's first responder is the control at the button's own place, rect for rect, found through a background probe view; a control that only covers it, a list's table scrolled up under the band, is not it) and is made again as the window's `firstResponder` moves (the probe's observation, a turn later), so it follows `makeFirstResponder` as Tab and a click do; the header's back button is Selection's `.goBack` the same way, called and keyed as the command is and shown while its rule says there's a step back (`canPerform(_:on:)`, the rule alone, so a press on the canvas doesn't take it away): the panel's counterpart of a menu item (it reads the editor from the panel's environment, `\.detailEditor`). A number being typed is committed in `boardWillChange` (`DraftTracker.commit`), so it lands on its shape before another board is shown. Sections write only through `$x.field` or `$x.update` (one transaction each, on the live shape, which the binding reads back until the panel redraws; a field's writes, one after another, are one undo step, and `$x.update(\.field) { … }` runs with them for a field written through a method), bind the narrowest key path, and use `LabeledContent` and DetailPanel's primitives, never their own layout or fonts (the one exception is Types' `FieldForm`, which a section places whole on a line of its own under a field's name, the section's full width: one AppKit view in `DetailStyle.textFont` with a layout, a text editor and a JSON box of its own, since a form of nested rows needs keys no SwiftUI control gives: [types](types.md)): among them `DetailTextArea` (its words' spelling checked as the app's is, `Spelling.app`; with `placeholder:`, and `onCommit:`, which makes Return commit, ⇧↩ a new line, and the keyboard leaving commit too, a turn later if the view left the window with it, so a commit captures its service weakly), `DetailCodeEditor` (code typed as keyed: monospaced, every substitution, automatic completion, prediction and Writing Tools off; lines never wrap; as tall as its lines, from `DetailStyle.codeEditorHeight`, a text area's 76, to what the panel shows; ⌘↩ and the keyboard leaving commit; `coloring:` names its runs, `DetailCodeSpan`, and the panel colors them, red only for `.invalid`; `completions:`, a `DetailCodeCompleting`, says what can be typed at the caret, UTF-16 in, a `DetailCodeCompletions` out (TextEditing's `CaretCompletions` by another name, which a row written as a line offers too: [text editing](text-editing.md)): the `range` a pick replaces, which holds the caret, the `query` typed so far, and every candidate as offered, unfiltered, each a `DetailCodeCompletion`, its `label`, `detail`, `insert`, the `selection` within it a pick leaves, `reopens` and `isRelevant`; ⌃Space, and AppKit's `complete:` (⌥⎋, F5), opens it in the app's one caret list (TextEditing's) while the text can be written and something's offered, else nothing, no beep: under what's typed, each label in the code's font, matched in its semibold, its detail after it, VoiceOver saying both, ranked with `FuzzyMatcher` (FuzzyMatching's, as every list ranks) (nothing typed: as offered; else by tier, then `isRelevant`, then as offered; what doesn't match left out); while it's open ↑ ↓ ⌃P ⌃N and Page Up and Down move, Return, Enter and Tab pick, Escape, ⌘., ⌃Space, ⌥⎋ and F5 close it, ⌘↩ closes it and commits, and the rest is the text's; it asks again after every keystroke and move of the caret, and closes once nothing's listed, the caret leaves the place it opened for (the range starts elsewhere), the text is shown from outside or can't be written, the keyboard or the window goes, the window resigns key, or what's typed scrolls out of view; a pick is `insertText` over the range between two `breakUndoCoalescing()`, one step of the text's undo that the box writes as typing, and one that `reopens` opens it again; `onCompleting:` hears it open and close (a pick that opens it again, not at all), for what waits on the person's choosing (a type's sync); without `completions`, F5 does nothing and ⌥⎋ leaves the panel: code gets no dictionary words), `.detailUpdating(_:)` (read-only and dimmed while something else writes the box; the words go on a status line where the person is, never over the text), and `DetailStatusLine` (a tone's symbol or, `isBusy`, a spinner, one width so the text doesn't move, then the text, which takes no tone and can be selected and copied (a line whose selected text has the keyboard as it goes hands it back to the canvas), with `DetailStatusAction` buttons under it). Text that isn't a string edits in a `DetailTextBox(value, height:placeholder:onCommit:make:)`, a box as a text area's (the panel's own, `DetailCodeEditor` and `DetailTextArea`, with `onCommit:` or without, are boxes over `PlainTextView`, on TextKit 1 as they always were: a text area's words checked as the app checks spelling, a code editor's code never), over the view `make` returns: a subclass of `EditingTextView` (TextEditing's: [text editing](text-editing.md)) that adopts `DetailTextContent` (`value`, which the box writes to the binding on every change, and `show(_:)`, which the box calls only when the binding changed from outside, an undo or another plugin's write: the storage alone, never `didChangeText`, since the board may be applying a step, and then the box drops typing's undo), set in `DetailStyle.textFont` (the panel's text, 11 pt), as Mentions' `MentionTextArea` is. A box's first text baseline is its first line's (`DetailStyle.textBaseline`, `codeBaseline` for a code editor: the box's padding and the font's baseline in its line, `detailTextBox(height:baseline:)`'s alignment guide, since an AppKit view tells SwiftUI none, and SwiftUI then lines a row up on its top edge), so a `LabeledContent` row's label sits on the text's line; a box in another font than the panel's text passes its own `baseline`. The panel's root hears Escape before the view does, and lets it through only to a view holding keys, and drops a draft first (a number being typed, a search field's text: `DraftTracker.pending`; the first Escape reverts it and the field stays, the next leaves), and ⌥⎋ to a view that `offersCompletions` (a code editor with completions it can write), list or not; ⌘. with no list open goes on up and leaves the panel from its root (`onExitCommand`). Disabled (a read-only shape's section, `detailUpdating`), a box is read-only and dimmed by its view (`showEnabled(false)`), never by SwiftUI, which would take every click over it: its text is still selected and copied, and its clicks land (a pill followed), but it never commits (`onCommit`): nothing was written. A section reaches a service of its plugin's with `$x.service(S.self)` (a type's `TypeSync`), never the editor, and `$x.shapeID` is the shape a binding writes, whatever its value. A read-only shape's panel (a locked one, one in a locked frame, or one on a locked subboard's board) shows everything with its sections' controls and its header disabled (`editor.isReadOnly(id)`, asked on every commit where the panel's root reads the shape's record, O(the shape's depth), and handed to the shape's panel, which never reads the document and draws again only when it changes: a container locked or unlocked, the shape joining or leaving one, a lock landing above its board in a commit on another), but a section's that changes nothing of the shape (`DetailSection(…).enabledWhileReadOnly()`: References' Go to Original, Neighbors' Connections lists); Back, the tabs and collapsing still work. The header is a view made from the shape's binding too, `x.details(header: { $x in DetailHeader("…") }) { … }`: a `DetailHeader`, or a view of the kind's own built on `DetailHeaderLabel` (its subtitle may be an address, `place:` and `lead:` ("Note · "): folded in the header's width less the symbol's column (`PlaceFold`) and always one line, its help the whole `subtitle` while it is folded or cut, and what VoiceOver reads the whole `subtitle` always; `DetailPlaceText(steps:lead:room:size:wraps:)` is the line, public, whole and wrapped where a panel shows the place in full) (with `DetailHeaderField` for a title renamed in place, an AppKit field, `HeaderTitleField`, drawn pixel for pixel as SwiftUI's plain one was, whose field editor is an `EditingTextView` of its own (`HeaderField.editor`, which its cell hands AppKit, keeping nothing itself, since AppKit may copy a cell bit for bit) that checks the title's spelling as the app does, since SwiftUI's fields can't be told to, and tests still find it as an `NSTextField`; `isEditable: false` shows it as text at full strength, for a title that can't be written just now), so every header looks alike, and as the table of contents' does (the window's look, Chrome's `ChromeStyle`, which `DetailStyle` reads: 44 points tall, 16 in, the symbol 15 points and dimmed in a 20-point column, the title 13 semibold, and in the window's inspector the title bar's row (below, the title bar's row); a chosen tab on the chrome's selected fill, and tabs and text boxes rounded as an item is, 6 points, a box's padding round its text staying 4, `fieldPadding`); the panel hands it the kind's name and symbol through the environment, and tests read it back with `layout.header` or `layout.header(as:)`. Keep the sugar's closure types unannotated, and never name `Transaction` in a file that imports SwiftUI. The window places it: `DetailPanelPlugin` gives `DetailPanelView(editor:onExit:)` as the window's inspector (`registrar.hostInspector`, the host's slot for one: [host slots](host-slots.md)), which CanvasUI's `BoardChrome` puts in its inspector's sheet over the canvas's trailing edge, as wide as `registrar.hostInspector(width:)` says (`DetailStyle.minWidth`, `idealWidth`, `maxWidth`: 248, 260, 340; the panel sets no width of its own), with `onExit` set to `CanvasFocus.take`, which gives the keyboard back to the canvas. It says the inspector has something to show while shapes are selected (`shownWhile: { !$0.selectedShapeIDs.isEmpty }`, so with nothing selected the window hides the panel, whatever the person chose), that it is wanted while a takeover is active (`registry.activeDetailTakeover(in:)`), and that dismissing it runs that takeover's `onEscape`, so the window shows the inspector for a takeover whatever the person chose and whatever is selected, leaves it as they chose (and as there is something to show) once the takeover ends, and escapes the takeover when the person hides the inspector meanwhile, knowing nothing of what took the panel over ([host slots](host-slots.md) holds the rule).
- What the panel shows in place of everything is a point of its own, in `Sources/DetailPanel/DetailTakeovers.swift` (beside it are two more points, bands, which show over the panel, and board headings, both below), which `DetailPanelView(editor:onExit:)` reads from the editor's registry itself (it takes nothing else), making each view as it's made (in its `init`, handed its editor and `onExit`), so it never learns what any is. **Takeovers** (`DetailTakeovers`, a list in plugin order, the first that's active showing; the report's `detail takeover`): `registrar.detailTakeover(isActive:onEscape:) { editor, onExit in … }` (`isActive: (CanvasEditor) -> Bool`, `onEscape: (CanvasEditor) -> Void`, and the view): while `isActive` holds the panel shows the view in place of everything else, every selection branch included, with the panel's environment, frame and width as ever. `isActive` is read in the body, so it reads observable state and the panel redraws only when it flips. Escape and ⌘. in the panel run the showing takeover's `onEscape`, then `onExit` (a text view holding keys hears Escape before either, as ever). Find gives its panel (`FindPanelPlugin`: `FindPanel`, while `editor.find?.isActive`; `onEscape` closes Find: [find](find.md)), and the issue walk its list (`IssueWalkPanelPlugin`, listed after Find's, so Find open wins: a `DetailRowList` of the walk's rows by board over the current stop's Issues tab through `DetailTabView`, while `issueWalk.isRunning && isListOpen`; `onEscape` closes the list: [validation](validation.md)). The point's owner is the panel's plugin, so a contributor is a plugin value of its own after `DetailPanelPlugin` (a face), left out of a list without the panel and refused in one with it and no panel (`ownerNotInstalled`). With no takeover active the panel shows by the selection: several shapes, their header alone (`SelectionSummary(header:)`: the header and a divider, with no list under it and no "Select one shape to see its details" line); one shape, its panel; and none, "No Selection", which only a panel hosted alone shows, since the window hides the inspector then (`shownWhile`, above). A takeover turning active over a shape's panel removes that panel as it stands, so a number field's uncommitted draft is dropped: one that can start while a field is being typed in should end the edit first.

- **Bands** (`DetailBands`, in `DetailTakeovers.swift` beside `DetailTakeovers`; a list in plugin order, the first that's active showing; the report's `detail band`, owner `.detailPanel` like the other two, so a contributor is a plugin value of its own after `DetailPanelPlugin`, refused where the panel isn't installed): `registrar.detailBand(isActive:onCancel:) { editor, onExit in … }` (`isActive` read in the panel's body, on observable state; `onCancel: (CanvasEditor) -> Void`), `Registry.activeDetailBand(in:)`. A band is held over the panel, not in place of it: the first active one shows above the takeover or the shape's panel, whichever shows, and does not rebuild it (`DetailPanelView`'s body is a `VStack` with the band above, `content` under it, and the modifiers on the stack; the band's view is made once in `init`, as a takeover's is, `PlacedBand`, and keyed by its place in the list so two bands are two views). It sits in the Tab ring first, being above everything (`WindowBox.controls()` reads by place), and the ring is closed again as a band appears or goes (on the active band's index), and as a takeover does (on the active takeover's place, once SwiftUI has swapped its views: Escape to the band closes the ring before it has), and a band going with the keyboard in it (Done, pressed) hands the keyboard to the canvas if the window or the view hosting the panel is left with it (`reclaimSoon`), so Tab from the panel's last control comes round to it and ⇧Tab from it goes to the last. It keeps the inspector requested (`DetailPanelPlugin`'s `isRequested` is a takeover or a band), and hiding the inspector runs its `onCancel` after the takeover's `onEscape`, both found before either runs. The first shipped band is Validation's issue walk (`IssueWalkPanelPlugin`: ‹ 12 of 63 › and Done, active while a walk runs, `onCancel` ending the walk; its buttons are `DetailCommandButton`s, standard controls that Keyboard navigation off leaves out of Tab, each with a menu item, and the walk's light reads `keyboardPlace` for `.band`: [validation](validation.md)).
  - **Escape and ⌘. differ when a band is over the panel** (`DetailPanelView.exitByKey(_:withOption:)`, `ExitKey`). Escape is one level out: the takeover's `onEscape` runs, then the band has the keyboard (`DetailPanelState.focusBand()`, the first control of the panel in the band's place, placed alike), else (no band, or a band with nothing the keys reach, as a button with Keyboard navigation off) `onExit` gives it to the canvas; from inside the band Escape goes straight to the canvas (`onExit`) and runs neither the takeover's `onEscape` nor the band's `onCancel`: the walk goes on, the band staying. ⌘. is all the way out: the takeover's `onEscape`, then the active band's `onCancel`, then `onExit`. Both reach the panel as `cancelOperation:` from a table (a list) with no key down, so the panel's reader view (`WindowReader.ReaderView.performKeyEquivalent`) notes a ⌘. going by as a key equivalent (`WindowBox.noteKeyEquivalent`, cleared on the next turn through the editor's scheduler, and by any other key equivalent) and `onExitCommand` asks `takeCommandPeriod()`; a text view holding keys and a number being typed still go first, as ever.
  - **`DetailPanelState.keyboardPlace`** (`KeyboardPlace?`: `.band`, `.takeover`, `.content`, nil with the keyboard out of the panel) and `focusBand()` sit by `keyboardEntry`: read when asked, from the window's first responder (the responder, or its outermost scroll view, with its middle in the band's place is `.band`; placed as `WindowBox.isPlaced` places every control, so a table scrolled through the band's strip is not the band's, else `.takeover` while a takeover shows, else `.content`), through closures the panel sets as it appears (`keyboardPlaceReader`, `focusesBand`). Nothing observes it: whoever lights something while the keyboard is in the band asks again at the moment it draws.
- **The title bar's row.** In the window's inspector the panel's sheet hands it the title bar's row (Chrome's `PaneTitleRow`, [host slots](host-slots.md)), and the panel's first line is in it: `detailTitleRow(else:height:)` (public, `DetailPanelView.swift`), which the header (`HeaderView`), Find's field and Done ([find](find.md)) and the issue walk's band ([validation](validation.md)) use, makes the line as tall as the row, its ends clear of the window's buttons (16 in, and ending 60 in, before the Inspector button), with `TitleRowDragArea` behind it, so a press on its words, its symbol or the room beside them is the window's; elsewhere the line is padded by its own insets, `height` tall where given; one chain of modifiers either way, so its views (the header's field) stay the same as a band comes or goes. `DetailPanelView` hands the row to the band while one shows and none to what shows under it, whose header is then a header's height again. In the row the header's title is in the window's title's type (`DetailStyle.rowTitle`, 15 semibold; over a subtitle the title's two-line form, `rowTitleOverSubtitle`, 13 bold, over `rowSubtitle`, 11: `DetailHeaderTitleType`, which `DetailHeaderLabel` hands its title through the environment for `HeaderTitleField`), its symbol and subtitle let a press through, and the field is as wide as its words (the placeholder's while it has none, and `DetailStyle.rowFieldSlack` past them) while no one types in it, so the room beside them drags the window; typed in, it's as wide as it's offered.
- **Taking the panel over and giving it back** (`DetailPanelState`). `commitDraft()` writes a number being typed, as Return in its field does, for a plugin about to activate a takeover (which removes the shape's panel as it stands, and its draft with it); `focusContent()` gives the keyboard to the first control of the shape's panel as a takeover closes over it (the controls there are when it is called are left alone, so the band keeps to its own; tried a few times as the panel draws; the canvas gets the keyboard if there is none). The panel sets how, as it appears (`focusesContent`). `hasTakeover(over: plugin)` says whether a takeover listed before the plugin's own is active (so it shows in place of the plugin's; for a plugin with none of its own, whether any is): the issue walk turns its list off while Find's panel covers it. `exitToCanvas()` gives the canvas the keyboard as the panel's `onExit` does (set as it appears, `exitsToCanvas`), for a plugin that remembers the canvas had it. TakeoverTests' `commitDraft` test holds both, and another `focusContent` with a shape whose panel has no control: the window left with the keyboard, `onExit` runs once and the canvas has it, and with the keyboard on the canvas already it does not run.
- **A tab chosen for a while.** `DetailPanelState.chosenTab(for:)` is the tab chosen for a kind (nil while none has been) and `forgetChoice(for:)` lets it go, so a plugin that chooses a tab as it arrives at shapes (Validation's issue walk chooses Issues for each stop's kind: [validation](validation.md)) gives each kind back the tab it had, or none.
- **A stand-in's panel** (`DetailPanelState.panelLayout(for:)`, `ShownThrough`, `ResolvedSection.onShown`).
