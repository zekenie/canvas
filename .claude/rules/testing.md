# Testing

Writing tests: the headless harness, views in unshown windows, key walks, and the board documents a test must close. Each subsystem's own test guidance is in the Testing section of its topic file (listed at the end).

Related: [build](build.md), [drawing](drawing.md), [editing](editing.md), [undo](undo.md), [keyboard navigation](keyboard-navigation.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Testing plugins](../../docs/plugin-system.md#testing-plugins).

## Verifying UI changes

- Screen capture isn't permitted here. Benchmarks and most tests draw into bitmaps, while the app's `CanvasView.draw` records a display list (AppKit's context isn't a bitmap: its `bitsPerComponent` is 0) that Core Animation renders on the GPU while the window is on screen and the display awake (headless, or with the display asleep, it replays it on the CPU), so what a drawing change costs on screen is seen only in the app on screen, and a clip of many rects is the known trap (the dot grid's, some 400 ms a frame, is why it clips only into a bitmap).
- Drive a headless editor with `EditorHarness` (CanvasTesting), with `KeyboardPlugin()` and `SelectionPlugin()` first in its plugins when the test presses, drags or selects as a user does (without Selection the default tool is Hand, and without Keyboard no key does anything). `EditorHarness(plugins:file:)` starts on a file of boards (with `PocketsPlugin()` for a kind that owns them), and `h.enter(owner)` shows the board a shape owns; `openingPockets()` (in SelectionTests, TableOfContentsTests and CompositionTests) makes pockets open onto their boards (`registrar.opens(Pocket.self, …)`). `h.key("v")` presses a key on the canvas (with what `h.hold` holds); CanvasTesting's fixture tools have no keys, so pick them with `h.editor.setTool`. One clock drives event timestamps and the `ManualScheduler`, so pointer speed, the arrow timers and the hand tool's slide (inertia) behave. Check drawing with `renderBitmap`, `pixel` and `changedPixels`.
- A shape laid out larger or smaller than it stores (`LaidOutBox`) is tested without Types or StickyNotes: CanvasTesting's `StretchesPlugin(log:shrinking:)` registers `Stretch`, a box laid out by the `Gauge` it names (no smaller than it stores, unless the plugin is made `shrinking`, which lays it out at exactly the gauge's size) (a layout input it provides, `Stretches.room`), a service that announces a gauge's change, and a `StretchLog` of every size and provider call asked (apart from `FixturesPlugin`, so the registry reports tests pin don't change). KindSchemaTests and ValidationTests have a `Gauge` kind of their own: CanvasTests refer to the fixture's as `StretchGauge`.
- A card (`editor.showCard`, [editor](editor.md)) is tested with CanvasTesting's `CardProbe` (an `NSView` that is flipped, takes the keyboard, logs the keys it takes, wants a settable size cut to the room it is asked about, and logs those rooms) and `probeCard(_:about:anchor:stepName:probe:closings:)`, whose `ClosingLog` holds the reasons it closed with. CanvasTests' `CardTests` run it headless over a counting `CanvasEditorDelegate`; CanvasUITests' `CardViewTests` put a `CanvasView` in an unshown window and call `pressBeganInWindow` (the press monitor's body; `NSApp.sendEvent` runs the monitor itself), `canvas.cardFrame` and `canvas.hitTest`.
- The gallery (CompositionTests' `GalleryKit.swift`, the harness, and `GalleryTypesLook.swift`, the states of the types cut: `galleryTests`) renders states of the app's look offscreen, light and dark, as PNGs named for the plan's board panel each answers (`Flow2-p1-list-types-dark.png`) with an `index.txt`, and a menu as its `outline` in a `.txt`: `GALLERY_DIR=/some/dir TEST_FILTER=Gallery ./test.sh`. A tool for design review, not the tests: with `GALLERY_DIR` unset it is one quick test (a state in both appearances, not blank, the two differing, no file named twice). It draws the canvas with `cacheDisplay` (editing view and all) at 2x and lays an open caret list's visible rows over it under the caret (its blur isn't drawn offscreen); the model is scripted and answers a type's highlights only, the pasteboard is private, a type's id (so its color) is fixed. A new state is a `GalleryState` in the list; other tracks add their own beside it. A type's rows are `GalleryRows.swift` (`rowStates`; `rows-read-failed`, `-no-key`, `-too-long` and `-failed-zoomed-out` are a failed read said at the foot of a type's rows), a note that is one's `GalleryValues.swift` (`valueStates`: its values, the row typed in, a choice focused and its menu, the marks' look alone through `rowBook.checks`, a value found, zoomed out and many), the types sitting far off the stage so a note is alone in view.  The panel's (`GalleryPanel.swift`, `panelStates`) hang the Types tab over the same fixtures. `GalleryCards.swift` (`cardStates`) holds the card's: board 5's Order from `FieldFixtures`, each card opened by a click on its real row (`click`: the stage's press and release on the row's value or the fold's words, which begins the note's editing there and asks for the card on the next turn; on a type's note and a locked note it opens at once), so it hangs from the row and the row is outlined, and a wrong cell is red from the real check; each kind's card, the fold (`+12 more`, `from Person`), a type's note, a locked note, a type deleted under an open card, the note low in the window and at the right edge, two zooms, a wide table, forty lines and a fold scrolled. `GalleryChecks.swift` (`checkStates`) draws needed and wrong from the real check, ring and all, never `rowBook.checks`: `Flow5-p6-needed-and-wrong`, `Flow5-p2-gift-note-needed`, `Flow3-p3-wrong-value`, and the states no board draws (an empty Order, the caret in a wrong value, a fold marked red, a note of a gone type and the type that refers to it, a rule across fields). A state that shows a wrong value stages a type the value is wrong for (`FieldFixtures.person`, whose email has the format; `personThree`'s is plain text), and the caret's state begins the note's editing in the row itself, since the render draws no value under the row's field. `GalleryConnections.swift` (`connectionStates`) is the Connections tab of a shape's panel ([neighbors](neighbors.md)): `GalleryStage.connectionsPicture(of:size:prepare:)` hangs the tab and draws it once its lists have landed (a note that points, is pointed at, mentions and is mentioned, inside a frame on a subboard's board; the subboard; an arrow; a type with its instances; two lists folded; notes with no titles; none; a list of thirty, and it searched). `GalleryColors.swift` (`colorStates`) is Colors' ([colors](colors.md)): the ten built-in colors on notes, frames, subboards and arrows in both appearances, a value and a file's own color, the Style tab's Color row and its grid (`panelPicture(of:tab:size:)`), `/color`'s list with its dots, and a type's note in its color. `GallerySlashBar.swift` (`slashBarStates`) is the command bar's, one state for each wireframe of its plan (`Bar1-press-slash` to `Bar7-zoomed-out`: the list under the bar, `/color`'s chips and the note after, a mixed selection counted, a frame's list and a locked note's, `/move-to @roa`'s list of places, a note's own `/`, the bar over a selection at the window's bottom and among skeletons; and `Name1-in-a-note`, `Name2-in-the-bar`, a thing's name typed after the `/`: `/idea` listing what the commands can do with a type and a frame of that name), the list drawn under the bar's `/` or `@` (`GalleryStage.openBar(on:typing:)`, `pictureWithBarList(_:under:)`).
  The list's rows are drawn under the plain appearance, not the list window's vibrant one, which draws a translucent line (a separator) as a blend and so dark.
- The tests of what ships (CompositionTests, BenchmarkTests) get the product's plugins from ShippedTesting's `ShippedPlugins` (`plugins`, `registry`, `makeEditor`, each taking `pasteboard:` and `model:`; the pasteboard is the test's own unless it passes one, `ShippedPlugins.pasteboard`, released as the test ends through TestKit's `afterThisTest`): the list the app is made of, each plugin made by its name, with a clipboard and a language model of the test's own ([build](build.md), What ships). `makeEditor` starts on ShippedTesting's `SampleBoard` unless it's handed a document: six notes in two rows, three of them linked by arrows (`SampleBoard.texts`, `document(texts:)`), where the proof of concept's welcome board had its notes, so the parity tests draw that board with the POC's texts. The app has no board of its own to start on: launched with nothing to open, it opens an empty one. Their lines in `Package.swift` end `+ shipped`, so they import whichever shipped modules they call.
- For focus, key routing and the editing view, put a `CanvasView` in an unshown `NSWindow` and send it synthesized `NSEvent`s (see CompositionTests).
- Each test runs in an autorelease pool of its own (TestKit's `runAsTest`, which `runTests` runs each test with), as the app handles each event in one, so what a test lets go is gone as it ends: its windows, their views and what those scheduled (a panel's keyboard handed back a turn later, `reclaimSoon`) never act in a later test. A closure a test hands a view (a panel's `onExit`) captures the test's own objects weakly, since the view may call it a turn after the test let them go; and a window a test closes is `isReleasedWhenClosed = false`, which ARC needs, else it's released once too often when the pool drains. DetailPanelTests' "a panel let go by its test goes with it" holds the pool.
- A test closes the `BoardDocument`s it edits (`defer { board.close() }`). AppKit autosaves an edited document 15 s after its last change (or after the last event sent through `NSApp`, if later), in whatever test is running then, and a test's board has no file type, so one given a `fileURL` throws "inTypeName is nil" and ends the run, only when the run is slow enough to get there (under load). After each test (`runTests(_:afterEach:)`), CompositionTests' `closeBoardsLeftOpen` fails one that left a board open with changes, and closes every board it left open (`BoardDocument.unclosed`, debug builds).

## Key walks

The one harness every surface's keyboard test goes through (P11 of [keyboard navigation](keyboard-navigation.md)), in CanvasTesting (`Keys.swift`, `Focus.swift`, `AccessibilityProbe.swift`, `KeyWalk.swift`), with the shipped readers in ShippedTesting (`ShippedFocus.swift`). CanvasTesting imports no plugin and not CanvasUI: a rig hands the walk its canvas view, its editor and closures.

- **Keys.** `Key` is a US keyboard's key: its key code (never 0 but for A), what it types alone and with ⇧ and ⌥, and the flags its events always carry (an arrow `.numericPad` and `.function`, Forward Delete, Home, the Page keys, F6 and Menu `.function`, the keypad's Enter `.numericPad`). `Chord` is a key and what is held: `.tab`, `.backTab` (the back-tab character, ⇧, code 48), `.optionTab`, `.up`, `.return`, `.commandReturn`, `Chord("v")`, `Chord("V")` and `Chord("!")` (⇧ added), `Chord(Key.down, .option)`; its event's characters are the layout's (⌃Q types "\u{11}", ⌥Q "œ"), and `Chord.inert` is the keys a stop that takes no text has no use for. `KeyDriver(window, menu:)` sends one as NSApplication routes a key-down, which an unshown window (never key) doesn't get from `NSApp.sendEvent`: `window.performKeyEquivalent` (a button's Return, the canvas's ⌘ keys), then the menu bar when one is given, then `window.sendEvent` to the first responder; `send` says where it went (`Delivery`: `.keyEquivalent`, `.menu(item)`, the item from `NSMenu.didSendActionNotification`, `.responder(first responder)`, or `.unhandled`, when the key-down, the text it types or the command it binds to reached the end of the responder chain, where AppKit beeps: the driver puts a responder after the chain's last for each key and takes it off after). `send(_:repeating:)` sets `isARepeat`, `hold(_:repeats:)` presses, repeats and lets go. `NSWindow.press`, `pressReturn`, `pressEscape`, `pressDelete`, `pressCommandPeriod` and `type` go through it with their old signatures (`press(_ chord:menu:)` beside them), and `keyEvent`'s code 0 is the key the US layout types the characters with. `EditorHarness.key(_ chord:)` builds the stroke a real canvas makes of the chord (`Chord.stroke`, the number row's digit included); CanvasUITests' KeyDriverTests hold the two the same for every key and modifier the plan uses, and `h.key(characters)` with `hold` too where no digit is involved.
- **Focus.** `Focus` is where the keyboard is: `surface`, `element`, `id` ("surface/element", or the surface alone), the accessibility `role`, `label` and `value`, `isMarked`, `acceptsText`, and `frame` (the part of it in view, in window coordinates). A `FocusReader` says it for what it knows (`.custom("note") { window in … }`, `Focus.of(window, surface:element:)` for the first responder named as the reader names it); the walk asks its readers in order, then the AppKit reader, which reads the first responder (a field for its editor): its element is its accessibility identifier, else its label, else its class; it is marked by a caret (an editable text view with the keyboard) or by `focusRingType` not `.none`; role and label come from the element accessibility says is focused when that is the control's own (a field's cell), since an `NSTextField` view's own role is unknown. `.canvas(view, selection:part:frame:)` is the canvas, which keeps the first responder while the selection or a shape's part has the keyboard: the selection's names ("A+B"), "/part" after them, marked while either is there. ShippedTesting's `.canvas(view, editor:names:part:)` names the selection by `names`, else title, and frames it in the `unobscuredViewport` (`CanvasEditor.shownFrame(ofWorld:in:)`); `.panel(of: canvas)` is surface "panel", whatever has the keyboard outside the canvas and what sits over it.
- **AccessibilityProbe.** `focused(in:)` (the window's own answer when it names a role, else up from the first responder), `tree(of:)` (`AccessibilityNode`: role, label, value, selected, frame, children; `outline`), `first(_ role:under:)` (a caret list's `.list` rows), `role(of:)`, `label(of:)` (label, title, then placeholder), `value(of:)`, `expectNamed`; all static (a role of `.unknown` is no role). Announcements are read from `editor.announcements`.
- **The walk.** `KeyWalk(window, editor:, menu:, readers:, settle:, sealsOnOwnerChange:)`. After each key it settles (`.runLoop`: `window.settle()`; `.manual(scheduler)`: the actions due now; `.both`; `.none`) and, but in a `BoardWindow`, which does it itself, seals the editor's undo history when the first responder moved, as a board's window does. `focus`, `press(_:times:)` (repeats after the first), `go(id, by:)`, `presses` (P12 counts them) and `trace` ("Tab -> canvas/A"), printed whole with any failure. The checks: `expectCycle(ids, wraps:, forward:, back:)` (from the first id: each in order, then `.closed` round to the first, `.stays`, or `.leaves(to:)`; at every stop `back` returns and `forward` comes again, P3 and P4; a press that stays put is a trap; it stops at the first wrong step and returns the `Cycle` of stops), `expectCycle(inOrder:)` (round from where it is, no stop twice, the ids among the stops in order: a long panel), `expectAxis(down:up:over:)` (a list, staying at its ends), `expectEscapeLadder(ids, keepsTyped:)` (P5: each Escape lands on the next; the text is still on the board or in a view), `expectInert(keys, at:)` (P8: no key changes the editor's `revision`, tool or `editingShapeID`, and Tab and Escape still move; it goes back to the stop after each) and `expectShows(stops)` (P7: marked and in the window's view; P9: a role and a label); both get to each stop with Tab, or with the key `by:` names (`.optionTab` for a shape's parts, which Tab steps out of). `pending` holds the known P9 gaps, "surface: reason, violation id", each let through until every stop of its surface a check sees is named, when it fails so the entry goes. `standardControls` names the stops that are standard controls, which a cycle expects only with Keyboard navigation on (`keyboardNavigation`, read as the run starts); with it off they're left out and listed in `skipped`. A walk of the toy window in KeyDriverTests checks each check, and that each fails a planted fault (a trap, a wrong order, an Escape that lands wrong, an unnamed stop, a pending gap that passes); SteppingShippedTests is the canvas's walk.
- **The census** (P1, P2, P10: the check any new clickable thing must pass). CompositionTests' `reachCensusTests` (`ReachCensusTests.swift`) put a shape of every shipped kind in a window (`CensusBoard`, on `Minute`: two types and their typed notes, a relationship type with fields, a relating arrow, a locked public note, a note mentioning it with an arrow to it, a reference, a frame, a subboard; a kind the registry lists that isn't on it fails) and, with each shape selected alone, sweep a grid over it and its parts through the select tool's own lookups, in the order a press takes them (`editor.button(atViewPoint:)`, `handle(atViewPoint:)`, `face(atViewPoint:)`), each thing found once (a face's point taken out of its identity), port dots excused (⌘L is their keyboard twin). Each must be one of: a handle part ⌥Tab reaches whose arrow keys move something; a part ⌥Tab reaches (the same identity, else the smallest whose rect holds the thing) whose Return does what a click there does, compared by effect (`CensusEffect`: the board, the selection, what is edited, the board shown, a card, a popped menu's outline, from the board as it started, reset between); a click that only selects the shape (Tab's) or edits it (Return's); or the same effect from inside the shape's editing (Return, Tab to a stop, → along its line, Return: a typed note's pill). The menu census holds every item of each shape's context menu, the canvas's and each chip's menu (Return on a `.menuButton` part, the menu caught by the canvas's `menuPresenter`) to the menu bar (an item of it, by title; an item of the selection's menu whose command a menu bar item runs, as the Shape menu leaves those out; a shortcut's title in `keyboardHelpRows`), else a Shape menu item with the same effect (a type chip's Remove “X” is Is a ▸ X). A gap is an actionable line, "PlantedFace face on Ask (Note): no part or command (a click changed the board; …)", failed unless the census's pending list (`reachPending`) has an entry that starts with it ("<gap>, <slice id>"), and an entry no gap starts fails, so it goes once the gap closes (`KeyWalk.expectGaps`); a planted face with no part (`PlantedFacePlugin`) holds that the census catches one. A new kind, chip, pill, button or face joins the census board and passes it.
- **Same key, same meaning** (P6). CanvasTesting's `KeyMeanings.swift` holds the principle's table as data: `KeyMeanings.canonical` (each key as the principle writes it, its chords, its meaning, `KeyMeaningOfKey`), `KeyMeanings.exceptions` (the named exceptions of the principle's text, each its keys, place, meaning and reason, and no others) and what each meaning allows a key to do on a surface whose stops run as its `KeySurface.Axes` say (`allows`: `KeyEffect` forward, backward, deeper, shallower, acted, none). A `KeySurface` takes an exception by its id for a key (`Override`); one that names none, or a key it isn't for, fails (`expectNamedOverrides`). `KeyWalk.expectMeanings(of:stops:at:depth:acted:reset:)` presses every key of the table from a middle stop, classifies what it did (to the stop after or before, an act — the revision, the tool, what `acted` says — a level in or out by `depth`, asked before and after, nothing) and lists each key that does what its meaning doesn't allow, failed unless the surface's pending entries have it. CompositionTests' `keyMeaningsShippedTests` hold the table against the principle's text (every key of its table a row here, every row with exceptions some named) and walk the canvas, a shape's parts, a note's rows being edited and the table of contents; `meaningsPending` is what no named exception yet covers there (none: the outline's ← →, ⌥Tab typing a tab in text and Return committing a one-line value are named exceptions now); an entry that passes fails, so it goes. The table is test data only: the Keyboard Shortcuts window stays generated from what is registered.
- **The first minute** (P12). CompositionTests' `firstMinuteKeysTests`, on a new board's window with a scripted model (`EmptyBoardWindow(model:)`, `configureBoards(model:)`), count each task's presses from the walk's log against the clicks the pointer takes for it, typing aside: a note (⇧Return, Insert › Note: 1 to 2), its words (typing), a type (`/is-a type` typed, Return: 1 to 1), its fields (Escape, the model writing them: 1 to 1), two notes connected (⇧Return twice, Escape, ⌥⇧⌘←, ⌘L: 5 to the Note tool and the canvas twice and a port's drag), a frame around them (⇧⌘F: 1 to 2); a task over its clicks is a gap (`firstMinutePending`).
- **What the spike found (2026-10-21), in an unshown, deferred window.** Tab sent with `sendEvent` moves AppKit's key view loop: a field's editor sends it on (`insertTab:`), and so does a view that leaves Tab to `NSView.keyDown` (the window's `keyDown` takes it); a view that interprets its own keys selects the next key view itself. With the window as first responder, Tab goes nowhere unless the window has an `initialFirstResponder`. So walks follow the real loop, not `nextValidKeyView`. `window.accessibilityFocusedUIElement` answers (a focused field's cell, `AXTextField`); `NSApp`'s answers nil, there being no key window. `isFullKeyboardAccessEnabled` reads (off on this machine), but a test can't turn it on: neither the argument domain nor the registration domain changes it, and with it off a button is no key view (`canBecomeKeyView` false), which is why walks record the setting rather than set it.
