# Properties and schemas

A kind's props as a list of properties (`SchemaDefined`), the JSON Schemas made from them, `KindSchema`, added properties, which a plugin adds to the kinds that opt in, and file values, which a plugin keeps on the file as a whole.

Related: [plugins and kinds](plugins-and-kinds.md), [boards on disk](boards-on-disk.md), [shape references](shape-references.md), [validation](validation.md), [titles](titles.md), [command line](command-line.md), [queries](queries.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Properties](../../docs/plugin-system.md#properties), [File values](../../docs/plugin-system.md#file-values).

## A kind's properties and its schema

- A kind's props, and any struct stored in them, are a list of properties (`SchemaDefined`): `static let properties = Properties<StickyNote>(title: "Sticky note") { Property("frame", \.frame).required(); Property("text", \.text).description("…") }`, with `init()` giving the defaults. The list is the type's `Codable` (a member missing from a board reads as its default; a `required()` one has none) and its JSON Schema (2020-12): each property's type from its member's (`SchemaDescribed`: the core's geometry and `ShapeID` as `core.*` definitions, `SchemaCases` for a string enum, a nested struct in place or, with `definition:`, shared and named after its module, `canvastesting.memo-note`), its default, and what its modifiers add (`PropertyModifiers`: `minimum`, `maxLength`, `pattern`, `examples`, `keywords` for any other). A type that codes itself by hand writes `schema(in:)` by hand (`ArrowTerminal`). The registry describes every kind's and added property's schema as it's built, and refuses a list of any struct those reach that misses a stored member (a board wouldn't save it), names a non-member or has a key path that isn't its member (a computed view), lists one twice, writes one member twice, has an optional that's required or defaults to non-nil, or holds optionals in a collection (nor may an added property's value); the first problem is the one reported, a property value's against its declarer; and two types under one definition name, or a struct that holds itself with no name. `registry.schema(for: kind)` is the kind's whole schema, its added properties included, and marked `x-canvas-board` for a `BoardOwning` kind. `registry.schemaViolations(of: shape)` checks a shape against it (its own and added properties as one object, `record.propertiesJSON`, through a fast `JSONValueEncoder`; each kind's schema compiled as the registry is built, `SchemaValidator`, which checks any JSON against any schema, strings code point for code point and patterns as ECMA-262 reads them; and a schema it couldn't check, a `$ref` to nowhere or back to itself before going into the value, a pattern ICU can't read, refuses the plugin list, a kind's or an added property's): typed props always have the schema's shape, so what breaks it are bounds (`maxLength`, `minimum`) and numbers that aren't finite. A bound is a guideline, never a refusal: Validation warns about each violation. A property a plugin keeps for itself says so with `unlisted()` (the schema's `x-canvas-unlisted`, `KindSchema.isUnlisted`): `canvas draw` takes no attribute of it and `canvas kinds` leaves it out (Draw's `KindVocabulary.isAttribute`, as for `readOnly`), and a query's vocabulary has no attribute of it, so no row lists it and `[it]` is `unknown_attribute`; its plugin gives the languages words of their own for what it means (Grouping's `groups`: [grouping](grouping.md)). Agents get the schemas from the command line (`canvas kinds --schema`). Text reads a kind's schema through the core's `KindSchema` (`Sendable`, holding the schema's JSON and no registry, so it reads anywhere, following its `$ref`s): which properties hold a place (`holdsPlace`: the core's rect or point, or what holds one), what each property's values are (`shape(of:)`, a `KindSchema.PropertyShape`), what each takes said briefly (`compactType(of:)`, `canvas kinds`' and a query's vocabulary's words), and a literal read as the property's JSON (`value(ofLiteral:quoted:for:)`, `forItemOf:` for a list's item), refused with a `KindSchema.Refusal` that holds no words, which each command says in its own (`draw` through Draw's `KindVocabulary`, a query through its resolution); so `canvas draw` and `canvas query` read a value alike.

- A struct stored in an added property is `SchemaDefined` too: Types' `endRule` is `EndRule { needed, onlyOne }`, an object with `definition: "end-rule"`, none while both are false (`isNone`), beside `relationship`, a bare `true` ([relationships](relationships.md)); each has a fixture in `Fixtures/added`.

- `SchemaValidator(schema) { uri in … }` (`resources:`) follows a `$ref` to a schema outside the schema (a `urn:uuid:…`, with or without a `#/…` fragment): its resolver is asked the ref's part before the first `#`, verbatim (no `$id` resolution, `$id` stays an annotation), once per URI; the fragment is walked in that resource, whose own `#/…` refs are to itself; nodes are filed under `uri + pointer`, so loops across resources are marked as within one. A schema the resolver lacks is a problem (`the $ref at P, U, can't be found`) and a value meeting it "can’t be checked"; with no resolver, an outside `$ref` is `isn't in the schema` as before. The resolver is non-escaping and not kept (the validator stays `Sendable`: a caller compiles off the main actor from a snapshot), and `validator.resources` lists the URIs asked, found or not, in the order met, for a caller to drop its validators on. The core knows nothing of what the schemas are. `SchemaResolverTests` (CanvasTests) resolve against a dictionary of schema objects, with no registry.

- A `SchemaViolation` has a `message` (the place's name, a space, then what is wrong) and a `detail` (what is wrong alone: `is 0, and should be at least 1.`), for a reader that says the place its own way (the types' rows say it as `line items › Plate › quantity`). `detail` takes no part in `==` or `hash(into:)`, which go by `path`, `keyword` and `message`: a violation made by hand (no `detail`, which then is its message) equals the validator's. Every report site in the validator words its name and its detail apart (`found.report(path, keyword, name:, detail)`); a detail may still name another place in the validator's way (`propertyNames`, `dependentRequired`). `SchemaFormatTests` (CanvasTests) holds that every keyword's message is its name and its detail.

- `format` is an annotation unless the validator is given the formats to check: `SchemaValidator(schema, formats: .standard)` (`SchemaFormats`, `none` by default, on both initializers; a resource the resolver gives is compiled with the same table). `standard` checks `email` (a dot-atom of 1 to 64 characters, `@`, labels of letters, digits and `-` of 1 to 63; no TLD needed, no quoted forms), `date`, `time` (the offset required), `date-time`, `uri` (a scheme, then RFC 3986's characters, one `#` at most) and `uuid`; hand-written scans of the characters. A string that breaks one is a `format` violation worded as `type`'s (`Email should be an email address, not "ann@".`); other values are not format-checked, and a format the table lacks stays an annotation. Opt-in because the core's kind schemas write `uuid` and `date-time`, and checking them would change what the schema rule says of every shape. `SchemaFormatTests` (CanvasTests) hold each format's good and bad values.

## Added properties

- Added properties are what a plugin adds to the kinds that opt in: something the shapes know that their kind doesn't declare (a title). The type is the key: `enum TitleProperty {}` with `extension TitleProperty: ShapeProperty { static let key: PropertyKey = "title"; static var defaultValue: String? { nil } }` (a nil default: only the shapes it's set on have one), and `static var keywords: PropertyKeywords<Value>` for what its schema says beyond its type (Titles' title: `.minLength(1).maxLength(80)`), and `static func isNone(_:)` for a value that's no value at all (Titles' blank title), which no shape holds: a shape set to one, or read from a board with one, holds nil, or the default for a property that has one (which can't be none). A value a board writes as null, added, kept or handed over, is none too. Its owner declares it (`registrar.declare(P.self)`); a kind opts in through the owner's sugar (`ShapeRegistrar.optIn(to:)`, as `note.title()` does), `registrar.optIn(Kind.self, to:)` for another plugin's kind, or `optInEveryShape(to:where:)`. The registry refuses an opt-in to a property nobody declares, a key declared twice, a kind opted in twice, and a key that's one of the kind's own property names; its report lists `property title` and `property title → sticky-note`. Read and write `shape[P.self]` (`record[P.self]`), in a transaction like the props; a write the shape can't hold (its kind doesn't opt in, nil for a property with a default, a value kept aside) is dropped. A placement sets one on what it places with `.setting(P.self, to:)`. A plugin that has only a key (a name in a user's text) reads one as JSON with `record.addedJSON(for: key)` (nil for a kind that doesn't opt in, an unset value, or one kept aside). Defaults are filled where shapes enter an editor (inserted or placed, `CanvasEditor.init` and `replaceFile` on every board, `replaceDocument`, a board read; `registry.fillingDefaults`); filling never marks a board edited by itself. In a kind's schema each one is a property marked `x-canvas-owner`. What a shape knows is a property; what a plugin keeps about a shape (the one it was copied from) is `ShapeMeta`, never a property.

- Two values a shape holds that say one thing are kept in step as they're written: `x.keepsInStep { before, record in … }` (`registrar.keepsInStep(Kind.self) { … }` for another plugin's kind; the core's `CorePoints.KeepsInStep`, a `StepRule`, found once a kind, `registry.stepRules(for:)`; the report's `keeps in step → sticky-note`). `Transaction` asks a kind's rules of a shape it puts in (`add`, and each shape of the boards `insert(_:contents:)` brings: `before` nil), of every `update` that changes a shape's added values (`before` the shape as it was; so `update(_:on:)` and `update(inFile:)` too) and of a `turn` that changes its kind or values, after `normalized` and before the read-only rules judge the write, so what a rule writes is in the same commit and step, and a refused write refuses it too (`keptInStep`: its id, stacking key and container put back, its values `normalized` again if it changed them). A move, a change of props alone and undo or redo ask nothing. A rule reads the record alone, and cheaply: every write of the kind's added values asks it. Types' is the one shipped (a type's color and its schema's `$color`: [types](types.md)). CanvasTests' `keepsInStepTests` hold it (`Stars` and `Sticker` on boxes, with pockets and `FreezingPlugin`).

## File values

- File values are what a plugin keeps on the file as a whole, no shape's and no board's (the colors a file names): to the file what an added property is to a shape, and the core knows nothing of what one means. The type is the key: `enum Letterhead {}` with `extension Letterhead: FileProperty { static let key: PropertyKey = "letterhead"; static var defaultValue: String { "" } }` (`Value` is `Codable`, `Equatable` and `Sendable`, with no schema: no kind's schema has it; `migrations` and `version` as an added property's, `PropertyMigration`). A file holds a value only while it differs from the default: every file reads the default until it's set, setting the default takes it off the file, and a file with none is written as one always was, byte for byte. Its owner declares it (`registrar.declare(file: P.self)`); the registry refuses a key declared twice among file properties (`conflict` in `FilePropertyDeclarations`; an added property may have the same key, a shape's values and the file's being kept apart), and its report shows `file property letterhead` (`v1` once it has a migration); `registry.declaredFileProperties`, `registry.owner(ofFileProperty:)`. Read it from the file, `editor.file[P.self]` (observed through `document`; `CanvasFile`'s subscript, settable on a file of one's own, never the editor's), in a transaction as it leaves it, `transaction.fileValue(P.self)`, in a render, `context.fileValue(P.self)` (`RenderContext`: read as the shape is drawn, and the commit that changes one redraws, so no service is needed), and in a layout, `reading.fileValue(P.self)` (`LayoutReading`, `context.reading`: the editor's committed, or mid-transaction as the transaction leaves it; nothing kept of a shape's geometry or laid-out size is let go because a file value changed, so the plugin that reads one there calls `editor.shapesDidChangeLayout` on hearing it). Write it only with `transaction.setFileValue(P.self, to:)`, in `editor.transact` or `transact(on:)`, whatever board the transaction is on (no board's lock holds it: it is the file's): it commits with the rest as one undo step ([undo](undo.md)), a body that throws sets nothing, a write equal to what it is (or there and back in one transaction) is no commit and no step, and a write is dropped for a property no installed plugin declares (by its type) and for one whose value the file keeps aside (`file.keptFileValues`: [boards on disk](boards-on-disk.md)). Services hear which changed in `ChangeSet.fileValues` (`Set<PropertyKey>`): an edit, an undo or redo, and a file put in place where they differ (`replaceFile`; with a switch, `BoardChange.fileValues`, and in its `changes`); a commit that changed only a file value names no shape and no board, writes no board (no revision moves) and still bumps `editor.revision` and redraws. Not built: the clipboard (a copy takes none), any UI. The command line writes one: Drawings' record of what a program drew, through `canvas apply` and `canvas draw --drawing` ([drawings](drawings.md)). Tests declare one with CanvasTesting's `LetterheadPlugin` (`Letterhead`, a string; apart from `FixturesPlugin`, so the registry reports tests pin don't change); CanvasTests' `fileValueTests` hold the editor's side and `fileValueCodecTests` the file's.
