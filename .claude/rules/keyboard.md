# Keyboard shortcuts

Keyboard: one shortcut per chord, who registers which, how a key reaches the canvas, AppKit's key bindings, the menu bar, and the Keyboard Shortcuts window, generated from what's registered.

Related: [selection](selection.md), [editor](editor.md), [undo](undo.md), [boards](boards.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Keyboard shortcuts](../../docs/plugin-system.md#keyboard-shortcuts).

## Architecture

- Keyboard shortcuts (Keyboard, platform, a horizontal in the window, first in the shipped list): every key the canvas answers is registered with it, one shortcut per chord (`KeyChord`: `"v"`, `KeyChord("a", .command)`, `.escape`), by the plugin that gives it its meaning: `x.tool(label:systemImage:shortcut:placing:)` and `registrar.tool(descriptor, shortcut:)` for a tool's key (`x.tool(label:systemImage:shortcut:placing:_:)` for a kind's tool of its own that still says what it places, the core's `ShapeRegistrar.tool(_:label:systemImage:placing:_:)`: the Frame tool, which draws, while `registry.placement(for:)`, what `canvas draw` places, is its placement), `registrar.command(.delete, "Delete", shortcuts: [...], isEnabled:)` for a command a menu item also runs, named as its item is (every command has a title: the core's `registrar.command(_:_:isEnabled:_:)` takes one, `registry.title(of:)` reads it) (its keys pass while it can't run, as its item dims: ⌘[ and Go › Back, ⌘↓ and `.openSelection`), `registrar.shortcut(chord, "Title", when:, repeats:) { editor in … }` for anything else, and `registrar.shortcut(chord, forTool:)` for another plugin's tool, and `registrar.shortcut(chord, forCommand:, repeats:)` for another's command (Keyboard gives the core's Hand H, Space held its pan (`registrar.shortcut(chord, "Title", whileHeld:released:)`: down, `editor.isHandHeld`; up, or every key let go, not), Undo ⌘Z and Redo ⇧⌘Z, held again and again, Escape and ⌘. `editor.cancel()`, Q the tool lock (`editor.isToolLocked`), and ⌘= and =, ⌘- and - (held, again and again), ⌘0 and ⇧0, and ⇧1 the zoom commands). The core knows no key: `CanvasView.keyDown` hands every key to the editor as a `KeyStroke` (host API `editor.keyDown`), which passes it to the plugin that claims key strokes, and so does `CanvasView.performKeyEquivalent` for a ⌘ key while the canvas has the keyboard, before the menu bar (so ⌘A is Keyboard's there; with a field focused, the menu's). A held key's repeats run a shortcut again only with `repeats:`, and only while the canvas has seen the key go down (one held down in the table of contents, whose pick gives the canvas the keyboard, repeats there as nothing). A key no shortcut takes goes on to AppKit's key bindings, and the standard actions they send that have a key of their own (`deleteBackward:`, `deleteForward:`, `insertNewline:`, `cancelOperation:`) come back to the shortcuts as ⌫, ⌦, ↩ and ⎋, so ⌃H does what Delete does; the moves they send (`moveLeft:`, `scrollPageDown:`) and typing (`insertText:`) stop at the canvas, so a stray key doesn't beep. ⇧ counts when a chord asks for it; a key held with ⇧ answers the chord without it too when ⇧ may be only what typed it (⇧ alone, or punctuation, a symbol or a digit: ⌘? is ⇧⌘/), never for a letter with ⌘, ⌥ or ⌃ (⇧⌘Z isn't ⌘Z). A digit's chord is its key on the number row, whatever the layout types with it (`KeyStroke.numberRowKey`, from the key code: ⇧1 is the key that types "!" on a US keyboard), and the menu bar (`MenuBar`) answers a View item's ⇧1 and ⇧2 the same way, and never takes a key without ⌘ from text, where it types (below; one held with fn, 🌐E's Emoji & Symbols, is AppKit's as ever). The table of contents' list runs the `.delete` command on Delete, as the canvas does. Every plugin with a key imports Keyboard, so any plugin list with Selection or a shipped tool needs `KeyboardPlugin()`. A tool's key is taken only while the editor takes the tool (`Shortcut.applies`: `editor.isToolEnabled`, false for a tool that places shapes on a board that takes none: a locked subboard's, `editor.isBoardReadOnly`), so there the key goes on as a command's does while it can't run, and the tool stays. The toolbar's picker (`ToolPicker`, `SwiftUIBridge.swift`) is an AppKit segmented control in an `NSViewRepresentable`, since SwiftUI's segmented `Picker` dims none of its segments (`.disabled` on a segment's content does nothing there, tried): a segment a tool, its symbol and tooltip, selected as `editor.currentToolID` is, dimmed as `editor.isToolEnabled` says (observed through `isBoardReadOnly`, so a board shown or a lock landing above redraws it, never a commit), the whole control's `isEnabled` following the environment's, and a click on a segment the editor refuses (it can't be made by hand, the segment is dimmed) leaving the selection on the current tool; CanvasUITests' `ToolPickerTests` host it in an `NSHostingView` in an unshown window and read the `NSSegmentedControl` (a segment each tool with its tooltip and symbol, the selection following a switch, a click picking a tool, the tools that place dimmed on a frozen pocket's board and as a lock lands above, a refused click leaving the selection), and KeyboardTests the key passing there. The toolbar's tooltips ("Note (N)") are Keyboard's, given to the host's slot for them (`registrar.toolTips { tool, registry in registry.help(for: tool) }`, read by `ToolPicker` as `registry.toolTip(for:)`: [host slots](host-slots.md)), since CanvasUI can't see Keyboard, and a list without Keyboard shows each tool's label; a button that runs a command names its key the same way (`registry.help(_:forCommand:)`: Find's "Next (⌘G)"; a command with no key, the table of contents' `.goUpBoard`, is its title alone). The inspector's toolbar button is Inspector, its tooltip "Show Inspector" or "Hide Inspector" as View › Show Inspector (⌃⌘I) is titled.
- The Keyboard Shortcuts window (Help › Keyboard Shortcuts, ⌥⌘/, `BoardMenus.showKeyboardShortcuts`, answered by the app's delegate with CanvasUI's `KeyboardShortcutsWindow(registry:menu:autosaveName:)`, made afresh each time it opens, as Settings is) is generated, never written by hand (the owner's call): it reads `registry.keyboardHelp` ([host slots](host-slots.md): `KeyboardHelp`, at most one, and `KeyHints`, any number) and the menu bar as it is when it opens (`NSApp.mainMenu`; a test hands `BoardMenus.make`'s). Keyboard gives the rows (`registrar.keyboardHelp { $0.keyboardHelpRows }`): each shortcut in registration order under its tool's label, its command's title (a `.command(c)` place) or its own title (`.canvas`), shortcuts under one name in one row (⌘↓, ↩ and ⌤ are Open Selection; a custom shortcut sharing a command's name is filed with the command), the four arrows held with the same modifiers written as one key (`KeyChord.written`: "←↑→↓", "⇧←↑→↓"; three arrows stay three). A key no shortcut has is a hint, said beside the code that reads it with the core's `registrar.keyHint(keys, title, while: .pointer | .text)`, so no plugin imports Keyboard for one: Keyboard says the core's (⇧ Drag, ⌘ Scroll), Selection the select tool's and resizing's, Snapping its ⌘ or ⌃, Arrows an end's ⌥, ⌘ or ⌃ and ⇧, Frames the Frame tool's ⇧ and ⌥, StickyNotes ⌘↩ or ⎋, ⇧↩ and ⇥ in a note, Mentions @, SlashCommands /, Types a note's rows' ⇥. `KeyboardShortcutSection.sections(menu:rows:)` (public, pure over its inputs) files them: Tools; each menu-bar menu in order (a submenu's items in its menu), an item's own key and, where its action runs a command (`BoardWindowController.menuCommands`: the controller's table, and Edit's Undo, Redo, Delete and Select All, the window's and the canvas's), the registered keys of that command under its title; then Canvas (commands no item runs, and the canvas's own), Pointer and Editing Text (`ShortcutsStyle`); a key listed once, where it first comes, a row left with none and an empty section dropped. A menu item's key is written as menus write it (`KeyboardShortcutSection.key(of:)`: ⌃⌥⇧⌘, a capital key equivalent held with ⇧, fn as 🌐). CanvasUITests' `keyboardShortcutsTests` hold the filing over a menu and rows of their own; KeyboardTests the rows (names, merging, arrows, the core's hints after); CanvasTests' `hostSlotsTests` the slot and the hints; CompositionTests' `keyboardShortcutsShippedTests` hold every shipped shortcut, every menu-bar key and every hint listed exactly once, each named, and where a few are filed (the four restacking keys under Arrange with their fixed items; Lock's ⇧L and Create Frame's ⇧⌘F under Canvas, since no fixed menu item runs them: the Shape menu is empty at rest, and its items are the selection's menu's, not a menu bar item the window reads).
- Find and Jump To's commands and menu items (Find's plugin claims `.find`, `.findNext` and `.findPrevious`, [find](find.md); JumpTo's `.jumpTo`, [jump to](jump-to.md)): the core names `.find`, `.findNext`, `.findPrevious` and `.jumpTo` (`Sources/Canvas/Model/Identity.swift`, beside `.enclosingBoard`), and the menus carry them: Edit › Find, a submenu after Select All (a separator before it) of Find… (⌘F), Find Next (⌘G) and Find Previous (⇧⌘G), and Go › Jump To… (⌘K) after Open Selection (a separator before it). Each runs `editor.perform` of its command through a selector of the window controller's own (`showFind:`, `findNextMatch:`, `findPreviousMatch:`, `showJumpTo:`), never AppKit's `performFindPanelAction:` or `performTextFinderAction:`, which a text view answers, and they're in the controller's `commands` table, so each is dimmed while `canPerform` says no, and not in `textKeys`, so they work from the canvas, a note being edited, a panel's field and the list (the plugin that claims one registers its keys with `registrar.command(_:shortcuts:isEnabled:_:)` as Boards does ⌘↑: the canvas answers them first, the menu bar elsewhere). `MenuBar` hands a ⇧⌘ letter to the item that names ⇧ (⇧⌘G is Find Previous, not Find Next, whichever item comes first). Find's plugin claims the first three (⌘F refused mid-gesture; ⌘G and ⇧⌘G while there are hits, or with Find closed and a query) and JumpTo's the last, ⌘K (refused mid-gesture).
- Arrange (between Shape and View): Group (⌥⌘G) and Ungroup (⌥⇧⌘G), the core's `.group` and `.ungroup` (Grouping claims them: [grouping](grouping.md)), through the window controller's `groupSelection:` and `ungroupSelection:`, in its `commands` table, so dimmed while `canPerform` says no, and in `textKeys`, so dimmed while text has the keyboard and the key is the text's; `MenuBar` hands ⌥⇧⌘G to Ungroup (the item that names ⇧) and AppKit ⌥⌘G to Group, never to Find Next's ⌘G. CompositionTests' BoardDocumentTests hold the items and keys, `groupingShippedTests` the routing.
- Arrange (continued): after Ungroup and a separator, Bring to Front (`]`), Bring Forward (⌥]), Send Backward (⌥[) and Send to Back (`[`), the core's `.bringToFront`, `.bringForward`, `.sendBackward` and `.sendToBack` (Reordering claims them, on the selection, enabled while shapes are selected and none is painted by anchor, with nothing under way or edited), through the window controller's `bringToFront:`, `bringForward:`, `sendBackward:` and `sendToBack:`: in its `commands` table (dimmed while `canPerform` says no) and in `textKeys` (dimmed while text has the keyboard). The same commands are the context menu's Arrange ▸ items, which stay (command-backed), and are left out of the Shape menu, whose Arrange submenu would hold nothing. A key without ⌘ is filed with the item that has it, in the Keyboard Shortcuts window, as the others are.
- Shape (between Edit and Arrange) is the selection's context menu in the menu bar, less what the menu bar already has ([context menus](context-menus.md): `registrar.menuForSelection`, `editor.menuForSelection(omitting:)`). `BoardMenus.make(appName:editor:)` makes it a `ShapeMenu` (`BoardMenus.swift`: an `NSMenu` that is its own delegate, `autoenablesItems` off), whose editor is the key window's board (`BoardMenus.keyBoardEditor`: the key window's, else the main window's, if a `BoardWindow`; a test hands its own). It holds nothing at rest, so the Keyboard Shortcuts window drops its section and no key reaches a stale item; `menuNeedsUpdate` fills it each time it opens with the items of the selection, moved out of the menu the plugin made, leaving out every item whose command is a value of `BoardWindowController.menuCommands` (Cut, Copy, Paste, Duplicate, Delete, Select All, Group, Ungroup, the four restacking items, and the rest of the menu bar's) so that nothing is in two menus; nothing selected, nothing in it (an empty menu), and no window with a board, nothing. Its items show their commands' keys (⇧L, ⇧⌘F) but they are not live there: `menuHasKeyEquivalent` says no, so a key never makes AppKit fill it to look, and `menuDidClose` empties it (after the chosen item's action, which AppKit sends after the delegate hears the close). The items are the ones the plugin made, with the editor they were made for, so a pick reaches that window's editor, and they enable and dim as their commands do (`canPerform`, asked now that the selection is the menu's), a pick ending editing first. The shape commands with keys: Locking's `.toggleLock` ⇧L, Frames' `.createFrame` ⇧⌘F, and Reordering's four, which are also fixed items in Arrange.
- Plain keys stay out of text. `MenuBar` never takes a key held without ⌘ or ⌃ from text, where it types: not ⇧L, `]` or `[` (nor ⇧1), and not ⌥] or ⌥[ either, which type a quote on a US layout; AppKit's menus would take a key equivalent without ⌘ before the text view sees it. A key held with ⌃ types nothing, so in text it goes on to AppKit's menus as it did (Window's ⌃⇥, a service's key), then to the text's own bindings (⌃A). Not in text (`NSApp.keyWindow`'s or the event's window's first responder an `NSText`): such a key is answered by the item that names it (the exact key and modifiers, a digit by its number-row key code), and while that item is dimmed the key goes on (AppKit's own menus take a dimmed item's key and beep); otherwise the item runs, once: a held key's repeats are taken and run nothing, as the canvas's shortcuts for those keys don't repeat (a held ⇧1 would flip between the fit and back, a held ⌥[ send a shape back a step a repeat). A key held with fn is AppKit's as ever. A ⇧⌘ letter goes to the item that names ⇧; where none does but one names the letter without ⇧ (⇧⌘F, and Edit › Find's ⌘F), the menu bar takes it for none (`MenuBar` returns false: AppKit would have run Find, which CompositionTests' `shapeMenuShippedTests` show). So typing L, `]` and `[` in a note being edited types them, and ⇧L, ⇧⌘F, `]` and the rest are the canvas's keys while it has the keyboard (⇧⌘F, with a field focused, goes nowhere). `shapeMenuShippedTests` hold it: the Arrange keys through `MenuBar` (run, a repeat running nothing, dimmed, off in text, and ⌃⇥ in text reaching an item that names it), the typed characters, ⇧⌘F past Find, ⇧L and ⇧⌘F on the canvas, the Shape menu's items for a note and a frame, in two windows, dimmed while editing.
- Edit › Spelling and Grammar (a submenu after Find): Show Spelling and Grammar (⌘:), Check Document Now (⌘;), then Check Spelling While Typing, Check Grammar With Spelling and Correct Spelling Automatically, AppKit's standard actions (`showGuessPanel:`, `checkSpelling:`, `toggleContinuousSpellChecking:`, `toggleGrammarChecking:`, `toggleAutomaticSpellingCorrection:`) sent to the first responder, as Cut and Copy are: the text's with the keyboard (a note being edited, a panel's field, the title's field editor), dimmed on the canvas, which answers none and whose shortcuts name neither ⌘: nor ⌘;. A text that checks its words as the app does (TextEditing's `Spelling`, [text editing](text-editing.md)) makes its three toggles the app's, kept between launches, for every such text at once. CompositionTests' BoardWindowTests hold the items, their keys and who answers them.
- A view in an editing view that takes the keyboard and is no text view (a focused box, choice or row with more in a note that is one: Types' `RowsView`) swallows every key it has no use for: up the responder chain from it are the canvas's shortcuts, where Backspace deletes the selection, which is the note being edited, and a letter picks a tool. It answers Tab and ⇧Tab, ↑ and ↓, Return, Space, Escape and ⌘↩ and never calls `super.keyDown`; ⌘ shortcuts reach the menus before it as for any view ([types](types.md), `noteRowEditingTests`).
- Moving between shapes (Selection's keys, [selection](selection.md); ⌘↑ Boards', [boards](boards.md)): Tab and ⇧Tab ("Next Shape", "Previous Shape") and ⌥⌘ and ⌥⇧⌘ with an arrow ("Select Nearest Shape", "Add Nearest Shape to Selection": the four arrows one row each in the Keyboard Shortcuts window, ⌥⌘←↑→↓ and ⌥⇧⌘←↑→↓) are shortcuts of Selection's `registrar.shortcut(chord, title, when: { $0.canStepSelection }, repeats: true)`, under Canvas, and pass only while a gesture runs or a shape is edited. ⇧Tab types the back-tab character on a Mac (`NSBackTabCharacter`, "\u{19}"), which `KeyStroke(event)` (CanvasUI) makes Tab with ⇧, so the chord is ⇧⇥ like any other (a test sends the character, CompositionTests' `steppingShippedTests`). A command named for the step it would take gives `registrar.command(_:_:shortcuts:menuTitle:isEnabled:_:)` a `menuTitle:` (Boards' `.enclosingBoard`), read by `BoardWindowController.validateMenuItem` as `editor.menuTitle(of:)` to retitle its menu item (Go › Enclosing Group, Enclosing Frame, Enclosing Board); the Keyboard Shortcuts window keeps the command's static title (`registry.title(of:)`), since it files keys by command, not by the item's title now. KeyboardTests hold the sugar, CanvasTests the core's, and `keyboardShortcutsShippedTests` that each new key is listed once under Canvas.
- Notes and arrows from the keyboard. In a note's editor (StickyNotes' `NoteEditor`, through TextEditing's `onKeyDown`, which an open `@` or `/` list never reaches), ⇧↩ puts a new note down beside it and edits it, and Tab and ⇧Tab edit the next and previous note in reading order (`NoteHops`, [editing](editing.md)): key hints, under Editing Text, since no shortcut has them (↩ alone and ⌥↩ stay the text's new line). ⌘L is Connections' `.connect` ("Connect", `PortsPlugin`'s, [connections](connections.md)): two selected shapes joined, the first selected to the other, enabled with exactly two selected and nothing under way or edited; under Canvas in the Keyboard Shortcuts window, since no menu bar item runs it (Connect is in a right-click on two shapes, `ConnectMenuPlugin`, so in the Shape menu while two are selected). StickyNotesTests' `noteHopsTests`, PortEdgesTests' `connectTests` and CompositionTests' `connectShippedTests` hold them.
- The tool lock, zoom and the window's own items. Q (a shortcut titled "Tool Lock", filed under Canvas) toggles `editor.isToolLocked` ([editor](editor.md)); the toolbar's picker shows it: `ToolPicker` reads `editor.isToolLocked` (observed), `ToolSegments` draws the selected segment's symbol with a small lock at its bottom right on a gap cut out of the symbol (`ToolLockStyle.image`, a template image the control tints, as tall as the symbol and as wide as the widest tool's symbol, `ToolLockStyle.widestSymbol`, the narrower one centered in it: the segments are equally wide (`fillEqually`), so the control keeps its width and the lock sits beside a narrow symbol, Select's arrow, rather than over its tail; its accessibility description adds ", locked") and adds ", locked" to the tooltip, each segment's image made again only when it changes (the coordinator's `shown`); CanvasUITests' `toolPickerTests` hold it (the lock on the selected segment and following a switch, the others the same objects, off again), and CompositionTests' `ToolbarRenderTests` renders the shipped toolbar both ways to PNGs in the directory `TOOLBAR_RENDER_DIR` names (a suite only with it set, as the Gallery is with `GALLERY_DIR`; light only, an unshown window draws the dark appearance the same). Plain = and - zoom as ⌘= and ⌘- do, held again and again, and ⇧0 is Actual Size (the number row's 0, as ⇧1's chord is its 1); Zoom to Fit's ⇧1 again goes back to where the camera was before the fit ([editor](editor.md), Zooming), and View › Zoom to Fit runs the same command. Three menu items need no registered command because the window answers them: Edit › Paste at Pointer (⇧⌘V, after Paste) is Clipboard's `.pasteAtPointer` through `BoardWindowController.pasteAtPointer:` (in `commands` and in `textKeys`, so text being edited keeps ⇧⌘V; [clipboard](clipboard.md)); Edit › Copy as Image (⇧⌘C, after Copy; `copyAsImage:`, which draws what the host slot says, [host slots](host-slots.md)) and View › Focus Inspector (⌥⌘I, after Show Inspector; `focusInspector:`, [host slots](host-slots.md)) are the controller's own, with no command, so Keyboard registers no key for them and the Keyboard Shortcuts window lists their keys from the menu bar (Edit and View, under their item's title). `keyboardShortcutsShippedTests` file them: Zoom In is `⌘=`, `=`, Zoom Out `⌘-`, `-`, Actual Size `⌘0`, `⇧0`, Tool Lock `Q` under Canvas, Paste at Pointer `⇧⌘V` and Copy as Image `⇧⌘C` under Edit, Focus Inspector `⌥⌘I` under View. KeyboardTests hold Q (on and off, the Hand's and a tool's, Escape leaving the tool and the lock staying), = and - (repeating) and ⇧0, and ⇧1 twice going back.
