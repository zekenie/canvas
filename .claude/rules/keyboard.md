# Keyboard shortcuts

Keyboard: one shortcut per chord, who registers which, how a key reaches the canvas, AppKit's key bindings and the menu bar.

Related: [selection](selection.md), [editor](editor.md), [undo](undo.md), [boards](boards.md) ([every topic](../../CLAUDE.md#map)).

In the guide, `docs/plugin-system.md`: [Keyboard shortcuts](../../docs/plugin-system.md#keyboard-shortcuts).

## Architecture

- Keyboard shortcuts (Keyboard, platform, a horizontal in the window, first in the shipped list): every key the canvas answers is registered with it, one shortcut per chord (`KeyChord`: `"v"`, `KeyChord("a", .command)`, `.escape`), by the plugin that gives it its meaning: `x.tool(label:systemImage:shortcut:placing:)` and `registrar.tool(descriptor, shortcut:)` for a tool's key (`x.tool(label:systemImage:shortcut:placing:_:)` for a kind's tool of its own that still says what it places, the core's `ShapeRegistrar.tool(_:label:systemImage:placing:_:)`: the Frame tool, which draws, while `registry.placement(for:)`, what `canvas draw` places, is its placement), `registrar.command(.delete, shortcuts: [...], isEnabled:)` for a command a menu item also runs (its keys pass while it can't run, as its item dims: ⌘[ and Go › Back, ⌘↓ and `.openSelection`), `registrar.shortcut(chord, "Title", when:, repeats:) { editor in … }` for anything else, and `registrar.shortcut(chord, forTool:)` for another plugin's tool, and `registrar.shortcut(chord, forCommand:, repeats:)` for another's command (Keyboard gives the core's Hand H, Space held its pan (`registrar.shortcut(chord, "Title", whileHeld:released:)`: down, `editor.isHandHeld`; up, or every key let go, not), Undo ⌘Z and Redo ⇧⌘Z, held again and again, Escape and ⌘. `editor.cancel()`, and ⌘=, ⌘- (held, again and again), ⌘0 and ⇧1 the zoom commands). The core knows no key: `CanvasView.keyDown` hands every key to the editor as a `KeyStroke` (host API `editor.keyDown`), which passes it to the plugin that claims key strokes, and so does `CanvasView.performKeyEquivalent` for a ⌘ key while the canvas has the keyboard, before the menu bar (so ⌘A is Keyboard's there; with a field focused, the menu's). A held key's repeats run a shortcut again only with `repeats:`, and only while the canvas has seen the key go down (one held down in the table of contents, whose pick gives the canvas the keyboard, repeats there as nothing). A key no shortcut takes goes on to AppKit's key bindings, and the standard actions they send that have a key of their own (`deleteBackward:`, `deleteForward:`, `insertNewline:`, `cancelOperation:`) come back to the shortcuts as ⌫, ⌦, ↩ and ⎋, so ⌃H does what Delete does; the moves they send (`moveLeft:`, `scrollPageDown:`) and typing (`insertText:`) stop at the canvas, so a stray key doesn't beep. ⇧ counts when a chord asks for it; a key held with ⇧ answers the chord without it too when ⇧ may be only what typed it (⇧ alone, or punctuation, a symbol or a digit: ⌘? is ⇧⌘/), never for a letter with ⌘, ⌥ or ⌃ (⇧⌘Z isn't ⌘Z). A digit's chord is its key on the number row, whatever the layout types with it (`KeyStroke.numberRowKey`, from the key code: ⇧1 is the key that types "!" on a US keyboard), and the menu bar (`MenuBar`) answers a View item's ⇧1 and ⇧2 the same way, and never takes a key without ⌘, ⌃ or ⌥ from text, where it types (one held with fn, 🌐E's Emoji & Symbols, is AppKit's as ever). The table of contents' list runs the `.delete` command on Delete, as the canvas does. Every plugin with a key imports Keyboard, so any plugin list with Selection or a shipped tool needs `KeyboardPlugin()`. A tool's key is taken only while the editor takes the tool (`Shortcut.applies`: `editor.isToolEnabled`, false for a tool that places shapes on a board that takes none: a locked subboard's, `editor.isBoardReadOnly`), so there the key goes on as a command's does while it can't run, and the tool stays. The toolbar's picker (`ToolPicker`, `SwiftUIBridge.swift`) is an AppKit segmented control in an `NSViewRepresentable`, since SwiftUI's segmented `Picker` dims none of its segments (`.disabled` on a segment's content does nothing there, tried): a segment a tool, its symbol and tooltip, selected as `editor.currentToolID` is, dimmed as `editor.isToolEnabled` says (observed through `isBoardReadOnly`, so a board shown or a lock landing above redraws it, never a commit), the whole control's `isEnabled` following the environment's, and a click on a segment the editor refuses (it can't be made by hand, the segment is dimmed) leaving the selection on the current tool; CanvasUITests' `ToolPickerTests` host it in an `NSHostingView` in an unshown window and read the `NSSegmentedControl` (a segment each tool with its tooltip and symbol, the selection following a switch, a click picking a tool, the tools that place dimmed on a frozen pocket's board and as a lock lands above, a refused click leaving the selection), and KeyboardTests the key passing there. The toolbar's tooltips ("Note (N)") are Keyboard's, given to the host's slot for them (`registrar.toolTips { tool, registry in registry.help(for: tool) }`, read by `ToolPicker` as `registry.toolTip(for:)`: [host slots](host-slots.md)), since CanvasUI can't see Keyboard, and a list without Keyboard shows each tool's label; a button that runs a command names its key the same way (`registry.help(_:forCommand:)`: "Enclosing Board (⌘↑)"). The inspector's toolbar button is Inspector, its tooltip "Show Inspector" or "Hide Inspector" as View › Show Inspector (⌃⌘I) is titled.
- Find and Jump To's commands and menu items (Find's plugin claims `.find`, `.findNext` and `.findPrevious`, [find](find.md); JumpTo's `.jumpTo`, [jump to](jump-to.md)): the core names `.find`, `.findNext`, `.findPrevious` and `.jumpTo` (`Sources/Canvas/Model/Identity.swift`, beside `.enclosingBoard`), and the menus carry them: Edit › Find, a submenu after Select All (a separator before it) of Find… (⌘F), Find Next (⌘G) and Find Previous (⇧⌘G), and Go › Jump To… (⌘K) after Open Selection (a separator before it). Each runs `editor.perform` of its command through a selector of the window controller's own (`showFind:`, `findNextMatch:`, `findPreviousMatch:`, `showJumpTo:`), never AppKit's `performFindPanelAction:` or `performTextFinderAction:`, which a text view answers, and they're in the controller's `commands` table, so each is dimmed while `canPerform` says no, and not in `textKeys`, so they work from the canvas, a note being edited, a panel's field and the list (the plugin that claims one registers its keys with `registrar.command(_:shortcuts:isEnabled:_:)` as Boards does ⌘↑: the canvas answers them first, the menu bar elsewhere). `MenuBar` hands a ⇧⌘ letter to the item that names ⇧ (⇧⌘G is Find Previous, not Find Next, whichever item comes first). Find's plugin claims the first three (⌘F refused mid-gesture; ⌘G and ⇧⌘G while there are hits, or with Find closed and a query) and JumpTo's the last, ⌘K (refused mid-gesture).
- Arrange (between Edit and View): Group (⌥⌘G) and Ungroup (⌥⇧⌘G), the core's `.group` and `.ungroup` (Grouping claims them: [grouping](grouping.md)), through the window controller's `groupSelection:` and `ungroupSelection:`, in its `commands` table, so dimmed while `canPerform` says no, and in `textKeys`, so dimmed while text has the keyboard and the key is the text's; `MenuBar` hands ⌥⇧⌘G to Ungroup (the item that names ⇧) and AppKit ⌥⌘G to Group, never to Find Next's ⌘G. CompositionTests' BoardDocumentTests hold the items and keys, `groupingShippedTests` the routing.
- Edit › Spelling and Grammar (a submenu after Find): Show Spelling and Grammar (⌘:), Check Document Now (⌘;), then Check Spelling While Typing, Check Grammar With Spelling and Correct Spelling Automatically, AppKit's standard actions (`showGuessPanel:`, `checkSpelling:`, `toggleContinuousSpellChecking:`, `toggleGrammarChecking:`, `toggleAutomaticSpellingCorrection:`) sent to the first responder, as Cut and Copy are: the text's with the keyboard (a note being edited, a panel's field, the title's field editor), dimmed on the canvas, which answers none and whose shortcuts name neither ⌘: nor ⌘;. A text that checks its words as the app does (TextEditing's `Spelling`, [text editing](text-editing.md)) makes its three toggles the app's, kept between launches, for every such text at once. CompositionTests' BoardWindowTests hold the items, their keys and who answers them.
- A view in an editing view that takes the keyboard and is no text view (a focused box, choice or row with more in a note that is one: Types' `RowsView`) swallows every key it has no use for: up the responder chain from it are the canvas's shortcuts, where Backspace deletes the selection, which is the note being edited, and a letter picks a tool. It answers Tab and ⇧Tab, ↑ and ↓, Return, Space, Escape and ⌘↩ and never calls `super.keyDown`; ⌘ shortcuts reach the menus before it as for any view ([types](types.md), `noteRowEditingTests`).
