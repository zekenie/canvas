# Drawing a codebase

`ingest` draws a commit of a codebase as boards in one command (HEAD, unless `--commit REF` says another, resolved once to a sha; the code drawn is that commit's, never the working tree's, so any commit draws again and comes out the same): a scanner reads the code into the scan (`scan.json`), the repository's lens makes the scan a digest (`.canvas/lens.py`, else the default lens, `lenskit/default.py`) and the canvas-digest skill measures, lays out and draws it (the canvas-digest skill beside this one, `digest all`). The root holds the modules as cards in bands, one band a layer, the top layer first: rows from the top or columns from the left, whichever the window shows larger; a module's board holds its files as notes in frames; which file uses which, and which module imports which, is an arrow or a pill, as the skill decides ([its rules](../../canvas-digest/SKILL.md)). It draws any git repository: a Swift package, or a TypeScript, Python or Ruby project through a SCIP index.

`$SKILL` below is the folder this skill is in (SKILL.md says how to find it); `ingest` and the scanners run by their paths there.

```bash
"$SKILL/ingest"                                  # the repository you are in, onto the board in front
"$SKILL/ingest" ~/code/app --new-file ~/Documents/Code.canvasboard
"$SKILL/ingest" --ranks rows                     # the layers as rows, whatever the window's shape
"$SKILL/ingest" --where                          # the cache's folder
"$SKILL/ingest" --scip index.scip                # an index made by hand (below: making the index)
"$SKILL/ingest" --commit v1.2                    # a commit other than HEAD, drawn from its own code
"$SKILL/ingest" --scan scan.json                 # a scan given by hand, scanning nothing
```

- **Nothing by hand.** The board is what the code says: its title the name the scanner found, its bands the layers the code tags (or how deep each module's imports go), a board's frames its folders. A repository may keep a `.canvas/lens.py` that changes the picture (below).
- **The settings**, `<repo>/.canvas/ingest.json`, read by `settings.py`. An unknown key is a warning and a bad value is refused, naming the key. Options on the command line win over the settings.

  | key | value |
  |---|---|
  | `scanner` | `"swift"` or `"scip"`. Without the settings, a repository with a `Package.swift` is scanned as Swift; any other is refused, with what to write |
  | `scip` | for `scip`: the command that writes the index, run at the checkout's root, with the indexer's version pinned; `{index}` stands for the path to write, written bare: it is replaced by a shell-quoted path, so quotes around it would be part of the name (`npx --yes @sourcegraph/scip-typescript@0.4.0 index --output {index}`). The last index is removed before the command runs, and a command that writes none is refused |
  | `prepare` | a command run in the checkout (below) before scanning, to install packages; it runs again only when a lockfile of the commit (at any depth: `package.json`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `Package.resolved`, `Gemfile.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `Cargo.lock`, `go.sum`, `composer.lock`, `gradle.lockfile`, `requirements*.txt`) or the command has changed. What it installs should be ignored by git (`node_modules`), since moving to a commit removes what git doesn't know. Run the package manager the repository pins (`packageManager` in `package.json`): a frozen install that fails on a lockfile mismatch is usually another version of it, so name the version in the command (`npx --yes pnpm@9 install --frozen-lockfile --ignore-scripts`). An older commit runs it on its own lockfiles, which may need other options |
  | `window` | `[width, height]`, the room every board is laid out for; absent, the window's size when the run starts (`--window WxH`) |
  | `mess` | 0 to 1, the digest's dial (`--mess`) |
  | `ranks` | `"rows"` or `"columns"` (`--ranks`) |

- **Whose code runs.** A repository's `prepare` and `scip` commands, and its `.canvas/lens.py`, are that repository's own code and run as its build would, not sandboxed: `prepare` and `scip` with your environment, in the checkout, the lens with a cleared one. An agent shows you these commands before the first run on a repository you didn't set up.
- **Where it keeps what it makes.** Nothing is written into the repository. One cache per repository, shared by its worktrees: `${CANVAS_INGEST_CACHE:-$HOME/Library/Caches/InfiniteCanvas/ingest}/<name>-<hash>`, where `<hash>` is the first 12 hex digits of the sha256 of the resolved path of `git rev-parse --git-common-dir` and `<name>` the name of the folder that holds it. `ingest --where` prints it. It holds `checkout/` (the repository's code at the commit drawn, below), `scans/` (the scan of each code drawn, by the commit's code and scanner: `<code>-<scanner>-<12 hex>.json`, `<code>` a hash of the commit's top-level tree without its `.canvas` entry and the last digits a hash of the scanner's files and, for SCIP, its command; each written as `.json.reading` until whole, so a scan that stops part way leaves none; the last 20 are kept), `index/` (Swift's index, a store a module, kept from run to run; the SCIP index the settings make is `index/index.scip`), `runs/<run>/` (one folder a run, with that run's `digest.json` and the driver's `out/`: the plan, the scripts, what the app said of each; the last 5 are kept), `drawn/` (the drawing records, one for each file drawn in: what the next run takes back) and `lock`.
- **The commit, and the checkout.** `--commit REF` (default `HEAD`) is resolved once to a sha, and the code drawn is that commit's: never the working tree, so an uncommitted edit is not drawn, and the same commit draws the same boards. The settings and the lens are read from the folder you run `ingest` in: the working tree, committed or not. The scanners run on `checkout/`, one copy of the repository for all its commits, made once with `git clone --shared` (it borrows the repository's objects) and moved to each commit asked for (`checkout --force --detach`, then `clean -ffd`: files git ignores, like `node_modules`, stay). It is not a `git worktree`, and does not show in `git worktree list`. If it breaks (the repository dropped an object it lent), `ingest` says so and makes it again. A partial clone (`git clone --filter=blob:none`, or `tree:0`) has only some commits' files: what the commit lacks is fetched first, into the repository, from the remote it was cloned from, as git fetches it to check that commit out: before the commit is scanned, and before a lens of your own reads it (a commit you have checked out fetches nothing). A shallow clone (`--depth`) has only its latest commits, and an older one is refused, saying so (`git fetch --unshallow` fetches the rest). A fresh copy for each commit would type-check every Swift module again and reinstall every package. **The scan is kept by the commit's code, not the commit**: a hash of `git ls-tree` of the commit's top-level tree with the `.canvas` entry left out. Commits that differ only in `.canvas/` (a lens or settings committed after a round of feedback) have the same code, share a scan, and a run on the second moves no checkout, runs no `prepare` and scans nothing. A change to any other file, or to a lockfile, is another scan. Submodules are not checked out. A scan's `name` is the repository's (the folder that holds its git directory), not the checkout's.
- **The same boards.** The same commit, lens, app and macOS draw the same boards: the same plan and the same scripts, whether the lens is committed or not.
- **One at a time.** A run holds `lock` (a folder with its pid) from the start to the end; a second run for the same repository is refused at once, naming the pid, and a lock whose process is gone is taken over. A process id that another process has since been given reads as a live holder: the lock is refused until that one ends, or its folder is removed. A signal stops the run at once, with the command it is waiting for (`prepare`, the indexer, a scanner), and frees the lock.
- **Where it draws.** It asks first, before scanning anything, whether the app is running and the board can take the drawing. The board in front, as that board: when it's empty, or when it holds the last ingestion and nothing else, which is taken back first (one Edit › Undo Draw brings it back) and drawn anew. A board with anything else on it (a note or an arrow drawn since) is refused before anything is taken back, never drawn among. `--board ID` names another open board, and `--new-file PATH` makes a new board file and draws there; a later run with that board in front draws in its place. A run that stops part way can simply be run again, whether or not you undid what it drew. What a run drew is remembered in the cache by the file it went into, so a drawing made on one file is not forgotten by a drawing made on another; a board drawn from another repository's cache (or before the cache was removed) reads as not empty, and the way on is an empty board in front or `--new-file`.
- **Shaped for the window.** Every board is laid out to fill the window it is drawn in, when it is fit to it: the skill asks the app how much room that window has as the run starts (`canvas boards`' `view`; for `--new-file`, the window in front's), so a wide window gets boards wider than tall, and the root's bands as columns. A `window` setting says the room instead. `--ranks rows` or `--ranks columns` says which way the root's bands run, whatever the window.
- **How long.** For Infinite Canvas's own code, about a quarter of a minute when the code is as the last run scanned it, and up to half a minute when it isn't: measuring, laying out and drawing the 6,000 shapes takes about fifteen seconds, and Swift's index up to fifteen more. The index is kept from run to run (`index/`), and only the modules that changed are type-checked again: none after no change, one after an edit inside a function, and the modules that depend on it too after an edit to what a module declares. A repository's first run also asks the compiler which SDK it accepts, some ten seconds (and so does the first with another compiler or `SDKROOT`). Deleting `index/` starts the index over. It says each step as it starts, and each script as it lands (`[n/146] ok ...`). A commit whose code was scanned before goes straight to the lens (it says so; `--rescan` scans it again), so drawing the same commit again, or one that changes only `.canvas/`, takes the drawing alone.
- **What it needs.** The app running, and `canvas`, which the canvas-digest driver finds: `$CANVAS_CLI`, else the one beside the skills (the app's), else the one on the PATH. Python is `/usr/bin/python3` (3.9: no `match`, no `X | Y` types).

## The scanners

A scanner writes the scan (`scan.json` below, kept by `ingest` as `scans/<code>-<scanner>-<12 hex>.json`), the only thing the digest is made from. There's one for Swift, and one for any language a SCIP indexer covers; `ingest` runs Swift's when the settings say `swift` (or are absent and the repository has a `Package.swift`), and SCIP's when they say `scip` or with `--scip`. By hand:

```bash
# Swift, a package: files and declarations from the sources, uses from the compiler's index
/usr/bin/python3 "$SKILL/scanners/swift_analyze.py" <repo> <scan.json> [--name NAME]
/usr/bin/python3 "$SKILL/scanners/swift_index_build.py" <repo> <scratch>        # a store a module, made with the compiler (Infinite Canvas's way; SwiftPM isn't used)
/usr/bin/python3 "$SKILL/scanners/swift_index_read.py" <scratch>/store <scan.json>

# TypeScript, Python, Ruby: run the language's SCIP indexer, then scan its index
npx --yes @sourcegraph/scip-typescript@0.4.0 index --output index.scip      # or scip-python, scip-ruby
/usr/bin/python3 "$SKILL/scanners/scip_read.py" index.scip <repo> <scan.json> [--name NAME]
```

`scip_read.py` says, after its counts (`scan:` lines), two things an indexer leaves out without a word: how many of the commit's files of the kinds it read (by their endings, tests aside) are not in the index, and where (a folder no project's `tsconfig.json` takes in), and when the packages' `package.json` files declare dependencies on each other that the index shows almost no use of (below).

### Workspaces that resolve through built files

An indexer follows an import of a workspace package the way the compiler does: through `node_modules` to the package's `package.json`, and from there to what its `main`, `types` or `exports` name. Where those name built files (`dist/index.js`, `dist/index.d.ts`) and nothing has built them, the import resolves to nothing, and no use is recorded: the board draws the packages unconnected. `prepare` installs with scripts off and builds nothing, so a monorepo whose packages are built before they're used (Medusa's: 2 uses of 19,822 crossed a package) gets the scan line `the index barely connects the packages`. Two ways out:

- **Build them in `prepare`**: `yarn install --immutable --mode=skip-build && yarn build`, or the workspace's own build (`turbo run build`, `nx run-many -t build`). It runs the repository's build scripts, and takes as long as a build does, again whenever a lockfile changes.
- **Map them to their sources for the indexer**: before the indexer, a step of the `scip` command writes `compilerOptions.paths` into each workspace's `tsconfig.json` in the checkout (the cache's copy: the next move puts the files back), each package's name (and each key of its `exports`) mapped to its sources (`dist/x.js` to `src/x`). A Medusa trial did it in a script of a hundred lines, run as `python3 <script> && npx --yes @sourcegraph/scip-typescript@0.4.0 index --yarn-workspaces --output {index}`: 21,840 uses then crossed a package. A scan is kept by the command's text, not by the script it runs: after changing the script, `--rescan`.

**The Swift scanner is Infinite Canvas's.** It relies on its habits: `// layer:` tags on the lines of `Package.swift`, a table of what ships (`let ships = [`) and lines that end `+ shipped`, and `swift_index_build.py`, which type-checks a package whose targets need nothing but each other, a module a compile, in the way build.sh does (debug flags, `-D DEBUG`). Another Swift package gets the files, the declarations and the uses, but not layers, unless it tags them the same way; a package Xcode or `swift build` builds can be scanned from the index store those leave (DerivedData's `Index.noindex/DataStore`, or `.build`'s `index/store`): `swift_index_read.py` reads any, one store or a folder of them.

`swift_index_build.py` keeps each interface and index with a hash of what it was made from (the compiler, the command, the module's sources and the interfaces of the modules `Package.swift` says it depends on), so a module is type-checked again only when one of those changed; it says which it made. A compile is given only the interfaces of the modules `Package.swift` says its module depends on, so an import that isn't declared there fails (`no such module`), as it should in a build. A line that ends `+ shipped`, as Infinite Canvas writes its app's and the tests of what it ships, depends for a compile on every module of the plugins its table of what ships names; the scan keeps only what the line itself writes, so the board draws no arrow from the app to every plugin.

`scip_read.py` takes the index's packages as modules. A project of one package is split by the folders under its sources' root, its own files making a module named after the package. A module imports another when one of its files uses one of the other's. What a file exports and how it describes itself come from its source, by its language's conventions: TypeScript's `export` and first block comment, Python's leading underscore and module docstring, Ruby's first comment. `scip.py` decodes the index with no dependencies.

## scan.json

```
language    "swift", "typescript", ...: the words a note uses (lenskit/text.py's WORDS)
name        what the code calls itself: a Swift package's name, else the repository's folder
modules     [{name, path, deps: [module], test, layer: a tag or null, files: [rel], lines, doc, folders: {folder: doc}}]
files       [{module, rel (its path in its module), path, lines, doc, api, decls: [{name, kind, visibility, line}]}]
uses        [{from: [module, rel], to: [module, rel], names: [what it uses]}]
```

A declaration's `kind` is `type`, `function`, `extension`, `value` or `other`. Its `visibility` is `public` (another module may use it), `internal` (its module's other files may) or `private` (its file only), and a file's `api` says it declares something public. A `doc` is a first sentence. Test modules are read but not drawn.

## .canvas/lens.py

`<repo>/.canvas/lens.py` is the repository's own picture: a function `digest(scan, repo)` that returns the digest as a dict. It is read from the folder you run `ingest` in, never from the commit, and run twice in isolation (a clean environment, an empty current folder, a different hash seed and a different clock each time): the two digests must be the same byte for byte, or the run is refused naming the first node or edge that differs. `repo` reads the commit through git (`repo.files("**/*.sql")`, `repo.read(path)`), never the working tree. Without a lens, the default lens draws (`lenskit.default.digest(scan, repo)`: below, The digest), and a lens can call it with arguments. A `.canvas/spec.py` is no longer read: `ingest` refuses it, saying to move its names into `lens.py` as those arguments. [lens.md](lens.md) is the guide to writing one: lenskit, the default lens's arguments, types, named rules and determinism.

Infinite Canvas's own `lens.py` is the default lens with the root laid out as `Package.swift` lays the module graph out: the three rungs stacked from product to core, the platform rung's modules in a frame for each heading over them, and the core rung in one row. Its other boards are the default lens's.

## At scale

One title query lists at most 10,000 titles, so the default lens keeps a digest to 4,000 file notes. Past that it draws a folder's files as one note, the deepest folders first, then the biggest, then by path, until 4,000 are left: the note is titled for the folder, lists its files with what each declares, and carries their edges merged (weights added up to 4). The warning says how many folders it collapsed.

That bounds the digest, not a board. A board with a frame of more than 150 shapes side by side, or more than 1,000 shapes in all, is laid out once and not searched (searching one takes hours: canvas-digest's planner lays every container out again hundreds of times), so its arrows are drawn as arrows and it reads as a crowd; the plan's summary names it and its frame. The default lens can make one, a folder of hundreds of files being one frame (Medusa's admin dashboard: 532): split it in the lens (`folder_boards`, `groups`), or leave the package out of the index.

Times from two TypeScript trials, with a lens of the repository's own: Temporal's samples (504 files) take 86 s the first time (installing 39 s, indexing 14 s, drawing 30 s) and about 30 s a round after; Medusa (7,019 files, 83 packages) 182 s the first time (installing 73 s, indexing 53 s with 6.6 GB of memory, drawing 94 s) and 80 to 120 s a round, nearly all of it drawing, since a round lays out and draws every board again. What `prepare` and the indexer print is kept in the run's folder (`prepare.log`, `scip.log`) and said only when they fail; a lens's warnings past the first 20 are in its `lens-warnings.txt`.

## The digest

The default lens, `lenskit/default.py`, makes the digest the skill reads ([its format](../../canvas-digest/reference/graph.md)) from the scan and the lens's arguments:

- each band a frame on the root with its `rank` (the skill puts ranked frames in rank order, as rows each as wide as the widest or as columns each as tall as the tallest), each module a subboard in its band, and each folder board a subboard on its module's board;
- each group a frame, nested as the `groups` nest them, titled by its folder's name (a board's own files in `<board>/`), and each file a note in its frame, titled by its name (else, where another note of its frame or card has that name, the shortest end of its path that tells it apart there) and saying its doc, what it declares and how long it is (`lenskit/text.py`'s `file_text`);
- every title given out once in the container that holds the shape, so two folders each have an `index.ts` and two boards a frame `src`: a module's card first, then a folder board's (their titles are the digest's alone, since a folder card's description mentions cards and `@[Title]` names a shape by its title alone), then a band's, and then, a container at a time, its notes and its frames. One that another shape of the container has (case aside), or that is over 80 characters, is reworded (a band `Level 1 (layer)`, a frame `utils (Core)`, a file its whole path, then a number; a long one keeps its end behind an ellipsis), which is said on standard error and never stops the run. A node whose title another node has gets an `id`, and the digest's `in`, `from` and `to` name it by that: the title, then the containers it is in (`index.ts  in Web layer > web > src`; [lens.md](lens.md#the-digest-builder) has the rest);
- a board's description, its card's `text` (`default.py`'s `about_text`): a module's layer, purpose and size, and a folder's module and the other folders it uses, as mentions of their cards (a `]` or `\` in a title escaped). A module's imports are its arrows and never mentions, which would crowd the card's mentions (a ⌃⌥ hover shows them) with what its arrows show; the root has no note of what the whole is;
- an edge for each module's import of another, and for each file's use of another, as heavy as the names it uses (up to 4); a use of a file on another board is a pill there, and that file is public. A `by_module` file's edges go to the modules it uses.

Test modules are read but not drawn.
